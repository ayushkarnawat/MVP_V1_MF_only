How we will build it

Principles

  • Tests first for every change: a failing test, then the code, as in UI round 2.
  • Mockups are the acceptance picture. After each change the orchestrator takes a screenshot and puts it next to the mockup on this page. Nothing is called done on tests alone (that is what went wrong with the sign-up screens).
  • Behaviour stays. Rules, flows and copy that QA passed do not change unless this plan says so.
  • Head of Family security is untouched: eligibility, the four codes, the locks and the undo window stay exactly as built; the server still decides everything.
  • Old cached front ends keep working: every back end change is additive or keeps the old reading valid.

Branch, release and rollback

  • One branch ui-qa-fixes cut from origin/leapswitch-redesign, merged after the QA rows pass.
  • No migration. Back end changes (C4, C5) need a backend rebuild and restart only; no stop, migrate, start sequence.
  • Front end and back end ship together in one deploy. A short deploy guide is written in the execution plan.
  • Rollback: previous front end commit, and the previous backend image (:previous must be confirmed first, it was stale after the last deploy).

Proposed waves (the real execution plans come after you say go)

Wave 1: back end (Codex)Packet qa-be-1: C5 email templates, C4 refusal bodies. Small and independent, so the front end can rely on the new shapes.
Wave 2: front end (Codex), three packetsqa-fe-1: A1, A2 · qa-fe-2: B1, B2, B3 · qa-fe-3: C1, C2, C3, C4 (front). Codex cannot see the screen, so the orchestrator takes every screenshot.
Wave 3: integrate and check (Claude)Merge, full suites, screenshots against these mockups, re-run the QA rows listed in each change, deploy, then the owner's QA pass.

Who builds: Claude is the orchestrator (writes the packets, reviews every diff, takes every screenshot, runs the gates) and Codex is the worker for back end and front end. If Codex usage runs out, the Claude worker in WSL takes over with the same packets, as it did in UI round 2. Desktop only: mobile screens and the /mobile paths are not touched.

A2

Smooth the Home donut hover and click

FRONT ENDM

Decided: Q2: fade plus a 3 px grow.

What QA saw
Rows B2 to B6 passed, but hover and the pop-up feel jittery.
Why it happens
Four things in AllocationDonut.tsx and sections/Allocation.tsx: (1) dimming is set directly to 38% opacity with no transition, so it snaps; (2) every slice clears the hover when the pointer leaves and sets it again on the next slice, so for a moment nothing is dimmed and the donut flashes; (3) the hover state lives in the whole Allocation section, so each change re-renders the section, legend and cards; (4) the slices are 22 px wide arcs with small gaps, so the pointer drops out between them.
Proposal
A 160 ms ease on opacity (and a gentle grow of the active slice if you want it, Q2); keep the highlight while the pointer moves between slices and clear it only when the pointer leaves the donut and its legend together; a wider invisible hit area so gaps do not drop the hover; memoise the donut and the legend rows so only the changed parts redraw; no motion when the system asks for reduced motion. Keyboard focus, Enter and Space, and the pop-up behaviour are unchanged.

C1

Fix a member's missing details from the Choose head dialog

FRONT ENDMDECIDED

Decided (Q6, Q7): reuse the existing Complete profile dialog, and select the member automatically once they are eligible.

What QA saw
Your suggestion. Members without an email and phone are greyed and cannot be clicked. To fix that the user must close the dialog, go to Family, edit the member, and come back.
Today
The server returns up to 12 reasons per member. The dialog shows only the first as small grey text. The Family page already opens the Complete profile dialog (features/dashboard/members/CompleteProfileDialog.tsx, fields: name, relationship, phone, email, PAN, with duplicate-PAN, other-account and success steps) with onSaved and onClose.
Proposal
Split the reasons into fixable here (no_email, no_phone, no_pan, label_missing, same_email_as_head, same_phone_as_head, email_in_use, phone_in_use) and not fixable here (pan_registered_elsewhere, account_pending_deletion, import_in_progress, head_change_already_open). A member with a fixable reason gets an "Add details" chip and can be clicked. Clicking opens the existing Complete profile dialog for that member. When its sequence ends (Save, Exit, success, or a merge) the Choose head dialog comes back with the list reloaded from the server; if the member is now eligible they are selected automatically, otherwise the remaining reason shows on their row.
One technical point
The two dialogs are not shown stacked. This app's dialog component has its own focus trap and Escape handler, and two of them open together fight for focus. So the Choose head dialog steps aside (its state is kept) while the profile dialog is open, then returns. To the user it reads as one continuous flow. Confirmed (R4).
Unchanged on purpose
Eligibility is still computed on the server. The email and phone typed here are still verified later by the codes in step 2. A PAN used elsewhere shows the same warnings as in Profile.

C4

Show the real reason when deleting a member or the account is refused

FRONT ENDBACK ENDMQ9 · Q10

Decided: Q9: a calm information notice with the date and a single OK. Q10: dates and times in India time (IST).

What QA saw

Why it happens
DeleteMemberDialog.tsx and DeleteAccountDialog.tsx catch every error and show the generic text. The server does send a reason. Member removal: 409 {code: "member_in_recent_head_change", message: "This person was part of a recent Head of Family change, so they cannot be removed yet. Try again in 7 days."}. Account deletion: 409 with a plain string, "The Head of Family was changed in the last 24 hours. You can delete this account after the undo window closes on ... UTC."
Proposal
Back end: make both 409 bodies the same shape, {code, message, available_after}, where available_after is the real date and time; the member message names the actual date instead of "7 days". Front end: read the refusal, show it as a calm information notice (not a red error) with the date, disable the destructive button, and offer a single OK. Any other failure keeps the generic message. An old cached front end still shows the generic message, so nothing breaks.

Today
_send_completion_notices in head_change.py sends three emails: a notice to the new head, a notice to each old-head address, and a separate "Undo the Head of Family change." to each old-head address. The notice text is the same for both people ("X is now Head of Family and signs in with this email"), which reads wrongly in the old head's inbox.
Proposal
The same three emails go out in the same order to the same people. Only the templates change: (1) New head: worded for them ("You are now Head of Family; sign in with this email"). (2) Old head's notice: worded for them (you remain a member and can no longer sign in), plus one sentence saying that a second email titled "Undo the Head of Family change." has the link to undo this. (3) Undo email: the green "Undo the Head of Family change" button, the plain link under it, and "valid until {time in IST}". All three share one cleaner layout.
