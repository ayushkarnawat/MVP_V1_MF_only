**Goal:** the desktop Home screen (eight sections, family or member scope) inside the new shell. Visual reference: the interactive mockups in `Docs/orchestration/2026-10-23-home-design-mockups.html` (artifact https://claude.ai/artifact/LXrBSCPeGcryPw3dSwnTsv); layout `2026-10-23-home-layout.md`; design system `2026-10-23-home-design-system.md`; palette `Docs/Unifolio Colour Palette.pdf`.

**Depends on:** the shell PR 1 from `2026-10-23-nav-shell-plan.md` (route registry, `PageLayout`, `PageState`, `AppLink`, `MiraComingSoonDialog`, `useScope`, `renderInShell`), built in this same effort (original four-plan strategy, reinstated by the owner 2026-10-23), and the Home backend endpoints (mock the API until they exist). A page may start stacked on `feat/shell-nav` before it merges, then retarget (contract section 9).

**Decisions this plan relies on:** M1-M17 (area fill, segmented periods, eye icon, movers rows with bar, others row, estimated pill, muted coming-soon rows, amber tint cards, news icon tile, empty page shows greeting and wealth only, family cards as in the mockup, scoped palette tokens, benchmark #2563EB, palette text shades, low-opacity dark tints, links to unbuilt pages greyed with tooltip), L48 greeting, L44/L49 status line, L26 Hide values, L24 calendar limited to 10 years, news live from day one, **tracking deferred (no analytics code)**, mobile untouched.

**Branch:** `feat/home-snapshot` (frontend part). Touches only `frontend/src/features/home/`, `frontend/src/components/ui/charts/line-area-chart.tsx` and its test, the new palette token file, and `frontend/src/shell/routes/home.route.tsx` (replace the placeholder and set it `live`). Nothing else under `frontend/src/shell/`; `App.tsx` is changed only by the shell PR 2. No commit or push without the owner's word.

**Test command:** `cd frontend && npx vitest run <file>`.

**Visual parity and chrome (added 24 Oct, owner-approved).** The finished page must look like its signed-off mockup(s) named in this plan, in light and dark. (1) The mockups' own sidebar, top bar, avatar and page-state buttons are not built: the shell draws the sidebar and top bar (contract v1.6). (2) **Parity step:** in the last run of this page the orchestrator runs it locally on the synthetic household and compares it with the mockup in the browser, light and dark, at 1280 and 1024 px, and lists every difference (layout, colours, type, spacing, states, copy, hover and click behaviour); differences are fixed before the run is DONE, or logged for a QA run with the owner's agreement. (3) Wherever this page lists a fund, the fund name opens the individual fund page through `paths` (the route is enabled by the Individual Fund runs). (4) Each page keeps the surface style of its own mockup (owner, 24 Oct).

## Shell integration (contract v1.2, section 8 template)

- Route id and path: `home` / `/home`. Menu: main 1, label Home, icon `Home`. Layout `app`. Scope `family-or-member`.
- How it registers: replaces `frontend/src/shell/routes/home.route.tsx` (a placeholder that the shell owners create) and sets status `live`. Home does not create shell files.
- Uses from the shell: `useScope()` (`viewMode`, `memberId`, `members`, `selectedMember`, `scopeKey`, `setMember`, `setAggregate`), `PageLayout`, `paths`, `AppLink`, `PageState`, `MiraComingSoonDialog`, `useImport`.
- Must not touch: anything under `frontend/src/shell/` except its own route file; `App.tsx`; the landing switch (L35) belongs to the shell work.
- Links to other pages: only through `paths.*`; links to placeholder routes render greyed with a tooltip automatically (M17).
- **Only if Home starts before shell PR 1 is available (optional fallback):** Home talks to the shell only through one adapter file, `features/home/shellAdapter.ts`, which re-exports those names. While the shell is missing, the adapter points at a local stub, `features/home/dev/shellStub.tsx`, that implements the same shapes (a fixed member list, `AppLink` that greys every unbuilt target, a plain `PageLayout`, `PageState` and dialog). When the shell lands, swapping the adapter to the real imports is a one-file change and the stub is deleted. Tests use a local `renderHome()` helper built on the stub, replaced by `renderInShell` later.
- **Visible in the real app only when** the shell PR 2 has switched the app on and `home.route.tsx` is live; before that Home is verified by its tests and a dev-only preview entry (a standalone dev HTML page and entry under `features/home/dev/`, not part of the production build and not touching `main.tsx`).

## Gate

Owner reviews the staging build against the mockups before merge; all user-facing strings go to the copy review (F5).

## Risks

The shell PR must land first (or Home uses the optional adapter and stub); Home is only visible once shell PR 2 switches the app on. The stub must match the contract shapes (the adapter test guards this). Palette tokens duplicate some existing token names (scoped names avoid collisions). Large synthetic statements make the chart payload bigger (about 9-12 KB per year of daily points; cap Custom at 10 years).
