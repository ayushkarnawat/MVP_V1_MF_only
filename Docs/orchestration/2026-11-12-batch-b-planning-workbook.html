7. Security explanation for stakeholders (draft)

You asked for both versions now. Both assume Batch B is built as planned, including the per-IP limit and the countdown. Numbers in square brackets are placeholders until Q24 is decided. If a change is dropped, remove its line.

How Unifolio protects sign-in codes

When someone signs in with their email, Unifolio sends a one-time code. These are the protections around that code.

  • Strong codes. A code is 6 digits from a secure random generator. Unifolio keeps only a scrambled form of it, never the code itself.
  • Short life. A code works for 5 minutes and allows 5 wrong tries. After that a new code is needed.
  • One code a minute for the same address. A new code for the same email can be requested once every 60 seconds. The screen shows a countdown and says why, so the user is never left guessing.
  • Fair to genuine users. A different email or phone number has its own timer, so someone who made a typo is not held up.
  • A cap per internet address. From one internet address, codes can be requested for only [10] different emails or phone numbers in [10] minutes. This stops one source from sending codes to many people.
  • Codes only go to real accounts. A login code is sent only if an account exists for that email. Unknown addresses receive nothing, so strangers are not emailed.
  • Failures do not lock people out. If an email could not be sent, the timer does not start.

Scope: this covers sign-in codes sent by email. Sign-in codes by phone message are not yet delivered by a provider.

How Unifolio protects sign-in codes: the full picture

In place
  • Codes: 6 digits, secure random, stored only in scrambled form; valid 5 minutes; 5 wrong tries per code.
  • One new code a minute for the same email or phone, with a countdown and a plain reason on screen. A different address has its own timer.
  • A cap per internet address: [10] different emails or phone numbers in [10] minutes, and [30] address checks in [10] minutes (after Batch B).
  • Login codes only go to existing accounts. Failed sends do not start the timer.
Not in place, with what that means
  • No lockout across codes. A new code resets the 5 tries, so an attacker could make about 300 guesses an hour against one account. With a million possible codes, that is roughly a 1 in 3,300 chance of a lucky guess in an hour of continuous trying (my estimate, not a measurement). Each new code is random, so earlier guesses do not help.
  • Anyone can check whether an email or phone is registered. The messages “No account found” and “already exists” reveal it. This was an accepted trade-off on 30 Sep 2026. The per-IP cap slows bulk checking but does not remove it.
  • No bot check. There is no CAPTCHA or similar test on the code request.
  • Shared networks. A per-IP cap can slow genuine users behind one shared address, such as an office. The limits are set generously for that reason and should be watched.
  • Phone codes are not live. No text-message provider is built, so none of this applies to phone sign-in yet. Choosing one, with its own limits and costs, is a separate task.
  • No alerting. Nothing warns the team when code requests spike.
Recommended next steps
  • A bot check on the code request and per-account alerts when requests or failures spike.
  • A firewall rule at the entrance to the app as a second layer.
  • A text-message provider with its own rate limits and spending cap before phone sign-in goes live.
  • Revisit the “No account found” messages if the product’s risk view changes.
Check before sending. Both versions describe protections that exist only after Batch B is built (the per-IP cap and the countdown reason). The earlier go-live report already recommended the cap. Counsel or a security reviewer should read version 2 before it goes outside the team.
