0 · Bottom line

Most of the monthly chaos is not the downloading. It is everything around it. Today each by-hand file is found on a site, renamed, copied to the VM with scp, imported with a long ssh … docker compose run … command with exactly the right house name and flags, and the result is pasted back into chat. There is no dry run, no undo, no list of what is still due, and no record of what was done. That repeats for about 25 house imports a month (11 disclosure houses, up to 14 factsheet houses).

My recommendation, in order:

  1. Status check now, read-only (S). Before the December cycle starts on 1 Dec, find out what the 20 Nov disclosure run and the 10 Nov factsheet run actually left in the database. Today nobody can say, because neither job keeps a log.
  2. Make failure visible, then fix the bugs (H1–H3, then F). One outcome row per fund house per run, a daily digest email, non-zero exits. Then the eight code fixes, ordered by funds recovered. Hard deadline: FX-L1 (the weekend date rule) must be live before 1 Feb 2027, because 31 Jan 2027 is a Sunday and Franklin's files will be missed again.
  3. Replace the CLI routine with an Ops console (A1). Drop files on a page; the house and month are detected from the file; a dry run shows what would be written, compared with last month; one click commits; one click undoes. Plus a due list, so nothing is forgotten. This removes most of the chaos on its own.
  4. Cut the clicks with a Collector browser extension (A2). A person still opens each AMC page in their own browser (so we never get around a site's block), but the extension picks up each download, tags it and sends it to the Ops console. The monthly routine becomes "open the due list, click through, review, commit": about 30–40 minutes instead of an afternoon.
  5. Work towards real automation in parallel (A5–A7): ask the blocked houses to allow our fixed server address, try an email inbox that receives AMC mailings (Amazon SES can receive mail in Mumbai), and get quotes from data vendors. Each one, when it works for a house, takes that house off the manual list.

What I do not recommend: an unattended AI agent that drives a browser from a home or office connection to download files from sites that refuse our server. It would work technically, but it is exactly the "access-control workaround" the project ruled out in Run 7 (10 Oct), the sites' terms usually forbid automated access, and it fails silently when a page changes. A supervised pilot is offered as an option in Q12, so it is your call.

Things you should know before reading the plan

  • Nobody can say today what the 20 Nov run did. The disclosure job writes no log file, its container is removed after each run, and lateness alerts fire only on days 10 and 20. That is why S comes first.
  • The factsheet job has no record per run at all. scheme_fund_managers keeps only the reference month per row. Whether the 10 Nov run worked can be read only by comparing the newest reference month per house (query S2).
  • The by-hand importers have no dry run and no undo. The disclosure importer replaces a house's waiting rows in one transaction; the factsheet importer checks every file first. Neither can show "what would change" before writing. This is the main thing the Ops console adds.
  • Two different "manual" lists exist and they do not match. Disclosures: 7 registered manual houses plus 4 that refuse our server (Bajaj, WhiteOak, Trust, Angel One). Factsheets: 10 registered manual houses plus 4 registered as automatic that fail (Angel One, Sundaram, SBI, Mahindra Manulife), which the CLI refuses to import by hand.
  • Upcoming dates. December cycle: disclosure job days 1–20 Dec for 30 Nov (a Monday, so the weekend bug does not bite); factsheet job 10 Dec; manual-factsheet check 15 Dec. 31 Dec is a Thursday. 31 Jan 2027 is a Sunday and 28 Feb 2027 too.

7.4 How detection works (so nobody types a house name again)

  • Pipeline: PDF → factsheet; .xls/.xlsx/.zip → disclosure (the same sniffing sniff_workbook_format already does).
  • House: match the file's text (title block, sheet names, the AMC name printed on every disclosure and factsheet) against registry keys and aliases; for the Collector and email, the page or sender domain is a second signal. Two signals must agree, or the console asks the person to pick.
  • As-of date: the date printed in the file (the factsheet reader's "as on" scan; the disclosure sheet header), never the file name, never the upload day. A date outside the expected month shows as a warning, and the existing 45-day and month-end rules still apply.
  • Auto-commit (optional, Q19): when house and date are certain, every sheet parses, matched series ≥ 90% of last month's, and no new sum-check failures, the intake commits by itself and the digest reports it. Otherwise it waits for a person.

7.5 What the monthly routine becomes

Today (≈ 25 imports, about 3–4 hours, two people)

  1. Work out which houses are due (from memory and runbooks)
  2. Open each site, find the month, download
  3. Rename every file
  4. scp to the VM from WSL
  5. One ssh + docker command per house, exact names and flags
  6. Read counts, judge them, paste into chat
  7. Someone re-runs the audit to see if it worked

After A1 + A2 (about 30–40 minutes, one person)

  1. The digest email says "9 by-hand houses due"
  2. Open the Collector; it opens each house's page in turn
  3. Click the site's own Download button; the file goes to intake, tagged
  4. Open the Ops console: each file shows a dry run next to last month
  5. Commit the green ones; look at any amber ones
  6. The due list empties; the board shows coverage

8 · Database changes

Migrations 0055–0057 (numbers to be re-checked against the MF new-features plan, which also adds migrations). Reference data only: no user data, no PAN, no CAS. Each new table is justified against reusing an existing one first.

New table 1: pipeline_run_outcomes (H1)

Why not reuse disclosure_batches? A batch is one row per scheme per as-of date. The failures we cannot see today are exactly the ones with no scheme to hang a row on (house blocked, file not found, wrong date, renamed house), and the factsheet pipeline has no batch table at all. Logs alone are what failed us in November. One small ops table serves both pipelines.

12 · Risks and how the plan handles them

  • FX-L1 creates two live batches for one month if a house later re-dates 30 Oct to 31 Oct. Covered by a fixture and by comparing by calendar month everywhere.
  • Auto-detection picks the wrong house. Two signals must agree; otherwise the person chooses. Commit is never automatic without certainty (Q19), and undo exists.
  • Undo after users already saw the data. Holdings consumers read the newest WRITTEN batch, so undo simply falls back to the previous month's batch; analytics recompute runs nightly.
  • Outcome noise floods the digest. The digest shows changes since yesterday, not the full table.
  • Extension distribution. An unlisted Chrome Web Store item or developer-mode install for two or three people; token revocable from the console.
  • Email intake links are login or tracking links. Only links to registered AMC domains are followed, plain GET, no credentials.
  • Vendor licence forbids showing raw holdings to users. Read before signing; derived numbers may still be allowed.
  • Migration numbering clash with the MF new-features work. The plan writer re-checks the head before writing migrations.
