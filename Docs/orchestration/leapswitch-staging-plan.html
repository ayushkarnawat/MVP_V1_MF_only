D2 Running recompute "exactly like AWS", and the risk Go received — worker container

What AWS does today. After a CAS import the backend calls ECS RunTask. AWS starts a brand-new container from the same image (0.5 vCPU, 1 GB), runs python scripts/run_analytics_recompute.py --household <id>, and the container disappears. Four properties matter:

  • It is a separate process with its own memory, so a heavy recompute cannot slow or crash the API.
  • Several households can recompute at the same time.
  • The code only counts the dispatch as successful if AWS actually placed the task. If not, it releases the claim, as it does now.
  • A daily 06:30 job (--all) backs it up, and a stuck claim clears itself after 15 minutes.

No VM setup is literally identical, because ECS does not exist on LeapSwitch. There are three ways to get close:

WayHow it worksCloseness to AWSRisk
1. Worker container (my recommendation)A second container from the same image sits on the VM's internal Docker network. The backend asks it to run the recompute. It starts the same command, as its own process, within a 3 GB/1.0 CPU ceiling shared across the pool (the CPU cap raised from the AWS task's 0.5, 16 Oct 2026 — see "Is a.gp1.16g right?" below for why).Same image, same command, same per-job memory behaviour, same success and failure rules. Differs: it shares the VM's CPUs, gets a higher CPU cap than the AWS task since this VM has spare cores, and runs at most 3 at a time instead of unlimited — matching the AWS "bumped" load-test shape of 3 containers used for sizing elsewhere in this plan (see "Which VM size" below).Low to medium
2. docker run per recomputeThe backend starts a fresh container for every job, the nearest thing to Fargate.Closest to AWSHigh The backend would need the Docker socket, which means anyone who breaks into the backend gets root on the VM. Not acceptable with PAN data.
3. Subprocess inside the backend containerThe backend runs the script as a child process.Shares memory with the API. Departs from your written spec.Medium

How much risk is option 1?

  • New code on the import path. About 100 to 150 lines plus tests, behind the existing RecomputeDispatcher protocol. The AWS dispatcher stays the default, so AWS staging and production are unaffected.
  • Worst realistic failure: the worker is down or busy, so analytics are stale after an import until the claim clears (15 minutes) or the 06:30 job runs. No data is lost or corrupted. The existing "release the claim if dispatch failed" rule covers it.
  • Memory: a household too big for 1 GB gets killed, exactly as on AWS today.
  • Blast radius: LeapSwitch staging only.

Go received, 15 Oct 2026: "something closest to the AWS setup that's not going to break our systems" — that is option 1, the worker container. It is the closest available option precisely because the AWS dispatcher stays the default everywhere else (AWS staging, production), so this code path only ever runs on LeapSwitch. Code work in Phase 3 is unblocked.

Will this cause loading-time or efficiency problems under load, and how is it different from AWS? Per-job speed is identical — it is the same image running the same script with the same 1 GB memory cap, so one household's recompute takes the same time either way, regardless of the worker pool size or CPU cap. That's worth being precise about, because it's easy to conflate "more resources" with "faster": recompute is I/O-bound (database queries, NAV API calls), not CPU- or memory-bound, so a bigger per-job ceiling doesn't speed up a single job — it only raises the ceiling for how large a household can be before an out-of-memory kill. The difference between AWS and the worker container is entirely about what happens when several imports land at once. On AWS, ECS places as many RunTask containers as the account's capacity allows, effectively unlimited for staging's traffic; on the worker container, a cap of 3 concurrent jobs means a 4th household's recompute waits in a short queue rather than starting immediately.

Back-to-back (sequential) recomputes versus genuinely simultaneous ones. These behave differently and it's worth separating them explicitly. If a 3rd, 4th, 5th and 6th recompute arrive one after another — each starting only once the previous tester has finished their import, not at the same instant — none of them ever queue, no matter what the pool size is, because each slot frees up again within seconds of the job before it completing. The pool size only matters when jobs genuinely overlap in time: several households importing within the same few-second window while their recomputes are still running. For realistic staging QA (a handful of testers, not concurrent production traffic), true overlap is rare, which is why 3 is already enough headroom — it was briefly raised to 5 on 16 Oct 2026, then reverted the same day: a 3rd uvicorn worker on the backend service (see "Uvicorn workers vs. the recompute pool" below) was judged more valuable than deeper recompute-pool headroom for a case that was never observed to need it, and the 16 GB budget can't comfortably fund both. If genuine simultaneous load ever does become common, the right fix is exactly what you'd expect: raise MAX_CONCURRENT_RECOMPUTES in worker_server.py (currently 3), a one-line change, or resize the VM to a.gp1.24g if CPU/memory headroom runs out first — not a redesign either way. The user-visible effect of a queued wait is the dashboard showing "recompute pending" a little longer than on AWS — not a failure, not lost data, not a crash, because the existing "release the claim if dispatch failed" rule and the 06:30 daily backup job both still apply unchanged.

Why Option B, not Option A — in depth

Option A (a second VM for the database plus a CloudPe load balancer, mirroring AWS's component count) looks closer to AWS on paper. It is not, and the reason matters for every future decision on this plan.

AWS's real guarantees come from managed services, not from the number of machines: Fargate's task scheduler and bin-packing, RDS's automated multi-AZ failover and point-in-time recovery, the ALB's health-check-driven routing, Secrets Manager's rotation, EventBridge's native cron. CloudPe has none of these at any price — it is plain IaaS (VMs, block volumes, object storage, basic networking), confirmed by everything in "What the welcome email already confirmed" and the research above. Splitting Option A into an app VM, a database VM and a load balancer does not restore any of that: the database VM still runs a self-managed Postgres container, not RDS; the load balancer still only routes to one backend, not the ALB's health-check semantics; backups are still the same pg_dump-plus-uncertain-volume-backup story either way. Option A spends ₹3,134/mo more than Option B for AWS's shape without any of the substance that shape exists to provide — and that substance cannot be bought on CloudPe, regardless of how many VMs are involved.

The compatibility that actually matters is at the application layer, not the infrastructure-topology layer, and the plan already builds it there: the RecomputeDispatcher protocol (D2) and the S3 client abstraction (file_storage.py) mean the code does not know or care whether it is talking to ECS or a worker container, AWS S3 or CloudPe object storage. Three rules make this a guarantee rather than an accident, and they are non-negotiable, not implementation details:

  1. Every AWS-facing integration point (the recompute dispatcher, the S3 client, the email provider) stays behind its existing abstraction and is switched only by configuration, never by a code branch that knows it is running on LeapSwitch.
  2. The same Docker image, the same migration set and the same environment variable names run on both hosts. A LeapSwitch-only environment variable is fine; a LeapSwitch-only code path is not.
  3. The CloudPe deploy plumbing (deploy/leapswitch/: Docker Compose, Caddy, systemd timers) is self-contained and never referenced by AWS's Terraform or vice versa. The two are siblings, not a shared system.

How hard is it to go from CloudPe staging back toward AWS production?

This has two different answers depending on which layer it's asked about, and conflating them is where the actual risk would come from.

Application layer: no porting work, by construction. Anything proven on the CloudPe VM — a bug fix, a new endpoint, a schema migration, a recompute change — is the same Docker image and the same code paths that run in AWS staging and production. The three rules above exist specifically so this stays true. Nothing written for LeapSwitch needs to be rewritten before it reaches AWS; it already runs there, because it was never written for LeapSwitch specifically.

Infrastructure layer: not portable, and not meant to be. deploy/leapswitch/ (Docker Compose, Caddy, systemd timers, the bootstrap script) is never going to run in AWS production, and AWS production's Terraform (ECS, RDS, ALB, EventBridge) is never going to run on CloudPe. There is no migration step where one becomes the other — production already exists on AWS today and does not change because staging moved. Production is not "promoted from" the CloudPe VM; it is already there, continuously.

The actual cost: less AWS-specific test coverage. What CloudPe staging cannot do is exercise ECS task placement failures, ALB health-check routing, RDS failover, or Secrets Manager rotation — because none of those exist on CloudPe to fail in the first place. That is the "Staging no longer proves the AWS production stack" risk below, and it is real. The mitigation in this plan is to keep AWS staging parked rather than deleted, and run the Phase 6 test checklist against it before every production release, and at minimum once a quarter even without a release pending — not a one-time "rehearse once" as earlier drafts of this plan said. That keeps the AWS-specific failure modes exercised on a cadence, at the cost of occasionally running tests twice.

One option this plan deliberately does not take: reshaping AWS production itself into VM-plus-Docker-Compose so staging and production match exactly. That would mean giving up RDS's automated failover and Fargate's isolation on the environment that actually matters most, to solve a staging cost problem. The asymmetry between a VM-shaped staging and a managed-service-shaped production is an accepted, intentional trade-off here, not an oversight — common practice wherever a managed-service production stack would be too expensive to also run 24/7 for staging.

The other direction: abandoning CloudPe and going back to AWS staging

This is a different, easier question from "moving to production" above, and worth answering separately since it's the one that actually matters if the 15–30 day CloudPe trial doesn't work out.

AWS staging is never turned off in the destructive sense. Nothing about this plan deletes, tears down, or stops managing AWS staging's Terraform, RDS data, or S3 buckets. The only thing that might happen to it while CloudPe is being tried is the existing cost-saving scripts/staging-state.sh off state — ECS at desired-count 0, RDS and the bastion stopped, nothing destroyed, resumable with staging-state.sh minimal in a few minutes (RDS start takes the longest, a few minutes to reach available). That script already exists and was built for exactly this kind of pause, not for this migration specifically.

Reverting is three things, all cheap:

  1. Run staging-state.sh minimal to bring ECS, RDS and the bastion back (a few minutes, no Terraform apply needed — Terraform was never touched).
  2. Point the DNS records back: staging.unifolio.in and staging-api.unifolio.in were never moved in the first place (only the new ls-staging/ls-staging-api records point at CloudPe), so there's nothing to revert on the AWS side of the DNS.
  3. Stop paying CloudPe: cancel before the next billing date, or just let the VM sit unused if cancellation is slower than desired (the Risks table already covers the postpaid/no-spending-alert exposure if this step is missed).

Nothing from the CloudPe experiment needs to be "merged back" into AWS to abandon it, because nothing on AWS ever depended on it: the three compatibility rules above mean every code change written during the CloudPe build (the dispatcher's worker-container mode, the S3 endpoint settings) is additive and config-gated, so AWS staging keeps running the AWS dispatcher and AWS S3 client the entire time, unaffected by whether the CloudPe branch exists or not. Abandoning CloudPe is closer to closing a browser tab than rolling back a migration.

If CloudPe does work out, the plan is the mirror image, not a full shutdown: AWS staging moves to the same staging-state.sh off state long-term to stop paying for it day-to-day, while still being the thing that gets switched back to minimal for the quarterly AWS-specific rehearsal described above, and before any production release. "Move AWS to a shutdown part" means stopped-and-parked, not decommissioned — production stays on AWS permanently either way, and the rehearsal cadence exists specifically because production never moves off it.

A harder version of this question, added 16 Oct 2026: what if CloudPe has already diverged by the time you want out? This is different from the zero-divergence case above, where nothing was ever built that AWS staging lacks. Suppose CloudPe becomes primary for a while and genuinely new work gets built and tested there — new features, not just bug fixes — while AWS staging sits frozen at today's state, and only later do you decide to move back. Splitting this by what's actually hard to move, rather than treating "CloudPe diverged" as one big problem:

  • Code is not the problem, by construction. Whatever gets built while CloudPe is primary is still commits in this git repo, on whatever branch deploys there — the same three compatibility rules from "Why Option B, not Option A" (abstraction behind existing interfaces, same image/migrations/env-var names, self-contained deploy plumbing) mean none of that code becomes CloudPe-specific just because CloudPe tested it first. Reverting to AWS at that point means pushing the latest image to ECR and updating the ECS service, and running the same Alembic migrations against RDS instead of CloudPe's Postgres — a normal deploy your CI already does, taking minutes, not a port or a rewrite.
  • Data is the actual problem, and it's real. Any test users, uploaded CAS files, or QA findings that only ever existed in CloudPe's database during that window do not exist on AWS staging, and reverting doesn't recreate them. If that data matters (not just disposable test accounts), it needs a deliberate pg_dump/restore from CloudPe to AWS RDS before cutting back — the same kind of data-copy step already described in Phase 5, run in the opposite direction.
  • The practical mitigation, if you want to avoid this entirely: keep CloudPe and AWS staging deploying from the same branch for as long as you're still evaluating CloudPe (i.e., don't let CloudPe-only feature branches sit unmerged for weeks) — that's the zero-divergence case above, by choice rather than by accident. Divergence only becomes a real cost once you deliberately let CloudPe run ahead of AWS staging for an extended period, which is a decision you'd be making on purpose at that point, not a trap this plan sets.

Troubleshooting: VM SSH access suddenly times outfirst hit 16 Oct 2026

Symptom: ssh deploy@<vm-ip> hangs and eventually prints Connection timed out — not Connection refused (that's the different, already-solved fail2ban scenario from Phase 2 hardening: a refusal means something on the VM actively answered and said no; a timeout means the packets never got a response at all). The app itself stays completely healthy the whole time — both https://ls-staging.unifolio.in and the API domain keep serving traffic normally, because this only blocks port 22, not 80/443.

Root cause: CloudPe's own network layer, not the VM. The VM's ufw and fail2ban are both fine and allow/haven't-banned anything — but CloudPe's dashboard has a separate Security Group (unifolio-web, under Security Groups in the CloudPe console) that allowlists inbound SSH by exact source IP (/32), independent of anything configured inside the VM. When your office's public IP changes, the old rule no longer matches, and CloudPe drops the packets before they ever reach the VM — which is exactly why nothing shows up in the VM's own fail2ban/journalctl logs: the connection attempt never arrives for the VM to log in the first place. This is a deliberate hardening choice from Phase 2's bootstrap-vm.sh, not a misconfiguration, and will recur every time the office IP changes.

Diagnosis order that confirms this quickly (don't start with the security group — confirming the VM itself is clean first is what makes the security group the only remaining explanation):

  1. Confirm the app is still healthy over HTTPS from the affected machine (rules out a VM-wide outage).
  2. Get into the VM out-of-band via the CloudPe web VNC console (not SSH — that's the thing that's broken) and check, in order: sudo ufw status verbose (is 22/tcp still allowed?), sudo fail2ban-client status sshd (any active bans?), sudo journalctl -u ssh --since "-24 hours" (any record of the connection attempt at all, from any IP?). All three coming back clean — no bans, ufw allowing 22 from anywhere, and zero log entries for the attempt — is itself the signal: it means the block is happening before the VM ever sees the packet.
  3. Check your current public IP (e.g. curl https://api.ipify.org) and compare it against CloudPe dashboard → Security Groups → unifolio-web → Rules, Inbound tab, the SSH / port 22 row(s). If your current IP isn't listed there, that's the fix.

Fix: CloudPe dashboard → Security Groups → unifolio-web → Inbound → Add → Protocol SSH, port 22, source <your current IP>/32. Takes effect immediately, no VM restart needed. Leave old IP rules in place rather than deleting them (harmless, and saves re-adding them if that IP recurs).

Why this isn't worth automating away: office IPs change rarely enough that a 30-second dashboard click is the right-sized fix. The 80/443 rules are deliberately left open to 0.0.0.0/0 (the public app needs that); only 22 is IP-scoped, by design. If this becomes frequent, the real fix is a static IP from the office ISP, not CloudPe API automation for an occasional click.

Why defer Terraform here, when it's what made AWS manageable?

Not because it's less valuable in principle — because the two jobs are different sizes. AWS's Terraform (infra/envs/staging, about 1,700 lines) earns its keep managing dozens of interdependent resources with real failure modes if done by hand: VPC and subnets, NAT routing, ECS cluster/service/task definitions, the ALB with its target groups and listeners, RDS, IAM roles and policies, Secrets Manager, EventBridge rules. Get an IAM policy or a security-group reference wrong by hand and the failure is often silent until something breaks in production. Terraform's value is highest exactly there: many resources, non-obvious dependencies, and a real cost to inconsistency between environments.

The CloudPe Option B build is a flat list of about seven things: one project, one security group, one SSH key, one VM, one data volume, one public IP, two object-storage buckets. There's no dependency graph to get wrong beyond "the VM references the security group and the key" — the kind of thing the VM form in this plan already walks through safely in under two hours. Against that, CloudPe's own downloadable Terraform sample only creates a bare VM on the public network, with no security group and no data volume shown — meaning building it out would mean writing and testing resource definitions CloudPe's own example doesn't exercise, against a provider we have no production experience with, for a stack an hour of manual clicking already covers. The OpenStack application credential also expires roughly every 60 days and needs manual renewal regardless of whether Terraform manages it, so there is ongoing upkeep either way.

Terraform's other main payoff — safe, repeatable teardown and rebuild — matters most when an environment gets rebuilt often, or when a second copy of it is needed. Here, the data volume is kept on VM deletion specifically so a full rebuild is rare, and when it happens, the documented manual steps already cover it. Concrete triggers to stop deferring: a second CloudPe environment is needed (a second QA tier, a second region), a from-scratch VM rebuild actually happens and proves painful by hand, or the 60-day credential renewal becomes a recurring source of broken scripts. Until one of those is true, writing and maintaining an OpenStack Terraform module is pure overhead with no reproduction need to justify it — the opposite of why it paid off on AWS.

In plain language: what each code change actually does

None of this is new logic — every change is "if a setting says to, do the same thing a different way," with AWS's way staying the default everywhere. Written out in order of how a recompute actually travels through the system:

  • dispatch.py — "who runs the recompute, ECS or the worker?" Today, when you import a CAS file, the backend tells AWS "please start a container to crunch this household's numbers," and AWS (ECS) handles the rest. There's no ECS on CloudPe, so this file now has a second option: "ask the worker container to do it instead," using a plain HTTP request (the same kind your browser makes) to a second container sitting right next to the backend. A setting (analytics_dispatch_mode) picks which one runs — it defaults to the AWS way, so nothing changes anywhere except CloudPe.
  • worker_server.py (new file) — the thing that actually does the crunching on CloudPe. This is a small, separate program that sits and waits for "please recompute household X" requests. When one arrives, it runs the exact same recompute script AWS already runs, just as its own process instead of inside an AWS container. It can handle up to 5 households at once; a 6th has to wait a few seconds for one of the 5 to finish, the same way a 4th container would have to wait for a free slot on AWS if AWS ever ran out of capacity (it doesn't, in practice, which is the one real difference).
  • config.py — the settings themselves. New entries like "which way to dispatch recomputes," "where's the worker," "where's the CloudPe file storage." All blank or set to the AWS way by default, so leaving them alone changes nothing.
  • file_storage.py and portfolio_disclosure_retention.py — "where do uploaded files actually get saved?" Today, CAS PDFs and some archived files go to Amazon S3. CloudPe has its own S3-compatible storage (same idea, different company), so these two files now build their storage connection through one shared helper that reads a setting for "which storage service, and with what keys." Leave the setting blank and it behaves exactly as before, talking to real AWS S3.
  • send_job_failure_alert.py (new file) — "email someone if a scheduled job fails." On AWS, CloudWatch watches for failures and SNS emails you. CloudPe has neither, so this is a tiny script that cron (CloudPe's version of EventBridge) runs after every scheduled job; if the job's exit code says "failed," it sends an email using the exact same email-sending code the app already uses for OTPs and notifications — nothing new was built for sending the email itself.
  • deploy/leapswitch/ (new folder) — "how does all of this actually get started on the VM?" This isn't application code, it's the instructions for running it: docker-compose.yml lists the four things that need to run (the database, the backend, the worker, and a web server called Caddy that handles HTTPS automatically) and how much memory/CPU each gets; crontab.leapswitch is the schedule for the 11 jobs AWS currently runs on a timer; deploy.sh/backup.sh/restore.sh are the "start everything," "back up the database," and "restore a backup" buttons, as scripts instead of dashboard clicks.

The common thread: every one of these is reachable only by a setting that's off/AWS-pointed by default. There is no code anywhere that checks "am I running on CloudPe?" and behaves differently — the same image runs identically on AWS staging, production, and CloudPe, and only the configuration handed to it differs.
