D2 Running recompute "exactly like AWS", and the risk Needs your go

What AWS does today. After a CAS import the backend calls ECS RunTask. AWS starts a brand-new container from the same image (0.5 vCPU, 1 GB), runs python scripts/run_analytics_recompute.py --household <id>, and the container disappears. Four properties matter:

  • It is a separate process with its own memory, so a heavy recompute cannot slow or crash the API.
  • Several households can recompute at the same time.
  • The code only counts the dispatch as successful if AWS actually placed the task. If not, it releases the claim, as it does now.
  • A daily 06:30 job (--all) backs it up, and a stuck claim clears itself after 15 minutes.

No VM setup is literally identical, because ECS does not exist on LeapSwitch. There are three ways to get close:

WayHow it worksCloseness to AWSRisk
1. Worker container (my recommendation)A second container from the same image sits on the VM's internal Docker network. The backend asks it to run the recompute. It starts the same command, as its own process, with a 1 GB memory cap and 0.5 CPU cap, the same limits as the AWS task.Same image, same command, same memory and CPU limits, same success and failure rules. Differs: it shares the VM's CPUs, and runs at most 2 at a time instead of unlimited.Low to medium
2. docker run per recomputeThe backend starts a fresh container for every job, the nearest thing to Fargate.Closest to AWSHigh The backend would need the Docker socket, which means anyone who breaks into the backend gets root on the VM. Not acceptable with PAN data.
3. Subprocess inside the backend containerThe backend runs the script as a child process.Shares memory with the API. Departs from your written spec.Medium

How much risk is option 1?

  • New code on the import path. About 100 to 150 lines plus tests, behind the existing RecomputeDispatcher protocol. The AWS dispatcher stays the default, so AWS staging and production are unaffected.
  • Worst realistic failure: the worker is down or busy, so analytics are stale after an import until the claim clears (15 minutes) or the 06:30 job runs. No data is lost or corrupted. The existing "release the claim if dispatch failed" rule covers it.
  • Memory: a household too big for 1 GB gets killed, exactly as on AWS today.
  • Blast radius: LeapSwitch staging only.

I still need your go, because CLAUDE.md says to stop when a build departs from a written spec, and option 1 does (the spec says ECS). Reply "D2 go: worker container" and I start.

D3 Why new keys, and why not reuse the old ones? Your call

You can reuse them. New keys are a precaution, not a requirement. The real trade-off:

Reuse AWS staging keysNew keys
Copy user accounts and PAN data from AWSWorks Encrypted PANs and lookup hashes still decrypt and match.Impossible Old encrypted PANs become unreadable. LeapSwitch starts with empty user tables.
If the CloudPe VM is broken intoThe same keys that protect AWS staging are exposed. You would need to rotate both.AWS staging stays safe.
Keys in more placesTwo places: AWS Secrets Manager and the VM's .envSeparate, one each

Recommendation, since you want to copy the data across: reuse the staging keys, on two conditions. They are staging-only keys that production never uses, and they live only in the VM's root-only .env (mode 600). If you decide to start with reference data only, use new keys instead.

D5 "Real stakeholder data" in detail Explained

What it means. During QA, stakeholders and testers upload their own real CAS statements. Those hold PANs, folio numbers, holdings and transactions. That is personal financial data. Putting it on LeapSwitch means a new company is storing it for you.

Why it needs a decision.

  • Under India's DPDP Act you are the data fiduciary, and a hosting company that stores the data is your processor. A processor should be bound by a written agreement (a data processing agreement) covering security and breach notice.
  • Your privacy policy and consent text may name where data is stored. Check whether they name AWS.
  • Copying real users' data from AWS to CloudPe is itself a transfer of personal data to that processor, so it falls under the same question.
  • Encryption confirmation (D4) must come first.

Options:

  • A. Synthetic only on LeapSwitch: the synthetic CAS set and test accounts. No agreement needed.
  • B. Real data after the data processing agreement is signed, CloudPe confirms encryption, and the consent text is checked.

Recommendation: start with A. Move to B when those three are in hand. This also affects D3: reuse the keys only if you will copy real user data, which needs B.

Why can't we automate backups?

We can, and the plan does. My earlier wording was misleading. What is manual is only the dashboard button "Create backup now". The docs describe no schedule for it. We cover this two ways:

  • Database backups: fully automatic. A systemd timer on the VM runs pg_dump every night, uploads it to object storage, keeps 7 days, and emails an alert through SES if it fails.
  • Volume backups: automatable through the API. The same OpenStack credentials the dashboard uses can start a volume backup from a scheduled script. I have not confirmed CloudPe exposes it, so the email asks. If it is not available, the nightly pg_dump remains the real backup.
  • The one manual part is a restore test in week one, to prove the dump actually restores.

Why not copy the infrastructure from AWS? Why build from scratch?

First a correction: AWS staging has no 3 vCPU machine. It is made of small pieces: the backend task (0.5 vCPU, 1 GB), the database (db.t4g.small, 2 vCPU, 2 GB), and short-lived job tasks (0.5 vCPU, 1 or 2 GB each). The 3 vCPU / 12 GB VM is my sizing for putting all of that on one server.

The infrastructure itself cannot be transferred. These are AWS-managed services, and AWS gives no way to export them to another cloud:

AWS pieceCan it be transferred?Why
Fargate backend and job tasksNoThere is no server to copy. AWS runs your container on hardware you never see.
RDS database serverNoRDS has no machine image to download. Snapshots restore only on AWS.
Load balancer, EventBridge, KMS, Secrets Manager, CloudFrontNoAWS-only services
Your Terraform (about 1,700 lines)NoIt describes AWS resources (aws_ecs_*, aws_lb, aws_db_instance). The AWS provider cannot create anything on CloudPe.
Docker image (the application)YesPull from ECR and run, or rebuild from the same code
Database contentsYespg_dump then restore into Postgres 16
S3 filesYesrclone copy to CloudPe object storage
SettingsYesThe same variable names in a .env file
Domain namesYesPoint the DNS records at the new IP

So the plan already is a copy. The application, its data, its files and its settings are copied. Only the plumbing around them (VM setup, Docker Compose, Caddy, job timers, backup script) is new. It is written once, kept in git, and re-runnable. With D3 (reuse keys) and D5 (real data allowed), the database copy is a full copy including user accounts, which is the closest to "the same as AWS" that exists. Rebuilding the AWS layout piece by piece (Option A in the price section) is possible, but it costs about the same as AWS, is not an exact copy either, and adds a second VM and a load balancer to maintain.

  • Add 4 GB of swap and per-container memory limits.
  • The included 30 GB boot disk is too small for Postgres, hence the separate volume.
  • If out-of-memory kills appear, resize to a.gp1.16g (+₹449). With the recompute worker in the mix, 16 GB is a reasonable starting point if you want margin. Ask support whether resize works on a reserved plan.
