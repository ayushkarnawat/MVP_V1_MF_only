Nothing is deployed between runs, so every run must pass these locally before the next begins. The risk of one deploy at the end is that a problem found on staging could touch several runs; these gates are there to prevent that.

Lessons from the first VM session (apply to the staging step too)

  • Never stop a recompute that is running. A stopped run leaves its user's claim in place for 15 minutes, and a recompute started in that window skips that user ("recompute already in flight"). If one was stopped, wait 15 minutes and run a one-household recompute for that user (run_analytics_recompute.py --household <id>), which clears the claim.
  • Check for claims before the forced recompute at staging. Query analytics_recompute_status: no user should show a claim in flight. Afterwards confirm every scope of every user has all 15 sections.
  • The wrapper script is silent until the job ends. run-job.sh collects the output and prints it at the end. Start long jobs in the background and watch the container and the log.
  • Timing scripts need a recomputed user and today's NAV stored. They abort on any database write, so run them after the 06:00 IST NAV job (after 06:35 IST), for a user whose recompute completed, twice each; the second run is the baseline.
  • The deploy user cannot read .env. Commands that source it (the database counts) run under sudo.
