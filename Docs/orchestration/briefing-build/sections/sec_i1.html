Item 1 build: Change Head of Family, in detail

Read from the code on leapswitch-redesign on 31 Oct. It covers how the database is swapped, which codes and emails are sent, how the phone stub appears on screen, every error state, and the label changes. Nothing is built.

The design in five lines

  • Same account, new sign-in. The users row, its id and all portfolio data stay exactly where they are. Only who can sign in changes.
  • Two markers stay in step. A new is_head flag (migration 0047) says who the head is. At the swap the self relationship moves to the new head in the same transaction (D29 option A), so the 15 places in the backend that test relationship = self keep working without edits. The flag is what new code reads, and a backfill makes it equal to self for every existing account.
  • Four codes. Each person confirms their email and their phone. Email codes go out through the same email template as sign-in codes, with different wording. Phone codes use the existing stub (D37), and the stub code is shown on screen.
  • Nothing changes until all four are verified inside 10 minutes. The swap is one database transaction and rolls back as a whole.
  • Safety: the current head re-confirms to start, everyone gets an email, and the old head has a 24-hour undo link (D31).

The single transaction, in order

  1. Lock the users row, then the account's members (by id), then the open request (FOR UPDATE, which works on Postgres; it is a no-op on the SQLite used in tests).
  2. Check again inside the lock: request open and not expired, all four codes verified, old head still head, new head still a member, account not pending deletion, no import preview open, contact details still free, PAN checks still true.
  3. Copy the old head's contact, identities, session count and every member's label into the audit row. Store the undo token hash and its 24-hour expiry.
  4. Delete the old identities. Flush.
  5. Set users.phone_number and users.email to the new head's values. Flush (this is where the unique rule would fire if a race slipped past the check).
  6. Insert the two new identities. Flush.
  7. Members: the old head's row first (clear head, change the self label, receive the old contact details), flush, then the new head's row (set head, set self). Flip the other labels.
  8. Delete sessions and pending link tokens. Delete the four used code rows.
  9. Insert the consent withdrawal rows. Write the audit row. Commit.
  10. After the commit, send the "head changed" emails to both people and to the old head's other email, if any. A failed email never undoes the swap; it is logged and retried.

If anything fails before step 9 the whole transaction rolls back and nothing has changed. A unique-rule failure at commit returns a "contact already used" error.

The two checks that must pass again at the swap

  • Contact availability. The existing check looks at the identity rows and at users.email. It does not look at the email column of identity rows, which is how a Google sign-in is recognised. The swap runs both that check and the sign-in collision check.
  • PAN. The new head's PAN must not be held by another account and the member must not have an "on another account" conflict. Once someone is head the app does not let that row's PAN be edited, so a head with no PAN could never add one. That is why a member with no PAN is not eligible.

The emails

The sign-in code email is the only email the app sends today, built in email_templates.py (a headline, a large code, a note and a disclaimer; dark-mode aware). Its headline says "to sign in", which is wrong here, and its 5-minute wording is fixed. The change: the template takes a purpose, a headline, a note and a time-to-live, and the header and footer are shared with the two notice emails, which is the second email type the module's own comment was waiting for.

On staging the email mode is real SES, so the code arrives in a real inbox. In stub email mode the code is returned on screen the same way as the phone code.

The phone stub, shown on screen

  • Phone codes use OTP_DELIVERY_MODE = stub: nothing is sent, and the API returns the code in the field otp. The backend refuses stub mode in production, so this can never leak there.
  • On the sign-in screens a "Local Dev OTP" banner already shows that value. The Profile contact-change dialog ignores it, so a tester cannot see the phone code there. The head-change dialog renders it under each phone box: "Test mode: no SMS is sent yet. Your phone code is 482 913." It appears only when the API returned a code.
  • The banner is extracted into one small component so sign-in and head change look the same.

Buttons

  • All green buttons use the brand green #22C55E with white text. That is already true of the shared Button component (primary variant) and of the hand-built page buttons that use the green token. The Change Head of Family button, Send codes, Confirm change and Confirm and move sign-in use the shared primary button, not custom colours.
  • Contrast, for your decision. White text on #22C55E has a contrast ratio of 2.28 : 1. The accessibility standard asks for 4.5 : 1 for normal text and 3 : 1 for large text, so it falls short on both. The existing darker green #15803D reaches 5.0 : 1 and #16A34A reaches 3.3 : 1. We build it as you asked; semibold 14 px or larger text and a visible focus ring reduce the problem. If you want it fully fixed later it is one token.
  • About 257 places in the app hard-code #22C55E instead of using the token (mostly sign-in and import screens). A cleanup pass is listed under the design rules.

Relationship labels: the flip, and the situations around it

The enum has six values: self, spouse, parent, child, sibling, other (with a required free-text label when other), plus "not set". There is no gender anywhere, so father versus mother, or son versus daughter, cannot be told apart by code. That is why the table uses only the neutral values and sends the unclear cases to other or not set. A wrong "spouse" or "parent" is worse than "Not set".

The dialog shows every proposed label for review before the person confirms. Where the code would have to guess it leaves the label as "Not set" and keeps the old one in the audit row.

More situations, each with the rule:

  • Members with no label (found in a statement): stay "not set".
  • Several spouses or several siblings: only the person chosen as the new head changes meaning; everyone else follows the table.
  • Free-text "other" labels such as "Mother-in-law": kept only when they read the same from either side ("Friend", "Business partner"); otherwise cleared and flagged for the new head to fill in. Code cannot invert gendered text.
  • The head must have a label to the old head before the change. An unlabelled or "other" new head needs a label first, or the old head's new label cannot be worked out.
  • An account that never finished onboarding (no self row): the Change Head button is hidden.
  • The Admin pill and Head badge follow the head flag, not the word self.
  • Greeting and name: the Home greeting and "self name" come from the head's row, so they switch to the new head's first name.
  • Onboarding answers, goals and investor type describe the old head. They stay on the account until the new head edits them (D29).
  • "Member since" shows the account's creation date, which is the old head's. It stays; it is the account's age.
  • Members added, removed or relabelled after the swap, then undo: undo restores only the labels the swap itself changed; later edits are kept.
  • The old head's contact details were stored on the account, not on their member row. They are copied onto their row, so their card shows an ordinary member's phone and email.
  • A legacy account with no email cannot start the change: the current head must add and verify an email first, because they need to enter an email code.
  • Changing back uses the same flow, at most once every 7 days.

What the screens do

  • Family page: the member cards stay as they are. A Change Head of Family button (green, white text) is added, shown to the current head only. A pending request shows a banner with the time left and a Cancel button.
  • Dialog, three steps: choose the member (greyed with a reason when not eligible); enter four codes, with the stub code visible under each phone box; a before-and-after summary that says plainly who signs in afterwards and that everyone is signed out.
  • After success: the app calls logout and shows the sign-in page with a notice. The new head signs in with their own email or phone, accepts the Terms, and sees the same data.
  • The existing six-box code input is reused; its sign-in wrapper has fixed wording, so a small variant is needed.

Open points on item 1 (D40), with my recommendation for each

PointRecommendation
Does "the Self row is not renamed" (D3) still hold?Self moves to the new head in the same transaction (D29 option A). The flag mirrors it. This is the smallest change to existing code, and it is what the swap table above assumes.
May a member with no PAN become head?No. The head's PAN cannot be edited later, so the member must already have a verified PAN with no conflict.
Does the member's origin change?No. The rules that read it only matter for members found in statements, and a head has a label.
Does the new head inherit the onboarding answers?Yes, until they edit them, as D29 says.
A separate OTP table or a purpose column?A purpose column plus the request table that holds the four verified stamps.

Tests to write first (added to the earlier list)

  • Swap leaves the user id, portfolio rows and analytics rows untouched, and moves exactly the rows in the table above.
  • A deleted Google identity cannot sign in to the account after the swap; the old email and phone become free to register.
  • A head-change code cannot be used to sign in, and a sign-in code cannot be used in the flow (purpose).
  • The one-self rule: the order old row, flush, new row never violates the unique index; a forced failure mid-way rolls back everything.
  • Each error code in the table is returned for its case, and the message is shown next to the right box.
  • The stub code appears in the dialog when the API returns it and not otherwise.
  • Label table: every cell, including the "other" and "not set" cases.
  • Undo restores identities, contact and the swap's own labels, and fails cleanly when a contact was taken.
  • Account deletion also removes the new request table's rows.
