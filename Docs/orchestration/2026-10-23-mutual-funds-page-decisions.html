Q5 — Performance page's benchmark + time-frame dropdown

Resolved — Option B

Precompute every (benchmark × time-window) combination, prioritizing read speed over backend load, matching the existing precompute-everything architecture. Time windows: 1Y / 3Y / 5Y / Since inception, computed as windowed XIRR (new math — today's benchmark XIRR is always since-inception).

Owner's answer"My mind is going toward option B... I am prioritizing... the utmost best speed to the user... along with that... add more indices to this, we already... run for more indices than these four, so why not use that background job's data."

Correction, checked against the real code: there is no existing job computing more than the current 4 indices. nse_indices_client.py's index-name mapping is a hardcoded 4-entry dict with a comment stating it's deliberately static ("only 4 members, no need to fetch IndexMapping.json at runtime") — nothing today fetches or stores any other index's history. Adding indices is new, scoped work (new enum members + trading-name mapping + a backfill run through the same fetch-and-cache mechanism — not a new integration, just more rows).

Index list finalized (2026-10-23): the owner confirmed the recommended candidates as-is — Nifty Next 50, Nifty Smallcap 250, Nifty 100, Nifty 200. No open sub-items remain on this question.

Owner's answer"Let's go with the recommended option as given."
