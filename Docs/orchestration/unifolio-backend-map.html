How the tables connect

GroupTablesHow they connect
Identityusers, auth_identities, sessionsauth_identities.user_id and sessions.user_id → users.id. One user, many login methods, many sessions.
Before an account existsotp_requests, pending_identity_verificationsotp_requests has no foreign key; it is matched by the phone or email value. pending_identity_verifications.matched_user_id points at users only when linking a new login method to an existing account. Both now carry a consent_snapshot JSON blob captured at the moment of agreement.
Consentconsent_recordsDeliberately no FK at all, not even to users — see the theory answer on why. Matched by the user_id value, append-only via a database trigger.
Householdhousehold_membersuser_id → users.id. Every portfolio row hangs off a member, never directly off the user. PAN lives here, now alongside phone_number/email contact fields, origin, name_source and the detected-PAN shadow columns.
Portfolioimports, folios, transactions, transaction_imports, portfolio_snapshotsimports, folios and portfolio_snapshots → household_members.id. transactions → folios.id and → imports.id (whichever import wrote it first). transaction_imports is the new many-to-many: every import that ever touched a transaction, so deleting one overlapping import doesn't remove a row another import still needs. folios.scheme_id → schemes.id.
Audithousehold_member_name_changes, household_member_mergesNew tables behind CAS member detection: every rename (CAS variant, user correction, manual edit) and every merge of two detected duplicates is recorded, independent of whether the member row itself still exists.
Reference data, shared by everyoneschemes, nav_history, scheme_ter, scheme_aaum, fund_scores, scheme_rankings, ranking_weights, scheme_fund_managers, benchmark_index_history, arn_directory, scenarios + 3 scenario tablesNo user or member column at all. All the per-scheme tables → schemes.id. arn_directory is looked up by folios.arn_code text, no FK. The scenario tables form their own small graph off scenarios.id.
Analytics outputanalytics_sections, analytics_recompute_statusBoth keyed by user_id → users.id. analytics_sections.household_member_id is filled for member scopes, NULL for the combined scope. 10 sections now, not 7.
Anonymousaccount_deletion_surveysDeliberately no FK, so exit feedback survives the account being deleted.
The spine, unchangedusers → household_members → folios → transactions, with schemes joining from the side.
User data vs market dataDeleting an account deletes the spine. It never touches schemes, rankings, fund managers, NAVs, TER, AAUM, scenarios or benchmarks, which every user shares.
Partitioned ledgertransactions is partitioned by year on Postgres, so its primary key is (id, date).
Two layers of duplicate guardThe unique key on transactions now includes occurrence, so two genuinely identical same-day rows both save; transaction_imports tracks every import that touched a row, so a safe delete only removes rows no other import still needs.

Verification always reads the newest unverified row for that phone or email. A resend therefore makes older codes useless even if they have not expired. Rows are only ever deleted by the account hard-delete job.

Q2 · The user generates an OTP and leaves

Nothing is rolled back and nothing is cleaned up — unchanged from before. The phone otp_requests row (with its consent snapshot and device fields) sits unusable after 5 minutes; no users row was ever created. There is still no scheduled job that deletes expired otp_requests or pending_identity_verifications rows.

Q3 · How the pending row is deleted after the email gate is verified

Same token mechanism as before, just the other way round: the phone-verify step mints the token and the pending_identity_verifications row (hashed token only, raw token returned once to the browser). The browser carries it through the email-gate screens. On a correct email code, complete_gated_signup() hashes the token, finds the matching pending row, and in one commit: INSERTs users, INSERTs both auth_identities rows, INSERTs 2 consent_records rows (GIVEN, using the carried-over snapshot), and DELETEs that pending row.

Q17 · How transactions are "calculated"

Still read off the CAS, never calculated from the folio table. What's different:

  1. Opening balance: casparser's own running total for each scheme at the start of the statement is now saved as an OPENING_BALANCE transaction, with an "earliest statement wins" rule — a longer-lookback statement uploaded later replaces a shorter one's opening row.
  2. Identify, not resolve-by-fuzzy-name: each fund is matched against a locally-refreshed AMFI scheme master (ISIN → NAV fingerprint → sibling NAV → ask), not a live fuzzy match against mfapi.in.
  3. Dedupe key widened: now (folio, date, amount, units, type, occurrence) — two genuinely identical same-day rows (two identical SIP installments) both save, where the old 5-column key would have silently dropped one.
  4. 4 new transaction types: reversal, gift_in, gift_out, bonus — these used to fall through to misc and were effectively ignored.

Q22 · The reference refreshes in AWS terms
  1. EventBridge Scheduler fires at the cron time using its own IAM role, scoped to ecs:RunTask on these task definitions.
  2. ECS starts a Fargate task (0.5 vCPU / 1 GB, or 2 GB for the fund-manager job) in a private app subnet; the execution role pulls the image and the DB password.

  4. A fetch failure for the fund-manager job logs FUND_MANAGER_ALERT, which a CloudWatch metric alarm turns into an SNS email — the only job with alerting wired up so far.

Theory answers

The questions that are about design choices rather than a flow.

Q4 · Why users.phone_number is unique and NOT NULL, and email is nullable and not unique
  • Phone is still the account's root identity — more so now, since signup starts and ends with phone verification, and email is the gate, not the other way round. A users row without a phone still can't exist.
  • Unique still makes "one account per phone number" a database rule, not just an app check.
  • Email is still optional — a Google account whose own email isn't verified is stored with none — but the login-side "phone with no account" path that used to create one is now fixed: it 401s instead, so there's no longer any real path that creates a phone-only account outside the intended signup flow.
  • users.email is still a copy, refreshed from the highest-priority verified identity, never the source of truth.
Q6 · auth_identities.provider_subject and email

Unchanged: the identifier the login method vouches for (phone number, email, or Google's sub), plus a denormalized, verified-only email used for collision detection. Nothing here changed with the auth-flow reversal — only the order in which phone_otp and email_otp rows get created flipped.

Q11 · sessions.device_info

Still always NULL — create_session() is never actually called with a value for it, confirmed by reading every call site directly. What's new is a separate, genuinely used mechanism one table over: otp_requests now captures IP (the real client IP, parsed correctly out of X-Forwarded-For behind the ALB), device type, OS family/version and browser family/version on every OTP request — explicitly for product analytics ("what are people signing up on"), not fraud prevention, and explicitly not copied forward into sessions.

Q16 · The imports table

Same purpose as before — one row per import event — but now: upload_group_id links every person's row that came from the same physical CAS file and S3 object; preview_state holds the encrypted, in-progress review session (replacing the old in-process RAM dictionary); statement_from_date/statement_to_date are reliably set at confirm now, for every path, which an earlier version of this investigation had flagged as broken.

Q26 · Where the raw PAN is while the CAS is only in memory

Changed in an important way: it's no longer purely RAM. Between parse and confirm, each detected person's raw PAN lives inside the review session, which is now encrypted and written to imports.preview_state in the database, not kept only in the serving task's process memory. It's still never written in plaintext anywhere, never logged, and the decrypted PAN only ever exists in memory for the moment it's being used — but the durability story changed from "lost if the task restarts" to "survives a restart, decryptable only with the same PAN keys."
