Q2 · The user generates an OTP and leaves

Nothing is rolled back and nothing is cleaned up. The rows written so far stay in the database: they simply stop working once their time runs out. There is no scheduled job that deletes expired otp_requests or pending_identity_verifications rows, and no users row was ever created, so there is no half-made account to clean up.

Q3 · How the pending row is deleted after the phone is verified

The link is a token, not a user id. POST /auth/signup/email generates a random token, stores only its SHA-256 in pending_identity_verifications.token_hash, and returns the raw token to the browser once (email_otp_required.token). The browser sends it back as pending_token on every later call.

On the phone verify call, complete_phone_gate_signup() hashes that token, finds the one pending row whose token_hash matches, checks it is unexpired and has matched_user_id = NULL, then in a single commit: INSERTs the users row, INSERTs the phone_otp and email_otp identities, and DELETEs that exact pending row. The backend does not look at users to decide what to delete; the token is the pointer. If any part fails, the whole commit rolls back and the pending row survives.

otp_requests rows are not deleted at signup. They stay with verified_at filled in.

Q23 · pan_pending_until
  • Set to upload time + 65 minutes when /imports/parse claims a PAN.
  • Cleared to NULL by Confirm Import, which is what makes the PAN permanent.
  • Why 65 and not 60: the review session lives 60 minutes. The claim must outlive any session that can still be confirmed, so a confirm can never find its PAN already taken by someone else.
  • Expiry is lazy. No job sweeps expired claims. An expired pending PAN is wiped the next time anyone uploads a CAS with that PAN (or the same member uploads again). Until then the encrypted value sits there, treated as free.
  • Discard clears all three columns at once, but only if the claim is still pending and matches that session's PAN. A permanent PAN is never touched by discard.

Q20 · How the three connect

A scheme is a fund (one row per AMFI code, shared by everyone). A folio is one member's account in one scheme at one AMC, identified by (member, scheme, folio number). A member holding two schemes under one folio number has two folio rows; the same scheme under two folio numbers is also two rows. Transactions hang off folios. To show a member's portfolio the backend reads that member's folios, joins each to its scheme, and processes each folio's transactions.

Q17 · How transactions are “calculated” for a member with 3 schemes

They are not calculated from the folio table. Transactions are read off the CAS by casparser, one row per line of the statement, and saved at Confirm against their folio. The calculations run the other way: from each folio's transactions the backend works out units held, cost, gains, value, XIRR, SIPs and coverage gaps, every time the dashboard asks (with a 15-minute in-memory cache).

  1. Detect: casparser types each line (purchase, SIP, redemption, switch, dividend, STT, stamp duty…); Unifolio maps those to 12 types and stores amounts and units unsigned. The type alone says which way units moved.
  2. De-duplicate: a line whose (folio, date, amount, units, type) already exists is skipped.
  3. Holdings (FIFO): purchases, SIPs, switch-ins and dividend reinvestments add lots; redemptions and switch-outs consume the oldest lots first. What is left gives units and cost; consumed lots give realised gain.
  4. Value: units × latest NAV from nav_history (fetched from mfapi.in if today's is missing).
  5. SIP detection: a folio is an active SIP if it has any purchase_sip and is not fully redeemed; the next date is projected from the pattern.
  6. Coverage gap: replaying units in date order, if the running total dips below zero the statement is missing earlier history.

Q18 · portfolio_snapshots

One row per member per month-end: (household_member_id, snapshot_month) → total_value. It is a cache for the value-over-time chart so month-end values aren't recalculated from every transaction on every load. It links to household_members only; the family chart sums the members' rows.

When rows are written: lazily, on GET /household-members/{id}/snapshots or the aggregate version. For each month-end from the member's first transaction to today that has no row yet, the backend replays FIFO up to that date, multiplies by the NAV on or before that date, and INSERTs the row. A month where any NAV is unavailable is skipped, not stored as a wrong number, so it is retried next time. Rows are never recomputed once stored, and only the account hard-delete removes them.

Q21 · Answers
  • From the name: classify_plan_from_name() upper-cases the scheme name and looks for the words DIRECT and REGULAR. Exactly one → that variant. Both or neither → unresolved.
  • Names without either word (older funds, ETFs, some FoFs): plan_name_variant = unresolved and plan_type = unclassified. We never guess.   • User override on the review screen is sent as plan_type_override. It updates only folios.plan_type, and only when that folio is being created by this import. An existing folio keeps its value. schemes.plan_name_variant is never changed by an override.

  • A similar scheme in future: nothing is learned from overrides. A new AMFI code gets a new schemes row classified by the same name rule. The same AMFI code reuses the existing row. A new folio is classified from its own name and ARN. So a scheme whose name never says Direct or Regular stays unclassified until someone overrides it for that folio.

Q12 · analytics_recompute_status, fully

One row per user (the household), three columns:

  • user_id: primary key and FK to users. A household-level fact, because one recompute run writes every scope at once.
  • started_at: NULL means idle. A timestamp means a run has been claimed or is running. A claim older than 2 hours is treated as a crashed run and can be taken over.
  • generation: a counter for “the household's data changed underneath you”. The worker notes it at the start, and before writing each section it re-reads it with SELECT … FOR UPDATE. If it changed, the worker stops without writing, so it can't put back numbers from deleted data. It is bumped by deleting an import and by the account hard-delete, in the same transaction as the delete. A new import does not bump it; it starts a fresh recompute instead.

Who claims a run: Confirm Import; GET /analytics/{scope} when that scope has no rows; the Retry button; the daily 06:30 IST --all job (which claims per user). All go through try_claim_recompute(), a single atomic upsert that only succeeds if started_at is NULL or stale. If the claim succeeds but ECS can't place the task, the claim is released straight away.

Q22 · The three reference refreshes in AWS terms

Theory answers

The questions that are about design choices rather than a flow.

Q4 · Why users.phone_number is unique and NOT NULL, and email is nullable and not unique
  • Phone is the account's root identity. The signup screen only offers Email or Google (Landing.tsx, signup mode) — there is no "sign up with phone" button. Every signup ends with the same mandatory phone step, so a users row without a phone can't exist by design, and NOT NULL states that in the schema.
  • Unique makes “one account per phone number” a database rule, not just an app check. Two signups racing with the same number can't both succeed; the second INSERT fails. The phone login path also relies on it to find the account (find_or_backfill_phone_identity).
  • Email is optional by design, but only one real path leaves it NULL today: a Google account whose email Google itself hasn't verified is stored with no email (a deliberate security choice, not a gap). A phone-only users row can also exist with no email — but only via the "Continue with Phone" button on the Login screen, when the number typed there has never signed up before. That is the same bug already flagged at Q10 (an unrecognized phone silently creates an account instead of saying "no account found"), not an intended second signup path.
  • users.email is a copy, not the source of truth. It is refreshed from the highest-priority login identity that has an email (Google, then email OTP). The real uniqueness for email logins is the unique (provider, provider_subject) on auth_identities, where provider_subject is the email.
  • Why not make email the key: it is missing for some users; it can change (contact change, linking Google); and one person can legitimately have the same email on a Google identity and an email-OTP identity. A unique key on the copy would break those cases without protecting anything auth_identities doesn't already protect.
  • Related tables: auth_identities holds a phone_otp row whose provider_subject equals users.phone_number; otp_requests is matched by the same phone or email value (no FK); pending_identity_verifications carries the email during signup; the account hard-delete gathers every phone and email to delete the matching OTP rows. Changing phone in Profile updates both users.phone_number and that identity row.
Q6 · auth_identities.provider_subject and email

provider_subject is the identifier the login method vouches for: the phone number for phone_otp, the email address for email_otp, and Google's sub (its permanent account id, not the email) for google. (provider, provider_subject) is unique, so one Google account or one email can belong to only one Unifolio user. Login looks identities up by exactly this pair.

email is the verified email that identity carries: NULL for phone, the address for email OTP, Google's email only if Google marked it verified. It is used for two things: detecting that a new Google login is the same person as an existing email account (auto-link, or ask to confirm), and computing users.email. An unverified email is never written here, so nobody can claim someone else's address.

Q11 · sessions.device_info

A free-text column meant to hold the device or browser a session was created from, for a future “your active sessions” list or suspicious-login checks. create_session() accepts it, but no caller passes it, so today it is always NULL. The other session columns: session_token_hash (SHA-256 of the bearer token, which is never stored), auth_method (the method that completed this login), expires_at (+30 days), last_active_at (set at creation; only /auth/session/refresh moves it, and the frontend doesn't call it).

Q16 · The imports table

One row per import event for a household member. It records where transactions came from (transactions.import_id is NOT NULL), feeds Import History, and holds the evidence: raw_parser_output (the full parsed CAS with PAN removed) and file_reference (the S3 key of the PDF, 30 days). Q26 · Where the raw PAN is while the CAS is only in memory

In the ECS backend task's RAM, inside the review session: _preview_sessions[session_id]["parse_result"].investor.pan (service.py). The PDF bytes, which also have the PAN printed in them, sit in the same session. It stays there until Confirm, discard, a PAN conflict, or 60 minutes. It is not in the database in plain form, not in imports.raw_parser_output (redacted before serialising), not in any API response (only the masked form, e.g. A********Z), and not in logs. The only other copy is the uploaded PDF in a temp file on the task's disk for the seconds casparser takes. Once the upload passes the PAN check, the PAN also exists in the database, as ciphertext plus HMAC.
