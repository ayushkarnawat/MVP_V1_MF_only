## 3. Deploy mechanics (to be completed at S.1)
Follow the Individual Fund guide's steps, with these differences and the 30 Oct VM lessons:
1. Pre-checks: query `analytics_recompute_status` first (`started_at` must be empty for every user); **never stop a running recompute**; `check-memory.sh`, `check-disk.sh`; no import in progress.
2. Backup before anything (GATE), then `alembic current` must be `0046`; after the deploy it must be `0052`. Run the migrations and start the new backend in the same window: the new code does not run on the old schema.
3. Start long jobs in the background with a completion notification, never `sleep`; read `.env` under `sudo`; every query through the compose Postgres container (the host has no `psql`).
4. Forced analytics recompute (GATE), then confirm **every scope of every user has all 15 sections, 0 failed** (30 Oct and 2 Nov: 3 scopes x 15 for the test household).
5. Install the `0 6 15 * *` cron line; confirm with `crontab -l`.
6. Timing scripts only after today's prices are stored (see 4.3 note).
7. **`FRONTEND_BASE_URL` (found by the Run 6 review, High).** The backend builds the emailed links (undo a Head of Family change, "this wasn't me" for a contact change) and the PDF export address from the single setting `FRONTEND_BASE_URL`, which is `https://ls-staging.unifolio.in` on the VM today. That site serves the OLD main-branch bundle, which does not have the pages `/undo-head-change` and `/reverse-contact-change`; the new bundle is at `https://ls-redesign.unifolio.in` (same backend API, frontend-only bundle, Caddy falls back to `index.html` for unknown paths). **At S.1, before the backend restart, set `FRONTEND_BASE_URL=https://ls-redesign.unifolio.in` in the VM's `deploy/leapswitch/.env`** (keep `ALLOWED_ORIGINS` as it is: it already lists both sites), restart the backend, and verify with a real emailed link in Q5 and Q7 (the link must open the new page, not the sign-in screen). Side effect to tell the manager: emailed links for everyone on this VM now point at the redesign site until the redesign replaces the main bundle. AWS staging (`infra/modules/backend/main.tf`) has the same setting; it is not part of this deploy. Note the older plan line (`Docs/superpowers/plans/2026-10-24-deploy-redesign-plan.md`, "FRONTEND_BASE_URL is used only by the PDF export") is no longer true.
8. **Order of a deploy that carries a migration (lesson of the 3 Nov deploy).** Run the deploy step, then STOP if its exit code is not 0 (use `set -e`, never a wrapper that carries on). Check that `docker compose ps` shows backend and worker running the NEW image id (`docker image ls` / `docker inspect`), and only then run `alembic upgrade head` with `docker compose run --rm backend alembic upgrade head` straight after (the new code does not run on the old schema, the old code does not run on the new). On 3 Nov the migration ran about four minutes while the old containers still served because the first `deploy-redesign.sh --full` stopped at its disk guard (8 GB free, 10 GB wanted) and the wrapper did not stop.
9. **Disk before `--full`:** a backend build needs 10 GB free. Resize the VM disk in the CloudPe dashboard (the owner) BEFORE the next backend deploy (the 29 Oct redeploy filled the disk to 100%); `docker builder prune -f` frees about 2 GB of build cache with the manager's yes. `--full` only when something under `backend/` changed.
