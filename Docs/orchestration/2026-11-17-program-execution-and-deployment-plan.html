2. The strategy in one page

The recommendation. Build in five waves on one integration branch, with one worktree and one branch per batch so lanes never collide. Merge a batch into the integration branch only after its own tests and review pass. Deploy to staging at four milestones, each small enough to check and each with its own rollback. Go to production once, after the fourth milestone. Backend changes are additive first, because the old staging link shares the same API and database.

Principles

  • Numbers before presentation. The truth-finding fixes (A1 to A3) land before charts, dates and exports repeat those numbers.
  • Settle shared places early. The top bar, page headers and the section list change once, early, so later batches build on a stable frame.
  • Small, checkable releases. Four staging milestones, each with a written checklist, instead of one large final round.
  • Backend additive first. A new field or route can go out at any time; an old one is removed only when nothing reads it.
  • One owner per shared file at a time (section 5).
  • Production once, only after the last milestone passes, with the recompute and a rollback written down.

7. Shared backend, the old link and migrations

The one structural trap. ls-redesign.unifolio.in is a frontend-only bundle that calls the same API, database and worker as the original ls-staging link (read in the README). A backend change therefore reaches the old link at once. Batch C’s decision (“remove the old folio field now”) would blank folios on the old link, and any renamed or removed field would break it.
RuleWhat it means
Additive firstNew fields and routes ship any time. Removing or renaming a field is a separate, later step, taken only when no frontend reads it.
The old link stays as it is (Q2, 17 Nov)You said to keep it and not touch it, so it keeps sharing the backend. Every backend change must therefore be additive only: no field is removed, renamed or changed in meaning while the old link exists. Batch C keeps the old folio field and adds the full folio number beside it; the new screens read the new one. Nothing is retired, redirected or edited on the old link.
Backend before frontendAt a milestone with a new route (search, the movers “all” switch), the backend deploys first; a frontend that loads before it degrades gracefully (search’s plan already says so).
Contracts in testsEach backend change has a test for the response shape, so a frontend and a backend cannot drift.

12. Size and duration (estimates, not measurements)

Counting each plan’s own sizes with S as half a day, M as a day and a half, L as three days, the in-scope work is about 190 worker-days (this includes reviews, writing and your own checks, not only code). With your capacity model (Q3: Codex on backend and Antigravity on frontend, one task each at the same time, Claude orchestrating), the finish time is set by the busier of the two queues, not by the total. I expect the frontend queue to be the busier one (search, the section rail, dates, charts, export dialog, tutorial), so the program is likely to run about 15 to 20 working weeks. That range is a guess: it will be recomputed once each batch’s own plan splits its tasks between the two builders, and again after M1 when we have a real pace. Claude’s own work (plans, investigations, guides, reviews, evidence) runs alongside and is not on either queue.

Read this as a shape, not a promise. The estimate leaves out GA4 and A4 (paused) and Batch L’s approved fixes (the audit itself is about 8 to 10 worker-days and is not in the chart); each adds to it when scheduled. The sizes are each plan’s rough estimate, search’s are the largest, and I have not measured how fast the workers actually go. The first wave will show the real pace, and I will revise this after M1.
