2. Duplicate categories in the allocation view (17a)

One category, two slices, because two spellings of the same name are treated as two categories.

What you saw

In the Allocation tab’s category donut, “Equity Scheme - Flexi Cap Fund” (15.2%) and “Equity Schemes - Flexi Cap Fund” (2.8%) appear as separate slices in the 44.97L donut; “Large Cap” splits the same way (8.6% and 2.5%) in the 93.13L donut. The two names differ by one letter.

Why it happens (read in code)

  1. Each fund in our reference table has a sebi_category text copied from AMFI’s NAV file. AMFI prints that file with one heading per fund house, so the same SEBI category appears under several spellings. A comment in backend/app/services/analytics/scheme_universe.py says so: “101 headings for ~80 categories”.
  2. That file already has the fix: canonical_category() turns “Equity Schemes - X” into “Equity Scheme - X” (and a short list of other known respellings). It is used by the category ranking, performance ranking, scorer and peer lookups.
  3. compute_category_allocation() in backend/app/services/analytics/allocation.py does not call it. It builds the donut with by_category[category] += value using the raw text, so two spellings become two buckets.
  4. So the two funds in your screenshot most likely come from fund houses whose headings in AMFI’s file are spelled differently. I have not checked the actual rows; the build confirms it with a test.
Already fine (read in code). The asset-class donut on Home (by_asset_class) turns each category into a broad bucket (Equity, Debt and so on) through a separate helper, so it does not show the two spellings. The AMC donut groups by fund house. Overlap’s category tabs match the end of the name (“Large Cap Fund”), so spelling of the first words does not matter. The Category column in the holdings table already strips everything before “ - ” (lib/categoryLabel.ts), so a row reads “Flexi Cap Fund” either way and will match the merged slice.

5. New member missing from the drop-down (17d)

After Add Data creates a new family member, the header drop-down only learns about them on the next full page load.

What you saw

Why it happens (read in code)

  1. The drop-down (shell/layout/FamilySelector.tsx) shows the list kept by ScopeProvider (shell/scope/ScopeProvider.tsx) in React state.
  2. That list is fetched once when you sign in, and again only when refreshMembers() is called.
  3. refreshMembers() is called by the Profile pages that change members (Family, Personal info, Import history). It is not called by the Add Data page: in shell/wrappers/ImportWrapper.tsx the onDone handler only navigates back with the notice.
  4. The members request (listHouseholdMembers in features/auth/api.ts) is a plain fetch, so there is no cache to blame. A hard refresh rebuilds the page state, which is why it “fixed” the problem.

A second effect you did not mention: with one member the drop-down has no “Family Combined” row at all (FamilySelector hides it when there is a single member), and the page stays in “member” mode on Prateek. So even after a reload, the user lands on Prateek’s numbers while the banner talks about 14 funds that belong to Lalchand. Your answer to Q12 keeps it that way for a normal import. The exception is the wrong-person case, described below.
