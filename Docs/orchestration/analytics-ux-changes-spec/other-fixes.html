1 · Benchmark labels say Price Return, the maths uses Total Return

SP1TinyFix

The Benchmark card labels every index "(Price Return)". The calculation behind it uses the total-return series (TRI), which includes reinvested dividends. That was decided on 9 Oct so the index compares fairly with a fund NAV. The label tells the reader the opposite of what the number is.

Proposed

What changes
  • The four labels in frontend/src/features/analytics/BenchmarkSection.tsx (lines 27 to 30): Nifty 50, Nifty 500, LargeMidcap 250, Midcap 150.
  • Check the Per-Fund vs Benchmark tab, the mobile view and the print view for the same words.
  • Update the label strings in the section tests.
  • Wording: "Total Return" (suggested) rather than "TRI", which a stakeholder may not know.
Why not change the maths to price instead

TRI was chosen on purpose. A price index leaves out dividends, so the benchmark would look worse than a fund NAV does and the comparison would flatter the portfolio.

5 · The US-Iran phases do not add up to the headline: cause found

SP1Check doneSmallQ16 answered: Option A

I ran the check. The gap is not an averaging effect. Phase 1 ends on 2 Apr and Phase 2 starts on 2 Apr; Phase 2 ends on 8 Jul and Phase 3 starts on 8 Jul. The engine counts the boundary day’s price move in both phases. With that fixed, the phases add up to the headline. The headline and the rupee figure were right all along; the phase figures are wrong.

What the check found
Measured on real pricesWhole eventPhases compounded, as builtPhases compounded, boundary fixed
Parag Parikh Flexi Cap (Direct)-2.28%-3.68%-2.28%
Nippon India Index Fund, Nifty 50 (Direct)-6.55%-8.39%-6.54%
Household, weighted by the p20 holdings-3.03%-4.62%-3.13%
Household phase figuresShockPartial recoveryRelapse
As built-8.73%+6.87%-2.21%
Boundary fixed-8.73%+6.68%-0.51%

Run on 19 Oct against the local database, read only. Prices there stop on 18 Sep and only two of the portfolio’s funds have price data in that older copy, so the figures differ from the staging screen (-4.68% and -6.32%). The gap is the same size: 1.59 points here, 1.64 on staging.

Why it happens
  • A phase’s start price is the last price before its start date, so the start day’s move belongs to that phase. This is the right rule for one event on its own.
  • A phase’s end price is the last price on or before its end date, so the end day’s move belongs to that phase too.
  • When one phase ends on the day the next starts, that day’s move is in both. The scenario’s own description says Nifty fell more than 2% on 8 Jul, and the Relapse phase shows that fall in this sample as 1.7 points of extra loss.
  • The whole-event headline is one window, so it counts each day once. That is why only the phases are off.
  • The averaging effect I first suspected is real but small: about 0.1 point here (-3.03% against -3.13%).

Today

Proposed

In the diagrams: NEW a step or column this change adds · READ an existing column the change reads · PK/FK keys. Unlisted columns exist but are not touched.

Option A (chosen): correct the data
-- run on every database that has the scenario, then recompute the three phase rows UPDATE scenarios SET end_date = '2026-04-01' WHERE name = 'US-Iran war -- Shock'; UPDATE scenarios SET end_date = '2026-07-07' WHERE name = 'US-Iran war -- Partial recovery';
  • Shock would read 2026-02-28 to 2026-04-01 and Partial recovery 2026-04-02 to 2026-07-07. Relapse stays 2026-07-08 to ongoing, so 8 Jul belongs to the relapse, which matches its description.
  • The phase descriptions mention "by 2 Apr". Reword them if the shorter date range reads oddly.
  • The seed migration (0037) still holds the old dates. A database built fresh would bring the bug back, so the correction should ship as a small data migration, or the seed be corrected before the next fresh build.
  • If the duplicate scenario rows (fix 3) are still present, update both copies or clean those up first.
Option B: change the engine
  • For a phase after the first, start from the previous phase’s end price instead of the price before its own start date.
  • The dates stay as they are, but the phases stop being independent: they only work if the data keeps them back to back. A single date typo would silently reintroduce a gap or an overlap.
  • More code and more tests than Option A for the same result.
Test to add
  • A portfolio with back-to-back phases: for each fund, the whole-event result equals the phases compounded, to the rounding of two decimals.
  • A guard that fails if one phase’s end date is not before the next phase’s start date.
