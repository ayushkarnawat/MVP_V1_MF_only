What “no migration” means here

Read first

The analytics sections are precomputed and stored as JSON, one row per user, scope and section. Changing what a section shows means changing that JSON and recomputing it.

In the diagrams: NEW a column or table this change adds · READ an existing column the change reads · PK/FK keys. Unlisted columns exist but are not touched.

Rollout consequence: ship the backend payload change first, let a recompute run, then ship the frontend that reads the new fields. The frontend should fall back to the old layout when a new field is missing.

Why a hybrid beats either alone. Option B alone hides switches in one line. Option C alone mixes real cash with internal moves, so both totals look bigger than the money that actually moved. Q2: what the data holds, and a different way to show it

No, we do not know how much of a fund each manager runs. The manager data comes from the AMCs' monthly factsheets, which list the team on a fund without saying who runs what share. So there is no per-manager percentage to pull, now or by pulling more of what we pull today.
What we store for each manager on each fund
  • Manager name.
  • Role, exactly as the factsheet prints it (or none).
  • Order listed, used only to keep the list steady, never shown as seniority.
  • Managing since (a date, where the factsheet gives it).
  • The reporting month, and how the fund was matched.
What we do not have
  • The share of the fund each manager runs.
  • Who the lead is, in any firm sense.
  • Where it could come from: an AMC disclosure or licensed vendor data. That is the open data-access question already on the priority list, not something a screen can fix.

So what is the table for? It shows who is in charge of the money in your funds, and roughly how your portfolio is spread across managers. What it cannot say is how much any one manager personally controls: shared funds are divided equally, which is an assumption, so a footnote stays under the table.

Q2 answered: one table, four columns, no overlap shown

As directed: fund manager, AMC, current value, and the share of the overall portfolio, and nothing else. No exposure column, no by-fund view, no overlap note, no expandable fund list.

The one assumption to know. For the numbers not to overlap, each fund's value has to be divided among the people who run it, and the data has no shares. The only way to do that without inventing a lead is to divide equally, so a fund run by two managers gives each half. The table carries one short footnote saying so ("Funds with more than one manager are divided equally between them"). If you would rather credit each manager with the full value of every fund they help run, the percentages add to more than 100%, and the footnote would have to say that instead.

Q3 and Q4 answered: do we have the values for all three periods?

Mostly yes. Almost nothing new has to be fetched. The only genuinely new work is three extra category averages, which are simple sums over numbers already in memory.

What the table needsDo we have it?Where it comes from
The fund's own 1Y, 3Y and 5Y returnYes, already computedThe category ranking already works out all three for every fund (_compute_category_returns_detailed). It then passes on only the blended figure. The three are thrown away at the end.

The difference rowYesFund minus category, worked out on screen.

How each number is calculated

  • Fund return, 1Y: price today ÷ price one year ago − 1. A plain one-year change.
  • Fund return, 3Y and 5Y: the same ratio, converted to a yearly rate (annualised), so a 5Y figure and a 1Y figure can be read side by side.
  • Category average, per period: the sum of (each peer's return × its latest AUM) ÷ the sum of those AUMs, over the peers that have that period. This is the same weighting the blended average uses today.
  • Peer group: the same category and plan type as today, so a Regular fund is compared with Regular funds.
  • Different pools: the 5Y average covers fewer funds than the 1Y one, because only funds with five years of history count. The screen says how many funds each average covers.
  • A fund too young for a period shows "—" for that period, never zero. Its category average for that period still shows.

How the numbers are worked out

Rules and limits to know

  • Who counts as a peer. Only funds that are ranked at all, which today means 3 or more years of history. A fund under 3 years old is not ranked, so it would not get a 1Y rank either. Including such funds would change the existing composite, which is a separate decision.

  • Minimum of 3 peers, the same rule as today (_MIN_RANKED_PEERS = 3). Below it a horizon shows a dash, not "#1 of 1".
  • Peers stay in the same category and plan type, so a Regular fund is ranked against Regular funds, as now.
  • Today's row is not updated. The ranking is stored with an insert that is skipped if the row for the day exists, so a fund already stored today keeps NULL until tomorrow. The live result has the values at once.

Q6 and Q7 answered: a forward-looking projection, with a totals row

Yes, this is for the future. The columns are headed "Next 1 year", "Next 3 years" and "Next 5 years", and mean: what these funds would cost you over that time if your holding stayed at today's value and each fund's TER stayed as it is today. It is not what you have already paid.

  • How it is worked out: today's value × the fund's TER gives one year's cost. The three-year and five-year figures are that number times three and five.
  • What it leaves out on purpose: growth or falls in your value, future SIPs and withdrawals, and any change in a fund's TER. In real life a growing portfolio pays more, so the projection is on the low side for a rising market. A one-line footnote says so.
