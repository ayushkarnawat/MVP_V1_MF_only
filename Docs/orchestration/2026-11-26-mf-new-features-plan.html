Things you should know before reading the items

  • "Shared with family" journal notes assume each member logs in. In Unifolio one person (the Head of Family) signs in for the family, so that setting has no meaning yet (Q7).
  • Contact Directory: most of it can fill itself in. The AMFI lookup we already call returns each distributor's address, phone and email (checked live). Escalation routes come from a small directory you collect once (list in item C). The user types only a person's own name and number where no register has them.
  • Freshness without a new card. Home already has a members chip under the greeting ("Data from 3 of 3 family members") with a popover per member. Freshness goes there, plus the slim amber bar only when someone is outdated.
  • Synopsis and Overview overlap a lot. Overview already shows the value, gain and XIRR strip, an AMC allocation card, a family members card and quick insights. The Synopsis adds allocation, top 3 stocks, the folio count and data age. Merged, the page gets shorter, not longer (item 01).
  • What-If, re-checked to the rupee. The PDF compares keep vs switch after tax at the end of the horizon, and that gives the 11.15% break-even. Comparing before tax would say 11.32%, and my earlier mockup did that (it showed 12.33% for different inputs). The mockups now use the PDF's method and numbers (item 03).
  • MF Central is consent-by-QR and user-driven. Each pull needs OTP, a QR download and a QR upload, so there is no background refresh. Per-folio mobile, lien and "redemption allowed" flags come only in the Summary response, but the decided import is Detailed only. Section 4 has the new points M8–M11.
  • SOA can't be fetched like factsheets. Factsheets and disclosures are public files, so a job can download them. An SOA is one investor's private statement. It goes only to the investor's registered email, to a linked distributor, or through a consent channel (MF Central, Account Aggregator). So every route needs the investor's action or consent, or a regulated relationship. The most automatic route we can build alone is a private forwarding inbox per account (item 05).
  • NSE: the earlier investigation is right, but it missed one thing. Changing the address alone still leaves the job broken. See item N1.

NSE address change (filings book value)

Phase 1 (bundled)
Earlier finding
The 15 Nov run stopped at step 1 with HTTP 301; 0 stocks processed. NSE now sends www.nseindia.com to www.nseindia.in. The code has a fixed address, does not follow redirects and only accepts hosts ending in nseindia.com.
Re-checked today
  • Confirmed. The handshake page and the filings API both return 301 → https://www.nseindia.in/…. The client uses follow_redirects=False and treats every non-200 as FilingSourceError("status_301"), so the run stops (filings_book_value.py:38, 381, 400).
  • New and important. On .in, the handshake and the list call both return 200. But every XBRL link in the answer now points to https://nsearchives.nseindia.in/corporate/xbrl/… (36 of 36 links for TCS). _safe_xbrl_url accepts only nseindia.com and its subdomains (line 147), so parse_filing_rows would silently drop every row. A fix that changes only the address would turn "the job fails loudly" into "the job runs and finds no filings for any stock". That is worse, because nothing alerts.
  • The .in XBRL file downloads (200, 107 KB). The same path on .com also still answers 200.
  • Other NSE calls are fine today: nsearchives.nseindia.com (EQUITY_L, bhavcopy, security file, PE file), archives.nseindia.com and niftyindices.com all return 200 with no redirect. stock_fundamentals_client already follows redirects. The symbol-fill job uses nsearchives…com and works.
  • The "10 held stocks have no NSE symbol" line is separate, as the earlier note said.
Fix
  1. Move the base address into config (nse_filings_base_url, default https://www.nseindia.in), so a future move is a setting change, not a code change.
  2. Host allow-list for XBRL links: nseindia.com, nseindia.in and their subdomains, https only. Keep the existing no-username, no-password rule.
  3. Keep "no redirects" (safer), but make a 3xx a clear alert reason: moved_to:<host>, so the next move is diagnosed in seconds.
  4. New alert when the list call succeeds but 0 rows survive parsing for every symbol in a run (no_readable_filings), so a silent drop cannot happen again.
  5. Tests first: a 301 gives the moved_to reason; an .in XBRL link is accepted; a foreign host is still rejected; a run where every row is dropped raises the new alert. Then re-run the job on staging and confirm it processes stocks.
DB / FE
No migration, no front-end change.
Timing
Decided 27 Nov: bundled with Phase 1 (Q2), and with Q1 the whole release deploys together once every item is done. So the job keeps failing every Sunday 04:30 IST (next: 29 Nov) until that release goes live, and book values stay at the last good run. Nothing else breaks, and the failure email keeps firing each week as a reminder. The fix is the first task in the build order, so it is ready on day one; if the wait gets long, it can still go out on its own with a one-line change of mind.
N2

Email alerts when an outside source moves or changes

Phase 1 (with N1)
What you asked
An email when NSE changes again, and the same for every other outside address the code uses, including redirects, so we hear about it before data goes wrong.
What we have today
  • Failure emails exist. Every scheduled job runs through deploy/leapswitch/scripts/run-job.sh; a non-zero exit pipes the output to backend/scripts/send_job_failure_alert.py, which mails OPS_ALERT_EMAIL through the SES provider. That is why the NSE failure emails every Sunday. Disk, memory and backup checks use the same sender, and the NAV runs have a daily digest (nav-digest.sh, subject OK or ATTENTION).
  • Gap 1: moves that don't fail. Seven clients follow redirects silently (amfi_factsheet_client, amfi_market_cap_client, nse_symbol_fill, portfolio_disclosure_client, scheme_universe, stock_fundamentals_client, and the factsheet's second call). If a source moves the way NSE did, they keep working on the new host until something else changes there, and nobody knows. Only the filings job refuses redirects, which is why it failed loudly.
  • Gap 2: warnings that don't email. Several jobs log *_ALERT lines but still exit 0 (for example FILINGS_BOOK_VALUE_ALERT many_stocks_skipped). Those reach the log only.
  • Gap 3: weekly jobs find out late. A Sunday job learns of a move only on Sunday; a monthly or half-yearly job (fund managers, market cap, AAUM) can be weeks late.
  • Gap 4: pages we send users to. The CAMS request page (CAMS_MAILBACK_BASE_URL) today, and the KFintech and CAMS SOA pages from item 05, are never checked. If CAMS moves its form, users hit a dead page first.
  • In all, the backend calls 84 outside hosts: NSE (4 hosts), AMFI (2), mfapi, niftyindices, Yahoo, Screener, GDELT, web.archive.org, and about 60 fund-house sites for factsheets and disclosures.
Proposal: three layers
  1. Every client reports a move. One small shared hook on all 14 outside-call clients: when a reply redirects to a different host, or a followed redirect ends on a different host, it logs SOURCE_MOVED source=<name> from=<host> to=<host>. Nothing else changes: clients that follow redirects keep following, and the filings job keeps refusing them (N1).
  2. Warning lines email too. run-job.sh also sends one ATTENTION email when a successful run's output contains _ALERT or SOURCE_MOVED, listing those lines. Same sender, same OPS_ALERT_EMAIL list. Tested in deploy/leapswitch/tests/test-deploy.sh the same way the disk alert is.
  3. A daily source check. A new job, source-check-daily at 05:15 IST (before the data jobs), reads one registry file listing every outside address the code uses: name, address, expected host, expected kind of answer (HTML, JSON, PDF, ZIP), which job or screen uses it, and whether users are sent there. It asks each one without following redirects and checks: answer 200, same host, same kind of answer, and for JSON APIs that the key fields are still there. Core sources and the user-facing registrar pages are checked daily; the ~60 fund-house sites weekly on Sundays (Q56). Any difference sends one email.

No repeat spam. A change is emailed once when first seen; while it lasts, it appears in a Monday reminder; when it goes back to normal (or the registry is updated), one "resolved" email. That needs to remember what was last seen, so: a small source_checks table (source name, last answer, last host, first seen, last emailed). No existing table fits (the job tables hold runs, not addresses), and a file on the VM would be lost on a rebuild. The option without a table is to email every day while a source is different (Q55).

What it won't catch: a site that keeps its address but changes the inside of its files. The existing parse checks and N1's new "no readable filings" alert cover that. Blocks and captchas already alert as blocked.

What an SOA is
  • A per-folio statement from the fund house (AMC), produced by its registrar (CAMS or KFintech). It lists the folio's transactions and closing units, and it is the investor's proof of holding.
  • It goes to the investor's registered email after each transaction and on request. Where a distributor is linked to the folio, the registrar also sends it to the distributor.
  • Related documents arrive the same ways: the CAS (consolidated, CAMS + KFintech, which we already import), the depositories' e-CAS (NSDL/CDSL, for demat units) and registrar capital-gains statements.
  • The PDFs are password-protected. On request, the investor chooses the password on the registrar's form. Statements sent automatically usually use the PAN in capitals.
The key constraint

Factsheets and portfolio disclosures are public files on AMC sites, so our jobs can download them. An SOA is private to one investor and is never at a public address. It reaches only (1) the investor's email, (2) a distributor or adviser linked to the folio, or (3) a consent channel (MF Central, Account Aggregator). A factsheet-style scraping job cannot fetch it. Every route needs the investor to act or consent once, or Unifolio to hold a regulated relationship.

  1. Receive: MX for in.unifolio… points to Amazon SES receiving in Mumbai. A receipt rule stores the raw email in an encrypted S3 bucket (KMS) and notifies a queue (SNS → SQS).
  2. Accept or reject: the worker reads the message: the token in the address must belong to a live account with the inbox on; SPF and DKIM must pass; the original sender domain must be on the allow-list (CAMS, KFintech, MF Central, NSDL, CDSL, the fund houses). Forwarded mail keeps the original "From" and DKIM signature in most cases; where Gmail's forwarding rewrites it, we check the forwarded headers and the PDF's issuer text.   4. Scan and open: each PDF attachment gets a malware scan (ClamAV) and a size and page limit. Then we unlock it: no password, or the password the user chose to remember for that member and sender (Q45), or we ask (needs_password, prompt in the app and an optional email).

  6. Match: the PAN printed in the PDF is hashed and compared with the member's pan_lookup_hash (already stored), and the folio numbers with our folios. No match means "We couldn't tell whose this is" and the user picks.
  7. File: a statements row with member, folio(s), kind, issuer, period and the file hash (the same file twice is ignored). Any open R1 request for those folios closes.
  8. Act: SOA, e-CAS and gains statements are filed. A detailed CAS is offered for import through the existing importer, with preview and confirm (Q44), which also refreshes the data for item 04.
  9. Clean up: the raw email is deleted from S3 once processed. The PDF is kept or not per Q12. Nothing from the email body is stored.

How it works, exactly
  1. Scope: one member, because tax, the ₹1.25 lakh exemption and the slab belong to one PAN. The family view shows a "pick a member" step first.
  2. Sell: one or more funds of that member, each by ₹, units or %. Units are taken FIFO per folio. If a fund sits in several folios, the user picks the folio or we take the oldest lots first and say so.
  3. Per lot: cost for tax (grandfathered where it applies: higher of actual cost and the lower of the 31 Jan 2018 value and the sale value); term from the holding period and the fund's tax class on the sale date; exit load if the lot is inside the load period, which reduces the sale value.
  4. Set-off within the sale: short-term losses against short-term then long-term gains; long-term losses only against long-term gains. Carried-forward losses from earlier years are out of scope (that is the user's ITR).
  5. Tax: long-term gain minus the unused exemption (₹1.25 lakh minus what 07 shows as used this year, editable) at the long-term rate; short-term at the short-term rate; slab rate for specified and debt funds; surcharge (capped at 15% on these gains) by income band; 4% cess.
  6. Costs: STT 0.001% on equity-oriented sales; stamp duty 0.005% on the new purchase. Reinvestable = sale value − exit load − STT − tax − stamp duty.
  7. Replace: 1–3 funds the user searches by name, with a split that adds to 100%.
  8. Grow and compare: keep side = sale value at the keep CAGR; switch side = reinvestable at the switch CAGR; over H years (1–30, default 10). At year H both sides are taxed as if sold, with the exemption once each; a switch fund held under 12 months at H is short-term. Result: values, tax, after-tax values, difference, and the difference as a yearly rate.
  9. Break-even: bisection on the switch CAGR until the after-tax values are equal (to 0.01%).
  10. Sensitivity: 5 × 5 grid, keep CAGR ±2 pp by rows and switch CAGR ±2 pp by columns, centred on the user's inputs. Projection: the after-tax difference if sold in each year 1…H.

Everything in Decimal; rupees rounded half-up only for display; rates and limits come from the 07 rule table by date, never hard-coded.
