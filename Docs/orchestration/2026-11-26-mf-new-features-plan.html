Things you should know before reading the items

  • Four of the eight features already exist in part. Portfolio insights covers half of 01. The CAMS request flow is the start of 05. FIFO lots in the holdings engine are the base for 03 and 07. The six months of stored fund-house holdings make 08 a diff with no new data pipeline.
  • The PDF's worked examples are correct. I recomputed them. Feature 03: ₹27,420 tax, ₹9,71,221 left to reinvest, the 10-year table and the 11.15% break-even. Feature 07: ₹20,940. One caveat: the rule table cites Income-tax Act 2025 sections 196/198, which I could not verify. That stays with the CA review the PDF already asks for.
  • Feature 06 cannot be built in full from a CAS PDF. The PDF prints one email and mobile per statement, not per folio. It prints KYC only as OK or NOT OK, and nominees only in the detailed CAS. Per-folio email and nominee status come from the MF Central API (dtSummary.email, kycStatus, nomineeStatus). So 06 splits into "now" and "with MF Central".
  • Feature 05 runs into a decided rule. Today we keep the uploaded CAS for 30 days, encrypted, and then delete it (ADR-004 reopened, 18 Sep 2026). A permanent statement vault would reverse that, so it needs your decision (Q12).
  • The PDF assumes an admin panel for tax rates and reminder timings. We have none. I propose a small settings table with effective dates, edited by an ops script for now (Q4).
  • "Shared with family" journal notes assume each member logs in. In Unifolio one person (the Head of Family) signs in for the family, so that setting has no meaning yet (Q7).
  • Contact Directory: most of it can fill itself in. The AMFI lookup we already call returns each distributor's address, phone and email (checked live). SEBI's register pages for advisers (RIA), brokers, PMS and AIFs list email, phone, address and contact person, and load as normal pages (checked live: 1,095 advisers, register as on 20 Nov 2026). Escalation routes come from a small directory you collect once (list in item C). The user types only a person's own name and number where no register has them.
  • Freshness without a new card. Home already has a members chip under the greeting ("Data from 3 of 3 family members") with a popover per member. Freshness goes there, plus the slim amber bar only when someone is outdated.
  • Synopsis and Overview overlap a lot. Overview already shows the value, gain and XIRR strip, an AMC allocation card, a family members card and quick insights. The Synopsis adds allocation, top 3 stocks, the folio count and data age. Merged, the page gets shorter, not longer (item 01).
  • What-If, re-checked to the rupee. The PDF compares keep vs switch after tax at the end of the horizon, and that gives the 11.15% break-even. Comparing before tax would say 11.32%, and my earlier mockup did that (it showed 12.33% for different inputs). The mockups now use the PDF's method and numbers (item 03).
  • MF Central is consent-by-QR and user-driven. Each pull needs OTP, a QR download and a QR upload, so there is no background refresh. Per-folio mobile, lien and "redemption allowed" flags come only in the Summary response, but the decided import is Detailed only. Section 4 has the new points M8–M11.
  • NSE: the earlier investigation is right, but it missed one thing. Changing the address alone still leaves the job broken. See item N1.

N1

NSE address change (filings book value)

Hotfix
Earlier finding
The 15 Nov run stopped at step 1 with HTTP 301; 0 stocks processed. NSE now sends www.nseindia.com to www.nseindia.in. The code has a fixed address, does not follow redirects and only accepts hosts ending in nseindia.com.
Re-checked today
  • Confirmed. The handshake page and the filings API both return 301 → https://www.nseindia.in/…. The client uses follow_redirects=False and treats every non-200 as FilingSourceError("status_301"), so the run stops (filings_book_value.py:38, 381, 400).
  • New and important. On .in, the handshake and the list call both return 200. But every XBRL link in the answer now points to https://nsearchives.nseindia.in/corporate/xbrl/… (36 of 36 links for TCS). _safe_xbrl_url accepts only nseindia.com and its subdomains (line 147), so parse_filing_rows would silently drop every row. A fix that changes only the address would turn "the job fails loudly" into "the job runs and finds no filings for any stock". That is worse, because nothing alerts.
  • The .in XBRL file downloads (200, 107 KB). The same path on .com also still answers 200.
  • Other NSE calls are fine today: nsearchives.nseindia.com (EQUITY_L, bhavcopy, security file, PE file), archives.nseindia.com and niftyindices.com all return 200 with no redirect. stock_fundamentals_client already follows redirects. The symbol-fill job uses nsearchives…com and works.
  • The "10 held stocks have no NSE symbol" line is separate, as the earlier note said.
Fix
  1. Move the base address into config (nse_filings_base_url, default https://www.nseindia.in), so a future move is a setting change, not a code change.
  2. Host allow-list for XBRL links: nseindia.com, nseindia.in and their subdomains, https only. Keep the existing no-username, no-password rule.
  3. Keep "no redirects" (safer), but make a 3xx a clear alert reason: moved_to:<host>, so the next move is diagnosed in seconds.
  4. New alert when the list call succeeds but 0 rows survive parsing for every symbol in a run (no_readable_filings), so a silent drop cannot happen again.
  5. Tests first: a 301 gives the moved_to reason; an .in XBRL link is accepted; a foreign host is still rejected; a run where every row is dropped raises the new alert. Then re-run the job on staging and confirm it processes stocks.
DB / FE
No migration, no front-end change.
Timing
The job runs Sundays 04:30 IST. Without a fix it fails again on 29 Nov. I recommend a standalone patch ahead of this whole phase (Q2).

Investment Journal

Phase 1
Today
Nothing. The only related data is users.primary_goals (six life-goal codes from onboarding: wealth creation, retirement, children's education, buy a home, …). These are labels, not goal records with targets.
Database

I checked reuse first: no existing table holds user-written content, so a new one is needed. Smallest shape:

  • journal_notes: id, user_id, type (one of the 8 built-in codes, or custom), custom_type_id (nullable), title, body_json (the editor document), body_text (plain text for search), note_date, tags (JSON array), pinned, review_on, snapshots (JSON: values captured when written), created_at, updated_at, deleted_at.
  • journal_note_types (custom types): id, user_id, name, colour, template (optional starting headings), archived_at. Reuse first: a free-text label on each note needs no table, but then a type can't exist before its first note, renaming or merging means rewriting every note, and colour and template have nowhere to live (Q29).
  • journal_note_links: note_id, kind (scheme | member | goal), target_id, plus an index on (kind, target_id), so "notes for this fund" on the fund page is one query.
  • Version history (the PDF's "edits keep the earlier version"): a third small table journal_note_versions, or none in v1 (Q8).
  • Goals: link to the life-goal code (no goals table exists). Goal records with targets belong to Planning later.
  • All notes are user data: they go in the account deletion cascade and in the data export.
Backend
New services/journal/ and api/journal.py: list (filters: type, tag, fund, member, date range; text search with ILIKE on Postgres; full-text search later if needed), create, update, delete (soft), pin. Fund-page read: GET /funds/{id}/notes. PDF export of a filtered set through the export pipeline.
Placement
Decided 26 Nov: Journal is a main item in the left panel (option B), beside Home, Portfolio and Planning, and covers every asset class. "+ Add data" stays as it is, and options A, C, D, E and F are dropped. A note can still be started from a fund page ("Add note", pre-linked to the fund) and from a What-If result.
A proper notes app
  • Three panes: views (All, Pinned, Review due), types with counts, your custom types and tags on the left; a searchable note list in the middle (Ctrl K); the editor on the right.
  • Editor: headings, bold, italic, underline, bulleted and numbered lists, checklists, quotes, links and simple tables. Markdown shortcuts (#, -, [ ]), a "/" insert menu, and @-links to a fund, member or contact that become the note's links. Saves automatically, with a "Saved" status.
  • Properties on every note: type, date, linked to, tags, review on, pinned.
  • Templates per type: Fund note (why I hold · what would change my mind), Advisor / CA (discussed · decided · action items), Goal (target · date · plan), Life event, Market view, Lesson. Each is a starting point the user can delete.
  • Custom types: "Custom…" at the end of the type menu asks for a name, a colour and optional starting headings. Custom types filter, count and colour like built-in ones, and can be renamed, merged or archived; notes of an archived type move to Free note.
  • Financial touches: a fund snapshot block captures NAV, your value and units on the day the note is written, and shows how the fund has moved since. "Review on" dates bring a note back with facts only (the fund's move and its category average since then). What-If results save as notes. A fund's notes appear on its page. Export to PDF.
  • Safety: the body is stored as editor JSON, never raw HTML, and rendered through the editor's schema, so pasted scripts can't run.

C

Contact Directory (your advisors, distributors and other contacts)

Phase 1
What it is
A simple address book of the people who look after the family's money: MF distributor (ARN holder), financial advisor / RIA, stockbroker or sub-broker, insurance agent, CA / tax consultant, bank relationship manager, PMS / AIF manager. Each contact has a name, firm, phone, email, WhatsApp, office address, registration ID (ARN, SEBI RIA no. INA… or broker no. INZ…), an escalation or grievance email, and notes. This is not Help & Support, which stays for contacting Unifolio. Useful for B2C now; in B2B the advisor's own card could be pre-filled for each client later.
Today
  • No user-owned contacts anywhere.
  • Every folio already stores the distributor's ARN from the CAS (folios.arn_code). The distributor comparison resolves it to a name and status through AMFI and caches that in arn_directory (name, status only).
  • Checked live today: the same AMFI call (arn_lookup._fetch_arn_record) also returns the ARN holder's office address, city, PIN, phone numbers and email, plus ARN validity and EUIN. We currently throw these away.
What can be automated

The aim is that the user never looks up an address, email or escalation route. Three sources do the work, and a person's own phone number is typed only where no register has it.

What-If Rebalancing & Tax Impact

Phase 3
What the PDF asks for

One question: "If I sell these funds and move the money to others, what is my extra expected return after tax and costs?" PDF pages 5–6 and 12 set out:

  • Five steps: select funds to sell (₹, units or %) → choose replacement funds and the split → see tax, exit load and amount left to reinvest → enter expected CAGR for both sides and the horizon → compare and save to Journal.
  • Seven calculation rules: FIFO lots per folio; term per lot; grandfathering (equity bought before 1 Feb 2018); exit load on units still in the load period; STCG/LTCG with the unused ₹1.25 lakh exemption, surcharge and 4% cess; STT 0.001% on equity redemption and stamp duty 0.005% on the new purchase; then grow both sides and tax both at the end of the horizon.
  • A worked example and a result screen (₹10 lakh from one equity fund), a sensitivity grid, a projection, and an assumptions panel: CAGR blank until typed, horizon 10 years by default, tax slab from the profile, exemption already used from 07 (editable), and fact-only nudges such as "Exit load ends in 202 days".
  • Rules for us: the user picks the funds and the returns; no suggesting or ranking; no "switch now" (could count as investment advice needing SEBI RIA registration); a fixed disclaimer; legal review of the wording; CA review of the tax rules. Dependencies: the 07 tax lot engine (which must pass the 03 example as a CA-approved test), 31 Jan 2018 NAVs, an exit-load master and the rule table. Phase 3.

How it works, exactly
  1. Scope: one member, because tax, the ₹1.25 lakh exemption and the slab belong to one PAN. The family view shows a "pick a member" step first.
  2. Sell: one or more funds of that member, each by ₹, units or %. Units are taken FIFO per folio. If a fund sits in several folios, the user picks the folio or we take the oldest lots first and say so.
  3. Per lot: cost for tax (grandfathered where it applies: higher of actual cost and the lower of the 31 Jan 2018 value and the sale value); term from the holding period and the fund's tax class on the sale date; exit load if the lot is inside the load period, which reduces the sale value.
  4. Set-off within the sale: short-term losses against short-term then long-term gains; long-term losses only against long-term gains. Carried-forward losses from earlier years are out of scope (that is the user's ITR).
  5. Tax: long-term gain minus the unused exemption (₹1.25 lakh minus what 07 shows as used this year, editable) at the long-term rate; short-term at the short-term rate; slab rate for specified and debt funds; surcharge (capped at 15% on these gains) by income band; 4% cess.
  6. Costs: STT 0.001% on equity-oriented sales; stamp duty 0.005% on the new purchase. Reinvestable = sale value − exit load − STT − tax − stamp duty.
  7. Replace: 1–3 funds the user searches by name, with a split that adds to 100%.
  8. Grow and compare: keep side = sale value at the keep CAGR; switch side = reinvestable at the switch CAGR; over H years (1–30, default 10). At year H both sides are taxed as if sold, with the exemption once each; a switch fund held under 12 months at H is short-term. Result: values, tax, after-tax values, difference, and the difference as a yearly rate.
  9. Break-even: bisection on the switch CAGR until the after-tax values are equal (to 0.01%).
  10. Sensitivity: 5 × 5 grid, keep CAGR ±2 pp by rows and switch CAGR ±2 pp by columns, centred on the user's inputs. Projection: the after-tax difference if sold in each year 1…H.

Everything in Decimal; rupees rounded half-up only for display; rates and limits come from the 07 rule table by date, never hard-coded.
