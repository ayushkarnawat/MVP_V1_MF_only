5. Privacy and consent

Facts from the repository are verified. Statements about the law are from my own knowledge, were not checked against the official text in this session, and need your lawyer's confirmation.

  • PAN (verified): stored encrypted per household member (ADR-004, reopened 18 Sep 2026); the API returns only a masked form. The mockup shows full PANs for every member.
  • CAS file (verified): the uploaded PDF is kept 30 days for dispute and re-parse support.
  • Consent records (verified): append-only, with document version and a hash. "Withdraw consent" is not built and is waiting on your lawyer (DEFERRED_FEATURES, Q11).
  • Data minimisation (verified in decisions.md): the original data decision aimed to store as little personal data as possible. Adding date of birth, address, income, net worth, occupation moves against that, which is why B1 to B5 are questions.
  • The DPDP Act, 2023 (my knowledge, unverified): asks for clear notice and consent for stated purposes, a way to withdraw consent that is as easy as giving it, rights to see, correct and erase one's data, and a named grievance contact. The Data & Privacy section is where these land. Today only erasure (account deletion) and consent history exist.
  • Notifications (verified): the only message we send is the sign-in code by email (Amazon SES) and the phone OTP. A notifications setting needs a sender first, so "Coming soon" (L7) costs nothing.
  • Third parties: none needed for the plan as it stands. A billing provider would be the first one (not planned, L4).

Risks

  • R1. Four of nine sections are "Coming soon" and one is a placeholder. The page will look thinner than the mockup. That is honest, and each fills in when its feature exists.
  • R2. The family list reuses existing cards whose look is the old one. Matching the mockup's table exactly needs a new table component that calls the same dialogs; that is more code than a wrapper.
  • R3. Every optional personal field we add is more personal data to protect, export and delete. Each one needs a consumer to be worth it.
  • R4. Data & Privacy will look incomplete next to the law's expectations (no export, no consent withdrawal, no grievance contact) until the lawyer answers.
  • R5. Bringing Profile sections forward changes the contract (X1), which the shell session is also working from.
  • R7. (Resolved by L49: the PAN is always masked, so there is no reveal endpoint.)
  • R8. (Resolved by L31: no financial fields are stored.)
  • R9. Import History inside Settings is an unusual home for a real list next to three placeholders; a user hunting for it under "Data & Privacy" may not find it. A link from Data & Privacy is cheap if testing shows this.
  • R6. The staging-only Import health route (/profile/import-health) must keep working while Profile moves to section routes.

To verify in the spec phase

  • Whether the account holder's own name can be edited today and through which call (PUT /household-members/{id}/profile or PATCH /auth/me).
  • Whether any "Add member" action exists on Profile, and what the onboarding add-member call needs.
  • Whether a session list or a server-side logout exists (matters only when Security is built).
  • That "MF Central" is not integrated (we parse uploaded CAS files; I found no MF Central link).
  • The exact masked-PAN format and where it is built.
  • The consent history wording per document type, and how many consent rows a normal user has.
  • Exact retention wording for "what we store" (PAN, CAS file, import data) against the ADRs.

Glossary

  • CAS: the consolidated account statement from CAMS or KFintech, which Unifolio imports.
  • Household member: a person whose portfolio the account tracks. Not a separate login.
  • Masked PAN: the PAN with the middle characters hidden.
  • Wrapper route: a tiny file that mounts a screen at a URL without changing the screen.
  • Coming soon page: a section that opens and says what is planned, with no working controls.
