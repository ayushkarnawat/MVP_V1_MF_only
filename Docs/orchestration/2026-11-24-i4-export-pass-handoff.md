## How it plugs into today's auth (decided)
Every data route uses `get_data_user` -> `get_active_user` -> `get_current_user` -> `get_current_session` (`backend/app/services/auth/session.py`, Bearer header). Only `app/api/auth.py` (sign-out and similar) calls `get_current_session` directly, and `tests/services/auth/test_session.py` tests it directly. Plan:
1. **Leave `get_current_session` and its behaviour exactly as they are** (it stays session-only: a pass must never work on `/auth/*`). Factor its body into a helper `_session_for_token(db, token) -> SessionModel` that both use; `get_current_session` keeps its signature and error messages.
2. **Change `get_current_user`** to take `request: Request`, `authorization: str | None = Header(default=None)`, `x_export_proof: str | None = Header(default=None)` and `db`: it extracts the Bearer token; **if the token has the pass prefix `exp1.`** it calls `user_from_pass(...)` (below); otherwise it does what it does today (`_session_for_token` then load the user, same errors). `get_active_user` and `get_data_user` stay untouched, so a pass user also gets the pending-deletion check and the head-change consent check for free. Existing tests that override `get_current_user` keep working.
3. **New module `backend/app/services/export/pass_token.py`** (the package `backend/app/services/export/` exists from I-3; if it does not yet, create its `__init__.py`):
   - `EXPORT_PASS_TTL_SECONDS = 180`; `PASS_PREFIX = "exp1."`; `MAX_PASS_LENGTH = 1024`; `AUD = "export-render"`.
   - `ExportScope = str` holding `"family"` or a member id (UUID string); `@dataclass(frozen=True) class ExportPass: user_id: uuid.UUID; scope: str; job: str; jti: str; expires_at: datetime`.
   - `@dataclass(frozen=True) class IssuedPass: token: str; proof: str; expires_at: datetime`.
   - `issue_export_pass(user_id, scope, job_id, now) -> IssuedPass`: token is `exp1.<base64url(JSON claims, no padding)>.<base64url(HMAC-SHA256(secret, "exp1." + payload_b64))>` with claims `sub, scope, job, jti (secrets.token_urlsafe(16)), aud, iat, exp` only; proof is `hex(HMAC-SHA256(secret, "proof:" + jti + ":" + job))`. **Refuses to issue (raises `ExportPassError`) when the secret is empty** (any environment: a pass signed with an empty key is forgeable; in development set a dev secret in `.env.example`).
   - `verify_export_pass(token, now) -> ExportPass`: reject on length over the cap, missing prefix, wrong segment count, bad base64, bad JSON, signature mismatch (`hmac.compare_digest`), `aud` not `"export-render"`, any missing or extra claim, `exp <= now` (**zero leeway**), `iat` in the future by more than 5 s; always raises `ExportPassError` with a **generic message** (the reason code goes in `.reason`, not in the text returned to callers).
   - `check_proof(p: ExportPass, proof: str | None) -> None` (constant-time compare against the recomputed proof; raises `ExportPassError("proof")`).
   - `user_from_pass(request, token, proof, db, now=None) -> User`: (a) method must be `GET` or `HEAD`; (b) the route must be on the allow-list (below) **by the matched route's path template** (`request.scope["route"].path`, not the raw URL); (c) `verify_export_pass`, then `check_proof`; (d) load the user, **401 if missing**, and refuse if `pending_deletion` is true (leave this to `get_active_user`; do not duplicate); (e) **scope checks:** a `member` pass is valid only if that member currently belongs to the user (`HouseholdMember` row for `user_id`), else 403; the route's scope parameter (below) must equal the pass's member id, and **a request with no scope parameter or with the aggregate value is 403 for a member pass**; a `family` pass allows the aggregate and any member of the user (the route's own `require_member` stays in force). Every refusal is `HTTPException(403)` (or 401 for an invalid/expired pass) with the **same generic detail** (`"Not allowed."`), never saying which check failed; the reason code is logged with the `jti` only (never the token or proof).
4. **New module `backend/app/services/export/pass_routes.py`:** `PASS_READ_ROUTES: dict[str, PassRoute]` keyed by the route's **path template**, `PassRoute(scope_in: Literal["query", "path", "none"], scope_name: str | None)`. It starts with **only the routes needed by the tests** (a fake GET route in the test app) plus a placeholder comment; **I-5/I-6 add the real entries** as the print route is built (one entry per GET route the Mutual Funds screens call). Add the test `test_every_allow_listed_route_exists_and_is_get_only` that imports the real app, looks each template up in `app.routes`, and asserts it exists and its methods are a subset of `{"GET", "HEAD"}` (with the starting list this passes trivially; it guards the future entries). A route with `scope_in == "none"` returns family-wide data: **a member pass is refused on it**.
5. **Setting and start-up guard:** `export_pass_secret: str = ""` in `backend/app/config.py` (env `EXPORT_PASS_SECRET`); in the `lifespan` of `backend/app/main.py` (**the shutdown edit from I-3 is already there; only add to the start-up part**) refuse to start in production when it is empty, shorter than 32 characters, or equal to `auth_guard_secret`: a `RuntimeError` like the existing guard. `.env.example`: a commented line `# EXPORT_PASS_SECRET=` with the note "at least 32 random characters; different from every other secret".
6. **Logging:** a helper `_log_refusal(reason: str, jti: str | None)` writes one line `export pass refused: reason=<code> jti=<jti or "-">` at WARNING; **no token, proof, user id, member id or path parameters** ever appear in a log line or an error body (a test checks it with `caplog`).

## AMENDMENT 24 Nov 2026 (after Codex's BLOCKED report; this section wins over the text above where they differ)
Codex stopped on four real conflicts and a route inventory that excludes almost everything. Decisions (the orchestrator, from the brief's intent):
1. **`get_current_user` keeps its direct-call shape.** Do not replace its signature. Add a helper dependency `get_optional_session(authorization=Header(default=None), db=Depends(get_db)) -> SessionModel | None` that returns `None` when the bearer token has the pass prefix `exp1.` and otherwise does what `get_current_session` does today (same errors). Then `get_current_user(request: Request = None, session: SessionModel | None = Depends(get_optional_session), authorization: str | None = Header(default=None), x_export_proof: str | None = Header(default=None), db: DbSession = Depends(get_db)) -> User`: **when `session` is not None it behaves exactly as today** (so the existing direct call `get_current_user(session=session, db=db)` in `tests/services/auth/test_session.py:113` keeps working, and so do the tests that override `get_current_user`); when `session` is None it takes the pass path (`user_from_pass`). `get_current_session` itself stays untouched.
2. **`/auth/me` uses `get_current_user`**, so a pass presented there is simply an off-list request: **refused 403** (not 401; the "401 on auth routes" in the first test list was wrong). Change the tests: `test_pass_refused_on_auth_me` (403, no data) and, for the routes that use `get_current_session` directly (`app/api/auth.py` lines about 665 and 832: find which endpoints they are; there is no sign-out endpoint by that name), `test_pass_gets_401_on_session_only_routes`.
3. **Generic refusals for pass requests.** On the pass path, `user_from_pass` performs the **pending-deletion check and the head-change consent check itself** (call `consent_outdated_reason` from `app/services/auth/head_change_consent.py` as `get_data_user` does) and refuses with the **same generic 403 `"Not allowed."`**. Ordinary-session responses (`Account is pending deletion...`, `reconsent_required`) stay byte-identical. `get_active_user` and `get_data_user` stay untouched (they pass trivially afterwards).
4. **The GET write rule is narrowed to what it was meant to protect.** A route may go on the allow-list if every write it can cause is one of: (a) an **idempotent cache of public reference data** (NAV rows in `nav_history` through `on_conflict_do_nothing`, or the shared in-process holdings cache) or (b) none. **A route that writes user-owned rows, replaces stored results, or dispatches a background job must not be on the list as it is**; it can go on only after I-5 makes it pass-safe (below). So: `holdings`, `allocation`, `portfolio-*`, `home/*`, `distributor-comparison`, `nav-history` are **allowed under (a)** (document each with its reason in `pass_routes.py`; `distributor-comparison` is allowed only if the print needs it: it does not, leave it out); `snapshots` (can rebuild, replace and commit) and `/analytics/{scope}` (a cold GET claims and dispatches recomputation) are **"pass-safe in I-5"**: under a pass they must never rebuild or dispatch, they return what is stored (or the section's not-ready state). `/analytics/funds/{scheme_id}/score` and `/analytics/export/payload/{token}` stay excluded. `coverage-gaps` is read-only and the Overview does not need it in print: leave it out.
5. **What you build now for point 4:** `PassRoute` gains a field `pass_safe: bool` (True = nothing to do, False = I-5 must add the guard before the entry may be added) and **`request.state.export_pass = True`** is set by `user_from_pass` so a route can ask "am I serving a pass?" (a tiny helper `is_export_pass(request) -> bool` in `pass_token.py`). Add `test_request_state_flag_set_only_for_pass_requests`. **Do not edit any route module** (I-5 does that).
6. **The route inventory you delivered is good and is accepted as the input to I-5.** Do not redo it. The inventory's "FLAG/EXCLUDE under literal cache-fill rule" rows are resolved by point 4 (allowed under (a)).
