## Notes
- **T5.1.** Head is `HouseholdMember.is_head` plus a partial unique index `(user_id) WHERE is_head`. The backfill sets it only on the `relationship = 'self'` row of each account; an account with no Self row has no head and the Change button stays hidden later. `head_change_requests` also needs a partial unique index for one open request per user (open = a status value you define and list in the report). SQLite and Postgres both support partial indexes: the tests run on both.
- **T5.2.** Signature rule is in the common rules (keyword-only `purpose` and `commit`, parameter `otp` not renamed). TTL is a parameter: 10 minutes for head change, 5 for sign-in. `otp_email_html` gets a headline and note parameters whose defaults reproduce today's HTML exactly (golden test). The two notice builders (`head_changed_email`, `head_change_undo_email`) take the wording from the briefing's email table; names in the examples (Aditi, Siddharth) are placeholders. The OTP model gets `purpose: str | None` (null means sign-in, so old rows keep working).
- **T5.3.** Reasons list is the plan's. `contact_check_also_looks_at_identity_email_column` is the Google gap: an email counts as taken if it appears in `users.email`, in an identity's subject **or in an identity's `email` column**. Label tables: take every cell from the briefing's two label tables; never guess a hard label (result "other" with no label becomes not set); free-text "other" labels are kept only if symmetric, else cleared and listed in `needs_input`. Write the table as data, and test every cell.

Decision to flag (the plan does not say how the current head's start code is requested).** The plan has `start_head_change(db, user, to_member_id, current_head_code)` and the test `start_requires_a_fresh_confirmation_from_the_current_head`, but its route list has no step that sends that first code.
