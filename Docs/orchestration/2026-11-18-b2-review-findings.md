# B-2 address guard: independent adversarial review, findings and what was done (18 Nov 2026)

Reviewer: an independent Sonnet agent given the code, the spec and the attack list (workbook 7b part F), not the orchestrator's conclusions. Verdict: **FAIL** (nine findings; none was a data leak, a lost pending record or a changed existing answer). It ran its probes on SQLite only; Postgres behaviour is reasoned, not run. Committed as `f2ebe085` on `batch/b-journey` after the fixes below.

| # | Severity | Finding | Disposition |
|---|---|---|---|
| 1 | Medium | Spellings of one phone number (`+91`, `0091`, `91`, `0`, spaces, dashes) count as one identifier in the guard but as eight different numbers in the 60-second rule, so both stop nothing: eight spellings got eight codes. Today phone sending is a stub, so no SMS goes out. | **Fixed** (owner decision 18 Nov: fix completely now; red tests first): `normalize_phone` in `schemas.py` turns every browser-accepted spelling into `+91XXXXXXXXXX` on the OTP request, OTP verify and phone contact-change bodies, and the guard uses the same function, so identity, resend rule and guard see one number. Anything that is not an Indian mobile is left as sent. Commit `b4a7a54e`. |
| 2 | Medium | The count-then-insert is not atomic: with a barrier forcing every thread to read before any inserts, 12 of 12 distinct identifiers were admitted at limit 4. Real overshoot is bounded by in-flight concurrency (about 3 workers times the thread pool), far above the intended "one extra". | **Fixed** (owner decision 18 Nov; red tests first, on real Postgres 16 in a throwaway container): a Postgres advisory lock per address (`pg_advisory_xact_lock(1096041028, hashtext(ip_hash))`) covers the count and the write in `begin`, and the code quota's check through to the stored outcome in `before_code`, released by the route's own commit or rollback. Different addresses never wait. A holder stuck past 5 seconds makes the guard fail open. Before: 12 of 12 passed a limit of 4 and 12 codes passed a limit of 3; after: exactly 4 and exactly 3. Commit `a3885221`. SQLite (development and tests) is single-writer and takes no lock. |
| 3 | Medium | IPv4-mapped IPv6 addresses (`::ffff:a.b.c.d`) were cut to /64 and became `::` for every IPv4 client: one bucket for everyone (latent behind the stated proxies). | **Fixed** (red test first): mapped addresses are unwrapped to IPv4 before hashing; zone ids are ignored. |
| 4 | Medium | Every admitted request wrote a row, including repeats of an identifier already tried, so one address could grow the table without bound until the 03:15 purge and slow the count. | **Fixed** (red tests first): one row per address and identifier; a repeat refreshes the row's time and keeps its last outcome until the route records the new one (so the code quota still sees the identifier as used). |
| 5 | Low | A sign-up stopped by the code limit still created a pending verification (with its consent snapshot) before the check. Pre-existing, identical with the guard off. | **Fixed** (red test first): `signup_email` checks the code quota before creating the pending verification. |
| 6 | Low | A malformed last `X-Forwarded-For` entry makes `get_client_ip` return `None` and the guard skips (fails open). Not reachable behind the AWS load balancer (appends) or Caddy (replaces). | **Accepted, recorded.** The spec says no address means skip and log; the log is at info level. The production gate repeats the proxy-header check. |
| 7 | Low | Only the first of two `X-Forwarded-For` header lines was read. | **Fixed** (red test first): the last line is read; one-line behaviour unchanged. |
| 8 | Low | Plus-addressing and a trailing dot count as different identifiers. | **Accepted**: within the spec as decided (workbook 7b part C: "plus-addressing counts as different, which is acceptable"). |
| 9 | Low | `AUTH_GUARD_SECRET` was in no env template or infra file; staging with it unset runs unguarded (one error log). | **Fixed in the template** (`deploy/leapswitch/.env.example`); the M1 deploy guide must set it on the staging VM and on AWS and check the log has no "Auth request guard skipped" line; production already refuses to start without it. |

| 1 | High | The code quota is not atomic: the routes commit the OTP (or the pending verification) before `record_outcome`, which released the address lock before the charge was visible. | **Fixed.** `before_code` now reserves the slot (`code_at`) and commits it inside the lock; the next request always counts it. New Postgres test commits between the check and the outcome like a route does: exactly 3 of 12 at a limit of 3. |
| 2 | High | The recipient limit counts the whole string, but the SES sender splits on commas, so `a@x,b@y` is one recipient to the guard and two inboxes to SES. Pre-existing, but it defeats the guard. | **Fixed.** Every email request body (OTP request, sign-up email, OTP verify, contact change) now requires exactly one mailbox (`single_mailbox`): a comma, semicolon, space, angle bracket, quote, second `@` gives `422`. The comma split in the SES sender stays: the ops alert list needs it. |
| 3 | Med | A slow email send held the address lock and a pooled connection, so same-address waiters (and, through the small pool, unrelated sign-ins) could stall or fail open. | **Fixed with 1.** The lock is released at the reservation commit, before the provider is called. Test: a request that is "sending" does not delay another from the same address (under 1 second). A 32-bit lock-key collision between two addresses only shares a very short lock; their quota rows stay separate. |
| 4 | Med | One row per pair with one refreshed timestamp: a check-only repeat could shorten or revive a code charge. | **Fixed.** Two clocks: `created_at` (the check limit) and `code_at` (the code limit, NULL = no charge). A check-only repeat neither erases nor revives a code charge. A failed send records `send_failed`, which clears the charge. |
| 5 | Med | A code issued before the deploy under a non-canonical phone spelling cannot be verified after it (the verify body is now canonical). | **Accepted, recorded.** The browser has always sent `+91XXXXXXXXXX`; only a direct API caller using another spelling inside the 10-minute code lifetime around the deploy would see a 401 and can ask for a new code. The M1 guide tells testers not to sign in during the deploy. |
| 6 | Low | The cleanup could delete the row a request was about to refresh. | **Fixed.** The refresh is one `UPDATE ... RETURNING`; no row back means a fresh row is inserted; the table now enforces one row per address and recipient (unique constraint). Migration 0054, never deployed, was edited in place. |
| 7 | Low | Retry advice could exceed the window (603 s for a 600 s window) from a row stamped slightly ahead. | **Fixed.** Clamped to the window. |
| 8 | Low | The Python and browser phone normalisers disagree on a few whitespace characters. | **Fixed.** The backend uses the exact whitespace set of JavaScript's `\s`. Fullwidth digits, an embedded `+` and an over-long number stay un-normalised here and are rejected by the browser; the backend leaves them as sent (as before). |
