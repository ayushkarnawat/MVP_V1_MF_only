## Notes
- This is the riskiest code in the release. Follow the briefing's ten steps in that order. No step commits; one commit at the end; email after it.
- The snapshot stored for undo holds the deleted identities (including Google), the old contact, every member's old label and the swap's own label changes, the session count and the undo token hash. Do not store the raw undo token or any code.
- Re-validation inside the lock covers: request open and not expired, all four codes verified, old head still head, new head still a member of this account, account not pending deletion, no import preview or PAN claim open, contact still free (both the existing check and the identity `email` column check from T5.3), PAN checks still true.
- Undo restores identities, contact and only the labels the swap changed; later member edits are kept. `undo_contact_taken` (409) and `undo_expired` (410) use the briefing's messages. Changing back is limited to once per 7 days. Undo ends all sessions and records a consent withdrawal.
- `/auth/me` gains `head_member_id` and the pending request state, additively: old clients and existing tests are unaffected. The existing `/auth/me` tests are in `tests/api/test_auth_routes.py`; `tests/api/test_auth_me.py` does not exist yet, create it for the new cases.
- Account deletion removes the new table's rows (`account_deletion.py`); add its test.
- Postgres functional tests for the swap are mandatory and need `FOR UPDATE` to be real: include the concurrent-second-swap test there.
- Report: the exact `HeadChangeResult` shape, the undo route and token delivery (email link shape), and the regression-suite run over the nine Self-reading files.

## Gaps found while planning (2 Nov 2026), decide and report in T5.5

The swap must re-check that the new head's member contact still equals the destination that was verified, and refuse (`request_expired` style, nothing changed) if it changed.

## T5.5 design decided by the orchestrator (2 Nov 2026; T5.4 and T5.4b are committed: `8e3e6d27`, `ce79e52e`)
**Signature.** `complete_head_change(db, user, request_id, evidence) -> HeadChangeResult` in `app/services/auth/head_change.py` (the plan's signature has no `user` or `evidence`: the caller must own the request, and the consent rows need the request evidence the sign-in routes already build; list this). Route `POST /auth/head-change/complete` body `{request_id}`, active-user dependency, `{code, message}` errors; response `{status: "completed", logout_required: true}` (the caller's own session is deleted by the swap, so the front end must log out and show the sign-in page). `HeadChangeResult` carries ids and status only: never the raw undo token, never a code.
**Order inside ONE transaction, no helper commits (every helper takes `commit=False`):**
1. Lock `users` (the account), then its `household_members` ordered by id, then the request: all `FOR UPDATE` (`with_for_update()`; a no-op on SQLite).
2. Re-validate inside the lock, nothing changes on any failure: the request belongs to the caller, status `pending`, not past `expires_at` (an expired one is marked `expired` in a separate commit and refused with `request_expired`); all four `*_verified_at` set; `from_member_id` is still the head and `to_member_id` is still a non-head member of this account; the account is not pending deletion; no open import or live PAN claim; the full `member_eligibility` for the new head returns nothing except `head_change_already_open` (the request itself is the open one; this re-runs the contact, PAN and label checks including the identity `email` column); the account's current email and phone still equal `snapshot["destinations"]["current"]` and the new head's member email and phone still equal `destinations["new"]` (else refuse with a new code `request_changed`, 409, message "Something changed since you started. Nothing has changed. Start again."); `flip_labels` gives a usable old-head label (not `None`). Every refusal returns the briefing's code and message where one exists.
3. Snapshot (JSON-safe, added next to `destinations`): every deleted `auth_identities` row (provider, subject, email, verified and created times, including Google and any password identity with its hash), the account's old email and phone, every member's old `is_head`, `relationship`, `relationship_other_label`, and the label changes the swap makes, the session count, the undo token HASH and its 24-hour expiry. Never the raw token, a code or an OTP hash.
4. Delete all of the account's `auth_identities` rows; flush.
5. Set `users.phone_number` and `users.email` to the new head's verified values; flush (the unique rules fire here if a race slipped past the check).
6. Insert the two new identities (phone: subject = the phone; email: subject = the email, `email` column filled) through the identity helpers with `commit=False`; flush.
7. Members: first the OLD head's row (clear `is_head`, new relationship and free text from the plan, receives the old account email and phone on its own contact fields); flush; THEN the new head's row (`is_head` true, relationship self, no free text); then every other member's label from `flip_labels` (`member_labels`, `member_other_labels`; members in `needs_input` become "not set"). This order is what keeps the one-Self and one-head unique indexes from firing.
8. Delete every `sessions` row of the account (the caller's included) and every `pending_identity_verifications` row with `matched_user_id` equal to the account.
9. Delete the four used code rows (purpose `head_change`, the four destinations; use the existing helper).
10. Insert consent WITHDRAWN rows for the sign-up documents (terms and privacy, `SIGNUP_DOCUMENTS`) with `record_consent(..., action=WITHDRAWN, surface="head_change", evidence=...)` (it never commits), so the new head must accept the terms at first sign-in.
11. Set the request `status` to `completed`, store the undo token hash and expiry, store the snapshot; commit. `IntegrityError` at the commit: roll back everything and answer `contact_in_use` (409, the briefing's message), never a 500.
12. After the commit only: send the notices. `head_changed_email` WITHOUT `undo_url` to the new head's email and to the old head's addresses; `head_change_undo_email` (WITH the link) ONLY to the old head's addresses (the old account email and any other email the deleted identities carried). The link is `settings.frontend_base_url` plus a path for the undo page (use `/undo-head-change?token=<raw token>`; Task 5.6 and Run 6 build the page and route). A send failure never undoes the swap: log it without addresses, record which roles failed (not the addresses) in the snapshot's `notices`, and return normally. A retry job is out of scope: report it.
**Postgres functional tests are mandatory** (`tests/functional_postgres/test_head_change_swap.py`, `TEST_DATABASE_URL=postgresql+psycopg2://unifolio:unifolio@localhost:5433/unifolio_test`): the full swap on real Postgres, the forced mid-way failure rollback, and `concurrent_second_swap_for_the_same_account_is_blocked` with two real sessions (the second must wait on the lock, then refuse because the request is already `completed`).
**Extra tests beyond the plan's ten:** a swap with only three of four codes verified refuses; an expired request refuses and changes nothing; a changed contact refuses; the undo link appears ONLY in the previous head's emails (never the new head's); the snapshot and logs contain no raw token and no code; account deletion removes the account's `head_change_requests` rows (edit `account_deletion.py`, list it as outside the Files list); the 15 `relationship == SELF` readers' tests still pass after a swap (run the nine files listed in the common rules).

## T5.6 design decided by the orchestrator (2 Nov 2026; for the next worker: Antigravity with Claude Sonnet 5.5 high, see memory `project-worker-fallback-order`)
Read first: `cr-r5-common-rules.md` (all 13 hard rules), this file, the review notes in the other handoff, the plan's "Task 5.6", and the T5.5 code in `app/services/auth/head_change.py` (`complete_head_change` is the mirror image of what undo does). Files: modify `head_change.py` (`undo_head_change`, the 7-day rule in `start_head_change`, a read-only pending peek), `app/api/auth.py` (`POST /auth/head-change/undo`, `GET /auth/head-change/eligibility`, `/auth/me` fields), `app/services/auth/schemas.py`; tests `tests/services/auth/test_head_change_undo.py`, `tests/api/test_auth_me.py` (new), a Postgres test `tests/functional_postgres/test_head_change_undo.py`. Do not edit the 15 `relationship == SELF` readers.
1. **Undo is called by someone who cannot sign in** (the old head's identities are gone), so `POST /auth/head-change/undo` body `{token}` has NO session dependency. Look the request up by `sha256(token)` against `undo_token_hash` (never store or log the raw token), status `completed`, one use: after a successful undo the status becomes `undone` and the token no longer works. Unknown, used or wrong tokens answer one identical `404 undo_not_found` ("This undo link is not valid."). After `undo_expires_at`: `410 undo_expired`, message "The 24-hour undo window has closed.".
2. **`undo_head_change(db, token, evidence) -> HeadChangeResult`**, one transaction, no helper commits, the same lock order as the swap (account, members by id, request, all `FOR UPDATE`), and a failure at any step rolls everything back. Refuse (`request_changed` style, nothing changed) if this request is not the account's latest completed head change.
3. **Contact check before any change:** the old email and phone (`snapshot["account_contact"]`) and every restored identity's subject and email must not belong to another account (users, identities including the identity `email` column, normalised as in `head_eligibility.py`). If taken: `409 undo_contact_taken`, message "The old phone or email has been taken since the change, so it cannot be undone.".
4. **Restore:** delete the account's current identities; re-insert the snapshot identities with their original times; set `users.email` and `users.phone_number` back; restore ONLY what the swap itself changed, per member from `snapshot["member_changes"]`: a field is restored only if the member's current value still equals the swap's "new" value for it (later edits are kept: test `later_member_edits_are_kept`). Order for the one-Self and one-head indexes: clear the current head first, flush, then set the old head.
5. **Then** delete every session of the account and its pending identity links, delete the head-change OTP rows, insert consent WITHDRAWN rows for the sign-up documents (surface `head_change_undo`), set the request `undone`, commit; after the commit send a notice to both people (`head_changed_email` wording is for the swap: write a short plain `head_change_reversed_email` builder in `email_templates.py`, no links, subject "The Head of Family on Unifolio has been changed back."), failures never undo the undo (same containment as the swap, including a missing provider).
6. **The 7-day rule** (briefing: "changing back uses the same flow, at most once every 7 days"): `start_head_change` and `request_head_change_start_code` refuse with `409 head_change_too_soon`, message "The Head of Family was changed recently. You can change it again on {date}.", when the account has a request that is `completed` or `undone` whose completion time is within 7 days. The completion time is `undo_expires_at` minus 24 hours (there is no completed-at column; do not add one without asking). Undo itself is exempt.
7. **`/auth/me`** gains, additively with defaults so old clients and every existing test are unaffected: `head_member_id` (the current head's member id, or null) and `head_change_pending` (the status object of the open request, or null). `/auth/me` is a GET that runs often: it must NOT write. Add a read-only `peek_pending_head_change` that ignores an expired row instead of expiring it. Create `tests/api/test_auth_me.py` for the new fields (the existing `/auth/me` tests are in `tests/api/test_auth_routes.py` and must stay green).
8. **`GET /auth/head-change/eligibility`** (active-user dependency): for each non-head member return the id and ONLY own-data reasons (`no_email`, `no_phone`, `no_pan`, `label_missing`, `same_email_as_head`, `same_phone_as_head`, `head_change_already_open`, `import_in_progress`, `account_pending_deletion`). Never `email_in_use`, `phone_in_use` or `pan_registered_elsewhere`.
9. The sign-in guard from T5.5 stays: `create_session(..., presented_identity_id=...)`. Test that a sign-in waiting behind the undo's lock is refused when its identity was deleted by the undo (Postgres, same pattern as `test_a_login_waiting_behind_the_swap_lock_is_refused_after_the_swap_commits`).
Tests first, with the plan's names: `undo_restores_identities_contact_and_the_swaps_own_labels`, `later_member_edits_are_kept`, `undo_blocked_when_contact_taken`, `undo_blocked_after_24_hours`, `change_back_limited_to_once_per_7_days`, `auth_me_returns_head_member_id_and_pending_request`; plus: the token is single use, an unknown token and a used token answer identically, an undo of a non-latest request refuses, sessions are all deleted, `/auth/me` writes nothing, the eligibility route never returns a cross-account reason, a missing email provider does not fail the undo.
