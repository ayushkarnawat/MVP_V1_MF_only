Unifolio Search Plan

Instead of one search box for the whole app, every page gets its own search bar. Each bar does two jobs: it filters what is on that page, and it jumps to anything in the family's portfolio. This page says where the bars go, what they find, how we build them, and what we still need you to decide.

The short version

  • One shared search component, placed in each page's header. Same look and keys everywhere, different things to filter per page.
  • Searching is not limited by the family or member selector. A fund held only by Asha shows up even when you are looking at Ravi, tagged "Held by Asha".
  • 14 kinds of result are in scope: funds, fund houses, categories, fund managers, members, folios, SIPs, transactions, stocks, sectors, page sections, terms, actions and smart filters.
  • Most of it needs no new back end. Almost every list is already loaded in the browser. One small new endpoint (a light "search index", no prices) is needed so the box can see other members' funds quickly.
  • Heavy things use a hand-off: typing "reliance" on Home does not load every stock. It offers "Search stocks for reliance", which opens the Holdings page with the search filled in.
  • The implementation plan (section "The implementation plan"): before and after flows, a file-by-file change list, the back-end endpoint in detail, the front-end design, tests, how Claude, Gemini and Codex build it, 21 tasks, and 10 traps found in the code. No database change.
  • UI mockups for every page (section "UI mockups"): the shell, the box in eight states, one row of every result type with what a click does, six journeys across pages, and each of 15 pages as it is today and with search, in light and dark.
  • 22 questions, 18 answered. Your answers are applied throughout, and the questions section shows them with "Answered" and "Chosen" badges. Four are still open: Q4 (household list source), Q7 (stock cap), Q8 (smart filters) and Q19 (selector after a jump). The plan assumes my recommendation for each until you answer.

How search finds things

Three sources sit behind one box. Keeping them separate is what keeps the box fast and the back end small.

SOURCE 1This page's own listFunds in the table, ledger rows, stocks, SIP capsules. Already in the browser. Filtering is instant and needs no request. This is the "filter" job.
SOURCE 2Household indexEvery fund anyone in the family holds, with the members who hold it, plus folios, SIP status and sold funds. Small: names and ids, no prices. This is the "jump" job. New small endpoint.
SOURCE 3Fixed list of app thingsPages, sections, terms, actions, smart filters. Written once in code, no data needed.
HAND-OFFHeavy things, by deep linkTransactions and stocks are big. From another page the box offers "Search transactions for…" which opens that page with the text already filled in (?q=).

How matching works (in plain words)

  • Typing is case-insensitive. Every word you type must appear somewhere in the item, in any order. "flexi parag" finds Parag Parikh Flexi Cap.
  • Items are searched on several fields at once, not just the name. A fund matches on name, fund house, category, plan (Direct or Regular, Growth or IDCW) and who holds it.
  • Short fund-house names work ("SBI", "HDFC"). The code already has an alias list for fund-house logos (lib/amcLogos.ts) that we can probably reuse.
  • Results are ordered: starts with your text, then a word starts with it, then contains it. Within a group, funds you hold more of come first.
  • Small spelling mistakes are forgiven (you chose A and C together in Q11). "parrag" still finds Parag Parikh. Exact matches always rank first.

What happens when the user does something to the box

User does thisWhat happens
Clicks the box, or presses "/"The box gets a green focus ring and opens the dropdown with recent funds, ready-made filters and a few actions (state b). The page does not change yet.
TypesOn every keystroke the page's own list filters at once, and the dropdown updates with matching groups (state c). The first row is pre-selected. No waiting for a button.
Presses ↑ or ↓Moves the green highlight through rows. Group headings are skipped.
Presses EnterRuns the highlighted row. If it is the "On this page" row, it just keeps the filter and closes the dropdown. If it is a fund, it opens the fund. If it is a filter or category, it adds a chip.
Clicks a result rowSame as Enter on that row. What each row does is in the table below.
Clicks a recent searchPuts that text back in the box, so the page filters again at once. "Clear" next to the heading deletes the list.
Clicks "See all N"The group opens out to up to 20 rows inside the dropdown (state h).
Clicks the × in the boxClears the typed text, keeps chips, and puts the cursor back in the box.
Clicks × on a chip, or Backspace in an empty boxRemoves that filter. The page list goes back to showing everything it matched before.
Presses EscFirst press clears the text. Second press closes the dropdown. Chips stay.
Clicks outside, or TabThe dropdown closes. The typed text and chips stay, so the page stays filtered.
Changes the family or member selectorThe page reloads its data and filters again with the same text. The household list does not reload.
Moves to another pageText and chips are cleared, unless the move came from a hand-off (then the destination page shows the text it was given, see Q6).

How the box behaves

  • Keys. "/" focuses the box. Arrow keys move through results, Enter opens, Esc clears and then closes. See Q12 for Ctrl+K.
  • Accessibility. A proper combobox with a result list that screen readers announce ("3 results"). The Overlap fund picker already has a keyboard-friendly list we can copy.
  • Scope. Filtering follows the selector, because the page itself does. Jumping ignores it, and tells you when a click will change it.
  • Money. Result rows show names, tags and who holds a fund. They do not show amounts, so nothing leaks when someone shares their screen.
  • The web address. Whether the typed text goes into the address (?q=) matters because the hand-offs need it. See Q6.
  • Desktop only, as the shell is. The old mobile views keep their own search boxes untouched.
  • Tracking. If Google Analytics (deferred, Priority 2) is built later, send only "search used" and the result type, never the typed text, because it can hold fund and member names.

Back end and data

What the box needs from the server, and why the obvious existing call is the wrong one.

  • Search covers the family's own funds only, not all 14,380 schemes. That keeps it small and fast, and avoids needing a text index on the scheme master.
  • Why not reuse the family holdings call. It exists (/household/aggregate/holdings) and lists every fund with per-member rows. But it also prices every fund. The deferred-features file records the dashboard's cold open taking about 4.5 seconds for 12 funds and 19 to 23 seconds for 42 to 46 funds, because stored prices are ignored until the evening. Calling it on every page just to search would be slow.
  • The light index endpoint (proposed): one fund per row with its id, name, fund house, category, plan, whether it is sold, and the members who hold it (with masked folios and SIP status). No prices, no returns. It should answer in tens of milliseconds, and is cheap to cache until the next import.
  • The fund page already opens for any scheme. Its endpoints only check that the scheme exists, not that you hold it. For funds you do hold, nothing new is needed there. For sold funds, the page needs a check that it copes with zero units (Q5).
  • Transactions and stocks stay on their own pages. They are large, and they already load where they are needed. The hand-off sends the typed text to them.
  • The stock look-through is capped at 100 rows, with a "showing the largest N of M" note. Searching it only covers those 100 (Q7).

The implementation plan

This part says exactly what changes, in which file, in what order, and who builds it. It is based on reading the real code, not on guesses. Where something could not be verified it says so. Nothing here is built yet.

The plan in six lines

  • Database: no change. No new table, no new column, no new index, no migration. The Alembic head stays at 0053.
  • Back end: one new read-only endpoint, GET /household/search-index. It lists every fund the family holds or sold, who holds it, folio last four digits, SIP status, the main fund manager and sector names. It prices nothing.
  • Front end: one shared search component in a new folder frontend/src/components/search/, plus small changes to 15 pages and four shell files.
  • Shell changes (their own small PRs): a search slot in PageLayout, the top-bar box relabelled "Ask Mira", a "scope intent" so a jump can switch the member, and logout clearing search data.
  • Built the way the last releases were: Claude orchestrates, Gemini in Antigravity builds the front end from packets with red tests already written, Codex (or a second Claude in WSL) builds the back end, and every step has a review gate.
  • Existing screens do not change. The live look stays exactly as it is today. Only the search box and a few small search elements are added (see "The rule: existing screens do not change"). Every mockup on this page carries a note saying so.
  • 21 tasks in 7 groups, listed in the task list. The back end and the shell work can run at the same time as the pure search logic.

1. Before and after, flow by flow

Each flow shows what happens today and what happens with search. "Index" means the household list from the new endpoint.

F1. Typing in a page's search box (Overview as the example)

Before

  1. The page loads its data (/household/aggregate/holdings and others).
  2. The user types in a plain box. The text is kept in useState on the page.
  3. The funds table filters by fund name or fund house.
  4. Nothing else happens. The text is lost when the page changes.

After

  1. The page loads its data as before.
  2. PageSearch mounts and reads ?q= and ?f= from the web address.
  3. On the first click or "/" press in the session, the index store fetches the household list once and keeps it in memory.
  4. On each keystroke the matcher filters the page's list (in the browser) and builds the dropdown groups.
  5. Enter or a click runs the highlighted row. The address is updated with replace, so Back is not flooded.

F2. Jumping to a fund

Before

  1. The user finds the fund in a table and clicks its name.
  2. The fund page opens, reading its position from the selector (useFundPageScope).

After

  1. The user types part of the name and picks the row.
  2. The fund id is saved to "recent funds". A typed search that ends in a result is saved to "recent searches" (the last 5).
  3. The app opens paths.mutualFunds.fund(id). Same page as before, same selector rules.

F3. Jumping to a fund another member holds

Before

  1. Not possible from the page. The user must switch the selector to that person, find the fund, open it.

After

  1. The row says "Switches to Asha" (Q3).
  2. On click, the box remembers the current selector (viewMode and memberId).
  3. It navigates with a router state, a "scope intent": {searchIntent: {scope: member Asha}}.
  4. The scope provider applies the intent after its normal reset rule has run (see trap 1 below).
  5. A notice with Undo appears. Undo puts the remembered selector back and returns to the old page.

F4. Hand-off: stocks and transactions from another page

Before

  1. No way to search stocks or transactions. The user goes to Holdings or Transactions and scrolls.

After

  1. On Home the user types "reliance". The box offers "Search stocks for reliance".
  2. Click opens /portfolio/mutual-funds/holdings?q=reliance.
  3. Holdings' own box reads q, filters the stock table and expands the match. The same happens for Transactions.

F5. Sections, terms and actions

Before

  1. People scroll to find a card. "Add investment" and the theme toggle are buttons in the top bar. Terms are small "i" tooltips.

After

  1. Section: navigate with state {searchIntent: {section: "ter"}}. The destination page scrolls to that card and outlines it for 1.5 seconds, then forgets the intent.
  2. Term: a small definition card opens under the box. No navigation.
  3. Action: calls the handler that exists today (openImport, the theme toggle, the Mira dialog).

F6. A statement import finishes

Before

  1. Pages refetch holdings when asked. Nothing else depends on the funds list.

After

  1. Import completion calls invalidateSearchIndex().
  2. The next time the box is focused it fetches a fresh list. The exact hook point (the import provider or the import orchestration hook) is found in task T07.

F7. Selector change, logout and login, reload

How the service builds it, step by step

  1. 1Members. list_household_members(db, user.id) gives the member ids and names.
  2. 2Folios and transactions. Load the folios for those members, then their transactions in one batch (the same shape the SIP code already uses, to avoid one query per folio).
  3. 3Open or sold. Replay each folio's transactions with apply_lot_rules (it understands switches, bonus, gifts, reversals and opening-balance rows). Group by member and fund and add up the units. More than zero means open. Zero with at least one transaction means sold. A plain sum of units would be wrong, so the plain sum is not used.
  4. 4Scheme facts. One query on schemes for name, fund house, category and plan.
  5. 5SIPs. Call the existing compute_active_sips(db, member_ids, include_stopped=True, today=today). It already makes no price calls and returns status and next due date per fund and member. It reads the folios and transactions a second time. That is accepted for version 1 because households are small; the test below measures it.
  6. 6Main manager. One query on scheme_fund_managers for the held scheme ids, newest reference_period per scheme, with the same "not older than two months" rule as the Allocation page.   7. 7Sectors. The existing load_sector_weights(db, scheme_ids, as_of) (one query, no prices) gives sector names per fund. Only names are returned, not weights.
  8. 8Folio last four. Return only the last four characters, so the front end can show "••••4821" and match on them. This avoids choosing between the two masking styles the app uses today.
  9. 9Shape and return. Sort funds by name, holders by member order, and return.

4. The front end in detail

How matching works (exact rules)

  • Normalise: lower case; remove "₹" and commas; collapse spaces; treat "-" and "&" as spaces. "Parag-Parikh" and "parag parikh" match each other.
  • Words: split the query into words. Every word must be found in at least one field of the item. A word is found if it is the start of a word in the field, or if it is inside a word and is three or more letters long. This keeps "in" from matching everything.
  • Fields searched on a fund: name, fund house (and its short name, for example "sbi" through the existing getAmcInfo helper), category, plan words ("direct", "regular", "growth", "idcw"), holder names, folio last four, the main manager's name.
  • Ranking: name starts with the text, then a name word starts with it, then any field matches. Ties go to funds the family holds open, then by name.
  • Query parts: a word like "purchase", "redemption" or "switch" is a type word; four digits are a year; a month name plus a year is a month; a number is an amount. The parser removes these from the text words and passes them to the page that can use them.
  • Spelling (Q11, options A and C together): a small mistake is forgiven. A word of 4 to 7 letters may differ by one letter (a wrong, missing, extra or swapped letter); a word of 8 or more may differ by two. Only name-like fields are checked this way (fund name, fund house, category, manager, holder), never folio digits or amounts. Spelling matches rank below exact ones. It is a few lines of our own code in matcher.ts, with no new library.
  • Caps: three rows per group, "See all N" opens up to 20, at most 30 rows in the dropdown. The page itself is never capped; it filters fully.
