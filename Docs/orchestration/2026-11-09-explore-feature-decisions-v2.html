2. Feasibility verdict

Explore is feasible. The formulas exist. What is missing is search, lists, a stored per-fund results table, a fresh price feed for the whole market, and a rule for funds with missing data.

In one paragraph. A user who opens a fund they do not hold can already see its chart, returns, risk, holdings, manager, peers and insights, once we stop the header route from returning a 404 and teach the page frame to render without personal tiles. A user who wants to browse, search or filter cannot do anything today: there is no endpoint that lists funds. To list funds fast we need one table with one row per fund holding its returns, risk, cost, size, score and rank, refreshed every night, plus a daily price top-up so those numbers are not stale. Phase 1 can ship without that table (search plus the fund page). Phase 2 (categories and fund houses) needs it, and is now the heart of the feature. The two things that can stop the project are not technical: the compliance view on scores and rankings, and the unresolved overlap between this work and the page-wise search session.

Engineering notes behind the table

E1. One envelope for every list

Every list response carries as_of (price date the numbers are based on), computed_at (when the job wrote them), the category and plan it covers, and a data_flags array per row. The frontend never has to guess whether a number is fresh. A list older than 36 hours is flagged stale and the page says so.

E2. Search algorithm

  1. Shortcuts first. A text that matches INF[0-9A-Z]{9} is looked up in the two indexed ISIN columns. A number matches the AMFI code.
  2. Normalise once, at write time. The metrics job stores a search_key per fund: lower case, "&" to "and", punctuation and brackets removed, spaces collapsed, noise words (fund, scheme, plan, option) removed, synonyms mapped (dir to direct, reg to regular, idcw to dividend, cumulative to growth), fund-house brand added. The repository has about nine different name-cleaning functions in different files and none does prefix or trigram matching, so this is a new, single normaliser, not a ninth variation.
  3. Match tokens. Every typed token must prefix-match a token of the key. Rank: exact name, then prefix, then token match, then trigram similarity. A boost for live funds and for the Direct Growth representative.
  4. Group by fund. The AMFI file has 2,179 live fund families averaging 4 variants (Direct and Regular, Growth and IDCW), up to 36. The result is one row per family with the variant of the user's chosen plan.
  5. Postgres versus SQLite. On Postgres, a trigram index (pg_trgm) gives typo tolerance. It would be the first extension in the repo (Postgres 16 ships it). On SQLite, which dev and most tests use, fall back to LIKE per token over the stored key. At about 9,000 live rows a full scan is a few milliseconds either way, so the trigram index is a quality feature, not a speed need.

E3. Sorting and pagination

The frontend has no pagination or virtual list. Category pools are at most 290 rows and the screener returns at most a few thousand, so use plain page numbers with a page size of 25 to 50, sorted on the server by an allow-list of columns (not free text), with a stable tiebreak on scheme_id. Infinite scroll is not needed.

E4. Caching

List responses are not user-specific except for the held flag. Cache the metrics read per (category, plan, sort, page, as_of) for a short time, and add the held flag after the cache. The frontend's cachedFetch already caches GETs by full URL for 60 seconds, so a repeated search costs nothing. No new cache layer is needed in phase 1.

E5. Sign-in and scope

The fund-page routes need only an active session and head-of-family consent. The shell resets the scope to Family Combined whenever the user moves to a different sidebar row, so Explore lists always see the whole household. The held flag should therefore mean "held by anyone in the household", and a fund held only by one member says "Held by Asha" when the user picks a member scope. The frontend already has a "held_by_other_members" shape for this.

E6. The held flag, and why it is the trickiest read

The only way the code answers "which funds does this household hold" today is compute_holdings. A household-wide call took 20 to 22 seconds cold on staging (23 Oct measurement). That is unusable for a search box. Options, in the order I would try them:

  1. A cheap SQL set. One query returning the distinct scheme ids with a positive net unit balance across the household's folios. Needs the transaction and lot tables checked in the spec phase; I have not verified that a correct net-units query is cheap. This is the preferred design.
  2. A stored section. Read the held scheme ids out of an already stored per-user section (allocation or look-through), written by the existing recompute. Fast and free, but it lags a fresh import until the recompute finishes.
  3. Per-request filter. For a list of 25 funds, ask compute_holdings with the scheme filter that the fund page already added. Cheap for one fund (tens of ms), not for 25.
Verify before building. I have not run any of these. The spec phase should measure option 1 on the staging copy before the badge is promised.

E7. "Overlap with my portfolio": a new formula

The PDF's overlap is defined between two funds: the sum over shared stocks of the smaller of the two weights. A portfolio has no single weight per stock, but the app already computes one: the look-through exposure, which is the sum over the user's funds of (fund weight in the portfolio times the stock's weight in the fund). The natural extension is:

overlap(candidate, portfolio) = Σ over stocks s of  min( w_candidate(s) , exposure_portfolio(s) )
  w_candidate(s)       = stock weight in the candidate fund, % of its net assets
  exposure_portfolio(s) = look-through exposure of the household, % of its equity value
  matched by ISIN, as the existing pair overlap is

This is a new formula, not in the PDF, so it needs your sign-off (Q12). Two honest caveats to print beside it: the portfolio exposure is expressed against the portfolio's equity value while the candidate's weights are against its own net assets (which may include cash and debt), and the holdings files are monthly and a month old at best. Reading the stored look-through section avoids a recompute; its date is shown as the basis.

E8. Similar funds

On demand it would run up to 290 pair overlaps per click, each over about 40 rows: fast enough in memory but loading 290 holdings lists is a heavy read. Precompute instead: for each fund store the top five most similar funds in its category (one column of ids in the metrics row, written by the nightly job from the same holdings it already reads). Phase 3, and only if Q10 puts it on the list.

E9. What-if calculator

J1. The price top-up

Why it exists

The 06:00 price job refreshes only held funds and their category peers (checked in the code; about 1,500 funds, or 1,476 of 14,441 had the latest day's price on staging on 3 Nov). Explore needs a fresh price for the whole market. AMFI's daily file already has every scheme's latest price and date.

What it does, step by step

  1. Download NAVAll.txt (about 1.5 MB, one request, 30 s timeout, one retry).
  2. Parse it with the existing parser. It already reads both the 6-column and the new 8-column layout. It already extracts price and date per row and currently throws the price away.
  3. Keep live rows: price present and date within 30 days (this is the rule the peer code uses; 39% of rows are dead funds with 2018 to 2022 dates).
  4. Map each AMFI code to a scheme id (one query).
  5. Insert (scheme_id, date, nav) in chunks of about 5,000 with ON CONFLICT DO NOTHING. The existing upsert helper does exactly this. Chunking is needed because SQLite allows only 32,766 bind variables per statement.
  6. Write a success row to job_runs and log the summary line.

Guard rails

  • Abort if fewer than 5,000 rows parse (same rule the scheme-master job uses).
  • Warn if fewer than 80% of live funds carry the newest date (holiday or late publication).
  • Idempotent: a re-run inserts nothing new.
  • First write wins. If AMFI later corrects a price, we will not pick it up. Acceptable; gap repair (J3) can fix known cases.
  • New funds get one row only, so they need a one-time history download. See "interaction" below.

The log line follows the repo pattern: refresh_explore_nav: parsed=14356 live=8786 inserted=8701 newest_date=2026-11-06 success=True.

Interaction with the existing price code (the main design trap)

  • warm_nav_history treats any fund with a row in the last 3 days as fresh and skips its download. After J1, every live fund looks fresh. For peers of held funds that is good: the 06:00 job stops hammering mfapi.in. For a new fund with a single row it is bad: it never gets history.
  • The one-off backfill selects only funds with zero price rows, so a fund with one top-up row is excluded as well.
  • Fix: judge "needs history" by depth (earliest stored date and number of rows), not by "has any row". The exact rule belongs in the spec; the point is that two existing selectors must change with J1.
  • The bulk history download has no concurrency limit and no retry. On 8 Oct, a 1,500-fund run lost about a third of calls (545 of 1,513), at 148 s average. The fix (limit to about 20 at a time, retry once) was logged as deferred and becomes necessary if Explore ever downloads history in bulk.

J2. The metrics job

Why it exists

Scores, ranks and peer statistics exist only inside a category-and-plan pool, so they cannot be worked out per row. Today they are computed per request and cached in each web worker's memory for 15 minutes to 6 hours; nothing stores them for the market. A category page of 44 funds would compute the whole pool on the request, in every worker. J2 does it once, at night.

What it does, step by step

  1. Take a single-run lock (none exists in the repo today; the recompute job relies on per-household claims only). An advisory lock on Postgres, a row on SQLite.
  2. Check the input: refuse to run if the newest stored price date is older than expected, and log why.
  3. Load all schemes once and derive, per scheme: option_kind, search_key, family key, live and index flags.
  4. For each of the 128 category-and-plan pools: read the peers from the database (not by calling the code that inserts missing schemes during a read), bulk-read prices at the eight anchor dates, the 3-year daily series for risk, the 5-year monthly series for scoring; compute returns, risk, score components, percentiles and ranks.
  5. Bulk-read cost, size, managers and holdings composition for the pool's funds in single queries (replacing today's one-query-per-fund cost lookup).
  6. Upsert the pool's rows and commit per pool, so a failure late in the run leaves earlier pools valid. Free the pool's memory.
  7. After all pools, mark rows of funds that left the live set, write job_runs, log the summary.

Guard rails

  • Exits non-zero if more than about 10% of pools fail, because the VM emails only on a non-zero exit (several existing jobs log failure and still exit 0, so nothing is emailed; this job must not copy that).
  • Emits a distinct EXPLORE_METRICS_ALERT line on partial failure for the AWS log alarm.
  • Pools with fewer than 5 funds get returns and risk but no score and no rank, using the existing thin-category flag.
  • Never writes to fund_scores or any user table.

15. Compliance research

Not legal advice, and not independently verified by me. A research agent read the primary documents below on 9 Nov 2026 and reported what they say, with links. I have not re-read them. Anything marked unverified could not be confirmed from a live source. A lawyer must make the call. This section exists so that call is informed and so the design avoids the obvious traps.

The headline

  • No SEBI text found says that a generic, formula-based ranked list or score of mutual funds is "investment advice". None says it is not. The Investment Advisers Regulations have no "impersonal general advice" safe harbour in their text.
  • The market is split. Morningstar India issues fund ratings under SEBI Investment Adviser and Research registrations. Value Research and Advisorkhoj publish ratings with "not advice" disclaimers (Advisorkhoj says it is unregistered). Unifolio's position is closest to Advisorkhoj's.
  • The sharpest practical exposure is indirect, through Regulation 16A of the Intermediaries Regulations. It stops SEBI-regulated entities (including AMCs and their agents) from associating with anyone who gives advice or recommendation, or makes "claims of returns or performance", without permission. That bites on partnerships, referral money, data feeds and affiliate links rather than on the display itself.

What this means for Q4, and wording we can adopt regardless

The research cannot tell us which side of the line a ranked list falls on. It does tell us what a cautious reviewer would ask for. These are suggestions to validate, not rules:

  1. Name the score as data, not a verdict. "Fund Score" is fine. Avoid "rating", "recommended", "top pick", "best", "buy", "avoid", "must-have". No buy, sell or hold labels. The existing insight engine already bans advice wording in generated text.
  2. Publish a methodology page: inputs, peer group (SEBI category and plan type), percentile method, update frequency, exclusions, and that no human opinion enters the score.
  3. Put a disclaimer next to every score, rank and return, not only in the footer: past data, not a forecast, not personalised advice, and (if accurate) not a registered adviser.
  4. Show the standard risk statement near the data even though it is mandatory only for AMC ads.
  5. Mirror the AMC returns conventions even though they do not bind us: CAGR for 1, 3, 5, 10 years and since inception, benchmark on a total-return basis, plan type and as-of date beside every figure, no return for funds under 1 year, footnote manager changes. This fits our "eligibility" rules in section 11.
  6. Keep Direct and Regular separate in ranks and scores.
  7. No "Invest now", no affiliate or referral links, no commission arrangement. If transacting is ever added, check the execution-only framework first.
  8. Ask counterparties early. Before any tie-up with an AMC, distributor, broker, registrar or data vendor, ask their compliance team about Regulation 16A and our scores.
  9. Keep personalised wording descriptive: "18% overlap", not "you should switch" or "you are over-exposed".
  10. Treat any "best in category" or "top 10" page as the highest-risk surface; consider a neutral default sort with rank as an opt-in column.
  11. Check the Common Advertisement Code's scope before about 7 Apr 2027.
  12. Consider asking SEBI for informal guidance on rank-based scores shown by a free platform that does not transact.

Q9

May I propose one new table and nightly jobs?

unanswered

What the question is. To show lists, categories and a screener quickly, Explore needs a table with one row per fund (returns, risk, cost, size, score, rank), refreshed every night by a job, plus a daily job that keeps prices fresh for every live fund. Do we build that, when, and in what shape? Sections 8 and 9 describe the table and jobs in full; this card is the decision.

What the nightly job is, in plain words. A script that starts by itself at a set time, reads data we already hold, works out the numbers for every fund once, writes them to the table and stops. When a user then opens a category, the page reads a stored row instead of working out a whole category while they wait.

The facts behind the choice, in one place.
  • J1 price top-up: 06:17 IST daily, 10 to 60 seconds, 150 to 250 MB, about 1.5 MB downloaded, 0.9 to 1.9 MB a day of database growth (estimates).
  • J2 metrics: 06:45 IST daily, about 3 to 6 minutes (plan 5 to 10), 250 to 400 MB when processed per pool, reads about 5.3 million price rows (estimates). Never run yet.
  • AWS cost: about $0.65 a month all in (compute $0.21, alarm $0.40, storage $0.05), under 1% of $68.46. The one number that could move is the small database instance's burst credits.
  • VM cost: ₹0 more if it fits; free memory and disk are the constraints, not CPU. Escape hatch +₹908 a month.
  • Without the table: $0, but every first open of a category costs 2 to 4.5 seconds per web worker (three workers), and lists cannot exist.
