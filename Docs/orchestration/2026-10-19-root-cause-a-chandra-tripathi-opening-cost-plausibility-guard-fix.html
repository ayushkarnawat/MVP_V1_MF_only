1 · The bug, and the real file that found it

Tripathi household · chandra.pdf

price_opening_lot() (backend/app/services/import_/opening_balance.py) prices every fund's opening lot — the units a household already held before its earliest imported CAS statement. It computes a cost per unit from the CAS's own figures, then runs a plausibility guard: if that computed cost falls outside the fund's entire pre-statement NAV range, it is distrusted and replaced with the NAV on the statement's start date instead.

Found via a real CAS, Docs/CAS Files/chandra.pdf (password MF@12345), Tripathi household. 2 of 38 opening-lot schemes were misclassified — both Surendra Kumar Tripathi's folios:

Both real failures are the same shape: the opening lot was never touched by any in-period transaction — confirmed by dumping both folios' full transaction histories against the real CAS, one row each, the opening balance itself, nothing else. That's exactly the case the guard doesn't need to run on, because there's no FIFO-subtraction step to distrust when nothing was sold from the lot.

2 · Why not just delete the floor check

Docs/investigations/2026-10-05-cas-import-fix-plan-final.html (§"Decided: the hybrid cost method", lines 371–408) built the band check to catch a different, still-real failure mode: an in-period sale consuming part of the opening lot, which can corrupt the (valuation_cost − held_cost) / remaining subtraction into a nonsense number. Deleting the floor for everyone would silently reopen that hole. The fix only relaxes the check for the specific case it was never meant to cover — an opening lot nothing was ever sold from.

3 · The one thing we couldn't close, closed

No longer a documented assumption

The first pass at this fix flagged one real residual uncertainty and left it as a documented assumption rather than resolving it: whether CAMS/KFintech's printed "Total Cost Value" column is always the FIFO-remaining cost of currently-held units, or sometimes a blended average-cost figure computed for display — and neither real failure has an in-period sale to test it against. Told not to leave it there, it was investigated properly instead of caveated.

What was found

CAMS/KFintech's "Total Cost Value" is average cost per unit × closing units — not a FIFO-remaining-lot figure. This is a deliberate RTA design choice: the plain Consolidated Account Statement (the document this app imports) shows a holding-level summary figure, not a lot-by-lot ledger. FIFO governs a different, optional document the same RTAs also issue — the Capital Gains Statement / Statement of Financial Transaction, used for tax filing — computed lot-by-lot because capital-gains law requires FIFO to determine which units are deemed sold and their holding period, not how the plain CAS displays an aggregate cost for units still held.

Corroborating evidence read inside casparser (the third-party library this app already depends on to read CAS PDFs)

FileWhat it shows
types.pyCAMS/KFin's SchemeValuation has exactly one cost field. The NSDL/CDSL demat MutualFund dataclass has two separate, explicitly named fields: avg_cost and total_cost — direct proof average cost is a real, named convention in this domain, printed and labeled as its own number by at least one depository format.
analysis/gains.pyA wholly separate FIFOUnits class computes realised capital gains — architecturally isolated from the plain CAS's cost-value field. It exists only to answer the Capital Gains Statement's question, and is never consulted for a scheme's plain valuation.cost.
parsers/cams_detailed.pyCOST_VALUE_RE = re.compile(r"Total\s+Cost\s+Value\s*:?\s*([\d,.]+)", re.I) — CAMS's "Total Cost Value" is extracted straight from the PDF's own printed text by regex. It's CAMS's number, not something casparser computes from a lot ledger.
cli.py (~L270–350)casparser's own "Portfolio Cost Value" summary is sum(valuation["cost"] for held schemes) — the exact reference total test_real_check.py already reconciles this app's dashboard against, confirming that figure is the right ground truth.

The mathematical consequence

For an untouched opening lot (no in-period sale), average-cost and FIFO-subtraction are the same number — there's only one lot, so there's no ordering question to begin with. The untouched-case fix, already proven against both real failures, is completely unaffected by this finding. It only changes the touched case's layered fallback: average cost is now tried first (well-justified, not a guess), FIFO-subtraction is kept as a secondary cross-check — the reverse of this doc's original FIFO-primary ordering.

Concrete proof this reordering matters, not just a theoretical point: §7's third test builds a case where the old FIFO-primary ordering would have accepted a wrong number (8.33/unit) via its loosened tier, while the new average-cost-primary ordering returns the mathematically correct number (50.0000/unit exactly) for the identical input.

Sources: CAMS's and KFintech's own public descriptions of their CAS and Capital Gains / Statement-of-Financial-Transaction products, and general explainers of SEBI/CBDT FIFO capital-gains rules for mutual funds — confirming FIFO is the capital-gains-computation convention, and that the Capital Gains Statement is a deliberately separate product from the plain CAS because the two serve different purposes. See §9.

4 · Decision log — every open question resolved

1Untouched opening lot — skip the band check entirely. There's no FIFO-matching ambiguity to doubt: a failed band check here can only mean the NAV history doesn't reach back far enough (pre-2006) or doesn't exist yet (a brand-new NFO), never a real cost problem.
2Touched lot, average cost passes the band — use it. Now the first tier tried, not the second: CAMS/KFin's printed figure is average cost, not FIFO-remaining.
3Touched lot, average cost fails, FIFO-subtraction passes — use FIFO. Kept as a cross-check in case average cost is wrong for some other reason (a parsing defect, or an edition that doesn't follow the usual convention) — not deleted just because it's no longer primary.
4Both fail the strict band — loosened fallback, same order. Average cost against [min/3, max×3], then FIFO-subtraction against the same loosened band. Loosening only the ceiling was tried, caught live to silently defeat the floor's job, and rejected — both sides loosened.
5All four tiers fail — unchanged final fallback: NAV on statement start.
6Corrupted zero-NAV points (Axis) — filter to n > 0 before computing the floor/ceiling. A non-positive reading is a known mfapi.in defect, never a real NAV; unfiltered it sets a false floor of 0 that lets anything positive through.
7"Extend our own NAV history further back?" — doesn't apply to either real failure. HDFC Flexi Cap: the data doesn't exist anywhere (industry-wide pre-2006 gap, already fetching mfapi.in's complete history). Sundaram: 2 years old, an NFO-par-value quirk unrelated to history depth. No schema/migration change for this reason.
8"Does our FIFO engine really track which units remain?" — yes, already proven, was never the ambiguity. FIFO lot order is a CBDT/SEBI capital-gains mandate, applied uniformly by every RTA, and lot_rules.py (the one shared FIFO engine behind holdings, opening-cost and conversion-cost, already audited once before) implements it correctly across every transaction type. This answers which units remain with certainty. The real ambiguity was a different question — how the CAS prints the cost of those remaining units — and that's now resolved too (§3): average cost, not a FIFO ledger figure.
9"Will this genuinely fix the dashboard's invested amount, with certainty?" — yes, proven against the real file, not just in theory. See §8: ₹1,082,539.38 off, 2 funds over tolerance → ₹0.91, 0 funds over tolerance.
10Prevalence across other households — not run this round, not a blocker. Local dev DB predates the cost_source column; LeapSwitch staging was recently wiped for multi-user testing. The fix is narrow and self-justifying enough not to need prevalence data to be correct — only to gauge how many dashboards will visibly change, a monitoring question, not a design one.

6 · The code — before and after

File: backend/app/services/import_/opening_balance.py. Not yet applied to the repo — see §10.

Before (the bug)

cost = ((scheme.valuation_cost - held_cost) / remaining if remaining > 0 and scheme.valuation_cost is not None else None) # one check, runs unconditionally, even when nothing was sold plausible = cost is not None and cost > 0 and (not before or min(before) <= cost <= max(before)) source = CostSource.CAS_COST if plausible else CostSource.NAV_ON_START # HDFC Flexi Cap: cost=49.73, floor=130.82 -> rejected -> wrong NAV_ON_START # Sundaram NFO: cost=10.0005, floor=10.0148 -> rejected -> wrong NAV_ON_START

After (the fix)

untouched = remaining == scheme.open_units # ... ok()/plausible()/loosened() helpers, series filtered to n > 0 ... fifo_cost = (scheme.valuation_cost - held_cost) / remaining if remaining > 0 and scheme.valuation_cost is not None else None if untouched: # no FIFO-matching step to doubt -- trust the CAS figure outright cost, source = (fifo_cost, CostSource.CAS_COST) if ok(fifo_cost) else (None, CostSource.NAV_ON_START) else: # CAMS/KFin's printed cost IS average cost -- try it first, not FIFO avg_cost = scheme.valuation_cost / held_total if held_total > 0 and scheme.valuation_cost is not None else None if plausible(avg_cost): cost, source = avg_cost, CostSource.CAS_COST elif plausible(fifo_cost): cost, source = fifo_cost, CostSource.CAS_COST elif loosened(avg_cost): cost, source = avg_cost, CostSource.CAS_COST elif loosened(fifo_cost): cost, source = fifo_cost, CostSource.CAS_COST else: cost, source = None, CostSource.NAV_ON_START # HDFC Flexi Cap, Sundaram NFO: both untouched -> trusted -> correct cost now

8 · Proof: the real statement, before and after

"110% sure" requirement — met

Algebra and unit tests prove the logic is internally consistent. They don't by themselves prove the dashboard's invested amount actually matches the CAS for a real household. For that, the pre-existing, permanent acceptance-gate harness Docs/CAS Files/synthetic/harness/test_real_check.py was run end to end (upload → parse → confirm → dashboard) against the real file that found this bug, Docs/CAS Files/chandra.pdf — not a new or hand-built check, the same one already used to reconcile this app's amount_invested per scheme against casparser's own printed valuation.cost, with a tight tolerance band.

The ₹0.91 residual is pure decimal rounding across 39 holdings, well inside the harness's own documented tolerance band (₹1 + units × ₹0.00005 per fund) — not a real gap. Member 1 is untouched both times, confirming the fix changes behavior only for the two schemes it was built to fix, nothing else in this household.

A bug caught by actually running the code, not by reasoning about it: the first draft of the loosened-band fallback only widened the ceiling (value <= max(before) * 3), which silently let a genuinely corrupted low-side result (0.5/unit against a real floor of 20) through as CAS_COST — defeating the floor's actual purpose. Caught by constructing and running that exact case. Fixed by checking both sides; re-verified the real-corruption case is caught again, and the originally-intended moderate-deviation acceptance case still passes.

Working tree confirmed clean (git status --short) before and after every scratch edit used to produce these numbers — nothing from this verification pass is applied to the repo; the plan doc and this artifact carry the full diff for sign-off.
