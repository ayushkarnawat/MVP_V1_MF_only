Issue 1

Sign-up with a registered number logs you straight in

Bug · regression from the phone-first redesign

What you saw

You created an account in an incognito tab, then opened a normal tab and signed up again with the same phone number. You got the code, verified it, and landed on the upload steps with no "this number already has an account" message.

Why it "used to work"

Before 28 Sep, sign-up started with email. The phone number was entered later, at the phone step, which carries a pending_token. That path checks for an existing number before sending the code and returns a 409. The redesign moved phone to the first step, where there's no pending_token, so that check never runs.

Root cause

backend/app/api/auth.py:297 — in verify_otp_route, the "number already exists → log in" shortcut runs before the flow == "signup" branch at line 304. So a sign-up with a known number is silently treated as a login. On top of that, OtpRequestBody (services/auth/schemas.py:35) has no flow field, so request_otp (auth.py:206) can't reject the number before sending the code the way the old phone step did. PRD-05 FR-1 to FR-3 describe the new-number path only; the known-number case was left out of the spec.

Landing on upload steps is correct for a logged-in user who hasn't confirmed an import yet. The routing isn't wrong; getting logged in at all is.

Fix

  • BE
    Add flow: "signup" | "login" | None to OtpRequestBody. In request_otp, when there's no pending_token and flow == "signup", call find_or_backfill_phone_identity; if it finds one, return 409 {code: "phone_already_registered"} before any otp_requests write.
  • BE
    In verify_otp_route's no-pending_token branch, check flow == "signup" before the login shortcut, and return the same 409 if the identity exists. This covers the case where someone registers the number between request and verify. flow == "login" and flow-omitted (legacy test callers) keep today's behavior.
  • FE
    features/auth/api.ts:32 requestOtp sends flow. AuthEntryFlow.tsx already has a "Log in" shortcut for the email and phone-step 409s (around line 109). Wire the new 409 code to that same shortcut and prefill the number.
  • DB
    None.
  • Tests

Decided 30 Sep: the matching login-side check ships too

Log In with an unknown number or email is also rejected at request time, before a code is sent. Both /auth/otp/request and /auth/email-otp/request get flow = "login". With no identity found, they return 404 {code: "account_not_found"} ("No account found for that number. Sign up instead.") and write nothing. The existing verify-time 401s stay as a backstop. This closes session.md item 9. You accepted the tradeoff: anyone can check whether a number has an account without receiving a code. The existing 60-second resend throttle limits how fast that can be probed.

  • BE
    request_otp / request_email_otp: when there's no pending_token and flow == "login", look up the identity and return 404 before calling create_otp_request. Leaving flow out keeps today's behavior for the internal test callers.
  • FE
    Log In sends flow: "login" on both request calls. The 404 shows under the input with a "Sign up instead" shortcut, the same pattern as the sign-up 409.

Issue 3

Review screen: ribbon grid layout, and auto-confirming clean members

3a · layout bug3b · change request

3a · Why the grid is cramped

The fund-card grid in ReviewTable.tsx:404 picks its column count from the browser window width (sm:2 · md:3 · xl:4). That was fine when ReviewTable filled the page. Inside a ribbon it sits in a much narrower box, but on a desktop window it still gets 4 columns:

MemberRibbonReview container max-w-4xl 896px − its side padding sm:px-6 − 48 − ribbon panel padding sm:p-4 − 32 − ReviewTable's own padding lg:px-8 − 64 ← page padding, applied again inside the ribbon = grid width 752px − 3 gaps lg:gap-6 − 72 ÷ 4 columns (xl:grid-cols-4, window ≥ 1280px) = about 170px per card

At about 170px, the card's top row (ReviewTable.tsx:423, a non-wrapping flex row) can't fit the folio chip and the "Action needed" pill. The folio number wraps onto three lines ("FOLIO: / 11223344 / / 0") and the pill, which is flex-shrink-0, sticks out past the card border. That's what your screenshot shows. Scheme names clip to "ABC Bluechip…", and the AMFI placeholder clips too.

  • FE
    Add an embedded prop to ReviewTable, set by MemberRibbonReview. When it's on, drop the page-level side padding and cap the grid at grid-cols-1 sm:grid-cols-2 lg:grid-cols-3. A true container query would be cleaner, but Tailwind 3.4 here doesn't have the container-queries plugin, so a prop avoids adding a dependency.
  • FE
    Widen the review container from max-w-4xl to max-w-6xl (MemberRibbonReview.tsx:129). At 1152px that gives 3 cards of about 330px each.
  • FE
    Harden the card itself so it can't overflow at any width: top row gets flex-wrap, folio chip gets whitespace-nowrap min-w-0 truncate with the full folio in title, and the AMFI placeholder gets shortened to "6-digit AMFI code".
  • Check
    The phone ribbon view (MobileReviewView.tsx) reuses this component and is already an open QA item (session.md item 3). Check it at 400px after the change.

3b · Auto-confirm members with nothing to resolve

Today

A ribbon counts as reviewed only after you open it and press its Confirm (MemberRibbonReview.tsx:49 starts reviewed empty; line 197 enables Confirm only at 0 unresolved). "Confirm imports" stays disabled until every ribbon is reviewed. A member whose funds are all matched and classified still needs open → scroll → Confirm.

Proposed

A ribbon counts as confirmed on its own when it has 0 unresolved funds. This includes ribbons with funds "matched by name" or "assigned by you". The closed ribbon shows a green Confirmed badge, and the line under the name keeps the name-match count visible, e.g. "Confirmed · 3 funds · 1 matched by name". It can still be opened to look through the holdings, and the Confirm button inside shows as already done. Ribbons with unresolved funds work exactly as today.

Decided 30 Sep: auto-confirm "matched by name" ribbons too

A ribbon auto-confirms whenever it has 0 unresolved funds, even if some funds were placed by name. The user can still open any confirmed ribbon to check its holdings and use "Move to…". This amends the member-detection spec, which required any name-matched fund to be seen before Confirm imports (FR-4 note; map §"Why folios matched by name are marked"). After the change, the name-match count on the closed ribbon header is what makes these funds visible. The spec note and PRD-01 get updated to match. Name notices (M8, "Update the name?") don't affect this: they're answered in the people popup before the ribbons appear.

  • FE
    In MemberRibbonReview.tsx, compute autoConfirmed = count === 0 and isReviewed = reviewed.has(key) || autoConfirmed. No new state. A "Move to…" that changes a ribbon's funds re-evaluates on its own. ReviewTable stays mounted while hidden, so its confirmations still reach the Confirm-imports payload without the ribbon being opened. The closed-ribbon header gets the badge and always shows the "N matched by name" count when there is one (today it only appears after a manual Confirm).
  • BE
    None. /imports/confirm already takes everyone in one request and re-validates each fund server-side (confirm_people._validate_schemes).
  • Tests
    MemberRibbonReview.test.tsx: a member with 0 unresolved is confirmed without being opened, including one with a matched-by-name fund, whose header shows the count; a member with 1 unresolved is not; Confirm imports is enabled when everyone is clean.

Issue 6

Statement period missing from import history

Older gap, not from member detection

Root cause

  • BE

  • DB
    Migration 0019 data step (no schema change): for rows with null dates, read raw_parser_output → statement_period. Every confirmed import already stores it, because _person_raw_output keeps the top-level keys. Accept both from_ and from key spellings.
