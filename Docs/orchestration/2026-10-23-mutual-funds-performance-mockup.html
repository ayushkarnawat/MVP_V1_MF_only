Reference-vs-spec note — flagging one reading, not silently resolving it

design.md §7.1's first bullet says the detailed XIRR section is "expanded with the per-fund XIRR table (BenchmarkSection's Tab 2 already has this: fund XIRR vs its assigned benchmark)." Read literally, that could mean Block 1 should contain the same interactive per-fund benchmark comparison that Block 3 already provides. I've instead built Block 1's table as a compact, non-interactive glance table (fund, XIRR, vs-benchmark delta only, no bars) and kept the full interactive version — with the new benchmark/time-window dropdowns — as Block 3, reasoning that the sentence is justifying why the data for Block 3 isn't new backend work (it already exists in code) rather than asking for the table to be duplicated in full. This is a judgment call, not a confirmed resolution — flagging per CLAUDE.md's "stop and say so" rule rather than picking a side silently. If the intent was a literal duplicate, say so and I'll merge them back into one table.

Round 7 (2026-10-24, owner said no re-check needed): fixed real congestion in the race track when two entities' values land close together (e.g. "You" vs a near-identical benchmark) — previously both dots sat dead-center on the axis regardless of how close their values were, so close values rendered as one overlapping blob (the "You" marker's halo ring visually swallowing its neighbour). renderRace() now does a lightweight beeswarm-style de-collision: true value position on the X-axis is never altered (this is finance data — fudging it would misrepresent returns), but when two sorted neighbours land within a minimum gap, their dots are nudged apart perpendicular to the axis (alternating up/down, magnitude scaled to how close they are), and congested markers get a z-index bump so overlapping halos render with a clean edge. .bm-race-wrap's bottom padding grew 18px→34px to give the jitter room.
