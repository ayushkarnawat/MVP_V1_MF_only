The case you asked about: only one PAN in the file

If the other people are nominees or joint holders, the file has one person, Me. They hold no funds of their own, so nothing is detected and the review shows a single ribbon (decision I1).

If there really are folios in another person’s name with no PAN (very old folios, PAN-exempt investments), each distinct name becomes a name-only person, shown as Meera Sharma (PAN not on statement). They have no detected PAN, so at unlock the typed PAN is checked only for format and uniqueness, then saved as pan_source = user_entered, unverified. The next statement that shows that PAN verifies it, or raises S3 if it differs.

Why folios matched by name are marked: FR-4 forbids fuzzy attribution, so any fund placed by name carries a “matched by name” tag in its ribbon, and the user sees it before Confirm imports. They can move it to another person there.

Fallbacks when the folio header can’t be read

Tried in this order for each person. At every level the name stays editable in the people popup, the unlock popup and, later, the member’s profile.

  1. Another folio of the same PAN. A person usually has several folios; use the first one whose holder line is readable.
  2. Me’s own name. If the group is Me (self’s PAN is known), use the onboarding name.
  3. The addressee name. Only when the file has a single PAN group, so it can’t land on the wrong person.
  4. A placeholder. Person 2 · BX******8L, with a required Add a name field in the people popup. Continue stays disabled until every placeholder has a name (state U9).
  5. No PAN and no name. The fund goes to “Funds we couldn’t match” in the people popup, with a person picker per fund, defaulting to Me (state U10).
  6. Two people end up with the same name. Both keep the name; the masked PAN, or “PAN not on statement”, is always shown next to it.
  7. Log it. Every fallback beyond level 1 writes a parse warning (no PAN, no name in the log) so we can add layouts to the parser.

Q8 · Why NAV backfill and recompute run at this point

Triggered by the Confirm commit, not by S3The S3 PutObject is just part of that same Confirm. Both jobs start because new transactions now exist.
They don’t slow the user downBoth run after the “Import complete” response is sent. NAV backfill is a background task inside the backend task; the recompute is a separate short-lived Fargate task.
NAV backfill: helpful, not strictly requiredHoldings fetch today’s NAV on demand if missing, but the value-over-time chart, XIRR history and month-end snapshots need past NAVs. Without the backfill the first dashboard visit is slower and some charts are empty until the 06:00 IST NAV job.
Recompute: required for the Analytics tabAnalytics only reads precomputed analytics_sections. Without it the tab shows “computing” until the 06:30 IST daily job, or until its own on-visit claim.
One run for everyoneOne claim covers the combined scope plus every member scope, so four people in one file still start one task.
Could we defer it?Yes: the on-visit claim already exists. Recommend keeping the trigger at Confirm, because the first visit to Analytics usually comes seconds later.

HONORIFICS = {MR, MRS, MS, MISS, DR, SHRI, SMT, KUM, MASTER, LATE}
WEAK = {KUMAR, KUMARI, DEVI, BAI, BHAI, BEN, BEGUM}   # never enough alone

def normalise(name):
    name = uppercase(name); replace . , ' - with space; collapse spaces
    return [t for t in name.split() if t not in HONORIFICS]

def same_token(a, b):
    if a == b: return True
    if len(a) == 1: return b.startswith(a)          # initial A ~ AYUSH
    if len(b) == 1: return a.startswith(b)
    if min(len(a), len(b)) >= 5 and edit_distance(a, b) <= 1:
        return True                                  # AAYUSH ~ AYUSH, MOHAMMAD ~ MOHAMMED
    return False

def compare_names(a, b) -> {result, shared, reason}:
    ta, tb = normalise(a), normalise(b)
    if sorted(ta) == sorted(tb): return exact
    short, long = sorter of (ta, tb) by length
    every short token matched to a different long token by same_token?
        and at least one matched pair is a full, non-WEAK token?
        -> variant
    else -> mismatch
