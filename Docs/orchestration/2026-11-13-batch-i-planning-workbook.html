Nine findings (read in code, to be confirmed on staging where marked)

#FindingWhy it matters
F1The pipeline exists and is server-side. POST /analytics/export/pdf stores the data under a random one-time token, opens a headless Chromium (Playwright) on the front end’s print page (/print/analytics?token=), waits for a ready marker, and returns an A4 PDF with backgrounds. Chromium is installed in the backend image and started at app start-up.You do not need a new PDF engine. The decision is whether to keep this approach (Q1).
F2It is attached to the old screen. The export button and the print page belong to the legacy analytics view (features/analytics). The redesigned “Other Analytics” route uses a different page, and the old wrapper is not routed to. So the redesigned app most likely has no export today (to be confirmed in the live app).The new export is a build, not a tweak.
F3A likely fault with several workers. The one-time token and its data are kept in a plain dictionary inside one backend process. Staging runs the backend with three worker processes. The request that makes the PDF and the request the browser makes to fetch the data can land on different workers, and the second would not find the token (to be confirmed on staging). The code comment says it is fine for “a single process”.On staging the old export would fail about two times in three. Any new export must not rely on one process’s memory.
F4The data comes from the browser. The old export posts the figures the screen already loaded. The redesigned tabs load their sections lazily, one tab at a time.A full report, or a report for a member other than the one on screen, cannot be built from what a tab happens to have loaded.
F5Fonts load from Google (index.html) at render time. The headless browser needs outbound access to fetch them; if it cannot, the PDF silently uses a fallback font.The brand look would vary by environment. The print template should carry its fonts with it.
F6The print style sheet is 27 lines: A4 with margins, a page break after a cover class, and a few break rules. The old view had a simple cover.The branded cover, contents, running header and footer, and print versions of the redesigned cards are the real work.
F7Every backend worker starts its own Chromium at start-up (three on staging).Three idle browsers use memory all the time, on a server that is already tight (Batch A’s load work). The new design should start one on demand.
F8The renderer opens FRONTEND_BASE_URL. The example settings file points at ls-staging.unifolio.in, while the redesign runs at ls-redesign.unifolio.in.If the live setting still points at the old front end, the PDF would be made from the old UI. The deploy guide must check it.
F9The account’s own name is available (self_name, the self member’s name) and the logo files exist in the repo (Logo/: transparent, ring, master and white-text versions).The cover page has what it needs. A family export names the account holder “and family”; a member export names the member (section 4).
An existing precedent. An earlier decision (12 Oct) said not to add Playwright as a production dependency for the portfolio-disclosure work. That was about scraping AMC sites. The export is different: Playwright and Chromium are already in the production image for the PDF export, so using them here adds nothing new to the stack.

2. How the PDF is made

Your decision from the list (server or browser), with the facts, and the two sub-decisions that follow from it.

Server or browser (Q1)

ApproachHow it worksStrengthWeakness
A. Server-side Chromium (my pick)The server opens a headless browser on a print page, waits until every section has loaded, and prints it to PDF. This is the pipeline that exists.One result for every user and browser; exact control of cover, fonts, headers and page breaks; the same components and numbers as the screen; nothing for the user to set up; works with the family or member the user picks.Uses server memory and CPU while rendering; needs the repairs in F3, F5, F7; a render takes seconds to a minute for a large household.
B. In the browser (print to PDF)The app opens a print-styled page and the user saves it from the browser’s print dialog.No server load; no new backend.The result depends on the user’s browser and settings (margins, headers, background colours); no reliable running header or page numbers; a dialog the user must understand; hard to guarantee the cover and brand.
C. Server-side, a new engineA report library (for example a templating-to-PDF tool) builds the PDF from data, not from the screens.Lighter than a browser; strong print control.A second layout for every section, which must be kept in step with the screens; a new dependency; charts need separate drawing code.
My recommendation: A. It already exists in the image, it gives the same branded result for everyone, and it reuses the screens. Its weak points are known and fixable (below). B is fine as a fallback for a user whose export fails, but not as the main path.

How the print page gets its data (a technical choice, my default)

OptionHow it worksStrengthWeakness
P1. The browser posts the data (today’s way)The page the user is on sends the figures it has.Simple; already built.Cannot make a full report or another member’s report (F4); large uploads; depends on one process’s memory (F3).
P2. The server builds a data bundleThe server calls its own services for every section of the chosen scope and hands the bundle to the print page.One consistent snapshot; any scope or contents.A second way of assembling every reply; the print page’s components must be taught to read a bundle.
P3. A short-lived, read-only export pass (my default)When the user exports, the server issues a pass that works for one scope, for a few minutes, for reads only. The print page, run by our own headless browser, loads the real sections through the normal routes with that pass. Nothing is held in one process’s memory.Reuses every route and component unchanged; any scope and any contents; works across all workers; a new section needs only a print style.A new kind of credential, so it needs a security review (section 5); the print page makes many requests.

How the pages are drawn (my default)

  • Reuse the screens in a print mode (no sticky rows, no buttons, tables fully expanded, charts at a fixed width, animations off, light colours). Where a card looks wrong on paper, it gets its own print variant. The audit of every section (task I-7) uses Batch F’s section list.
  • The cover, contents, running header and footer are new, built as the print template (section 4).
  • Fonts are bundled with the print template, so the PDF does not depend on Google at render time.
  • One browser, started when needed, and closed after a quiet period, instead of one in every worker; at most two exports at once, the rest wait.

3. What the user does

One button, one dialog, the same everywhere it appears.

Where the button is

The “Export PDF” button sits in the tab bar’s right-hand slot on the seven Mutual Funds tabs and on the fund page, in the stack agreed with search and the section index (Batch F, section 5). It is one component. In the dialog the user chooses who and what; it does not simply print the page they are on.

Dialog

Made-up names and numbers; laptop view. The presets (Full report, This tab, Custom) fill the checklist from Batch F’s shared list of sections, so the dialog never hard-codes a section.

PartWhat it does
Who is it forFamily Combined (everyone in the household), or one member. It starts on whatever the page is showing, but the user can change it; the choice is independent of the page’s own selector.
What to includeThree presets: Full report (every section on every Mutual Funds tab), This tab (the tab or fund page the user is on), Custom (a checklist of sections grouped by tab, with counts). Which sections are offered comes from the shared list, so a tier can hide Pro ones.
OptionsCover page (on). “Data dates” (on): the page strip’s dates, printed on the cover and in each section’s footer (Batch E).
While it runsA progress state with plain words (“Preparing your report… this can take a minute for a large household”) and a Cancel button. The user can keep using the app; the dialog can be closed and reopened to the same job (see I-10).
When it is readyThe file downloads with a plain name such as Unifolio-portfolio-report-2026-11-13.pdf (no name, PAN or folio in it), and the dialog offers a second download. The file is not kept on our server.
If it failsA clear message with Try again; for a report that is too large, an offer to export fewer sections. The failure is logged without any content.

Before and after

Before

  1. There is no export in the redesigned app (most likely, F2).
  2. The old pipeline prints only the old analytics screen, from data on the page, and probably fails on staging (F3).

After

  1. One “Export PDF” button on every Mutual Funds tab and the fund page.
  2. A dialog to choose who and what, then a branded report with a cover, contents and the user’s name.
  3. The same numbers and wording as the screens (dates from Batch E, fixes from Batch A).

4. What the PDF looks like

A4 portrait, light colours whatever the screen theme, the app’s fonts and brand green. Six representative pages, drawn at A4 proportions, including three section pages (a donut card, a chart card and a table card).

Page

Made-up name, funds and numbers. The real section pages are the screens’ cards in print mode; these three show how the main card types adapt to paper: a donut with legend, a line chart with a fixed width and printed legend (no hover), and a table with every row expanded (no scrolling or sticky header). The Holdings page continues on the next page when it is long, with its header row repeated.

PartWhat it contains
CoverThe Unifolio logo and a green band; the title “Mutual Fund Portfolio Report”; “Prepared for” the user’s name (see below); the scope (“Family combined, 3 members” or the member’s name); the date it was generated; the data dates in Batch E’s words; and a one-line confidentiality note. No PAN, no folio, no contact details.
The name on the coverFamily: the account holder’s name and “and family” (from self_name, for example “Asha Rao and family”). One member: that member’s name. If the account holder’s name is missing, the cover says “Your family” or leaves the line out; it never guesses.
ContentsThe chosen sections by tab, with page numbers, from the shared section list.
Section pagesA running header (Unifolio, the report title, the scope) and footer (page “n of N”, the date generated); each section in the screens’ own look, kept together on a page where it fits; the section’s data dates in its footer.
Last pageNotes: how the numbers are calculated in brief (with the same explanations as the “i” icons, Batch E), what the dates mean, and the usual line that the figures are indicators and not a recommendation.
Always lightThe PDF ignores the screen’s dark mode.

5. Privacy and safety

A PDF is a portable copy of personal financial data, so the rules are stricter than for a screen. These are the rules the plan builds in.

ConcernWhat we do
PANNever printed, in any form. (The app never returns it; the export must not add it.)
Folio numbersYour decision (Q3, still open). Batch C chose to show them in full on screen; a PDF can travel, so the default I recommend is none in the PDF.
NamesMember names appear (the report is for them). The file name has no name, PAN or folio.
Where the PDF livesGenerated on request and sent straight to the user; not stored on our server, in line with the project’s rule against keeping documents.
The export pass (P3)Issued only to a signed-in user for scopes they own; valid for one export and a few minutes; read-only (it cannot change anything); tied to one scope; usable only by our own renderer; revoked as soon as the export ends. A separate security review before it ships (task I-4), in the same spirit as the earlier adversarial reviews.
Logs and analyticsOnly that an export happened and its size and duration, never its content. A GA4 “export started” event, if Batch G adds it, carries a label only.
AbuseAt most two exports render at once and each user has a short cooldown, so one user cannot tie up the browser; a failed export cleans up its browser page.
ConsentThe export shows the user their own data; it needs no new consent. The existing consent rules for imports are unaffected.
