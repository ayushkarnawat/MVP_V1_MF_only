01 · Before / after

Today: entry-method-first, phone is the odd one out

Email or Google both stage in a holding table and require phone as a mandatory second step. Phone alone skips that table — the root of the known silent-signup bug.

04 · New this pass

otp_requests: how it connects to users, and how it stays bounded

Not a foreign key — there's no user_id column, and none is being added. Three application-logic changes, zero new tables, zero AWS infrastructure.

How is it "connected" to users?

It isn't, structurally. Every cleanup action below matches on the phone_number/email values already sitting in the row — the exact same reason this table has never had a foreign key to users: most rows never correspond to an account at all. This differs from how pending_identity_verifications gets deleted today (by a direct token reference to one specific row) — but the effect is the same shape: a synchronous, in-application delete, triggered by a real lifecycle event, not a scheduled job.

flowchart LR
    subgraph EVERY["Every OTP-request call — phone or email, signup or login"]
        R1["Look up the existing unverified row<br/>for this identifier<br/>(same lookup the 60s resend-throttle<br/>check already runs)"] --> R2{"Found?"}
        R2 -->|"Yes, < 60s old"| R3["429 throttled, unchanged"]
        R2 -->|"Yes, >= 60s old"| R4[("UPDATE existing row<br/>new hash · expires_at reset<br/>attempt_count reset<br/>NEW: upsert, not insert")]
        R2 -->|"No row exists"| R5[("INSERT new row, as today")]
        R4 --> R6
        R5 --> R6[("NEW: opportunistic sweep<br/>DELETE FROM otp_requests<br/>WHERE verified_at IS NULL<br/>AND expires_at < now() - 30 days")]
    end

Lifecycle of one otp_requests row, updated

stateDiagram-v2
    [*] --> Waiting: no unverified row exists for this identifier — INSERT
    Waiting: WAITING<br/>verified_at = NULL, attempt_count = 0
    Waiting --> Waiting: wrong code, attempt_count + 1
    Waiting --> Waiting: NEW — resend after 60s UPDATES this SAME row<br/>(new hash, expires_at reset, attempt_count reset)<br/>no second row created
    Waiting --> Verified: right code within 5 minutes
    Verified: VERIFIED<br/>verified_at = time of success
    Waiting --> Expired: 5 minutes pass, never touched again
    Expired: EXPIRED<br/>row unchanged, verify refuses it
    Waiting --> Locked: 5 wrong attempts
    Locked: LOCKED<br/>row unchanged, verify refuses it
    Verified --> Deleted: NEW — this identifier completes a signup,<br/>same transaction as the users INSERT
    Deleted: DELETED<br/>value match on phone/email, no FK
    Verified --> [*]: verified login, no signup completed —<br/>stays (lower priority, see facts below)
    Expired --> Purged: NEW — 30 days pass, never verified
    Locked --> Purged: NEW — 30 days pass, never verified
    Purged: PURGED<br/>swept by the NEXT otp-request call anywhere<br/>in the system — no scheduled job
    Deleted --> [*]
    Purged --> [*]
The 10-minute TTL is untouched. Everything above is scoped to otp_requests only. pending_identity_verifications's 10-minute token life and its delete-on-completion behavior are exactly what they were before this pass — no code path here reads or writes that table.
Repeat attemptsBounded to one row per identifier while unverified — a typo, a resend, ten retries all update the same row.
Completed signupsEvery historical attempt for that phone/email deleted immediately, the moment it becomes a real account.
Abandoned attemptsSwept within 30 days of the last activity — expires_at doubles as the recency signal, since it's refreshed on every resend.
Verified logins (not a new signup)Left alone — that's an existing account's own already-known number, a smaller privacy concern than a stranger's wrong number.
05 · Clarified this session

What actually tells you "phone, tablet, Windows, or Mac"

Neither MAC nor IP address answers that — even if MAC were obtainable, which it isn't from a browser.

FieldWhat it tells youReliability
MAC addressNothing — not obtainable from a browser at any step, and even if it were, it's a hardware network identifier, not a device/OS signalN/A
ip_addressNetwork/geographic origin only (roughly which city/ISP) — stored raw only this pass, GeoIP parsing deferredCountry: high · city: low, especially on Indian mobile carriers' NAT'd IPs
user_agent → parsed device_type/os_family/browser_familyThis is the field that answers the question. Parsed once at write time via a standard library (Python user-agents)High — standard practice for exactly this kind of analytics
06 · Status

Resolved this session, and what's still open

SMS provider — stub modeNo SMS/OTP provider is wired in anywhere. Staying in otp_delivery_mode="stub", same as today. Real SMS delivery is deferred; dev/functional testing is unaffected.
Google — hidden, not removedHidden from the signup screen, backend left fully intact, re-enabled later with a UI-only change.
IP — raw only, for nowGeoIP parsing (country/region/city/ISP) considered and deferred. Not a one-way door — the raw value is retained.
otp_requests retention — fixed, zero infraUpsert-on-resend, delete-on-completion, 30-day sweep for unverified rows. See §04 above.
Still openDetail
Abandoned pending_identity_verifications rowsNot cleaned up — no ordinary-traffic hook to piggyback a sweep on the way otp_requests has. Lower priority: one row per abandoned attempt, holding a hashed token rather than repeated PII.
