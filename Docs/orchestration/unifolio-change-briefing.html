Deep dive, part 3: cross-cutting rules

  • Migrations, in order. Alembic head is 0046. Proposed: 0047 head flag, head change requests and OTP purpose (item 1); 0048 fund managers (item 4); 0049 scheme benchmark: each fund's factsheet benchmark and the tracked index of index funds (items 9 and 11); possibly 0050 if more benchmark indices are added (item 11). Dropping the old composite rating tables is a later cleanup (D36). Items 2, 3, 5, 6, 7, 8, 10, 12 and 13 need none.
  • Payload changes are additive first. Add the new fields, ship the UI that reads them, force one recompute, then remove old fields in a later release. Home, the fund page and the Insights engine read stored sections, so removing a field first would break them.
  • Decimal, never float. All new sums, averages and ranks use Decimal; the frontend formats strings it receives and does not add money.
  • Test-first order for every item. Backend red test, backend green, payload golden fixture, frontend red test, frontend green, print and mobile parity test, then the section-list test for the page. Run only the affected test files, per project practice.
  • Docs that must change. PRD-04 and the decisions of 2026-08-13 and 2026-10-06 (item 10), a new ADR or decision entry for the head of family (item 1), PRD-01 holdings table (item 2), and the redesign decisions register for the choices above.
  • Staging, once, at the very end. Nothing is deployed between runs. After all runs and the documentation update, everything goes to staging together: migrations 0047 to 0049, a forced analytics recompute because stored payload shapes change, the check queries, and manager QA across all items.

What this does to the current system

  • No migration for most items. Analytics results are stored as JSON per section. Changing a section's shape needs no schema change. Old results keep serving until the next recompute, which runs daily at 06:30 or after an import. The frontend must tolerate old shapes, or we force a recompute.
  • Migrations are needed only for new columns or tables: LinkedIn links (item 4), a persisted head of family (item 1), and dropping score tables if item 10 deletes them.
  • Three copies of every analytics section. The desktop page, the print view, and the mobile view each reference the same sections. Every UI change has to be made in all three.
  • Tests move with the code. The project requires test-first work. The analytics page test asserts the exact section list, so adding or removing a section updates it.
  • Uncommitted change in your tree. test_overlap.py has a one-line edit I did not make. I will leave it alone unless you say otherwise.
  • Redesign collision. The shell-nav redesign is replacing the old dashboard view, so holdings table work (item 2) can collide with feat/portfolio-page and feat/mf-frontend.
