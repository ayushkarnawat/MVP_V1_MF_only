Item 7 build: fund-wise P/E and P/B (factsheet first, NSE/BSE second)

The full method for the Valuation by Fund section, from where each number comes from to what changes in the backend, database and screen. Nothing is built. This replaces the earlier wording of item 7, which said to compute every fund's ratio from holdings and to add no new scraping.

The rule, in one place

  • Decided separately for P/E and for P/B, for every fund. A fund can show its P/E from the factsheet and its P/B computed by us.
  • If the fund house's factsheet prints the number, we take it exactly as printed. We do not recompute it and do not compare it with ours. It shows a small label: Fund factsheet, Sep 2026.
  • If the factsheet does not print it, we compute it from the fund's published holdings and stock-level P/E and P/B from NSE and BSE. It shows the label Computed (NSE/BSE data).
  • Changed 31 Oct (Q4): the Portfolio Valuation vs. Benchmarks section stays on the page and keeps its look and its two collapsible lists, but its P/E and P/B are now built the same way as the fund table (factsheet where printed, otherwise NSE/BSE), so the page uses one method. Forward versus trailing P/E in that total is decided by D39.
  • The only check on a factsheet number is a sanity check on the parsing: a value that cannot be real (for example a P/E of 0 or 4,000) is treated as not found, so a misread PDF never reaches the screen. It is not a comparison with our own figure.

End to end, step by step

  1. Monthly, the factsheet import. The existing monthly job (fund-managers-monthly, plus the hand import for the houses we cannot fetch) already downloads each fund house's factsheet. It gets a second reader that looks for P/E and P/B.
  2. Parse by layout. Each fund house prints these numbers differently, so each gets its own small parser, the same way fund managers are read today (fund_manager_layouts.py, fund_manager_resolvers.py). A parser returns: scheme name, P/E, P/B, the basis (trailing or forward), the averaging method if stated, the page and the factsheet date.
  3. Match to our schemes. The factsheet name is matched with our scheme list using the same name normaliser used for managers. A factsheet covers a scheme, not a plan, so one printed value applies to both its Direct and Regular plan (they hold the same portfolio).
  4. Reject impossible values. Not a number, zero or negative, or outside a wide plausible range (for example P/E outside 3 to 200, P/B outside 0.2 to 40) is dropped as a parse error and logged.
  5. Store. The accepted values go into a new reference table (see Database), one row per scheme, metric and factsheet month.
  6. Daily, stock data keeps refreshing (stock-fundamentals-daily, 05:45 UTC), now with BSE as a second source (Phase B) and later an official-filings route for P/B (Phase C).
  7. In every analytics recompute, for each held fund and each metric: use the latest stored factsheet value if it is fresh enough (Question Q1); otherwise compute it from the fund's holdings, using the same weighted harmonic mean and 70% coverage floor as the portfolio figure. Only the missing ones are computed, so the recompute gets cheaper, not heavier.
  8. Store the result in the existing valuation section as a new funds list. Each metric carries its value, its source (factsheet or computed), its date, its basis and, when computed, its coverage. No migration is needed for this, because stored sections are JSON.
  9. The screen reads the stored section and shows the Valuation by Fund card with a small source label on each number.

Risks and honest limits

  • Coverage is limited. Only 5 fund houses print a per-scheme P/E and P/B (Invesco, ITI, Kotak, UTI, ABSL). The exact share of funds is known only after Step 0 (S2, S3) on the VM's files.

Item 1 build: Change Head of Family, in detail

Read from the code on leapswitch-redesign on 31 Oct. It covers how the database is swapped, which codes and emails are sent, how the phone stub appears on screen, every error state, and the label changes. Nothing is built.

The design in five lines

  • Same account, new sign-in. The users row, its id and all portfolio data stay exactly where they are. Only who can sign in changes.
  • Two markers stay in step. A new is_head flag (migration 0047) says who the head is. At the swap the self relationship moves to the new head in the same transaction (D29 option A), so the 15 places in the backend that test relationship = self keep working without edits. The flag is what new code reads, and a backfill makes it equal to self for every existing account.
  • Four codes. Each person confirms their email and their phone. Email codes go out through the same email template as sign-in codes, with different wording. Phone codes use the existing stub (D37), and the stub code is shown on screen.
  • Nothing changes until all four are verified inside 10 minutes. The swap is one database transaction and rolls back as a whole.
  • Safety: the current head re-confirms to start, everyone gets an email, and the old head has a 24-hour undo link (D31).

The single transaction, in order

  1. Lock the users row, then the account's members (by id), then the open request (FOR UPDATE, which works on Postgres; it is a no-op on the SQLite used in tests).
  2. Check again inside the lock: request open and not expired, all four codes verified, old head still head, new head still a member, account not pending deletion, no import preview open, contact details still free, PAN checks still true.
  3. Copy the old head's contact, identities, session count and every member's label into the audit row. Store the undo token hash and its 24-hour expiry.
  4. Delete the old identities. Flush.
  5. Set users.phone_number and users.email to the new head's values. Flush (this is where the unique rule would fire if a race slipped past the check).
  6. Insert the two new identities. Flush.
  7. Members: the old head's row first (clear head, change the self label, receive the old contact details), flush, then the new head's row (set head, set self). Flip the other labels.
  8. Delete sessions and pending link tokens. Delete the four used code rows.
  9. Insert the consent withdrawal rows. Write the audit row. Commit.
  10. After the commit, send the "head changed" emails to both people and to the old head's other email, if any. A failed email never undoes the swap; it is logged and retried.

If anything fails before step 9 the whole transaction rolls back and nothing has changed. A unique-rule failure at commit returns a "contact already used" error.

The two checks that must pass again at the swap

  • Contact availability. The existing check looks at the identity rows and at users.email. It does not look at the email column of identity rows, which is how a Google sign-in is recognised. The swap runs both that check and the sign-in collision check.
  • PAN. The new head's PAN must not be held by another account and the member must not have an "on another account" conflict. Once someone is head the app does not let that row's PAN be edited, so a head with no PAN could never add one. That is why a member with no PAN is not eligible.

Item 3: what is "6% of your equity could not be sorted", and why show it?

The market cap card does not decide a company's size. It looks every stock up in AMFI's half-yearly list, which puts the top 100 listed companies in Large, the next 150 in Mid and the rest in Small. A stock is left out of all three when the list has no row for it:

  • Overseas stocks (an international or Nasdaq fund) are not Indian listings, so AMFI never classes them.
  • Stocks added after the list's date (a recent listing) are not on it yet.
  • Delisted, merged or renamed stocks, and rows where the fund house gives no ISIN, cannot be matched.

You asked for Large, Mid and Small to add to 100%. We do that by dividing by the part we could sort. The note says what the 100% is of. Without it, a family with a large international fund would read "Large 54%, Mid 31%, Small 15%" as a split of all their equity, when it describes 94% of it. The note costs one line and is shown only when the unsorted part is 0.5% or more; it can sit in the info tooltip instead. It is optional in the sense that the chart works without it, but it is what keeps the three numbers honest. This is D8, answered with option A.

LinkedIn (ON HOLD 31 Oct): no link until the profile is verified, and how we know it is the right person

No link is shown, and none is stored as usable, until a person has verified it. We never show a search page and never guess. A profile is accepted only when these checks are written down:

  1. Name. The profile's name matches the factsheet name (allowing an honorific, a middle initial or a different order).
  2. Employer in the headline or current position. The headline or current role names the same fund house, by its brand or legal name (for example "Fund Manager at Nippon Life India Asset Management", "Portfolio Manager, HDFC AMC"). This is the strongest check, as you suggested.
  3. Role. The title is an investment role (fund manager, portfolio manager, head of equities, chief investment officer, analyst), not an unrelated job.
  4. Dates. The experience entry at that fund house covers the "managing since" date printed in the factsheet.
  5. Second source, when available. The fund house's own page for the manager (name, photo or qualifications) agrees with the profile.

Rule: at least checks 1, 2 and 3 must pass, and one more of 4 or 5. If two profiles both fit, or the profile is private or shows no employer, or the person has left the fund house, we do not link.

Process: a person finds the candidate and writes down what they saw (the headline text, which checks passed, the URL, the date); a second person approves it before it can show (two-person check). Nothing is matched or scraped by code. The link is stored once per manager and fund house in fund_managers with columns for name key, fund house, URL, evidence note, checks passed, verified on, verified by, reviewed by and re-check due. The card shows the icon only when a verified, unexpired row exists.

Staying right: the link expires and is re-checked every 6 months, and straight away when a monthly import shows the manager at a different fund house or off the fund. A failed re-check hides the link automatically. The link opens the profile in a new tab with rel="noopener noreferrer".

#!/usr/bin/env python3
"""Read-only factsheet scan: which pages print P/E, P/B and a benchmark, and which pages are pictures.

Usage:  python scan_factsheets.py --dir <folder with PDFs> --out <output folder>
Needs:  pypdfium2 (already in backend/requirements.txt). No database, no network, writes only to --out.

Outputs three CSV files in --out:
  files.csv  one row per PDF: pages, text pages, image-only pages, hit counts
  pages.csv  one row per page: characters, image objects, image coverage, page class, P/E and P/B hit flags
  hits.csv   one row per matching line: kind (PE, PB, BENCHMARK), the line, the next line, the page class
"""
import argparse, csv, hashlib, os, re, sys
import pypdfium2 as pdfium

PE = re.compile(r"(p\s*/\s*e\b|price[\s/-]*(?:to)?[\s-]*earning|\bpe\s+ratio\b|\bp/e\b)", re.I)
PB = re.compile(r"(p\s*/\s*b(?:v)?\b|price[\s/-]*(?:to)?[\s-]*book|\bpb\s+ratio\b|\bp/bv\b|\bpbv\b)", re.I)
BM = re.compile(r"(benchmark|\btier\s*[-]?\s*(?:1|2|i|ii)\b|additional\s+benchmark)", re.I)
NUM = re.compile(r"\d+(?:\.\d+)?")

def classify(chars: int, img_count: int, img_cover: float) -> str:
    if chars >= 50 and img_cover >= 0.5:
        return "mixed"
    if chars >= 50:
        return "text"
    if img_count >= 1 and img_cover >= 0.3:
        return "image_only"
    if img_count >= 1:
        return "image_small"
    return "blank_or_vector"

def scan_pdf(path, writers, root):
    rel = os.path.relpath(path, root)
    amc = os.path.splitext(os.path.basename(path))[0]
    data = open(path, "rb").read()
    sha = hashlib.sha256(data).hexdigest()[:12]
    pdf = pdfium.PdfDocument(path)
    tot = len(pdf)
    counts = {"text": 0, "mixed": 0, "image_only": 0, "image_small": 0, "blank_or_vector": 0}
    pe_pages = pb_pages = bm_pages = 0
    for i in range(tot):
        page = pdf[i]
        tp = page.get_textpage()
        try:
            text = tp.get_text_range() or ""
            chars = len("".join(text.split()))
        finally:
            tp.close()
        w, h = page.get_size()
        area = max(w * h, 1.0)
        img_count, cover = 0, 0.0
        try:
            for obj in page.get_objects(filter=[pdfium.raw.FPDF_PAGEOBJ_IMAGE]):
                img_count += 1
                l, b, r, t = obj.get_pos()
                cover += max(0.0, (r - l)) * max(0.0, (t - b)) / area
        except Exception:
            pass
        cover = min(cover, 1.0)
        cls = classify(chars, img_count, cover)
        counts[cls] += 1
        lines = [ln.strip() for ln in text.splitlines() if ln.strip()]
        pe = pb = bm = False
        for j, ln in enumerate(lines):
            for kind, rx in (("PE", PE), ("PB", PB), ("BENCHMARK", BM)):
                if rx.search(ln):
                    nxt = lines[j + 1] if j + 1 < len(lines) else ""
                    val = ";".join(NUM.findall(ln)[:4])
                    writers["hits"].writerow([rel, amc, i + 1, kind, ln[:220], val, nxt[:160], cls])
                    pe |= kind == "PE"; pb |= kind == "PB"; bm |= kind == "BENCHMARK"
        pe_pages += pe; pb_pages += pb; bm_pages += bm
        writers["pages"].writerow([rel, amc, i + 1, chars, img_count, round(cover * 100, 1), cls, int(pe), int(pb), int(bm)])
        page.close()
    pdf.close()
    writers["files"].writerow([rel, amc, sha, len(data), tot, counts["text"] + counts["mixed"], counts["image_only"], counts["image_small"], counts["blank_or_vector"], pe_pages, pb_pages, bm_pages])
    print(f"{amc:28s} pages={tot:4d} text={counts['text'] + counts['mixed']:4d} image_only={counts['image_only']:3d} blank={counts['blank_or_vector']:3d} | PE pages={pe_pages:3d} PB pages={pb_pages:3d} benchmark pages={bm_pages:3d}")

def main():
    ap = argparse.ArgumentParser()
    ap.add_argument("--dir", required=True)
    ap.add_argument("--out", required=True)

Lessons from the first VM session (apply to the staging step too)

  • Never stop a recompute that is running. A stopped run leaves its user's claim in place for 15 minutes, and a recompute started in that window skips that user ("recompute already in flight"). If one was stopped, wait 15 minutes and run a one-household recompute for that user (run_analytics_recompute.py --household <id>), which clears the claim.
  • Check for claims before the forced recompute at staging. Query analytics_recompute_status: no user should show a claim in flight. Afterwards confirm every scope of every user has all 15 sections.
  • The wrapper script is silent until the job ends. run-job.sh collects the output and prints it at the end. Start long jobs in the background and watch the container and the log.
  • Timing scripts need a recomputed user and today's NAV stored. They abort on any database write, so run them after the 06:00 IST NAV job (after 06:35 IST), for a user whose recompute completed, twice each; the second run is the baseline.
  • The deploy user cannot read .env. Commands that source it (the database counts) run under sudo.
