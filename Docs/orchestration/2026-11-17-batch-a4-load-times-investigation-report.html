Investigation documentation only · nothing measured on staging, nothing changed · 17 Nov 2026 · item 7 · for your review; execution later

What this is. The report for item 7: why the Mutual Funds Overview is slow on some stakeholder laptops, and how long every other page takes at about 40 lakh. It is a reading of the code and a design for the investigation, not a set of measurements. It records what the code shows, what is still unknown, exactly how we would measure it, how we would read the results, and which fixes each possible result would point to. 1. Summary

In five sentences. The Overview asks the server for about four-plus-N requests at once, where N is the number of members. On the server, the holdings work is cached inside each of the three backend processes separately, and the XIRR is recomputed in exact arithmetic on several routes with no cache found. The front end is delivered as one bundle: I found only one lazily loaded screen, a developer index. Several of the plausible causes would hit only some people (a weak laptop, a slow network, a bigger household, a cold process), which matches “fine for us, slow for some”. Which of them is the real cause is not known: that is what the measurements are for.
We know (read in code)We do not know yet
  • The Overview request fan-out and what each request does.
  • Where the XIRR is recomputed (four routes) and that one call took 0.48 s for 1,801 flows on my machine.
  • That caches are per process, with three processes.
  • That the app is not code-split beyond one screen.
  • When the daily jobs run (06:00 to 06:30, 10:30, 14:00).
  • How long each page really takes at 40 lakh, cold and warm.
  • How much is server, network or laptop.
  • How big the replies and the app bundle are.
  • What the slow laptops, networks and accounts have in common.
  • Whether the per-process caches cause visible cold opens in practice.

2. The symptom, and what its pattern suggests

What was reportedWhat it points at
Fine on your laptop and your manager’s; slow on some stakeholder laptops.Something that differs between people: the laptop (CPU, memory, browser, extensions), the network, the account (size), the time of day, or which backend process answers. A pure server fault would be slow for everyone.
The Mutual Funds Overview in particular.It is the heaviest page: the largest table, a chart, several requests, and the XIRR work.
“Audit every page at about 40 lakh.”The cost grows with the household’s size, so we need a repeatable large household and a small one for comparison.

This is why the plan separates three kinds of time for every page: server (how long each route takes), network (when each request starts and ends, and how many bytes), and browser (the main-thread work after the data arrives, with the CPU slowed to imitate a weak laptop). A slowdown that appears in only one kind names its cause.

3. How a page load works today (read in code)

The path of one request

1. BrowserLoads the app files, then asks for data (about 4 plus one per member on the Overview).
2. CaddyThe web server on the staging VM passes the request on.
3. One of 3 backend processesThree uvicorn workers; each is a separate process with its own memory.
4. PostgresOne database container on the same VM.
5. ReplyJSON back to the browser, which then builds the table and charts on the laptop’s CPU.

One solver call took 0.05 s for 97 flows, 0.15 s for 481 and 0.48 s for 1,801 (measured on my machine, invented flows, not the staging server). The dashboard computes it for Lifetime and for Current, once more when a rate is above 35% (the opening-balance check), and again on each of the routes above. I found no result cache for it.

Caches, and why three processes matter

Process 1Holdings cache: warm for a household after the first request it served.
Process 2Holdings cache: empty. The same household’s next request that lands here recomputes everything.
Process 3Holdings cache: empty. Same.

The holdings cache is an in-memory dictionary inside each backend process (dashboard/holdings.py, 15-minute lifetime, keyed by the members and the date). Staging runs three backend processes (deploy/leapswitch/docker-compose.yml). A request is answered by whichever process is free, so a household’s “second open” can still be cold. To be confirmed by measurement: how often this shows as a cold open, and whether the cache is invalidated across processes after an import (a side finding, section 4).

How the app reaches the laptop

The front end is a React and Vite app. vite.config.ts has no manual chunking, and in the source I found one lazily loaded screen (a developer index, App.tsx) and no other dynamic imports. So the Overview’s code, and every other page’s, probably ships in one bundle, loaded before anything appears (to be confirmed by building and measuring the bundle).

What we record for each run

ServerPer route: time in the handler, time in the XIRR, number of database queries, cache hit or miss, which process answered.
NetworkPer request: start, end, bytes sent and received, whether compressed.
BrowserTime to first paint, time until the page is usable, long tasks, script parse and run time, memory.
ContextEnvironment, date and time, household, scope, throttling, browser version.

“Usable” defined

The page is usable when the summary strip shows its figures and the holdings table shows its first rows. We take the time to that point, because the stopwatch a stakeholder would use is “when can I read it”, not “when did the last request finish”.

Tools and how many runs

  • Server: the existing staging timing scripts (measure_fund_page_staging.py as the base) and a small timing wrapper behind the staging flag; counts and times only.
  • Network and browser: an automated browser (Playwright) with a performance recording and throttling, the same way the app is already tested.
  • Statistics: five runs per cell; report the median and the slowest; flag any cell whose runs differ by more than a factor of two.
  • Safety: only invented data; nothing writes; a quiet window; nothing runs during a deploy.
