Batch L: Portfolio Disclosures Audit

Planning only · nothing built or run · 17 Nov 2026 · the sister of the fund-manager factsheet audit · branch leapswitch-redesign

Every month each fund house publishes the full list of stocks and bonds in each fund (the portfolio disclosure). A daily job collects these, and the look-through screens (stock overlap, large/mid/small cap, asset allocation, P/E and P/B) depend on them. This batch is a check of that job for November, the same way the factsheet job was checked: how much is covered, a percentage we can quote, what is still done by hand, what the automatic job failed to get, and why (layout changes and the like).

An honest starting point. I have no access to staging, so I have not measured November. Everything below marked “from the code” is read from the repo; every November number comes from read-only queries you (or the manager’s Claude) run on the server from a guide I write. No number in this workbook is invented, and the report layout in section 8 uses blanks, not figures.

What “November” means. The job runs on days 1 to 20 of the month and looks for the previous month-end (read in the code: the target is the last day of the month before today). So the November round is the 31 October disclosures, published in the first ten days of November. This is the default used below (Q1).

1. What this batch is

An audit, not a build. It answers four questions about the November portfolio-disclosure round, and proposes fixes for you to approve.

1. CoverageHow much of the November round is in, counting the by-hand imports too, as a percentage.
2. By handWhich fund houses still need someone to download a file, and what is waiting.
3. Automatic missesWhich fund houses the job should have read but did not.
4. WhyFor each miss: a layout change, a moved address, a block, a late publication, or our own matching.
5. Next stepsA short, ordered list, with fixes proposed only.

What the system already does when something is missing

  • Each scheme and month gets one batch row with a status: pending, fetched, parsed, written, failed or awaiting manual upload. Screens read only written batches.
  • A batch is kept only if its weights add up to between 90 and 101 percent; otherwise it is stored as failed and ignored by screens.
  • On days 10 and 20 an alert is logged naming by-hand houses still waiting; on day 20 another lists any fund house with no written batch for the target month.
  • If a month is missed, funds keep showing the last month and are tagged older than 60 days; the Analytics banner reads “Based on X% of your portfolio” and names the uncovered funds.
  • The manual import refuses a file older than 45 days unless told otherwise, and never guesses its date.

3. How coverage is measured

“How much is covered” can mean three different things. The audit reports all three, in this order, so the headline cannot be misread.

MeasureDefinitionGood forWeakness
1. Fund housesFund houses with at least one written batch for the target month, out of the 52 in the registry (the five expected-absent houses excluded)A quick health check; matches the “45 automatic, 7 by hand” storyA house with one fund in and 100 out counts as covered
2. FundsSchemes with a written batch for the target month, out of the live schemes at covered-or-expected fund housesWhat most people mean by “coverage”Treats a tiny fund like a huge one; the count of live funds needs one query (section 6)
3. MoneyThe same, weighted by each fund’s assets (from AMFI’s average assets data already in the system)The number closest to what a user’s “Based on X% of your portfolio” banner showsNeeds assets data for the same month; approximate for the newest funds
My pick: report all three; quote funds as the headline (like the factsheet audit’s 8,582 of about 8,776), and money as the number that explains what users see. Fund houses is a footnote. (Q2.)

Three more cuts the percentage needs

CutWhy
Automatic versus by-handYou asked “including the manual hand imports”. The report shows each separately and together, and also “with by-hand houses assumed imported” so you can see the ceiling.
Fresh versus staleEach batch carries the date written in the file itself. A fund whose newest batch is the previous month counts as stale, not covered. This avoids the factsheet audit’s problem, where old files were stamped with the new month.
Written versus failed or unmatchedA failed weight check or an unmatched scheme name is a different kind of gap from “not published”, and has a different fix.

4. Why the automatic job can fail

The job writes a labelled warning for every failure. These are the labels in the code and what each usually means, so each miss in the report gets a real cause, not a guess.

How the audit tells a layout change from a delay

  1. Compare each fund house’s October and November: schemes written, rows per scheme, failed batches.
  2. A house that worked last month and now logs no_file_found, parse_error or failed_sum_check has very likely changed layout or address. We then open the page or file once by hand and record what changed.
  3. A house whose newest file is last month’s is late; we check again on day 20.
  4. A house with many unmatched_scheme lines has a naming problem; we list the names.
A known gap in the code (not changed by this audit). The alerts are written to the job log only, and I have not confirmed how long the server keeps those logs; the factsheet job’s were discarded after each run. If the November run’s log is already gone, the causes have to be rebuilt by re-checking each house, and the audit says so. A fix (keep the reasons in the database) is proposed in section 8, not built.

6. How the evidence is gathered

Read-only, on the staging server, using the access you already have. I write the guide and the queries; you or the manager’s Claude run them and send back the results. I never run anything on the server.

Timing. The round is complete by day 20, and the by-hand houses usually need until about day 10 to 12. A mid-month audit shows a lower percentage than the final one; the report is stamped with the date it was taken and can be re-run.

9. Where it fits in the program

  • Wave 1, independent of everything. It touches no screens and shares no files with the other batches. Approved fixes would touch only the portfolio_disclosure_* files and the job script.
  • No deploy for the audit. It is read-only. A fix that changes code ships at the next milestone that has a backend deploy, with the usual checks.
  • Timing matters, not order. The audit is most useful once the by-hand imports are done (about day 10 to 12) and again after day 20; the program plan does not wait on it.
  • What it feeds. The coverage banner wording and the evidence behind “Based on X% of your portfolio”; also Batch I (the PDF repeats that banner) and the later Explore and look-through work.
  • Not part of it: the NSE book-value job failure found in the other session (the redirect to a new NSE address) belongs to the factsheet and valuation side. It is a real, separate failure; say the word and I add it here or plan it on its own.
