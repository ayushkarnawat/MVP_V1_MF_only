D-11 · What is wrong, and what I checked

In Profile, "Choose who will be Head of Family" shows every member greyed out with "Finish or cancel the statement you are importing first." and Next disabled, although all member details were filled in. One CAMS request sat on "Waiting for CAMS email" (0 of 5 done). Because of that the four Head of Family emails (QA rows M1-17, M1-18, M1-19) could not be tested. Sources read: Docs/orchestration/2026-11-24-qa-round-report.md (item D-11) and the decisions.md entry "2026-11-24 - QA finding D-11".

Owner decision (24 Nov): a pending or abandoned import must not stop a Head of Family change. This section plans exactly that, and finds one place where a naive removal could do harm.

3. What a head change swaps, and what it leaves alone

What this means. A CAMS request waiting for its email has no file, no parse and no PAN claim (it is a placeholder row on a member), so a swap cannot corrupt anything there: the later upload is attributed from the file's own PAN against the members as they are then. The only plausible harm is a live review session (an uploaded file that was parsed while the old head was Self and is confirmed after the swap), a window of at most about 65 minutes. It is not proven: steps R4 to R6 settle it.

D-11 · Proposed fix and alternatives

Part 1 (certain, whatever the investigation says)

A dormant import (a CAMS request waiting or abandoned, a failed row, a legacy status) can never stop a head change. Remove the household-wide non-terminal-status check from member_eligibility, remove import_in_progress from START_CODE_ELIGIBILITY_REASONS, remove the 409 branch and the dialog sentence. Because the final step re-runs the same function, start code, start, the dialog and the final step all change together. The other eleven eligibility reasons stay exactly as they are.

Part 2 (decided by steps R4 to R6): the live review window

OptionWhat happensTrade-off
A · Nothing blocks, nothing extraAlso drop the PAN-claim half. A live review simply continues after the swap.Simplest. Only safe if R4 and R6 show the swap cannot change attribution. Otherwise a rare wrong-member import.
B · Narrow guardBlock only while a review is live: previewing with expires_at in the future, processing, or pan_pending_until in the future (self-heals within about 65 minutes). The dialog names the member and the time and offers Cancel (the existing discard route).Safest for data, but it still blocks sometimes, and needs a new field in the eligibility response and a Cancel button. Against your decision unless R4 shows real harm.
C · Never block; discard live reviews at the final stepInside the swap transaction call the existing discard_member_reviews (it releases pending PAN claims and deletes the preview rows). The user is signed out by the swap anyway, so an unfinished review is lost either way; tell them in the completion notice. If a confirm is processing at that very moment, answer the final step with a retryable "try again in a minute" (seconds, not hours).Matches your rule (nothing blocks) and removes the only harm path. Cost: a half-finished review must be uploaded again, which is rare and only within an hour.

Recommendation: Part 1 now. For Part 2, C if R4 or R6 show harm, A if they show none. B only if you do not want a review ever discarded. If any import-related blocker survives (option B only), the dialog must name the import and offer Cancel; under A and C no dialog text about imports remains.

Code comments required by the plan: where a PAN-related check survives, a comment explains it ("a pending claim sits on a member for at most 65 minutes; the swap moves the Self label that the confirm step reads").

Option B only: the eligibility route and its schema gain an optional blocking_import object (member, kind, expires at). No migration in any option.

Migration check

None expected. No model column changes: the fix reads and, in option C, deletes preview rows through existing functions, and any "your review was discarded" note lives in the request's JSON snapshot. If R4 to R6 reveal a need for a schema change, the plan stops and asks you before building.

Rollback

Revert the patch commit(s) and redeploy backend and frontend. Nothing persistent changes except discarded review sessions (temporary, 60 minutes by design), so there is nothing to restore. Check that an older build ignores an extra key in the request snapshot (part of R9).

Deploy

A patch deploy: backend restart plus a frontend bundle, no stored-results rebuild, no Alembic step (head stays 0054). It touches different files from the XIRR work (auth/ and profile-v2/, not dashboard/xirr.py or the holdings screens), so it can ship before, with or after XIRR.

Risks

  • Unproven race (R4): the live-review window above. That is why option C or A is chosen after the evidence.
  • Half-fix: forgetting the final-step re-check leaves the failure after all four codes. The test test_import_started_after_start_does_not_fail_the_final_step covers it.
  • Lock order: the swap's lock order (account, members by id, request) is a stated contract. Option C touches import rows inside it; R5 checks this before any code is written.
  • Old clients: a browser still showing the old bundle may receive no reason it knows; the generic-sentence test covers an unknown code.
  • Not verified: I read the code and documents only. I did not run the app, a local database or staging; every "confirmed" above means read in the source.
