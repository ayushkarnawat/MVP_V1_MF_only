In plain words

Short answer: no. The unfinished checklist did not cause the block. The block comes from a record on our server, not from anything in your browser.

  1. What you saw. In Profile, "Choose who will be Head of Family" showed every member greyed out with "Finish or cancel the statement you are importing first." and Next was disabled, although every detail was filled in.
  2. What really happened. The moment you press Request from CAMS, our server saves a small record: "a statement was requested for this person, waiting for the CAMS email". It stays for about 2 days. The Head of Family check looks at the whole family, sees any such record, and blocks everyone. It does not care who the record belongs to.
  3. The checklist is only a note-to-self. Its ticks, its "0 of 5 done" and its open or closed window live only in your own browser. The server never hears about them. So ticking all five boxes, or closing it, changes nothing on the server.
  4. Finishing everything would not have helped. Even if you had ticked all five, clicked "I have the file", closed the checklist and uploaded the statement, the "waiting" record would still be there. We found that nothing in the code closes it when the file is imported. It ends only when (a) you press "Cancel request" (which stops working after a page reload), (b) about 2 days pass and the nightly clean-up runs, or (c) you request again (that restarts the 2 days).
  5. What we will do. (A) The Head of Family check must never look at waiting or abandoned requests. (B) A waiting request must be closed when its file is imported, and old stuck ones cleaned up. (C) A waiting request must be visible, with a Cancel that always works. (D) The checklist becomes a pure reading aid, connected to nothing, and easier to see. Each part is its own piece below, with its own tests.

The plan: four parts, each with its own tests

Part A · Head of Family never looks at requests (the original owner decision)

A waiting, abandoned, failed or old import can never stop a change. The household-wide check is removed from the eligibility list, from the start-code step, from the start step, from the dialog and from the last step (which re-runs the same check). The other eleven reasons stay exactly as they are. For the one narrow case of a live review (an uploaded statement on the review screen, up to about 65 minutes): see decision D1; my recommendation is to discard it inside the swap, with a note, because the swap signs everyone out anyway.

Part B · Close the waiting record when it has done its job

  • When a statement for that member is imported (the confirm step finishes), close any waiting request for that member (mark it expired, the same status "Cancel request" uses).
  • When the user presses Cancel request or Start over, close it too (see decision Q3).
  • A one-time clean-up of rows already stuck: any waiting request that has a later confirmed import for the same member, or is past its 48 hours, is closed. This is a data fix with a script, not a schema change (confirm in step R7).

Part C · A waiting request is visible and cancellable

  • Add data shows a small "Your CAMS request is waiting" card driven by the server (not by browser notes): who it is for, how long is left, a Cancel button. It appears on any device and after any reload.
  • Cancel works from that card, so it no longer depends on a request id kept in the page's memory. This needs the server to tell the page "this member has a waiting request, id X, expires at Y" (a small read, or one extra field on an existing response).
  • The Head of Family dialog may add one quiet line when a request is waiting ("a CAMS request for Rohan is still waiting; this does not stop the change"). Not a blocker, not a button. Decision Q4.

Part D · The checklist becomes a reading aid, and easier to see

  • Decouple. The checklist is opened by its own button and by Request (still the first thing in the click, because of the browser rule), but: the page never waits for it; its notes never choose the Add data screen; coming back to the tab never changes the screen because of it; "Start over" and "Close" only touch the checklist; its failure shows a message and nothing else breaks.
  • The page chooses its screen from the server. If a request is waiting, show the waiting card; if not, show the usual choice. One source of truth.
  • Make it visible. Replace the plain "0 of 5 done" line and the quiet "closed" banner with a proper status strip (see mockups): a progress bar, the current step name, and Reopen. The floating checklist gets a clearer header and a progress bar.
  • Wording. "Start over" becomes "Reset checklist" so it cannot be mistaken for cancelling the request. Copy stays plain; no advice wording; no em dashes.

Size: this is bigger than the first D-11 plan. Part A is small and independent (back end plus one sentence in the dialog). Parts B and C touch the CAMS request flow (back end plus Add data). Part D is the front-end clean-up. They can ship in that order; each is valuable alone. Decision Q1 asks whether to do all four now.

Migration check

None expected: the fix reads and closes existing rows and, for a live review, deletes preview rows through existing functions. The one-off clean-up is a script. If R7 shows a schema need, the plan stops and asks before building.

Rollback

Revert the patch commits and redeploy. Closed requests cannot be reopened, but a closed request only means "stop waiting"; a user can simply request again. Discarded reviews are temporary by design.

Deploy

Goes into the next combined staging guide (the manager's Claude runs it). The clean-up script runs once after the deploy, dry-run first.

Risks

  • Closing a record too early: a user who imported one statement but still waits for a second CAMS email for another person. Part B closes only the member whose statement was imported.
  • The unproven live-review race (R6): that is why D1 is a decision after the evidence.
  • Half-fix: forgetting the last step leaves the failure after all four codes. A named test covers it.
  • The click rule: the checklist must still open first in the Request click or the CAMS tab is blocked as a pop-up. Part D keeps that and removes only the waiting and the screen steering.
  • Not verified: I read the code only; I did not run the app, a local database or staging.
