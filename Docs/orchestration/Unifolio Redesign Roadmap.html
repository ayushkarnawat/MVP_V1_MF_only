Merge-back safety

The merged staging branch is the exact tree you tested.

  • Merge staging into the redesign branch first; the final merge is fast-forward only.
  • Full backend and frontend suites on that merged tree.
  • Old branch's backend tests run against the migrated database.
  • Same synthetic CAS statements on both links; every shared number must match.
  • Mobile smoke test on both links; rollback tag pre-redesign-staging.

Decisions already taken

  • Sidebar active row uses the green underline; Profile uses plan defaults.
  • Home uses stored prices and adds no new table; its staging measurement is done.
  • News is shown directly (GDELT only).
  • Fund logos reuse the old review screen's source, initials as fallback.
  • Individual Fund page: Overview, Overlap, Insights; comparison is a second state, no URL.
  • Benchmark windows 1Y / 3Y / 5Y / Since inception, stored beside the old payload.

Biggest risks, and the guard

  • New indices change old output → old code paths keep a legacy four-index tuple, tested.
  • Recompute gets slower → one index load per index, a timing gate before merge.
  • compute_holdings is shared → one owner (Home T1), Opus review.
  • Wrong checkout on the VM → pinned compose project, absolute bundle paths, script guards.

Run counts for planned items come from each plan's own run table or from batching two to three tasks per run. Waves 5 to 7 are estimates; Wave 6 is open-ended and depends on QA findings.
