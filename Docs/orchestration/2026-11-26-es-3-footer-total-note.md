# Note for patch 3b: the contents-only print needs a footer-total fix before it can ship (found by the G3 review, 26 Nov 2026)

**Status:** the contents-only print (ES-3: `es-3-be` commit `6f859b7f`, `es-3-pr` commit `58744518`, both on `batch/es-be` and `batch/es-pr`) is **built and passes its tests, but it is NOT in the first QA-round release**: it was reverted on `patch/qa3` (commits `3353134f` and `ab057ccc`) and its branches are kept for patch 3b. The old second whole-report print stays in the release, so the PDF is exactly as today.

## The problem (confirmed in the code)
Every page footer is drawn by `frontend/src/print/print.css` (the `@page` rule, `@bottom-right`, line ~46): `content: "Page " counter(page) " of " counter(pages)`. `counter(pages)` is the total page count **of the document being printed**. The contents-only print has only `n` pages (the cover plus the contents, usually 2 or 3), so after the splice the contents pages would read "Page 2 of 2" while every other page reads "Page 3 of 40". The old second pass printed the whole report, so the total was always right. The replacement-page-count check (`len(replacement) == n`) does not catch this. Header text and the footer's left text are CSS variables on `documentElement` and are the same in both prints; **only the `counter(pages)` total differs**. `counter(page)` is the same in both prints (both start at 1; the cover has no footer).

## The fix to build in patch 3b (small)
1. `print.css`: change the footer to `content: "Page " counter(page) " of " var(--print-total-pages, counter(pages));` (the fallback keeps the normal print unchanged: the variable is unset in the first print).
2. `PrintReport.tsx`: the hook takes the total: `window.__unifolioShowContentsOnly?: (totalPages: number) => void`, and also sets `document.documentElement.style.setProperty("--print-total-pages", `"${totalPages}"`)` (a quoted string so it is valid in `content`); cleanup removes the property. Verify in the real browser that Chromium accepts `var()` with a `counter()` fallback inside an `@page` margin box (the file already uses root CSS variables in the margin boxes for the header and the footer's left text, so variables work there).
3. `render.py` `_contents_pdf`: call `window.__unifolioShowContentsOnly(total)` with `total = len(texts)` (the first PDF's page count).
4. Tests: a CSS-source test that the footer rule uses the variable with the `counter(pages)` fallback; a hook test for the argument and the cleanup; a render test that the hook is called with the first PDF's page count.
5. **Acceptance is the look gate on a real cover-on report**: `compare` with `--allow-pages` set to the cover and contents pages must PASS **and** the footer text of the spliced pages must read the same "of M" as the rest (the gate compares pixels, so a wrong total shows as a pixel difference on those pages; allowing those pages hides it: so also compare the first spliced contents page against the baseline with a mask over the numbers column only, or check the footer text with the manifest's text hashes of the pages after the contents).

This is the only known look change of the contents-only print; the splice, the page closing on every path and the fallback to the first PDF were reviewed and are sound.
