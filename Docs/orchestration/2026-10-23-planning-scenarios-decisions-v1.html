3. What the code has

Verified by reading the files named. Nothing was run in this session.

  • Frontend (frontend/src/features/scenarios/): ScenariosScreen (list, then result, one at a time, "Back to scenarios" button), ScenarioPicker (curated cards, a "More scenarios / Hide" toggle, category pills, card with name, dates, badges, stat line), four result views chosen by resolveResultShape (standard, multi-phase, redemption-freeze, hypothetical), shared pieces in ResultParts (hero numbers, benchmark bars, by-fund rows, by-member rows, disclaimer). 752 lines in total, with tests beside each file.
  • API: GET /scenarios?curated= (list; hypotheticals hidden unless SCENARIO_HYPOTHETICALS_ENABLED) and GET /scenarios/{id}/results (always the whole household: it passes every household member to the engine).
  • Tables: scenarios (name, description, dates, type, ongoing, display_rank, parent for phases, freeze list, four stored quick-stat columns), scenario_scheme_results, scenario_category_averages, scenario_hypothetical_assumptions. Results per fund are computed in advance by a job; the household result is computed at request time from current holdings.
  • The engine already takes a list of member ids. Computing for one member is a parameter on the route, not new engine logic. The route must check the member belongs to the signed-in account.
  • Per-fund rupee impact is built inside the engine (value times percent) and returned only inside each member's fund list. An asset-class total can be summed from it. The engine has a nine-bucket asset-class helper (underlying_asset_class: Equity, Hybrid, Debt-short, Debt-long, Gold, Silver, Overseas, Other, and so on), built for hypotheticals.
  • Benchmarks: five Nifty total-return indices (Nifty 50, Nifty 500, LargeMidcap 250, Midcap 150, Smallcap 250). They are empty for multi-phase and freeze scenarios.
  • Speed (not measured for this endpoint): the result route calls compute_holdings. The Home staging run found a cold compute_holdings took 4.9 to 24.3 s because it re-downloads fund NAV history until today's NAV is published. You decided to leave the Dashboard as is and log it. Scenario detail will inherit the same cost unless it uses the stored-price setting Home is adding (card D5).
  • Known open decision (DEFERRED_FEATURES.md): three pre-2006 scenarios (Dot-com bust, 2003-07 India bull run, 2004 election result) have no fund data, so every fund says "Not enough historical data". The list shows them. Card C6.
  • Shell and contract: contract v1.4 maps scenarios to /planning/scenarios and redirects /planning to it; Planning has no sub-menu; scope none. The shell's MiraComingSoonDialog exists for the Mira placeholder.

5. Privacy, consent, third parties, billing

Facts from the repository are verified. Statements about the law are from my own knowledge, were not checked against the official text in this session, and need your lawyer's confirmation.

  • New personal data: none. Scenario results are computed on request from holdings the user already imported; nothing new is stored per user. No consent record or purpose changes.
  • PAN: not used anywhere on this page.
  • Member parameter (verified need): the route must reject a member that does not belong to the signed-in account, so one household cannot read another's numbers. This is the one real security point in the plan.
  • Disclaimers: the existing "not a prediction of future returns" line stays. The decisions file records that the SEBI-style disclaimer wording is a release gate that needs a compliance reviewer. That review is not part of this plan.
  • Hypothetical scenarios: stay behind SCENARIO_HYPOTHETICALS_ENABLED until a markets-literate review. Your screenshots show no Hypothetical pill, which agrees.
  • Data export and deletion: nothing is stored per user for this page, so nothing to export or delete beyond what Profile already covers.
  • Notifications and OTP: none.
  • Subscription and billing: the PDF shows none on pages 28 and 29.
  • Third parties: none for this page. Mira is a placeholder and calls nothing.
  • "Coming soon" cards: collect nothing unless you choose the "Notify me" option in card E1.

Risks

  • R1. Detail load time. The result route inherits compute_holdings's cold cost (Home measured 4.9 to 24.3 s). Card D5.
  • R2. The member parameter is an access-control point. A missing ownership check would expose another household's numbers. It needs a dedicated test.
  • R3. Asset-class totals are derived, so funds with no data or frozen funds are left out of both the rupee sum and the covered value. The chart must say how much of the portfolio it covers, or it will look like it reconciles to the headline when it does not.
  • R4. Contract v1.5 touches the shell, which another builder is working from.
  • R5. Benchmark comparison against Nifty 50 for a debt-heavy portfolio is not like for like. The tile needs a one-line caveat (card C4).
  • R6. Pre-2006 scenarios show nothing useful for funds until card C6 is decided.
  • R8. With the by-fund list dropped (L25) and the old screen edited in place (L27), estimated and frozen funds lose their labels unless F1 is answered, and the existing tests for these files must be rewritten with the code.
  • R7. The release gates (hypothetical values, SEBI disclaimer wording) are outside this plan but constrain what can ship.

Glossary

  • Scenario: a past market event (or a hypothetical one) with fixed dates, replayed against the user's current holdings.
  • Quick stat: the stored market, equity-fund and debt-fund move shown on a scenario card.
  • TRI: total return index, the index including dividends.
  • Covered value: the part of the portfolio that has data for the scenario's dates.
  • Wrapper route: a tiny file that mounts a screen at a URL without changing the screen.
  • Coming soon state: a card or page that says what is planned, with no working controls.
