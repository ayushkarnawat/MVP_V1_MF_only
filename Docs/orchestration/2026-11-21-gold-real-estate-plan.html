Manual first. Automatic wherever it is free and legal.

About half of Gold can run itself. Real Estate is almost all manual. We keep the manual part under a minute by filling in everything we already know.

The short version

It fits the codebase well, and the shell is already waiting for it. The live branch has Gold and Real Estate rows in the sidebar as placeholders (status: "placeholder"), "coming soon" slots in the Investments page and Home allocation, and a Liabilities placeholder. Both modules plug in through the existing route registry, member scope switcher, Decimal rules and daily-job pattern. No existing mutual fund screen has to be rebuilt.
Automation is real for part of Gold and almost none for Real Estate. Gold Funds and Gold ETF prices can be fully automatic and free. The one real gap is a legally clean daily IBJA gold rate, which is a paid, enquiry-only licence with a one-year minimum. Real Estate has no free, legal, automatic value feed in India. The best free help is an RBI index-based estimate and a guided manual flow. The PDFs already assume this ("manual entry always works; external data only pre-fills").

What I recommend, in one paragraph each

1. Build a shared "asset spine", then two thin modules

One small set of tables (assets, owners, cash flows, valuations, liabilities) serves Gold and Real Estate now and Debt, Others, FDs and Bonds, Direct and US Stocks later. Each module adds one detail table. This is fewer tables than the PDFs list and reuses the existing XIRR engine. The reuse alternative for Gold Funds is simply to read the MF tables that already exist. Detail in Data & backend.

2. Start the IBJA conversation this week

It is the only source the Gold PDF names for SGB, physical gold and the 10-year benchmark, and RBI itself redeems SGBs at an IBJA average. Ask for written permission to display the rate to our users, the price, and 20 years of history. Build the price provider behind one interface so a source can be swapped. Detail in Research.

3. Make adding data the easiest part

Pre-fill everything: the scheme search fills ISIN and scheme code, the SGB series master fills issue price and maturity, purity defaults by form, and the first add takes under a minute. Offer a demat statement upload as the "bulk" path for ETF and SGB once a spike confirms the parser reads them. Detail in Frontend and Gold mockups.

4. Count each rupee once

Home allocation today is computed from mutual fund holdings. Gold Funds would be counted twice (MF and Gold) and the existing "Gold" and "Real Estate (REITs and InvITs)" slices already mean something else. I propose a single net-worth aggregator with a classification map and a source breakdown inside the existing class dialog. Needs your call (Q3, Q4).

Things the PDFs get right, and where they meet the codebase

  • I recomputed the PDFs' worked examples. They are correct and safe to use as golden test fixtures: SGB 2020-21 XIRR 22.28% (20.65% without interest), SGB 2023-24 41.39%, ETF 31.16%, necklace 15.72%, Baner flat CAGR 9.62%, loan EMI ₹44,693, estimated outstanding ₹45,00,648, LTV 33.3%, yields 4.00% / 6.51% / 3.41%.
  • The PDFs say "family_id". Unifolio has users (the account) with household_members under it. Every new row hangs off a household member and every route authorises through get_household_member_for_user, like the dashboard does.
  • The PDFs say "admin panel". I found no admin UI in the repo. Configurable values (staleness limits, purity list, SGB series) become a config table plus a script, with an admin screen as a later decision (Q14).
  • The PDFs say "imports must tag Gold ETFs and Gold Funds so MF totals exclude them". Today a Gold Fund is a normal MF holding in every MF number. I propose leaving MF screens alone and deduplicating only in net worth (Q3).
  • The PDFs show the exchange closing price for SGBs "for information". We have no licence to display exchange prices, so I drop that line from v1 (Q5).

What this plan does not do

No code, no migrations, no commits. Nothing here is a go. The list of out-of-scope items in each PDF stays out (forecasts, tax calculations, digital gold, silver, property-management features, document OCR).

A. How mutual funds work today, and what that tells us

For mutual funds Unifolio uses the user's CAMS / KFintech statement (casparser) plus mfapi.in and AMFI files, refreshed by cron jobs (nav-daily at 06:00 IST with retries, benchmarks, TER and others). There is no equivalent single statement for gold or property. The closest things are the demat statement from NSDL or CDSL (for ETFs and SGBs held in demat), the Account Aggregator network (investments only), and RBI Retail Direct (for SGBs). Property has no statement at all.

E. Open-source and competitors

Open source

  • Wealthfolio: private tracker with manual assets including real estate. Gold not confirmed. Good UX reference, not code to reuse.
  • Ghostfolio (AGPL-3): sources disagree on custom or manual assets. AGPL would force us to open our code if we embedded it.
  • Nothing open-source covers Indian SGB schedules, IBJA, or Ready Reckoner. I found no Indian open-source module to adopt.

Indian trackers

  • INDmoney: manual entries for property and gold at an estimated value, plus a net-worth view.
  • MProfit: reported to support real estate; I did not verify from the app.
  • Kuvera, Groww: reported as mutual fund or in-app only.
  • Competitor blogs are the only source here, so treat these as unverified.

F. If it has to be manual, how to make it the easiest possible

  1. Pre-fill from what we already know. Scheme search fills ISIN, scheme code and gram factor. Series search fills issue date, issue price, maturity and interest dates. Purity defaults by form (22K jewellery, 24K coins and bars).
  2. Ask for the two numbers on the bill, calculate the third (PDF section 02). One purchase takes under a minute.
  3. Never ask for what we can calculate: amount, current price, value, P/L, return, XIRR, maturity, interest.
  4. Bulk paths: gold funds appear automatically from the existing statement; a demat statement upload adds ETFs and SGBs in one step (after the spike).
  5. Guided value update for property: one small sheet with value, date and source together, a nudge at 12 months, and an optional RBI-index suggestion the user accepts or ignores.
  6. "Where do I find this?" helpers beside Ready Reckoner, loan balance and gram factor.
  7. Honest labels everywhere: source and date on every price and value, "Estimated" vs "Official", and "Price delayed" instead of silently stale numbers.
  8. Gentle reminders for SGB maturity, early-redemption windows, stale valuation and stale loan balance.

G. What I could not verify

  • IBJA price, and whether "display" in the FAQ covers showing per-gram rates to end users. Needs a written answer.
  • NSE end-of-day tariff (the PDF timed out twice). Irrelevant if we use NAV.
  • RBI house price index download method and reuse terms (RBI site redirects blocked my fetcher). Needs a human to open DBIE.
  • RBI "Data on Outstanding SGBs" spreadsheet (bot check blocked my fetcher).
  • How an SGB or gold ETF line is labelled in an NSDL or CDSL e-CAS, and whether casparser 1.3.0 parses it. Needs a real file.
  • RBI Retail Direct statements, credit-bureau loan data, HUID lookup details, Mappls and Ola pricing, Liases Foras.
  • Whether AMFI NAV redistribution terms extend to displaying derived gold prices. We already depend on AMFI and mfapi.in for MF NAV, so this is the same position.

2. Do we need new tables? Reuse first

Reuse alternative, before proposing anything new Gold Funds and any MF-folio gold ETF: read from folios, transactions, schemes, nav_history through compute_holdings. Nothing new is stored. Gold module shows them as read-only rows tagged "from your mutual fund statement".
Could manual SGB, demat ETF, physical gold and property also live in folios and transactions? No. transactions is range-partitioned by date, keyed to an imports row and to NAV, deduplicated by import identity and processed by the FIFO engine. Property and jewellery have no scheme, no NAV and no import. Forcing them in would break the schema's own rules ("build for the schema that exists").

6. Net worth, double counting and the allocation merge

Today Home allocation reads MF look-through only, so "Gold" there means gold held inside funds. When real gold and property exist, one service owns the answer.

  • Classification map: a Gold Fund or gold ETF scheme counts once, in Gold. MF screens (holdings, analytics, XIRR) are not changed. Only the aggregator subtracts them from "Mutual Funds" (Q3).
  • Net worth today is not "net worth": Equity and Fixed Income are not live, so a Gold "share of net worth" would read 3.3% only if all classes existed. Label it "of tracked wealth" until they do (Q7).
  • Home donut: keep the five live classes. Gold = MF look-through gold + Gold module. Real Estate = REITs/InvITs inside funds + properties. The existing class dialog (AllocationClassDialog) gets a "source" breakdown so the user sees why (Q4).
  • Property loans: netted once inside Real Estate and shown greyed in Liabilities as "already netted in Real Estate", as the PDF requires.

9. Integration hazards to design for (found by reading the code)

Account deletion

account_deletion.py and the delete_expired_accounts_daily job must cascade through every new table. A test per table.

Member merge and Head of Family

member_merge.py moves folios and transactions between members. Assets and owner shares must move too, and shares must still total 100 after a merge.

Consent gate

After a head change every data route answers 403 until Terms are agreed again. New routes join that gate. Property data is sensitive, so the consent copy in services/legal needs a line for it (Q15).

Stored analytics

Home reads stored, recomputed results (analytics-recompute-all). Gold and property are computed live and cheaply (no NAV history), so they stay out of the recompute pool.

Dual dialect

Postgres CHECK and deferred constraints need SQLite-safe fallbacks, as migrations 0002 and 0050 do. Each migration tested on both.

Price job failure

If the gold rate job fails, show "Price as on 25 Sep · feed delayed" after 3 business days, never a silent stale number. Same email alert as nav-daily.

4. Behaviours every screen shares

  • Scope: routes use scope: "family-or-member". Family combined is the default; picking a member re-scopes every tile. A member with no gold or property shows a clear placeholder, never silently excluded (same rule as the MF dashboard).
  • Every price or value shows source and date ("₹15,500 / g · IBJA 999 · 30 Sep 2026"). A client estimate never looks like an official valuation: grey badge for self-estimated, green for report or API, outlined for Ready Reckoner.
  • States: skeleton while loading, empty state with the easiest ways to add, partial state (price missing, shows "–" with a tooltip), error with retry, stale state chips ("Price delayed", "Value last updated 14 months ago").
  • Disclaimers on every gold and property screen, using the PDFs' text.
  • Forms: controlled inputs with Radix Select, no new form library. Inline errors under the field. Auto-filled fields are green and editable. Never block save on optional fields.
  • Accessibility: labels with htmlFor, focus-visible outlines, charts have a table alternative, chips carry text not colour alone. (Your last frontend review found a missing label and a float re-sum, so both are explicit test cases.)
  • Desktop only. Phone UI is out of scope, as in the other batches.
  • Tests: Vitest per component with the fixtures above; route test that the Gold and Real Estate rows are live and open the right page; no full-suite runs.
