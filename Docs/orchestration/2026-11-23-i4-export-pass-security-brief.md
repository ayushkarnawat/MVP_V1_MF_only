# Security brief: the export pass (Batch I, task I-4, step 5)
**Status:** DRAFT FOR THE BUILD AND FOR THE FRESH REVIEWER (written 2026-11-23 by the orchestrator). Two jobs: (1) it is the design the Codex handoff for I-4 builds to; (2) it is the brief the fresh adversarial reviewer receives before I-5 merges ("attack the pass"). Plan: `Docs/superpowers/plans/2026-11-17-batch-i-pdf-export-plan.md` (Tasks I-4, I-5). Workbook: `2026-11-13-batch-i-planning-workbook.html` section 5. **Findings are never applied automatically**: the owner decides each one.

## What the pass is for, in one paragraph
Today's export keeps its one-time token in a plain dictionary inside one backend process, while the VM runs three (`--workers 3`), so a request that stores the data and the request that reads it can land on different processes. The new design replaces the dictionary with a **pass**: a short-lived, signed, read-only credential that our own headless browser presents to the **normal read routes** while it prints the report. Nothing is held in one process's memory, so any worker can issue it and any worker can check it. A pass is a new kind of credential that can read a person's whole financial picture, which is why it gets its own review.

## Assets and attackers
- **Asset:** one household's holdings, transactions, returns, names (member names), folio numbers (when the option is on). Never PAN (the app does not return it; the export must not add it).
- **Attacker A, a signed-in user:** tries to read another household's data, or a member they do not own, or widen "this member" to "the family".
- **Attacker B, someone who obtains a pass** (from a log, a URL, a screenshot of the print URL, a browser history of the renderer, a shared screen): tries to reuse it from their own machine, after the export ended, or for a write.
- **Attacker C, a stolen session or an old pass after the account changed** (deleted account, a Head of Family swap, a revoked session, consent no longer current): tries to keep reading.
- **Out of scope:** an attacker who already controls the VM or the signing secret (they can read the database anyway).

## The design to build (the reviewer attacks this)
1. **Signed, not stored.** An HMAC-SHA256 token (compare in constant time; reject any other algorithm or an unsigned form; no `alg` field to confuse) with these claims only: `sub` (user id), `scope` (`"family"` or one member id), `job` (the export job id, so a pass belongs to one export), `jti` (random nonce, for logs and tests), `aud` (the fixed string `"export-render"`), `iat`, `exp`. **`EXPORT_PASS_TTL_SECONDS = 300`**, but the build should prefer **180** if a typical render fits (I-2 and I-13 measure it). The secret is a new setting `EXPORT_PASS_SECRET` (at least 32 random bytes; the app **refuses to start** in production with it empty or equal to any other secret in the settings; never logged; rotation: changing it kills all outstanding passes, which is fine at five minutes).
2. **Read-only by an allow-list, not a deny-list.** The pass is accepted by **one dedicated dependency** (not by the general session dependency) that is attached **only** to a fixed list of GET routes the print page needs (the list lives in one file, `backend/app/services/export/pass_routes.py`, one entry per route function, with a test that fails when a route is added to the list without a matching entry in the print page's section list). Any other route, and any method other than GET or HEAD, answers **403** with no detail about why. A pass is never accepted on `/auth/*`, `/legal/*`, import, member management, profile, deletion, or any POST/PUT/PATCH/DELETE.
3. **Scope is re-checked on every request, not only at issue.** On each use the dependency loads the user and checks: the user still exists, is not `pending_deletion`, and (for a member scope) the member still belongs to that user **now**; and it applies the same head-change/consent check the data routes apply (`get_data_user`'s `reconsent_required`, `backend/app/services/auth/session.py` line ~147) so a pass cannot read data a session could not. A `family` pass resolves to the user's own household only. A `member` pass resolves to exactly that member: routes that take a member id or "aggregate" must be forced to the pass's scope (a request that asks for another member or for the aggregate with a member pass is **403**, not silently narrowed).
4. **Usable only by our renderer (a second factor).** The signed pass alone is not enough. The renderer also sends a **proof header** (`X-Export-Proof`) that is `HMAC(EXPORT_PASS_SECRET, "proof:" + jti + ":" + job)`, added by the headless browser at the context level (Playwright `extra_http_headers` scoped to the API origin), never placed in any URL or in page JavaScript. A pass copied out of a log or a URL is useless without the proof, and the proof is never exposed to page scripts. (Open for the reviewer: is this enough, or should the API also only accept the pass from the renderer's loopback or private address? That is a deploy detail to confirm with the manager; Caddy's forwarded headers make the source address hard to trust, so the proof header stays the main control.)
5. **How the pass reaches the print page without leaking.** It goes in the **URL fragment** (`/print/report#pass=...`), which browsers never send to a server, so it cannot appear in Caddy's access log, in `Referer`, or in the backend's logs. The print page reads it from `location.hash`, keeps it in memory only (never `localStorage`, `sessionStorage` or cookies), removes it from the address with `history.replaceState`, and sends it as `Authorization: Bearer` (header) on its API calls. The same string must **never** be logged by the backend, the front end or the renderer (a test greps the log output of a full export for the pass and the proof).
6. **Ending an export.** The pass dies by **expiry** (stateless), and the renderer closes the browser context (so the pass, which lives only in that page's memory, is gone) in a `finally`, on success, failure and cancellation. If the reviewer finds that expiry alone is too long, the alternative is a stored revocation (a small table: `jti`, `job`, `revoked_at`), which would be **the first new migration in this program**: stop and ask the owner before adding it.
7. **Rate and abuse.** Issuing needs a signed-in user and an owned scope; at most two exports render at once and each user has a cooldown (task I-3). A pass cannot issue another pass. Failed verification returns one generic 401/403 body (no "expired" versus "bad signature" difference), logs only the reason code and the `jti` (never the token), and is counted.
8. **Nothing personal in the file name, the logs or the error bodies.** Logs carry: an export happened, the scope kind (family or member), section count, duration, size, success or failure. Never names, figures, member ids, the pass or the proof.

## What the reviewer should attack (a checklist, not a limit)
- **Scope widening:** member pass reading the aggregate, another member, or another account's member id by guessing; family pass reading a member of another account; a UUID in a path that the route trusts without the household check.
- **Replay:** the pass used after expiry (clock skew: is there leeway, and is it zero?), after the export ended, from another machine (no proof header), after the account was deleted, after a Head of Family swap, with an old `EXPORT_PASS_SECRET`.
- **Write routes:** any POST/PUT/PATCH/DELETE, and any GET that has a side effect (a "recompute", a cache fill, a CAS download, `/analytics/export/payload/...` of the old pipeline, anything that writes `nav_history`). The allow-list must not contain a GET that writes **user-owned data, replaces stored results, or dispatches a job**; GETs whose only writes are idempotent caches of public reference data (NAV rows, the shared in-process holdings cache) are allowed and documented per route (amended 24 Nov after the route inventory showed that the screens' read routes fill those caches).
- **Algorithm and format attacks:** `alg: none`, a different hash, a token with extra claims, a token with the claims in another order, base64 padding tricks, an oversized token (length cap), a pass whose `aud` is different, a session token presented as a pass and a pass presented as a session token (each must fail on the other dependency).
- **Leakage:** the pass in a URL, a log line, an exception message, a Sentry-style report, `Referer`, the front end's error text, the PDF itself, the browser's history in the renderer, the page title; the proof header in a request log.
- **Header and URL injection:** the section ids and options the dialog sends (`ExportOptions`) reaching a URL, a header or the print page unescaped; a crafted `section_ids` value that makes the renderer fetch an arbitrary URL (SSRF) or a non-allow-listed route; `FRONTEND_BASE_URL` being changed to point the renderer, with the pass and proof, at another host (the renderer must refuse to navigate away from `FRONTEND_BASE_URL`'s host and to refuse any request to a different API host).
- **Denial of service:** many exports to tie up the two slots; a huge `section_ids` list; a pass issued and never used; a print page that never signals ready (timeout and cleanup).
- **Old pipeline:** the old `POST /analytics/export/pdf` and `GET /analytics/export/payload/{token}` stay, so the reviewer also checks that the new code did not weaken them and that the old payload endpoint (no auth, token only) cannot be used to read anything new.
- **Folio and PAN:** the folio option cannot be switched on server-side by a crafted request when the user's eye icon is off **if** the owner decides that is a rule (today it is a dialog default, not a server rule: the reviewer should say if it needs to be); a test scans every section's JSON and the final PDF text for PAN patterns.

## Tests the build must contain (names from the plan, plus these)
`test_valid_pass_verifies`; `test_expired_pass_rejected` (zero leeway); `test_pass_for_other_scope_rejected`; `test_pass_cannot_call_a_write_route`; `test_pass_for_a_member_of_another_account_rejected`; `test_tampered_token_rejected`; `test_pass_works_in_a_different_process`; `test_empty_secret_refused_in_production`; **new:** `test_pass_without_proof_header_rejected`; `test_pass_not_accepted_off_the_allow_list`; `test_pass_refused_for_pending_deletion_user`; `test_member_pass_cannot_read_aggregate`; `test_session_token_is_not_a_pass_and_a_pass_is_not_a_session`; `test_pass_and_proof_never_appear_in_logs`; `test_every_allow_listed_route_is_get_only`; `test_family_pass_follows_member_removal` (a member removed after issue is refused on the next request); `test_reconsent_required_blocks_the_pass`. Backend tests that need the database run in Postgres where the Codex sandbox cannot (Claude runs them).

## How the review runs
A fresh reviewer with no part in the build reads this file, the diff of I-4 and I-5, and `backend/app/services/auth/session.py`; it **runs** the tests, tries each attack above against the code (writing throw-away tests, not changing the repo), and reports findings as: severity, the exact request or input, what it reads or writes, the fix suggested. The orchestrator verifies each finding himself before telling the owner (a reviewer is often wrong, and sometimes right about something the tests missed). Whole-batch reviews are Opus only (owner rule); **this is a named security gate, so the orchestrator recommends Opus for it and asks the owner first**.

## Owner decisions (23 Nov 2026: the owner accepted the orchestrator's recommendations)
1. **TTL: 180 seconds** (`EXPORT_PASS_TTL_SECONDS = 180`; raise to 300 only if I-13's measurement shows a typical report needs it).
2. **Stateless.** No table and no migration. If the fresh reviewer decides expiry alone is too weak, that is a finding for the owner, not something to add silently.
3. **Folio masking stays a dialog default only** (as decided 17 Nov); PAN-never is enforced everywhere.
