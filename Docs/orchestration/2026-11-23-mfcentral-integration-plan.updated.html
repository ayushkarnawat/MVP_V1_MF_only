MFCentral CAS integration plan

Plan only, nothing built. Test mode (UAT) first, then production. Written against the three MFC files you gave me and a read of this codebase (leapswitch-redesign, Alembic head 0054). I read "tested in Mailer" as "tested in UAT"; tell me if you meant something else.

1. Summary

What we build

A third import path, Fetch from MF Central, beside PDF upload and the CAMS mailback. The backend talks to MFC. The user does OTP consent on MFC's own screen, downloads a QR image, uploads it to us, and we exchange it for JSON. A new adapter turns that JSON into the same ParseResult the PDF parser makes, so the existing preview, prompts, PAN claims, dedup and confirm all run unchanged.

Why it is safe to plan this way

Every secret (client secret, password, AES key, RSA private key, URL key) is used server-side only. The browser only ever sees an already-encrypted redirect URL. So Claude can build and test the whole thing without any real secret, and a human installs the real UAT secrets on the VM and runs the live checks.

Decisions made so far (3 of 12). Decided Q2 v1 imports detailed statements only; a summary shows a "start again" screen. Decided Q6 popup on desktop, full redirect on mobile or when the popup is blocked; no iframe in v1. Decided Q11 MF Central appears as a third row on Add data and on the onboarding upload step. The other nine are still open in section 11 and the plan keeps my recommendation for them until you answer.

Five findings that shape the plan

  1. Only a detailed CAS can feed the ledger. Decided Q2: detailed only The importer rejects summary CAS (parser.py:406) and a summary response has no transactions. The user must pick "Detailed" on MFC's screen, and we must catch the case where they do not. A summary is never imported; it shows the "start again" screen. Snapshot-only import stays parked in DEFERRED_FEATURES.md.
  2. Detailed rows have no running balance. Our dedup (_match_rows) is strongest when each row carries balance_units. MFC rows do not, so it falls back to count matching. The per-scheme closingBalance in dtSummary becomes our reconciliation check.
  3. Transaction descriptions are free text (trxnDesc), and trxnTypeFlag was blank in the sample. UAT data is fake, so the real vocabulary only shows up on real accounts. This is the biggest technical risk.
  4. One request means one PAN. There is no multi-holder grouping like in a family PDF, which removes most of the member-detection prompts.
  5. Access is a business question first. In September 2025 AMFI told MF Central to stop sharing data with third-party apps; the QR consent flow in your PDF is the replacement route, and MF Central said it will tighten third-party access further. Production approval, terms and any fee have to be settled with MFC before the production phase. See sources at the end.

Credentials note. You said test credentials were included. The PDF only contains one value, the URL encryption key (in plain text on page 1), plus the UAT OTP rule and test PANs. I did not copy that key into this page or anywhere else. No client id, secret, username, password, IV or RSA keys were in what I received. Keep it that way. The PDF is already in this session's context, so if you want to be strict, ask MFC to rotate that UAT key. Also scan Docs/749204247-MFCentral-API-Integration-Document-CAS-v2-2-1-2.txt for secrets, and keep the PDF out of the repo.

2. How MFC works (from your docs)

StepWhoWhat happens
0 TokenOur backendPOST /oauth/token, Basic auth (client id:secret), form body username, password, grant_type=password. Token lives about 30 days.
1 newCasRequestOur backendPayload (clientRefNo, pan, email or mobile, fromDate, toDate, redirectUrl) is AES-256-CBC encrypted with SHA256(key) and a constant IV from MFC, base64, then JWS-signed (RS256). Response is verified with MFC's public key and decrypted. Gives reqId and otpRef.
2 RedirectOur backend builds, browser opensSeparate encryption: AES-256-CBC, URL key used raw, random 16-byte IV, format IVhex:cipherhex, URL-encoded, appended as /api/auth/start?data= on the MFC redirect host.
3 ConsentMFC screenOTP, then the user picks Summary or Detailed, then MFC makes a QR.
4 ReturnMFC to usAfter QR download: iframe or popup sends postMessage mfc-cas-complete; standalone redirects to redirectUrl?status=&reqId=&type=; React Native uses ReactNativeWebView.postMessage.
5 QR uploadUser to usUser uploads the QR image to our app.
6 validateQRCodeOur backendSame encrypt and sign flow with {reqId, clientRefNo, qrCode(base64)}. Returns summary or detailed JSON.

UAT facts: API uatservices.mfcentral.com, redirect host mfc-cas-uat.mfcentral.com, test OTP is 00 plus the last 4 digits of the PAN, a shared test email and mobile, and nine test PANs (page 26 of the PDF). Errors: 400 business, 401 token or client id, 422 bad format, 404, 500, and 202 meaning accepted but not finished.

Gaps and contradictions in the MFC documents (confirm with MFC)

  • Page 5 says "either email or mobile, both cannot be provided", the field table says "email required if mobile not provided". We will send exactly one.
  • The redirect sample uses a token variable it never defines; the field table says leave it blank. We send "".
  • Base URL variable is MFC_REDIRECT_BASE_URL in config but MFC_BASE_URL in the sample.
  • Origin to trust in postMessage differs across files (cas-oauth.mfcentral.com vs cas.mfcentral.com vs the UAT host). We make it a setting, never a literal.
  • Completion type is "summary or transactions" in one file and "full" in another.
  • jsonwebtoken adds an iat claim by default; the spec never says whether MFC needs or tolerates it.
  • The older spec in Docs/ (v2.2) may differ from this newer PDF. We treat the PDF as authoritative and ask MFC.
  • The IV is constant and the API crypto is mandated by MFC, so we follow it exactly, but note it as a known weak point.

Key design decisions

  • The browser is never trusted for outcome. The postMessage and redirect params are UI hints. Truth is a successful validateQRCode for a request we created, owned by that user.
  • Reuse the CAMS placeholder pattern. An imports row in WAITING_FOR_USER with an expiry is already hidden from history and already swept by the daily expiry job.
  • Return mode Decided Q6. Desktop: popup, with a full redirect as the fallback if the popup is blocked or closed. Mobile web and any in-app WebView: full redirect (popups and downloads are unreliable there). No iframe in v1, so we do not need MFC to allow framing; we only need the completion-message origin and a registered return URL.
  • Never store the QR image or log it. The QR is the bearer credential for that consent. It is read, sent, and dropped.
  • Environment lock. Each request row stores environment (uat or prod). A request made in one is rejected in the other.
  • Kill switch. MFC_ENABLED (bool setting, same pattern as news_enabled) hides the card and rejects the routes.

4. Secrets: the manual plan and the Claude-safe plan

Rule for both: no real secret ever enters a chat, a repo file, a log, a screenshot or an AI tool's read path. The code reads secrets from the server's environment or mounted files only.

Track M: fully manual (you or your manager do everything touching secrets)

  1. Custody. MFC delivers credentials to one named owner. Put them in a password manager vault with two named people. Never email or paste them on chat.
  2. Out-of-repo sanity test first. On your own machine, in a scratch folder outside the repo, run MFC's sample code (Node) with the UAT secrets to prove four things: token works, newCasRequest returns a reqId, the redirect URL opens MFC's UAT screen, and your RSA key pair and IV are correct. Do this before we write any app code; it separates credential problems from our bugs.
  3. Install on staging VM by hand. SSH to the LeapSwitch VM and put the string values in deploy/leapswitch/.env (chmod 600, root only, same as today). Put the RSA private key and MFC public key as files in a root-only secrets/ folder mounted read-only into the backend container; the app reads MFC_PRIVATE_KEY_PATH and MFC_PUBLIC_KEY_PATH, so no multi-line PEM lives in an env var.
  4. Run the live UAT smoke script yourself (Claude writes it, you run it). It prints only status codes, field names and value types, never values.
  5. Rotation. Production gets different secrets, installed the same way. Rotate UAT secrets after UAT ends and whenever someone who held them leaves.
  6. Hygiene. Add a secret scan (gitleaks) to pre-commit, make logging redact PAN, otpRef, tokens, QR and encrypted blobs, and keep .env and secrets/ in .gitignore (confirm they already are).

Track C: with Claude, safely (yes, this is possible)

The split is simple. Claude never needs the real values because the whole integration can be proven against a local mock MFC server that uses throwaway keys Claude generates itself (random AES key, random IV, a fresh RSA pair). The crypto is deterministic and fully specified, so a mock proves our code matches the spec. Only "does MFC accept it" needs the real UAT, and a human runs that.
