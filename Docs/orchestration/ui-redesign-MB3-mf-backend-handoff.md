## What to build
1. `backend/app/services/analytics/schemas.py`: `PortfolioBenchmarkSummary.windows: list[BenchmarkWindowRow] = []` (last field) and `FundBenchmarkRow.windows: list[FundWindowXirr] = []` (last field). Defaults mean old payloads validate and old clients ignore the key. Touch nothing else in that file.
2. `backend/app/services/analytics/benchmark.py` (add `logger = logging.getLogger(__name__)` and the new imports; do not alter any existing helper):
   - A private helper `async def _window_inputs(db, member_ids, transactions) -> tuple[WindowContext, dict[BenchmarkIndex, IndexLevels]]` used by both computations, so each computation builds its context once:
     - `today = date.today()` (read once, passed down).
     - `ctx = await build_window_context(db, member_ids, today)`.
     - `earliest = min([t.date for t in transactions] + [s for s in ctx.starts.values() if s is not None])`.
     - **Top up the four new indices' stored history**: for `index` in `ALL_BENCHMARK_INDICES` that is **not** in `LEGACY_BENCHMARK_INDICES`, `await ensure_index_history_fresh(db, index, earliest, today, return_type=BenchmarkReturnType.TRI)` and ignore the boolean result (a failure just leaves that index's columns `None`; the legacy four are already topped up by the existing code and the daily job fills the rest).
     - `levels = load_index_levels(db, ALL_BENCHMARK_INDICES, earliest, today)`.
   - `compute_portfolio_vs_benchmarks`: **after** the legacy rows are built and exactly as before, `windows = []`; inside `try:` call `_window_inputs(db, household_member_ids, transactions)` then `compute_window_rows(ctx, transactions, current_value, levels)`; `except Exception: logger.warning(..., exc_info=True)` leaving `windows = []`. Pass `windows=windows` to `PortfolioBenchmarkSummary`. The empty-household early return keeps returning `windows=[]` (the default). `current_value` is the existing `sum(_current_value_by_scheme(holdings).values())` already computed in that function.
   - `compute_fund_vs_benchmark`: build `_window_inputs(db, household_member_ids, <fund_level_transactions plus transactions, deduplicated by object identity or id>)` **once, before the per-fund loop**, inside the same kind of `try`; for each scheme call `compute_fund_window_rows(ctx, scheme_id, scheme_txns, current_value_by_scheme.get(str(scheme_id), Decimal("0")), index, levels)` (the same `index` the existing code already chose for that fund) and pass `windows=rows` to `FundBenchmarkRow`. If the inputs could not be built, every fund gets `windows=[]`; a failure inside one fund's window rows gives only that fund `windows=[]` (separate `try` per fund, with a warning that names the scheme id, not the name).
   - Nothing else in `benchmark.py` changes: not `_benchmark_xirr_for_transactions`, not `_benchmark_index_for_category`, not the aggregate wrappers.
3. `backend/scripts/measure_benchmark_matrix.py` (new), in the house style of `scripts/measure_fund_page_staging.py` and `measure_home_staging.py` (read both first; reuse their argument handling, statement counter and printing helpers by copying the pattern, not by importing from another script):
   `python scripts/measure_benchmark_matrix.py --user-id <uuid> [--runs 3]`. It reads the household's members (`list_household_members`), and for the **combined scope and each member scope** prints, per scope, over `--runs` runs (milliseconds and SQL statement counts; counts and timings only, no names or amounts): (a) `build_window_context`; (b) `load_index_levels` for all eight indices over the earliest needed range; (c) `compute_window_rows` plus every fund's `compute_fund_window_rows` (pure, time only); (d) the total of (a) to (c) as **"added by windows"**; (e) the existing `compute_portfolio_vs_benchmarks` and `compute_fund_vs_benchmark` end to end, warm. It prints a final line `GATE: PASS` when the largest scope's "added by windows" is under **3000 ms**, else `GATE: FAIL (<ms>)`, plus a reminder that the owner must also compare a full `run_analytics_recompute.py` run against the 15-minute stale ceiling. **Read-only:** it must abort if any statement other than SELECT is issued (copy how the other scripts enforce it); `get_snapshots` may rebuild stale snapshot rows, so run it only with fresh snapshots and say so in the script's docstring (if a write would happen, abort with a clear message, as the other scripts do). Do not run it (there is no staging access on this laptop); import-check it (`python -c "import runpy; runpy.run_path(...)"` is not needed: `python -m py_compile scripts/measure_benchmark_matrix.py` is enough) and unit-test only its pure helper(s) if you add any.

## Review Focus (for the gate)
Old payloads still validating and the legacy numbers byte-identical; the failure isolation (a failing window never fails the section, and one fund's failure never blanks the others); that the context and index levels are built **once per computation**, not per fund; the network top-up touching only the four new indices and TRI; that no existing helper or aggregate wrapper changed; and that the script is read-only and states its gate.

## Approaches considered and rejected
Storing the windows as a 16th section (`analytics_sections` keys are fixed by design, and the matrix belongs with the benchmark payloads that the frontend already reads together); sharing one window context between the portfolio and the fund computation through a module cache (the two computations are separate sections run one after the other; a cache would be a hidden cross-section coupling, so each builds its own, and the gate measures whether the doubled cost is acceptable; if it is not, the fix is a short-lived memo keyed by `(member ids, today)`, to be decided with the numbers); fetching all eight indices' PRICE history (nothing compares against price); making `build_window_context` write snapshots itself (it only calls the existing `get_snapshots`, which already rebuilds when stale).
