Found while planning: the name is never saved

The name step keeps the name only in the browser. It reaches the server at Upload, when your member record is created. Anyone who leaves and comes back after the name step loses it and ends up named "Me". This is an existing bug.

Fix: save the name as soon as it's entered (create your member record right then). /me reports it, so resume can check it.

ColumnHolds

Purposes (the lawyer confirms the list)

DocumentPurpose
T&Cservice_agreement
Privacyaccount_and_authentication: phone/email for login and OTP
Privacyportfolio_tracking_analytics: dashboards and analytics
PAN disclaimercas_pan_processing: read PANs, assign funds to family, block the same PAN on two accounts, keep the CAS 30 days

One tick writes one row per purpose. If a new document version changes a purpose, the old consent stops counting and the user is asked again.

Why the record holds up

  • Can't be edited. A database trigger rejects every UPDATE and DELETE. Changes are always new rows.
  • The server stamps it. The browser only says "I accepted version X". The server checks X is current and adds the time, fingerprint, IP and device itself.
  • Saved together. No account or upload exists without its consent rows.
  • Checked on the server. Hiding the checkbox in the browser gets a 422.
  • Easy to pull. scripts/consent_trail.py --user … prints the full history for a lawyer.

What I changed after the external review

  • User ID: it's no longer a foreign key. Otherwise account deletion would try to edit consent rows, the no-edits rule would block it, and the deletion would fail.
  • IP: stored shortened plus a keyed hash, never in full.
  • Given/withdrawn: added. Withdrawing adds a row.
  • Purpose: added, with Unifolio's real purposes in place of the review's credit-check examples.

Build order and how each step gets checked

  1. F · OTP email

    A single template edit plus tests. Delegated, with a normal review.

  2. A · Remove the privacy screen

    Includes saving the name at the name step and the resume rule (first missing answer, else Upload), with a test for each branch. Delegated, with a normal review.

  3. C · "All of the above" + goals script

    Delegated, with a normal review.

  4. D + H · Name and PAN from the CAS

    Goes before E because the member form depends on it. I design the server checks myself, and it gets the adversarial review.

  5. B · Consent

    The riskiest piece. I design the table, trigger and transaction myself. Tests cover rejection on every sign-up and upload path, the trigger blocking edits, and rollback when either write fails. Full adversarial review.

  6. E · Profile

    Uses B (Terms of Service section) and H (read-only fields).

Testing: affected tests only

The full frontend and backend test suites are not run. Each step runs only the test files for the code it touches, plus its new tests. For example, F runs only test_email_templates.py. The Profile step runs only the four Profile test files and the member routes. The plan lists the exact files for every step, and the step's list grows if the change reaches further. Never the whole suite. A quick type-check still runs per frontend step. The Postgres-only tests run only for the name/PAN and consent steps, where database constraints and the no-edits trigger are what's being tested.

After the build: update database.md, backend.md, decisions.md, the PRDs, session.md and log.md. Nothing gets committed; you commit. One housekeeping note: migration number 0021 is already reserved for dropping the old goal column, so whichever ships first takes it.
