## Decided approach (orchestrator; exact)
1. **A faster solver for the new numbers only.** New module `backend/app/services/analytics/xirr_fast.py` with `def xirr_fast(cash_flows: list[tuple[date, Decimal]], guess: Decimal = Decimal("0.1")) -> Decimal | None`. **Same contract and same `None` conditions as `app/services/analytics/xirr.py::xirr`** (read it first and mirror every early return: fewer than two flows; no outflow or no inflow; `base <= 0`; `f_prime == 0`; no convergence within 100 iterations; `Overflow`, `InvalidOperation`, `DivisionByZero`), same Newton update, same tolerance `Decimal("0.0000001")`, same year fraction (`Decimal((d - start_date).days) / Decimal(365)`, `start_date` the earliest date). Differences allowed, and only these: (a) run the whole solve inside `decimal.localcontext()` with `prec = 18` (the tolerance is 1e-7, so 18 significant digits is ample; document that in a comment); (b) per iteration compute `ln_base = base.ln()` **once** and each flow's discount as `(years * ln_base).exp()` instead of `base ** years`, and reuse it for the derivative term (`base ** (years + 1)` is `discount * base`), so each flow costs one `exp` instead of two powers. The legacy `xirr()` and every caller of it stay untouched.
2. **Reuse the numbers the legacy code already computes for the since-inception row.** `compute_portfolio_vs_benchmarks` already solves the portfolio since-inception rate and the four legacy indices' rates (and `compute_fund_vs_benchmark` the fund and benchmark rate per fund); the engine currently solves them all again. Add an **optional** parameter so the production path passes them in and the engine does not re-solve them:
   - In `benchmark_windows.py`: `@dataclass(frozen=True) class SinceInceptionRates: portfolio: Decimal | None; indices: Mapping[BenchmarkIndex, Decimal | None]` and `compute_window_rows(ctx, transactions, current_value, levels, since_inception: SinceInceptionRates | None = None)`. When given, the `SI` row's `portfolio_xirr` is `_xirr_str(since_inception.portfolio)` and each index listed in `since_inception.indices` uses `_xirr_str(<that rate>)` with **no solve**; any index not listed (the four new ones) is solved with `xirr_fast`. When `since_inception is None` (standalone use, and the existing tests), the `SI` row behaves **exactly as today** (the legacy `xirr` path, digit for digit equal to the legacy numbers). For funds: `compute_fund_window_rows(..., since_inception: tuple[Decimal | None, Decimal | None] | None = None)` meaning `(fund_rate, benchmark_rate)`, used the same way.
   - In `benchmark.py`: keep the raw `Decimal` rates while building the legacy rows (`portfolio_xirr`, and `rate` per legacy index in the existing loop; `fund_rate` and `benchmark_rate` per fund) and pass them as `since_inception=...` to the engine calls. Do not change any legacy computation or value.
3. **The 1Y, 3Y and 5Y windows (portfolio, all eight indices, every fund) use `xirr_fast`.** The `SI` solves that remain use `xirr_fast` for the four new indices and the legacy `xirr` only in the standalone case above.
4. Nothing else: no new table, no stored-payload change, no change to `xirr.py`, `dashboard/xirr.py`, or any existing function's result.

## Approaches considered and rejected
Changing `xirr()` itself to be faster (every legacy number would shift in its far digits, breaking "existing numbers unchanged" and any stored-payload comparison); a float solver (the repository rule is `Decimal`, never `float`, for rates); computing the windows lazily when the tab is opened (a stored payload is the design: the frontend reads the stored benchmark section, and an on-request compute would put seconds of CPU on a page load); aggregating a household's flows by month before solving (approximates the rate); dropping the windows for the four new indices (the matrix design needs all eight).
