What changes, where, and how the data moves

Every file, table and job this fix touches, with the flow and the database before and after. Analytics becomes read-only and finishes in seconds instead of 30+ minutes. Total Invested starts including stamp duty, so it equals the CAS. Scope is as decided on 7 October: fixes A, B, C, D and F plus stamp duty; E is documented but not built.

The change in six lines

No TER refresh in AnalyticsAnalytics never runs the TER refresh, and peer NAVs are prepared by the morning job. It still makes its small existing calls (benchmark index, AMFI list, held funds’ NAV), kept on purpose for now (decided 7 Oct).
TER is linked, never guessedEach fund is linked once to SEBI’s scheme code in AMFI’s TER feed by an exact name, and every month joins by that code. No fuzzy matching, which on 8 Oct gave ~1,040 funds another fund’s TER. The job takes seconds.
TER refreshes daily06:20 IST, after the fund-list job. The monthly run on the 1st was getting the previous month’s figures.
Peers are fetched by the NAV jobThe 06:00 NAV job also refreshes the other funds in every held fund’s category, so ranking and scoring never wait on mfapi.in.
Stamp duty is keptThe parser stops discarding the stamp-duty row and stores it on its purchase. One new column, transactions.stamp_duty.
Nothing changes on screenSame pages, same layouts. Analytics loads quicker, and Total Invested, gains and XIRR use the full amount paid.

Read first

Things this map takes a position on, including two small additions found while mapping the files.

Decided 7 Oct: deferredAnalytics makes two more network calls than the speed page listed

The benchmark section refreshes NSE index history itself (ensure_index_history_fresh in benchmark.py, about 5 s locally), although the 06:00 benchmark-daily job already does that. Ranking and scoring load each category’s peer list by downloading AMFI’s 1.6 MB fund list (get_category_universe), although the 06:15 fund-list job already saves the same list in schemes. Decision: leave the AMFI list as it is; fix the NSE call’s freshness check now (8 Oct). Measured 8 Oct: the AMFI download is 0.3 s per run, but NSE took 127 s over 32 downloads. Changing them safely needs four coordinated changes (see Inputs check), kept for later.

Found 8 OctFuzzy TER matching gave ~1,040 funds another fund’s TER, live on staging today

Run 1’s comparison on real data showed every fuzzy match was wrong. 923 funds were matched to a different fund house (Kotak Business Cycle → Tata Business Cycle, HDFC Ultra Short Term → HSBC), because AMFI fills each month gradually and on 8 Oct HDFC, Kotak and Nippon hadn’t filed October (11,647 rows against September’s 62,393). About 116 more matched the wrong year or series within one house (Bandhan Gilt April 2026 → April 2028 at 0.81; SBI FMP Series 50 → 51). Exact names cover 7,041 funds correctly. Decision (8 Oct): link each fund to SEBI’s scheme code (NSDLSchemeCode, in every TER row, one per fund) by an exact name ignoring case, spaces and punctuation; store it on schemes; join by code; never fuzzy. An unlinked fund gets no TER and appears under the existing “TER Exclusions” list. The deploy clears the wrong TERs saved on 7 Oct.

No frontend changeE and the “still calculating” message were dropped

With those out, nothing in frontend/ changes. The TER card already shows coverage as “₹x / ₹y”, which handles funds with no TER.

Saved sessionsReviews open during the deploy keep working

Upload previews are saved encrypted between upload and Continue (migration 0029). The saver handles any field generically, and the new stamp_duty field defaults to empty, so a preview saved before the deploy still opens after it. It just has no stamp duty, like any old import.

Staging wipeData uploaded before the deploy has no stamp duty

The parser threw those rows away, and re-uploading the same statement is refused as already imported. So staging is wiped after the deploy, user data only (clean-staging-db.sh), and statements are uploaded again. TERs, the fund list and NAV history stay.

Why a run can take hours today: the “refresh at most once per 15 minutes” guard counts from when a refresh starts. On AWS a refresh lasts 30+ minutes, so by the time the TER section finishes, the next section that checks TER is allowed to refresh again. After the change there is no refresh to repeat.

MigrationsDetail
0031: schemes.ter_scheme_code, ter_link_source, ter_linked_atThree nullable columns plus an index on the code. Filled by the TER job (exact_name) or by hand later (manual, never replaced by the job). No backfill: the first run after the deploy links about 7,000 funds.
0032: transactions.stamp_dutyNumeric(14, 2), nullable, no default. Set on purchase rows (lump sum, SIP, switch-in) from 1 July 2020 when the CAS prints a stamp duty. NULL everywhere else, including every row imported before this deploy.
Postgres (staging)transactions is partitioned by date. ALTER TABLE transactions ADD COLUMN on the parent adds it to every partition. A nullable column with no default needs no table rewrite, so it is instant.
SQLite (local)Plain ADD COLUMN in batch mode, like 0027–0029.
Indexes, enums, backfillNone. Old rows stay NULL; staging is wiped and re-uploaded instead.
DowngradeEach drops its columns. Tested 0030 ↔ 0032 on local Postgres, as for every migration.

Why 06:20, and why this order

The answers to “why these times” and “will they really run then”, from the scheduler’s Terraform settings and the job logs on staging.

Why the TER job runs at 06:20

ConstraintWhat it means for the TER job
After the 06:15 fund-list jobThe TER match uses each scheme’s name and plan from schemes, which the 06:15 job refreshes. Running after it means a fund AMFI added yesterday gets its TER the same morning. That job takes 1–3 minutes, so 06:20 leaves a few minutes’ margin.
Before the 06:30 daily Analytics runThe daily recompute then uses that morning’s TERs. After the fix the TER job takes seconds, so it’s long finished by 06:30.
Inside the hours staging is onStaging is off from 21:00 to about 05:00 (database 04:45, NAT 04:50, backend 04:58). Anything earlier than about 05:15 risks finding the database still starting.
Why not 06:00 with the othersThe fund list isn’t refreshed yet at 06:00, so new funds would wait a day for their TER.

Why the whole morning runs in this order

  • Data first, results last. NAVs, index values, the fund list and TERs are all inputs. Analytics is built from them, so it runs last. Each job only needs the ones before it.
  • 06:00 for the inputs. Fund houses must publish each day’s NAV by 11 PM, and mfapi.in and NSE have it overnight. 06:00 is an hour after staging wakes up, so the database and the NAT instance are fully up. I found no written reason for the exact 06:00 in the docs (the August job plan just says “6 AM IST”), but this is what that time achieves.
  • 15–30 minute gaps leave room for each job to finish before the next one needs its output, with margin for a slow day.
  • Before people use it. Everything is ready by about 06:35, before the working day.

Will the jobs really run at those times?

Start timeYes, each job starts at its minute

The schedules use flexible_time_window = OFF in infra/modules/scheduler/main.tf, so AWS starts each one at the exact minute, Asia/Kolkata time, not somewhere in a window. Staging confirms it: the 1 Oct TER run was scheduled for 06:00 and its log ends at 06:07:12. The container itself takes about 30–90 seconds to start (it pulls the image), so work begins a minute or so after the scheduled time.

OrderThe order is by clock, not enforced

Each schedule is independent. The 06:15 job doesn’t wait for the 06:00 jobs, and 06:20 doesn’t wait for 06:15. If a job runs long, the next one starts anyway and uses the previous day’s data for that input. Nothing breaks: a late fund list means TER matches against yesterday’s list, and a late NAV job means Analytics uses yesterday’s peer NAVs. Tomorrow’s run catches up. The gaps are sized so this should be rare.

FailuresA failed job isn’t retried until its next run

AWS retries only if it fails to start the container. If the job starts and then fails (AMFI down, for example), nothing retries it. It runs again the next day. Under a monthly TER schedule that would mean a month’s wait, which is another reason daily is better. The success= log line and the TargetErrorCount check from 7 Oct show whether a run worked.

Possible laterA strict order would need one chained job

If the order ever matters more, the four morning jobs could run as one task, one after another, so each starts only when the previous finishes. That’s a bigger change than this fix needs, so it isn’t proposed now.
