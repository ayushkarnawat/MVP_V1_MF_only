QUESTION 1

Why is it so slow, and what did we change?

When you open Analytics, AWS starts a background task that works out all seven sections of the page. I timed each one:

Bars share one scale (0–205 s). The second pass, for the member’s own view, took about 5 s because everything was cached by then. Staging runs on half a CPU, so the CPU-heavy TER step is several times slower there.

How the TER refresh got this slow

Aug 2026 · original design
The schemes table held only the funds users actually owned, a few hundred rows. The TER refresh went through those and compared each fund’s name with AMFI’s TER list using a fuzzy text match. A few hundred fuzzy matches was fast enough.
6 Oct · CAS fixes, Phase 5
A new daily job loads AMFI’s full fund list (14,356 schemes) into schemes, so fund identification can use AMFI’s own data. That broke TER for held funds: the new rows don’t have the old plan field the refresh selected on, so no held fund got a TER. The Phase 5 reviewer caught this and logged it as item 13 on the list of problems for the next phase to fix (the “carry-over” list in Docs/orchestration/cas-import-fixes-handoff.md).
6 Oct · CAS fixes, Phase 6 Task 7
The fix selects funds by the new plan_type field instead. That now matches about 8,661 Direct/Regular schemes, every one in the master, not just the held ones. The plan said “match by exact name within the AMC”. What was built checks the exact name against all 1,813 rows of AMFI’s TER list and cleans up every one of those 1,813 names again for each scheme. Then it falls back to the old fuzzy match, which compares against all 1,813 rows again. Each scheme is also saved with its own database lookup.
7 Oct · staging
The monthly TER job took 30+ minutes. The same refresh also runs inside Analytics, as question 3 explains.

So, plainly: the slow part is that ~8,661 schemes are each compared, in plain text, with 1,813 AMFI names. Locally one fuzzy match takes about 52 ms, which adds up to 205 s. On staging’s half-CPU machine it’s 30+ minutes. Each step was a reasonable fix on its own, but nobody timed the combination against the full fund list, and our test runs don’t measure Analytics time. That gap in our checks is ours to close.

The second slow step: peer NAV history

Category ranking and the quality score compare each of your funds with every other fund in its SEBI category. To do that they download each peer’s full NAV history from mfapi.in: 6 categories, around 30–150 funds each. The daily NAV job only refreshes funds that someone holds, and a downloaded history counts as fresh for 3 days. So the first Analytics run after 3 days, for anyone, downloads whole categories again in the middle of the run. This was already true before this release; nothing in this week’s changes caused it.

Why the AMFI address changed, and what the Analytics task costs on AWS

portal.amfiindia.com

QUESTION 3

Why Analytics refreshes TER itself, and how we take that out

The TER section, the Direct vs Regular section and the quality score each first check whether every fund involved has a TER row for the current month. If any fund lacks one, they run the full refresh before carrying on. This dates from August, when Analytics was computed while you waited on the page and there was no guarantee the monthly TER job had run. It was a safety net: “if this month’s TER is missing, go and get it”. Analytics has since moved to a background task, and the monthly TER job runs on its own schedule, so the safety net now costs far more than it protects.

How we remove it, step by step

  1. Take the refresh out of Analytics. Delete the three refresh calls: two in backend/app/services/analytics/ter.py, one in scorer.py. Analytics only reads TER rows already in the database. A fund with no TER row shows as “TER not published yet” in coverage, which the page already supports.
  2. Make the TER job fast (question 5 has the details) so it can run daily at 06:20 IST, after the 06:15 fund-list job and before the 06:30 daily Analytics run. Then a new fund or a changed TER is picked up within a day, with no Analytics run ever waiting for it. Running it daily needs one Terraform schedule change, which you or your manager apply.
  3. Count only funds that can have a TER. Funds with no AMFI code (CAS-only, unlisted, closed) are left out of the “missing” check and shown as “not available for this fund”, so they can never make anything look stale again.
  4. Test it: a test that fails if any Analytics section runs the TER refresh (the small existing calls stay for now, decided 7 Oct). A timing check in the harness: Analytics for p20_20yr must finish in under 30 s locally.

QUESTION 5

Why the refresh runs again even though the TER job just ran

  1. Before refreshing, Analytics asks: “does every fund here have a TER row for October?” Funds the refresh has checked get a row even when no TER matched, a “checked, nothing found” marker, so they count as covered.
  2. But the refresh only looks at funds with a known Direct/Regular plan in AMFI’s master. Funds outside that set get no row at all: funds that exist only in a CAS (old plans like the pre-2013 “HDFC Liquid Fund – Growth”), funds unlisted on AMFI, and closed funds. They are never checked, so they never get a row.
  3. So for any portfolio holding one of those funds, the answer is always “no, something’s missing”, and the full 8,661-scheme refresh runs again. That happens on every Analytics run, for every such household, forever. The p20 statement has funds like this, and many real long-history statements will too.
  4. There is a guard meant to stop repeats: “don’t refresh again within 15 minutes”. But it lives in the running program’s memory, and every Analytics run on AWS is a new container. Each one starts with an empty memory and refreshes again. The guard only ever worked when Analytics ran inside the web server, as it did in August.

Running the monthly job doesn’t help, and a new account hits this too. The quality score checks TER for every peer fund in each held fund’s category, not just your own funds. 5,695 of AMFI’s 14,356 funds have no readable Direct/Regular plan (older plans, ETFs, fixed-maturity plans), so the refresh never gives them a row. They sit in the categories almost everyone holds: Large Cap 14 of 110, Mid Cap 4 of 81, Small Cap 5 of 47, Index Funds 25 of 1,058, Liquid 85 of 301. So anyone holding one of those triggers the refresh.

It can repeat within one run. The guard only blocks a refresh within 15 minutes of the last one started. On staging one refresh takes 30+ minutes, so the next section that checks TER (Direct vs Regular, the score for each category, then the person’s own view) starts another. One Analytics run can do the refresh several times, which could mean hours (not measured on staging). After 2 hours the page assumes the run crashed and starts a second one. Locally a refresh is 205 s, so it ran only once.

None of this was intended. The missing check, the guard and the refresh were each written for an earlier setup: computed on the page, a small schemes table, every fund having a plan. Once those three changed, the pieces no longer fit, and no test runs Analytics against the full fund list or with a CAS-only fund. Steps 1 and 3 in question 3 remove the cause. The fast TER job below removes the cost if it ever runs anyway.

Making the TER job itself fast, and right (revised 8 Oct)

Found while building (8 Oct): fuzzy name matching isn’t just slow, it’s wrong. On real data 923 funds were matched to a different fund house (Kotak Business Cycle Fund got Tata Business Cycle Fund’s TER), because AMFI fills each month gradually and HDFC, Kotak and Nippon hadn’t filed October yet. About 116 more got the wrong year or series from their own house (“Gilt April 2026” → “April 2028”). Those wrong TERs are on staging now, from the 7 Oct run.

  1. Link each fund once to SEBI’s scheme code. Every row in AMFI’s TER feed carries one (NSDLSchemeCode, one per fund, shared by Direct and Regular). A fund is linked when its name equals a TER row’s name, ignoring case, spaces and punctuation. That covers 7,041 funds today. The link is stored on schemes (migration 0031).
  2. Every month joins by code, so a fund keeps its TER even if AMFI renames it.
  3. No fuzzy matching at all. A fund that isn’t linked gets no TER that month and shows under the existing “TER Exclusions” list. Most of these are fund houses that haven’t filed yet; they link the morning after they do.
  4. Save in bulk: one query to load the month’s rows, one batch to write.
  5. Result: the job’s matching takes a fraction of a second (was 205 s locally, 30+ min on staging), and no fund ever shows another fund’s TER. A script to link the few remaining funds by hand is deferred until we see how many stay unlinked after every house has filed.

OTHER ANALYTICS ISSUES FOUND

Other Analytics issues

  1. The quick sections wait behind the slow ones. Analytics is computed for the whole family view first, all seven sections including the 30-minute ones, and only then for each person. You were looking at one person’s view, so even its instant Allocation section waited the full run. That’s why your screenshot showed every section as a placeholder. not fixing (decided 7 Oct) Computing everything together was a deliberate earlier change, and once runs take seconds the wait is short anyway.
  2. No “still working” message. The page shows grey placeholders with no explanation however long it takes. not fixing (decided 7 Oct) Not needed once runs take seconds.
  3. Peer NAV histories go stale after 3 days and are downloaded again mid-run (question 1). fixing with D.
  4. Our tests never time Analytics. The 88/88 synthetic gate and the real-file runs check numbers, not speed. That’s how this slipped through. fixing with F.
  5. The stuck-run timeout is 2 hours. If an Analytics container crashes, the page keeps showing placeholders for up to 2 hours before a new run can start. Once runs take seconds, this can safely drop to 15 minutes, a one-line change in recompute.py. fixing
PROPOSED FIX · STAMP DUTY

Stamp duty in Total Invested

A correction to what I told you earlier. I said we read the stamp-duty rows from the CAS and store them. That was wrong. The parser drops them at upload: they carry no units, and parser.py skips “tax rows with no units” on purpose (_SILENT_TAX_TYPES). So the ₹0.25-type amounts never reach the database at all. The fix has to start at the parser.

What happens today

A ₹5,000 SIP after 1 July 2020 shows in the CAS as a purchase of ₹4,999.75 and a separate “*** Stamp Duty ***” row of ₹0.25. The CAS’s cost column counts the full ₹5,000. We count only the ₹4,999.75 (units × NAV) and throw the ₹0.25 away. On the “CAS 10 Yr” statement that adds up to ₹186 across 13 funds: exactly 0.005% of each fund’s cost.

The fix, step by step

  1. Parser: attach each stamp-duty row to the purchase it belongs to (same fund, same date). If one day has several purchases, match each stamp duty to the purchase it is 0.005% of. A new stamp_duty field goes on the purchase. Rows before 1 July 2020 have none.
  2. Database: one nullable column, transactions.stamp_duty (migration 0032; 0031 is the TER link). Postgres adds it to every partition of the partitioned table in one statement. Nothing else changes shape.
  3. Cost: each purchase’s cost becomes amount + stamp duty, set once in the holdings cost calculation (dashboard/holdings.py). Everything built on it follows automatically: invested, average NAV, unrealised and realised gain (a sold unit carries its share of the stamp duty).
  4. Cash flows: the money paid out becomes amount + stamp duty in XIRR (dashboard/xirr.py), in the Analytics benchmark (analytics/benchmark.py), and in monthly history’s invested line (dashboard/snapshots.py). Total Invested and XIRR then use the same rupees.
  5. No double counting: opening balances already use the CAS cost, which includes stamp duty, so they stay as they are.
  6. Tests and gate: unit tests for the parser matching, plus a new gate check that Total Invested equals the CAS cost to the rupee for every fund, on all synthetic files (they include stamp duty) and the real files. Our gate never checked invested against the CAS cost, which is why this slipped through.

What it means for data already uploaded: rows imported before the fix have no stamp duty stored, and uploading the same statement again is refused as “already imported”. So staging needs a wipe (scripts/clean-staging-db.sh) and fresh uploads after this deploy. Production has no users yet, so nothing else is affected.

Visible effect: on “CAS 10 Yr”, Total Invested goes from ₹37,22,451 to ₹37,22,637, the same as the CAS. Unrealised gain drops by the same ₹186, and XIRR moves by a few hundredths of a percent. No frontend change.

A normal morning, in order

  1. 04:45–05:00 staging wakes up: database, then NAT, then backend.
  2. 06:00 today’s NAVs and benchmark values come in, now including peer funds (fix D).
  3. 06:15 AMFI’s fund list is refreshed.
  4. 06:20 (if daily) TERs are refreshed against that fresh list, in seconds.
  5. 06:30 every household’s Analytics is recomputed from the saved data, with no downloads, so it’s ready before anyone opens the app. If the 06:00 NAV job is still running, Analytics uses the previous day’s peer NAVs. That’s harmless, and the next run catches up.
  6. During the day imports trigger single-household recomputes, now under a minute.
  7. 21:00–21:10 staging shuts down for the night. No job is scheduled inside the night window.
