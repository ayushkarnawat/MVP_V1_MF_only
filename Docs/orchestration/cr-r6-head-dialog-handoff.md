## What exists on the server (Run 5, reviewed)
All under `/auth/head-change/`, bearer session, errors are the HTTP status plus `detail: {code, message}`. A pending-deletion account gets 403 `account_pending_deletion` on every one of them.
- `GET eligibility` -> `{members: [{member_id, reasons: []}]}` for every NON-head member. Reasons are only own-data ones: `no_email`, `no_phone`, `no_pan`, `label_missing` (this now also means the label is "other"; only spouse, parent, child or sibling work), `same_email_as_head`, `same_phone_as_head`, `head_change_already_open`, `import_in_progress`, `account_pending_deletion`. An account with no head answers 409 `{code, message}`. The 7-day rule is NOT in this list.
- `POST start-code` `{to_member_id}` -> `{message, otp: string | null}`: emails a code to the head's own email (the code is only good for that member). Errors: member reasons above as `member_not_eligible` / `contact_same_as_head` / `import_in_progress` / `head_change_already_open`, `current_email_missing`, `otp_throttled` (429), `email_send_failed` (502), `head_change_too_soon` (409, with the date in the message), `member_not_found` (404).
- `POST start` `{to_member_id, current_head_code}` -> `{request: <status>, codes: [{party: "current"|"new", channel: "email"|"phone", verified: boolean, otp: string | null}]}` (4 entries; the current head's email is already verified with `otp` null). Errors: `wrong_code` 401, `code_locked` 401, `code_expired` 410, plus the member errors above and `contact_in_use`, `pan_registered_elsewhere`, `phone_in_use`, `email_in_use`.
- `POST verify` `{request_id, party, channel, code}` -> `<status>`. `POST resend` `{request_id, party, channel}` -> `{request: <status>, code: {party, channel, verified, otp}}` (`otp_throttled` 429). `POST cancel` `{}` -> `<status>` with `status: "cancelled"`. `GET pending` -> `{request: <status> | null}`.
- `<status>` = `{request_id, status: "pending"|"ready"|"cancelled"|"expired", expires_in_seconds, verified_count, ready, current_email_verified, current_phone_verified, new_email_verified, new_phone_verified}`.
- `POST complete` `{request_id}` -> `{status: "completed", logout_required: true}`. After it the caller's session no longer exists. Errors: `request_not_found` 404, `request_expired` 410, `request_not_ready` 409 ("Enter all four codes before confirming the change."), `request_changed` 409, and the member and contact errors.
- `POST undo` `{token}` (NO session) -> `{status: "undone"}`. Errors: `undo_not_found` 404 ("This undo link is not valid."), `undo_expired` 410 ("The 24-hour undo window has closed."), `undo_contact_taken` 409, `request_changed` 409, `account_pending_deletion` 403. The link in the previous head's email is `{FRONTEND_BASE_URL}/undo-head-change#token=<token>` (the token is in the URL **fragment**).
- `GET /auth/me` has `head_member_id: string | null` (the current head's member id) and `head_change_pending: <status> | null`.
- **Server rules added after the Run 5 gate (the front end only needs to show the messages):** (a) while the 24-hour undo window of a change is open, `POST /auth/account-deletion` answers 409 with a plain string `detail` ("The Head of Family was changed in the last 24 hours. You can delete this account after the undo window closes on ..."); the existing deletion screen already shows a string `detail`, so do not add UI, but list in the report what it shows. (b) After a swap or an undo the sign-up consents are withdrawn and every DATA route (home, dashboard, imports, portfolio, funds, analytics, scenarios, news) answers 403 `{code: "reconsent_required", message: "Please review and agree to the Terms to continue."}` until the person agrees through the re-consent screen (`POST /legal/consents`); `/auth/me`, `/legal/*` and the rest of `/auth` stay reachable. `/auth/me.consent_outdated_reason` is `"head_change"` in exactly that state. (c) A sign-in that races a swap is refused with 401 "This sign-in is no longer valid. Please sign in again."; show that message as any 401 on the sign-in screens is shown today.
- Removing a member who took part in a change in the last 7 days answers 409 `{code: "member_in_recent_head_change", message}` from the member-removal route; show the message where that removal is triggered **only if** the existing removal UI already shows a server message for a failed removal (do not add UI for it; list it in the report if the existing UI would show something wrong).

## T6.0 Backend: the preview route (small, do this first)
**Files:** modify `backend/app/services/auth/head_change.py` (add `preview_head_change`), `backend/app/api/auth.py` (the route), `backend/app/services/auth/schemas.py`. Tests: add to `backend/tests/services/auth/test_head_change_flow.py` and `backend/tests/api/test_head_change_routes.py`. Do not touch any other backend file.
1. **`GET /auth/head-change/preview?request_id=<uuid>`** (same active-user dependency and `{code, message}` 403 as the other head-change routes). A request of the caller's own account in status `pending` only; an unknown, foreign, expired or non-pending id answers the same 404 `request_not_found` ("Head change request not found."). It never writes anything and sends nothing. It computes exactly what `complete_head_change` would do to the labels, using the same `flip_labels(...)` call with the same inputs (read how `complete_head_change` builds `label_plan`; do not copy-paste a second version of the rules: extract one small shared helper that both call, and keep `complete_head_change`'s behaviour byte-identical, its tests must still pass). Response:
   ```json
   {
     "request_id": "...",
     "old_head": {"member_id": "...", "name": "..."},
     "new_head": {"member_id": "...", "name": "...", "email": "...", "phone_number": "..."},
     "old_head_new_label": "spouse",
     "members": [
       {"member_id": "...", "name": "...", "label_before": "parent", "label_before_other": null,
        "label_after": "other", "label_after_other": "parent-in-law", "review_recommended": false, "cleared": false}
     ],
     "everyone_signed_out": true
   }
   ```
   `members` lists every member EXCEPT the old head, including the new head (before: their label; after: `"self"`). `label_*` are the relationship values as strings or null; `cleared` is true when the member had free-text "other" wording that the change removes. `old_head_new_label` is what the old head becomes. `everyone_signed_out` is always true.
2. **Already done by the orchestrator (do not build it):** `/auth/me` has `consent_outdated_reason: "head_change" | null` (see `app/services/auth/head_change_consent.py` and its tests in `tests/api/test_head_change_consent.py`). Use it as the contract describes below; do not edit those files.

- **Shows an explanation and a button; it does NOT call the server when the page loads** (email security scanners open links, and a page that undoes on open would let a scanner reverse the change): "The Head of Family on your Unifolio account was changed. Errors show the server `message` (404 `undo_not_found`, 410 `undo_expired`, 409 `undo_contact_taken`, 409 `request_changed`, 403 `account_pending_deletion`); the button stays disabled after a success and after a 404 or 410, and is enabled again after any other error so the person can retry.
