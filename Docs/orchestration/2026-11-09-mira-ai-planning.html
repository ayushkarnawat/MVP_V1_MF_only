What Mira is (owner's words)

A back-and-forth conversation, "as if the user is having a personal assistant". It answers about the user's portfolio and about anything financial. It can also reason about funds the user does not hold. Anything outside finance gets a polite "this is not in my domain".

What is settled (provisionally)

M1: Mira states facts and does not give advice, because Unifolio does not have the certificate yet. M2: Finance in general is in scope. Portfolio questions use the user's data and say "insufficient data" when it is missing. General questions are answered without the portfolio.

What the reviewer should decide first

O1 where the AI runs (it changes the privacy position and cost). O6 legal wording and sign-off for the no-advice rule. O2 and O3 on general-answer sources and chat history. The rest can follow.

Claude's headline view proposal

Do not train a model. Use a hosted model with a strict system prompt, give it read-only access to Unifolio's existing calculations, and put the effort into guardrails and a test set of questions. Section 4 explains why.

"Training" Mira: what, where, and whether

The owner asked how to train Mira and where. This is Claude's view of the question. Claude's proposal Not agreed.

Mira does not need a model trained for it. The things the owner wants (answer from the user's own numbers, stay in finance, never advise) are better done by controlling what the model is shown and what it is allowed to say. Three approaches, compared:

ApproachWhat it meansFits Mira?
A. Use a hosted model, no trainingCall a general model through an API. A system prompt sets Mira's role, tone, scope and no-advice rule. Tools give it the user's numbers at question time.Recommended. Portfolio numbers change daily and are private, so they must be fetched live. They cannot be "taught" to a model. Quality improves by editing the prompt, the tools and the test set, not by retraining.
B. Fine-tune a modelTrain a model further on example conversations so it adopts Unifolio's style and refusals.Not now. It needs hundreds to thousands of reviewed example conversations that do not exist yet. It freezes knowledge (tax rules, SEBI categories change). It does not give live numbers. It could be revisited if tone or refusals stay weak after A.
C. Train or host your own modelRun an open-weight model on your own infrastructure.Only if O1 decides data cannot leave Unifolio's servers. It needs GPU hosting, which the current single-VM and AWS plans do not include, and answer quality would likely be lower. Treat as a fallback depending on O1.

What replaces training: four things to build and improve

  1. System prompt: Mira's role, finance-only scope, the no-advice rule, refusal wording, how to say "insufficient data".
  2. Tools: read-only functions over existing services (portfolio summary, fund details, returns, risk, overlap, scenarios). The model asks for a number; Unifolio computes it with Decimal; the model only phrases it.
  3. Curated content: approved explanations (for example the 37 SEBI category definitions already planned for Explore). Whether to rely on it is open question O2.
  4. An evaluation set: a fixed list of test questions (in-domain, out-of-domain, "should I switch" traps, missing-data cases, prompt-injection attempts) that is re-run on every prompt or model change. This is how "training" quality is measured. It is the most valuable thing to build first.

Where does it run? If A, nothing is trained anywhere. The model runs at the provider (O1). The evaluation set runs in CI and on staging. This is why O1 comes first.

Proposed architecture

Claude's proposal A sketch to react to, not a design. It follows the existing rules: one FastAPI monolith, Decimal not float, get_current_user as the boundary, no new framework.

Design points worth the reviewer's attention

  • Numbers come from tools, not from the model. Money, units and NAV are Decimal everywhere in this codebase. The output check should reject any figure in a reply that did not come back from a tool.
  • User scoping lives in the tools, not the prompt. A tool receives the user and member ids from the authenticated session. The model is never trusted to choose whose data to read.
  • Family view: the app has "Family Combined" and per-member views. Mira has to know which one the user is looking at, and must not reveal a member's data the user is not allowed to see. Needs a rule (part of O9).
  • Prompt injection: text from outside (fund names, news headlines, uploaded data) can contain instructions. Tool results must be treated as data, never as instructions.
  • Fallback: if the model is down or slow, Mira says so and the existing rule-based Home sentence and fund insights still work (O14).
  • No PAN, no raw CAS: already final project rules. Mira must never receive them and tools must not expose them.

Keeping Mira in its domain

Claude's proposal Decision M2 says finance is in, everything else gets "this is not in my domain". A prompt alone is not enough; here are three layers.

Layer 1: cheap pre-filter

Obvious non-finance requests (write code, translate, recipes, politics) are refused before any model cost. Low cost, catches the common cases, will miss subtle ones.

Layer 2: system prompt and classifier

The model is told its scope and given examples of in and out. Borderline cases (a "Python question" about calculating SIP returns) need a rule: finance topic in, coding help out.

Layer 3: output check and test set

Replies are checked after generation, and the evaluation set holds off-topic and sneaky prompts ("ignore your rules", a finance question wrapped around a coding task). A failure blocks release.

The no-advice rule (M1)

Provisional: Mira states facts and does not give advice until the certificate is in place. The owner is working on the certificate.

Not a legal opinion. Claude is not a lawyer. The Explore compliance research found no SEBI text saying whether a formula-based ranked list is investment advice, and none saying it is not. A chat assistant is closer to "advice" than a table because users can ask it directly. A lawyer must set the line (O6).

What this means for design

  • Wording rules: no "best", "buy", "sell", "switch", "recommended", "you should" in replies. Same rule as Explore.
  • Facts can still steer. Choosing which facts to show, and in what order, can read as advice. Reply formats should be fixed (same facts, same order, for every fund) so Mira does not pick favourites.
  • A standard line when asked for a recommendation, for example: "I can show you how these funds compare on returns, cost and risk. Unifolio can't give investment advice, so the decision is yours or your advisor's." Exact text needs approval (O6).
  • Tested, not just prompted: a set of "should I..." questions must pass on every change. Any slip fails the build.
  • When the certificate arrives the rule can be relaxed in a later phase. The prompt, output check and tests should keep the rule as a setting so it can be changed without rebuilding.
