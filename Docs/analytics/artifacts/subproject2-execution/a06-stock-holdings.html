Overall stock holdings

Combines every fund's portfolio into one number per stock and shows the top 10, split by fund, with a searchable full list. The shared look-through table built here feeds the other four attributes. The formula

One table, five readers

client exposure(stock) = Σ over held funds ( fund weight × stock weight in that fund ) fund weight = fund value ÷ total MF value stock weight = % to NAV from the fund's newest WRITTEN batch ≤ NAV date Worked example (spec §3) Reliance 8% in a 40% fund, 6% in a 35% fund, 5% in a 25% fund 0.40×8 + 0.35×6 + 0.25×5 = 3.20 + 2.10 + 1.25 = 6.55% (not 8+6+5 = 19%) Grouped by ISIN. Rows with no ISIN (cash, CBLO, TREPS, net receivables) stay one row per fund, never merged.

Q17Decided

Does the stock table show only stocks?

The issue

The shared table keeps every holding that has an ISIN, including bonds, certificates of deposit and gold ETFs. Attribute 06 is called "overall stock holdings" and its top 10 would include any of those that rank high.

Why it matters

A conservative or hybrid portfolio could show a government bond or a deposit as its "top holding", which reads wrong under a stocks heading.

Options
  1. AAttribute 06 lists only domestic and international equity rows. A one-line summary underneath says how much sits in debt, gold and cash, linking to attribute 13.
  2. BList every instrument, with a type filter that defaults to All.
  3. CSame as B but the filter defaults to Equity.
Recommended

A. Matches the heading and the PDF's example. Debt detail lives in 13.

After your answer
  • StockHoldingsSection filters on asset_type; the shared table is unchanged.
Decided 2026-10-13

A confirmed. Equity-only table, debt/cash/derivative excluded at source, one-line summary linking to attribute 13 — in Task 2 of the consumer plan.

Q18Decided

How old can a fund's holdings be before we say so?

The issue

The spec takes each fund's newest WRITTEN batch at or before the NAV date, with no age limit, and shows the oldest date as "Holdings as on". Funds disclose monthly, but publication can lag by up to about 10 days, and a half-yearly AMC (Taurus) is up to six months old.

Why it matters

One 5-month-old fund quietly mixes with 9 fresh ones, and the label only shows the oldest date.

Options
  1. ANo limit; show the dates as the spec says.
  2. BPast 60 days, treat the fund as having no data and count it in the coverage notice.
  3. CKeep counting it, but tag it "older than 50 days" in the coverage notice and the drill-down.
Recommended

C. Nothing is dropped silently and nothing stale is hidden.

After your answer
  • One constant and one tag in the coverage banner copy.
Decided 2026-10-13

C confirmed, standardized at 60 days (the artifact's own options disagreed internally — option B said 60, option C said "older than 50" — settled on 60: two monthly cycles plus the ~10-day typical lag), with a cadence-exception refinement for Taurus/Monarch Networth Capital so their known non-monthly cadence doesn't falsely tag as stale.

Q19Decided

Is a sector breakdown part of this release?

The issue

The PDF's drill path runs Equity, then cap bucket, then sector, then stock. The format survey already records that AMCs spell sectors differently (its example: "Banks" at one AMC, "Banking & Finance" at another) and recommended a sector-name normalisation table. The spec stores sector_raw exactly as each AMC prints it and leaves normalisation to attribute 06, but defines no mapping, no sector table and no sector view. stock_master.sector is mentioned as an optional backfill; none of the sourced files (NSE P/E file, security master, Yahoo modules named in the plan) carries sector.

Why it matters

A sector chart built on raw strings may split one sector across spellings. Building a mapping is its own piece of work.

Options
  1. ANo sector chart in this release. Show sector_raw as a column in "View all", as the spec says.
  2. BAdd a small label-to-sector mapping table seeded from the labels seen in real files, and a sector bar chart.
  3. CTake sector from a source that already exists: NSE's Nifty 500 constituent file has an Industry column (checked live, F15), covering Nifty 500 stocks only, or Yahoo's assetProfile.
Recommended

A. Keeps this release to what the spec defines.

After your answer
  • The sector step is recorded in DEFERRED_FEATURES.md with the reason.
Decided 2026-10-13

A confirmed. No sector chart this release; both free sector-data candidates (NSE Nifty 500 Industry column, Yahoo assetProfile) stay documented in DEFERRED_FEATURES.md, not built.

F7Plan fix

The shared function has the wrong signature

applied 2026-10-13
Applied
Revision-block rules 1 and 2: the sync Session and household_member_ids signature, and get_lookthrough_table memoized on db.info so the five sections of a scope build the table once. Task 2 has the test. The consumer spec's snippet now carries a dated correction.
The problem

The consumer spec writes async def compute_lookthrough_table(db: AsyncSession, client_id: uuid.UUID) -> LookthroughTable, and its dataclass carries a client_id field. In the code, every analytics compute function is async def compute_x(db: Session, household_member_ids: list[uuid.UUID]) on a sync SQLAlchemy Session (grep AsyncSession app/services/analytics returns nothing), and _SectionSpec.compute is typed Callable[[Session, list[UUID]], Awaitable[BaseModel]]. There is no "client" concept at this layer: recompute_household_analytics runs the same compute once for the combined scope (all members) and once per member.

Evidence
recompute.py lines 67 and 225 to 260; compute_holdings at services/dashboard/holdings.py:159.
Why it matters

Written as in the spec, the function would not plug into _SectionSpec, would not accept the scope the recompute passes, and would need an async engine the app does not use. For a household with 4 members it runs 5 times per recompute, so the table must be built per scope, and the overlap read too.

The fix
  • Signature: async def compute_lookthrough_table(db: Session, household_member_ids: list[UUID]) -> LookthroughTable.
  • Replace the dataclass's client_id with the member ids it was built for (or drop it); keep nav_as_of, holdings_as_of, total_portfolio_value.
  • Register each attribute as its own _SectionSpec(name, compute, wrap_combined) in recompute.py. Within one scope the shared table can be built once and handed to the section computes (the existing per-process caches in category_ranking.py and scorer.py are the precedent for sharing work across scopes).
Effect on the current system
  • Nothing existing is edited except one list in recompute.py (five more entries). Existing sections keep their own compute functions and results.
  • Run time per recompute grows by five sections times (members + 1) scopes.
Effect on the plan
Task 2's red tests are written against db_session (sync) and member ids. Each later task (02, 10, 13, 15) takes the same signature. Spec section 2's snippet is corrected with a dated note.

F8Plan fix

There is no reusable fund-weight function

applied 2026-10-13
Applied
Revision-block rule 3 and Task 2's first test: a scheme_values helper next to lookthrough.py. allocation.py is not edited.
The problem

The plan says to reuse "allocation.py's existing scheme-value calculation" and "do not re-derive it". In the code that calculation is not a function. It is inline inside compute_category_allocation (lines 36 to 63): it calls compute_holdings, sums Decimal(h.current_value), and buckets by category. The shared piece is compute_holdings(db, household_member_ids) in services/dashboard/holdings.py, which returns HoldingRow objects where current_value is a string or None, with one row per folio (so several rows per scheme), and flags nav_unavailable and stale_nav.

Evidence
allocation.py lines 36 to 63; dashboard/schemas.py lines 45 to 69.
Why it matters

A literal reading of the plan would send the implementer looking for a function that does not exist, then copying the inline code, including Decimal(h.current_value), which fails on a row with no NAV. Fund weight is the multiplier in every one of the five attributes, so an error here is an error everywhere.

The fix
  • Add one small helper, for example scheme_values(holdings) -> (dict[UUID, Decimal], total, unpriced_scheme_ids), next to the new lookthrough.py.
  • It sums current_value per scheme_id across rows, converts the string id to uuid.UUID, skips rows with no value, and returns the skipped schemes so the coverage notice (Q7) can name them.
  • Do not refactor allocation.py to use it. Existing analytics stay byte-for-byte as they are.
Effect on the current system
  • No change to allocation.py, compute_holdings, or any existing result.
  • compute_holdings is cached; the helper only reads what it returns.
Effect on the plan
Task 2 gains its own red test list for the helper: two rows for one scheme sum together, a row with None is excluded and reported, the total equals the sum of scheme values. The "reuse allocation.py" wording in Tasks 2 and the architecture paragraph is replaced.

F9Plan fix

No separate backend endpoint is needed

applied 2026-10-13
Applied
Revision-block rule 4: schema classes and one _SectionSpec per attribute, no route.
The problem

Task 2 lists "StockHoldingsSection.tsx + its backend endpoint". New Analytics sections are not served by their own routes. GET /analytics/{scope} reads every AnalyticsSection row for the household and scope and returns them as sections: dict[str, AnalyticsSectionState]; the section name is not validated on the server.

Why it matters

An extra route would duplicate the precompute design (and could tempt someone into computing on request, the BUG-001 mistake the plan itself warns about).

The fix
  • Replace the endpoint step in Task 2 (and the equivalent in each later task) with the real three steps: add the schema classes in services/analytics/schemas.py including an Aggregate…Response wrapper for the combined scope, add one _SectionSpec in recompute.py, and let the existing GET return it.
Effect on the current system
  • app/api/analytics.py needs no change.
Effect on the plan
