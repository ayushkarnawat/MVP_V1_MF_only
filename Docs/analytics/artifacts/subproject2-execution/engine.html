Q8Your call

Where does asset_type enter the schema?

The issue

The engine spec (amended 2026-10-12) puts asset_type on scheme_holdings. The ingestion plan's Task 1 model, migration and ParsedHolding do not have it (zero mentions in the plan). The consumer plan's Task 1 adds it later as a second migration, with a backfill to an OTHER value that is not in the six-value enum, on a column the spec makes NOT NULL.

Why it matters

Parse is the only stage that sees the section headers ("Equity & Equity related", "Debt Instruments", ...). The current parse_sheet_rows skips any row without numbers, so those headers are thrown away. Stamping asset_type later means reopening Parse, the writer and every test after they are built.

Options
  1. APut asset_type in the ingestion plan from Task 1: column, migration, ParsedHolding, section-aware Parse, writer. The consumer plan's Task 1 shrinks to a check.
  2. BKeep two migrations as the plans are written, and fix the OTHER/NOT NULL mismatch in the consumer plan.
  3. CMake the column nullable and stamp it in a later pass.
Recommended

A. One migration instead of two, and Parse is designed once around sections.

After your answer
  • Ingestion plan Tasks 1, 2, 4 gain asset_type tests.
  • Consumer plan Task 1 becomes a verification step.
Q9Your call

How do we prove the parser against real files?

The issue

Task 2's parser is tested only against workbooks the plan builds itself. The docs record no real sheet-level layout: nothing on blank rows between sections, "Sub Total" rows, derivative lines, or segregated-portfolio sheets, and the format survey itself says a real column-by-column diff was "still recommended" and never done.

Why it matters

I ran the plan's % to NAV pattern against real header spellings. "% to AUM" does not match (ABSL and Choice use it), nor does "% of NAV". A sheet with no matching column is silently skipped as a non-holdings sheet, so an AMC would look fine and write nothing. Other gaps: a blank spacer row ends the sheet early; a "Sub Total" row with numbers is ingested as a holding and double-counts weight; "2.50%" text is dropped; an unknown unit defaults to rupees instead of failing, against the spec's own rule.

Options
  1. ABefore the Parse task is built, download one real file for each of the registered AMCs and keep them as test fixtures (small ones, or trimmed copies). Tune header patterns, section handling and terminators against them, and make an unrecognised unit raise.
  2. BBuild as written and fix each AMC when the live run fails.
  3. CA, plus a per-AMC check after Write that the batch's pct_to_nav sum is between 90% and 101%, otherwise the batch is marked FAILED.
Recommended

C. A is the minimum. The sum check in C is cheap and catches the double-count and the missing-section cases A can miss.

After your answer
  • Plan Task 2 gains a fixtures step and a sum check; FAILED becomes a state that is actually written.
  • Fixtures live in backend/tests/fixtures/, not in Docs/.
Q10Your call

One holdings copy per plan variant, and how long to keep history

The issue

The writer copies the same holdings rows onto every plan variant of a fund (Direct/Regular, Growth/IDCW). Every re-parse deletes and re-inserts all of them. Nothing in the docs gives plan-variant counts or rows per fund, and nothing says how many months to keep.

Why it matters

My rough estimate, assumptions stated: about 1,500 funds, 60 rows each, 4 to 6 variants each, gives roughly 400,000 to 550,000 rows a month and 5 to 7 million a year. That runs on Postgres, but it is a guess, not a measured figure. The consumer reads by the scheme a client actually holds, which is why one copy per variant is simple.

Options
  1. AKeep one copy per scheme as planned, and keep all months.
  2. BOne copy per scheme as planned, keep the latest 3 months plus each period's last disclosure, and prune older months in the daily job.
  3. CStore holdings once per fund family and have readers resolve the family. Needs a family key that does not exist today.
Recommended

B. A is the least change and the volume is manageable; B caps growth with one extra delete. C is cleaner but touches the schema and every reader.

After your answer
  • B adds a small pruning step to Task 9's job and one test.
Q11Your call

Keep the original downloaded files?

The issue

raw_file_reference is meant to be an S3 key of the downloaded file. The plan never fills it. The only S3 bucket today is the CAS-file bucket, which has a PAN-retention lifecycle, so it is not a place for these.

Why it matters

Without the raw file, a parser bug found a month later cannot be re-run on that month's source. Some sources vanish: Wayback captures, rewritten AMC pages.

Options
  1. ADo not store raw files. Leave the column NULL. Re-fetch if the source still exists.
  2. BNew private bucket with a 12-month lifecycle rule, written by the ingestion task. Needs a Terraform change that you apply.
  3. CStore only the files that fail to parse or fail the sum check.
Recommended

C. Keeps the useful evidence for debugging without a standing archive.

After your answer
  • C needs the bucket from B but writes far fewer objects.
Q12Your call

When does a missing AMC raise an alert?

The issue

The plan alerts on every daily miss. It also marks an AMC "done" the first day any scheme is written, so a day-one partial success is never retried. Schemes the matcher cannot match are logged at INFO only. The spec asks for an alert only when an AMC is "not found by day N", and the states FETCHED, PARSED and FAILED are defined but never written.

Why it matters

Without this, a quiet partial failure looks like success, and a normal late publisher floods the ops topic.

Options
  1. AAlert only after day 10 of the month, again on day 20, once per AMC per run. "Done" means every scheme in that AMC's file matched or was explicitly skipped; unmatched schemes raise an alert.
  2. BAlert on the first miss, as the plan is written.
  3. CA, plus a monthly summary line listing AMCs with zero batches.
Recommended

C. Matches the spec's wording and gives you a month-end list of what is missing.

After your answer
  • Task 6 gains an unmatched-scheme alert and a day-threshold; the retry check compares matched against expected, not just "any batch".
Q13Your call

What become derivative, fund-unit and unrecognised-section rows?

The issue

The six-value AssetType has no place for futures/options lines (arbitrage and hedged funds list them, often with negative weights), for mutual-fund units held by a fund of funds, or for a section header the parser does not know. The spec says no AMC was found without sections, but no sample was shown.

Why it matters

If these rows are forced into "Equity", an arbitrage fund counts its stock and its offsetting future as exposure, and a fund of funds shows another scheme as a "stock".

Options
  1. AAdd two values, DERIVATIVE and OTHER. Both are stored but left out of the stock table, cap split, overlap and P/E, and counted in a coverage note.
  2. BSkip those rows at parse time and record how many were skipped in parse_errors.
  3. CForce them into the six existing values by section name.
Recommended

A. Keeps the data without letting it distort exposure. The consumer spec's "six classes" wording becomes "six plus two excluded".

After your answer
  • Enum, migration, Parse and four consumer tests change.

F2Plan fix

Job memory and holding every download in memory

no decision needed
The problem

The scheduled ingestion task would run on the default task size, 512 CPU and 1024 MB (infra/modules/scheduler/main.tf, the jobs task definition). The plan's code then holds a lot at once. _download_workbook builds a bytearray up to 60 MB and copies it to bytes. _fetch_candidates with keep_all downloads every file for an AMC and returns them together as a list of LocatedFile. parse_workbook then turns every sheet of every workbook into Python lists ([list(row) for row in ...]).

Evidence
infra/modules/scheduler/main.tf: default memory 1024; fund-managers entry sets 2048 with the reason in a comment.
Why it matters

Some sources are large: ICICI Prudential is a 151-file ZIP, Aditya Birla Sun Life is a 105-sheet workbook, DSP lists 345 links. The fund-manager job hit this same wall: its entry carries memory = "2048" with a comment that the 40-AMC run peaked at 937 MB, too close to 1024. A killed task here would look like a missing AMC (alert, no data) and would be retried the next day only to be killed again.

The fix
  • Infra: add memory = "2048" to the new portfolio_disclosures_daily job entry, using the same lookup(each.value, "memory", "1024") mechanism the other job uses.
  • Code: change Fetch to hand over one file at a time (an async generator, or download-parse-write per file) instead of returning all files for an AMC, and release each workbook after parsing.
  • Parse: keep rows as an iterator rather than materialising whole sheets, where the header scan allows it.
Effect on the current system
  • Terraform diff is a one-line addition inside a new resource. No existing task definition changes.
  • Cost: a larger Fargate size for a few minutes a day on 20 days a month. I have not priced it; it is small next to the always-on resources, but treat that as an estimate, not a figure.
Effect on the plan
Task 6 (_fetch_candidates and the refresh loop) changes shape, so its tests that read the returned list adapt. Task 10 gains one line. The behaviour (what is written, idempotent rerun) does not change, so the Review Focus tests stay as they are.

no decision needed
The problem

F4cPlan fix

Locate kinds the plan cannot run yet

no decision needed
The problem

_locate_and_fetch handles WAYBACK_LOCATE, DETERMINISTIC_TEMPLATE and STATIC_REGEX. For any other kind it raises NotImplementedError. The refresh loop skips MANUAL entries with continue. No JSON_API or MANUAL entry exists in the registry today, so nothing raises today: the 23 JSON AMCs and the 6 manual ones are simply absent.

Why it matters

The problem arrives with wave 2 (Q14). If JSON entries are added before a JSON Locate exists, each one raises on every daily run, which counts as a failed AMC and sends an alert 20 times a month. The manual AMCs, by contrast, can be registered but never produce an AWAITING_MANUAL_UPLOAD row (Q15).

The fix
  • Add a guard: a registry entry whose kind has no Locate implementation is reported once per run as "not onboarded" in the end-of-run summary, not raised as a failure.
  • Build the JSON_API Locate and the manual-queue write as part of wave 2 (Q14, Q15), before any such entry is registered.
