Q14Decided (overridden)

How many AMCs must be live before the attributes ship?

The issue

The spec classifies 44 of 57 AMCs as automatable. The ingestion plan builds 10 of them. It does not build any of the 8 JSON-API AMCs with known endpoints, the 15 that still need a network-trace pass, the 6 manual ones, or 9 of the plain static ones. The large AMCs I can name from outside the docs (SBI, ICICI Prudential, Kotak, Axis, Aditya Birla Sun Life, UTI, Mirae, DSP) are not among the 10. No document gives an AUM share for the 10, so I cannot say what fraction of a typical portfolio they cover.

Why it matters

Every one of the five attributes is only as good as the funds it can see. With 10 AMCs a typical investor will have several holdings with no stock data, and "Top 10 stocks" would describe only part of the portfolio.

Options
  1. AShip the 10 as planned. Build the consumers on them. Everything else is a later plan.
  2. BPlan a second wave of 19 more AMCs whose mechanism is already known (9 static, Baroda, Kotak, 8 JSON endpoints). It is not registry rows alone: the 8 JSON AMCs each need their own Locate function, Bank of India needs an index-sheet parse (its workbook names sheets by scheme code, YB01 to YB44, mapped by an Index sheet), and Aditya Birla Sun Life needs its dead-CDN host rewritten. Build it right after the engine, before the attributes go to users. The 15 research-gap AMCs, Old Bridge, and the other index-sheet bundles (Abakkus, Sundaram, ICICI Prudential, Bajaj Finserv) are a third wave.
  3. CAll 44 before anything ships, including the 15 that need their own research.
Recommended

B. A is fast but thin. C waits on research nobody has done. B gets the biggest names in without new research.

After your answer
  • A wave-2 plan is written the way Sub-project 1's A04 research batch was: a registry file per AMC, no pipeline changes.
  • The attribute work can start as soon as one AMC is WRITTEN, so waves and attributes can overlap.

Overridden: all 57, in this one execution. You rejected the wave framing: "I need all the AMCs covered in the execution. Nothing should be left out to later." So there is no wave 2 or wave 3. Q16Decided

Wayback dependence, and a spec-versus-plan conflict on Canara Robeco

The issue

HDFC, Kotak and Canara Robeco are fetched by asking the Internet Archive for a capture and then downloading from the AMC's own file host. Two separate points. Conflict: the engine spec lists Canara (and Baroda) as multi-scheme bundles needing a custom index-sheet parse. The spike document describes Canara's files as separate per-scheme workbooks with a two-letter fund-code prefix (SC-...-Small-Cap-Fund-...-August-2026.xlsx), and it names Bank of India, Abakkus, Sundaram and ICICI Prudential as the index-sheet bundles. So the plan's generic parse for Canara is probably right and the spec row is probably mislabelled; the custom index-sheet parse belongs to the wave-2 AMCs. I have not opened a Canara file myself. Bug-shaped gap: the prefix search passes every captured upload under wp-content/uploads/ (up to 50) to the fetcher with no link pattern, so unrelated files get downloaded.

Why it matters

Kotak's real path is built from the date alone (Consolidated-SEBI-Portfolio-as-on-{Month}-{DD},-{YYYY}/ConsolidatedSEBIPortfolio{Month}{YYYY}.xlsx), so it could be fetched directly with no archive lookup. The archive lookup adds a failure point and a capture lag (Kotak's file was crawled a day after it appeared).

Options
  1. AKeep Wayback for all three as the plan has it, add a link pattern to the prefix search, and get a real Canara file to decide between generic and custom parsing.
  2. BKotak: fetch directly from the date-built path, Wayback only as the fallback. HDFC and Canara as in A.
  3. CB, plus an alert when a Wayback lookup returns no capture newer than the previous month.
Recommended

C. Removes the archive from Kotak's normal path and tells you when it stops working for the other two.

After your answer
  • Task 7 gains a pattern filter, a Kotak template entry and a stale-capture alert.
  • Canara's parse choice waits on the real file from Q9; the spec row is corrected either way.
Decided 2026-10-13

C confirmed and applied to the plan. Kotak is now a direct date-built template (Task 5) with no automatic Wayback fallback: a changed path raises the day-10 or day-20 alert, and the fix is a one-off re-discovery. Canara's conflict is settled in the plan's favour: its files are per-scheme workbooks, not an index-sheet bundle, and the spec row is corrected (Task 16). Canara gets a link_pattern filter (Task 7), and HDFC and Canara raise a stale_wayback_capture alert (Task 14). A latent bug was found and fixed alongside: _locate_deterministic_template never supplied month_name, yy and yy_plus_1, which AlphaGrep's and Kotak's templates use.

F6Plan fix

Cadence cases need one stated rule

applied 2026-10-13
Applied
Global Constraints, last bullet (the cadence rule); a cadence field on registry rows, set on Taurus and Monarch (Task 11 Steps 3 and 7); a test in consumer Task 2 that a half-yearly fund's old batch is used and tagged, not dropped.
The problem

Different AMCs publish on different calendars: Taurus half-yearly (March and September), Monarch fortnightly only, Canara Robeco monthly for equity and fortnightly for some debt schemes, and Helios and Groww publish fortnightly files next to the monthly ones. Today the plan handles only the last pair, through an exclude_pattern of fortnightly in the registry. The rest is described in notes.

Why it matters

Without a stated rule, the first Taurus run would write a six-month-old batch that the consumer treats as current, and a fortnightly Monarch file could be mistaken for a monthly one.

The fix
  • State once, in the engine plan and spec: the engine stores every disclosure's own as_of_date exactly as the file states it (the spec already says so).
  • The consumer picks, per fund, the newest batch at or before the NAV date.
  • Age is handled by Q18's tag (older than 50 days), not by dropping data.
  • Keep fortnightly files out only where the registry excludes them; Monarch is ingested as its real cadence, and Taurus as half-yearly.
Effect on the current system
  • None.
Effect on the plan
A paragraph in the engine plan's Global Constraints and one test in the consumer plan: a half-yearly fund's old batch is used and tagged, not dropped. No new code in the engine.

F17Plan fix

Workbooks whose sheets are named by scheme code never match a scheme

found 2026-10-13, applied to the plan
The problem

The plan's note for Bank of India (Task 5, written when Q16 was decided) says its workbook needs no custom parse code because the multi-sheet parse is generic. The parse is generic, but the matcher in Task 6 identifies a scheme by sheet.sheet_name. The spike's description of Bank of India is a single workbook with an Index sheet that maps scheme codes YB01 to YB44 to names, plus one sheet per scheme, named by code.

Evidence
Consolidated spike doc line 83; plan Task 5 (Bank of India entry) and Task 6 (match_key = file.scheme_hint or sheet.sheet_name).
Why it matters

Every one of those sheets would be handed to the matcher as YB01, YB02 and so on, match no scheme, and be logged as unmatched. The AMC would then count as processed with nothing written, for all of its roughly 44 schemes. Task 2 already skips the Index sheet as a non-holdings sheet, which is right for parsing but throws away the one table that says which code is which scheme.

The fix
  • Add read_index_sheet(data) -> dict[str, str] to the parsing module: find the sheet whose header row has a scheme-code and a scheme-name column, return code to name.
  • In the refresh loop, match on index_map.get(sheet.sheet_name, sheet.sheet_name) when the file has no link-text hint. A workbook with no index sheet behaves exactly as before.
  • Task 12 records which other bundles name their sheets by code. The candidates are Abakkus, Sundaram, Baroda BNP Paribas, Bajaj Finserv and ICICI Prudential. I have not opened any of those files; only the spike's description is behind this.
Effect on the current system
  • None. A new function in a new module. Nothing already built is touched.

F18Plan fix

An HTTP 200 does not prove a file was downloaded

found 2026-10-13, applied to the plan
The problem

_download_workbook (Task 6) accepts any response body up to 60 MB that comes back with a success status. The fifth-pass research found that Mirae Asset's CMS answers with HTTP 200 and an HTML error page under a .xlsx name for a file that does not exist.

Evidence
Fifth-pass reconciliation doc, Mirae Asset row.
Why it matters

The HTML would count as a located file, so the AMC is treated as found. Parse then rejects it as an unknown format, and the AMC is reported as an error every day it stays missing, instead of as 'not published yet'. The right alert is the quiet one that waits for day 10.

The fix
  • Check the first bytes. A real workbook starts with PK\x03\x04 (xlsx or zip) or \xd0\xcf\x11\xe0 (xls). Anything else returns None, which the callers already treat as no file.
  • Applies to every AMC, not only Mirae.
Effect on the current system
  • None for existing code; the function is new in this plan.
Effect on the plan
Task 11 Steps 1 and 2 (a test with an HTML body under an .xlsx URL). Review Focus gains one line.
