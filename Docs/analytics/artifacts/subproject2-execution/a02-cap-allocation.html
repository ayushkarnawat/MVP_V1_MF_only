Q20Decided

Which AMFI list applies to a holding, and how far back do we load?

The issue

The AMFI file is named for the six months that ended on 30 Jun 2026. The spec stores that as effective_date and picks the newest list with effective_date ≤ holdings_as_of. Two problems. First, a list that averages the six months to 30 Jun is normally used from the start of the next period, so a June month-end portfolio would be bucketed with the new list if the period end is used as the effective date. I have not checked the SEBI circular's effective rule; that is for you to confirm. Second, the plan ingests only the current list. A holding dated before it finds no list at all and falls into "Other".

Why it matters

A wrong effective date moves every stock near rank 100 or 250 in the month it changes. A missing earlier list makes recent months look 100% unclassified.

Options
  1. AEffective date = the day after the period end (1 Jul 2026 for the file above, which is then used for holdings dated 1 Jul onward). Load the last 4 lists (two years) when the client is first deployed.
  2. BEffective date = the period end as written. Load the current list only.
  3. CEffective date = the day the list was published. Load the last 4 lists, capture each publication date by hand.
Recommended

A. Matches how the two lists meet at a boundary and gives every normal holding date a list to use. You confirm the rule against the circular.

After your answer
  • Task 3's date-join test uses the A rule in its example.
  • The older URL pattern (verbose name on www.amfiindia.com) is needed for the backfill and was only spot-checked.
Decided 2026-10-13

A confirmed via live research, not assumed. SEBI circular SEBI/HO/IMD/DF3/CIR/P/2017/114 (6 Oct 2017) confirms the Jan-Jun average list is effective 1 Jul and the Jul-Dec average list is effective 1 Jan — exactly A's rule. In Task 3 of the consumer plan.

Q21Decided

The Nifty 500 comparison strip needs data nobody has sourced

The issue

The spec says the strip "needs no new data source" because Nifty 500's constituents already define AMFI's rank 1 to 500 split. Two things in that sentence are unverified. Nifty 500 is built by NSE on its own free-float basis; AMFI's rank is average market cap over six months, so the two lists can differ at the edges. And a cap split of an index needs each constituent's index weight. I checked today that NSE's constituent file (ind_nifty500list.csv) is live and has company, industry, symbol and ISIN, with no weights.

Why it matters

Without weights the strip cannot be drawn honestly. Counting constituents by AMFI bucket is a different, simpler claim ("of the 500 companies, 100 are Large") and says nothing about weight.

Options
  1. ADrop the strip from this release. The spec already calls it optional.
  2. BShow a count-based strip, labelled "companies by AMFI bucket", using the constituent list and the classification table.
  3. CSource index weights (not investigated yet) and draw a weight-based strip.
Recommended

A. The attribute works without it and nothing new needs sourcing.

After your answer
  • Recorded in DEFERRED_FEATURES.md with the reason.
Decided 2026-10-13

A confirmed. Strip dropped after checking for a free source of real Nifty 500 constituent weights and finding none — not guessed or stubbed. Recorded in DEFERRED_FEATURES.md.

Q22Decided

What goes in "Other / Unclassified"?

The issue

The bucket mixes unlike things: debt, cash, gold and REITs (not equity at all), foreign stocks, and Indian listed stocks missing from the AMFI list (a new IPO, a recent merger). The toggle "% of equity only" removes only the first group.

Why it matters

A reader cannot tell "3.5% other" meaning cash from "3.5% other" meaning listed stocks we could not classify.

Options
  1. ASplit into "Not equity (debt, cash, gold, REITs)" and "Equity not in AMFI list".
  2. BKeep one bucket as the spec says and rely on the toggle.
  3. CShow one bucket in the donut and the split in the drill-down only.
Recommended

C. Keeps the donut as drawn in the PDF and the visual map, with the detail one tap away.

After your answer
  • One more grouping in the drill-down data.
Decided 2026-10-13

C confirmed. Single donut bucket, with the "not equity" vs. "equity not in AMFI list" split pushed to the drill-down — in Task 3 of the consumer plan.

F12Plan fix

The plan has no model, migration, job or schedule for the classification table

no decision needed
The problem

Task 3 goes from the feasibility spike straight to amfi_market_cap_client.py "writing market_cap_classifications (isin, rank, bucket, effective_date)". There is no step for the SQLAlchemy model, the bucket enum, the Alembic migration, a job script, or a scheduler entry. The spike's note says it parsed the PDF with pypdf, but pypdf is not in requirements.txt; the repo has pypdfium2==5.12.1.

Evidence
backend/requirements.txt lines 42 and 48; plan Task 3.
Why it matters

An implementer would have nowhere to store the data, nothing would run twice a year, and a new PDF dependency could slip in unreviewed (the CAS import already depends on the PDF stack).

The fix
  • Add steps in order: model and MarketCapBucket enum, migration (next free number), a half-yearly job script and its scheduler entry.
  • Before writing the client, prove text extraction on the real 48-page file with pypdfium2; pin pypdf only if that fails.
  • The client re-checks the URL each half-year, as the plan already says, and treats a changed host or name as a failure to alert on, not a silent empty table.
Effect on the current system
  • One new table with no foreign keys; no existing table changes.
  • A PDF library pin could affect the CAS import's dependency set, so its tests run after any pin.
  • New scheduler entry: you apply it at the single end-of-project staging.
Effect on the plan
Task 3 grows by four steps and a dependency decision. Its existing tests (date join, both denominators) are unchanged.
