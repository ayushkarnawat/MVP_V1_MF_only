01

Layout decision — manager-first grouped cards

Two options were presented; Ayush chose Option A because it matches the "aggregated across the whole portfolio" framing directly, rather than surfacing aggregation only as a summary strip above a fund-first table.

Option A (chosen): one card per manager, sorted descending by this household's rupee value under them, expandable to the specific funds held under that manager.

Option B (not chosen): a fund-first table with a 3-stat summary strip above it (managers / largest / uncovered) — felt closer to a restyled TerSection.tsx table than a feature that actually answers "who's running my money."

Schema & pipeline — backend grounding

Added for implementation handoff: the real table this screen reads and the resolver/extraction/matching pipeline that fills it. Not part of the originally approved mockup/layout decision above — purely explanatory, grounded verbatim in 2026-10-07-sub-project-1-planning.md's "Attribute 04" section.

        date reference_period
        text match_method "EXACT or FUZZY"

    }

    Parsed --> Match{"Step 0: exact match\nnormalized name vs.\nschemes.base_name\n(AMC-scoped)"}
    Match -->|"matches, majority case"| Exact["match_method = EXACT\nmatch_confidence = 1.000"]
    Match -->|"no exact hit"| Fuzzy{"Fallback: scoped + normalized\nfuzzy match, threshold 0.80,\nambiguity guard vs. runner-up"}
    Fuzzy -->|"score ≥0.80,\nclear of runner-up"| FuzzyOk["match_method = FUZZY\nmatch_confidence = ratio"]

Key honesty guarantee carried from the backend doc: a factsheet whose layout doesn't match either observed AMC shape, an ambiguous fuzzy match, or a below-threshold score all produce zero rows for that scheme — never a guessed or low-confidence row silently attached. This is exactly what feeds this screen's "not available yet" trailing block (§04).
