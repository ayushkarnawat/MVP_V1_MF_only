Sub-project 1 · Attribute 09 · 3rd in run order

Fund ranking

Ranks every held fund inside its SEBI category on a 5-factor score and shows a small leaderboard: the 2 funds just above it and the 2 just below, by name. Tapping a fund opens its factor breakdown.

6 tasks (incl. 2a, peers) 1 migration (expected 0034) 2 new tables 1 new route · 1 new analytics section 0 new jobs or data sources 2 Codex runs
The score

Five percentiles, weighted, renormalized when one is missing

Each factor is a percentile within the category, never a raw number, because a 3Y CAGR and a TER percentage aren't on the same scale. When a factor is missing, the others are re-weighted to sum to 1. A missing factor is never filled with 0.

Weights 3Y return 0.25 · 5Y return 0.25 · category-relative 0.20 · low volatility 0.15 · low TER 0.15 Example 3Y 92nd · 5Y missing · cat-rel 70th · volatility 60th · TER missing (no exact TER link) available weight = 0.25 + 0.20 + 0.15 = 0.60 composite = 92 × 0.25/0.60 + 70 × 0.20/0.60 + 60 × 0.15/0.60 = 38.33 + 23.33 + 15.00 = 76.67 Floors under 3Y of history → "Insufficient History", not ranked fewer than 5 ranked funds → ranked, flagged "Thin Category (N peers)", shown as "#2 of 3 ranked · 8 in category" 1Y return → shown, never weighted

1 · composite_score holds the percentile, not the score

was: Blocker
The problem

Two different numbers describe each fund:

  • Composite score (0–100): the weighted sum of the 5 factor percentiles. It answers how good is this fund on our formula.
  • Category percentile (0–100): where that composite sits among the category's composites, (total − rank) ÷ total × 100 (category_ranking.py:177). It answers what share of peers does it beat.
The plan computes the composite correctly, then ranks it with _rank_and_percentile, which returns (rank, percentile). It writes rank_info[1] — the percentile — into both composite_score and percentile. The neighbor rows use each neighbor's real composite.

Worked example, a 4-fund category:

RankFundCompositeShown by the planShown after the fix
1Fund A81.4081.4081.40
2Fund B79.0079.0079.00
3Your fund76.6725.00 ← percentile76.67
4Fund D60.2060.2060.20

Your fund is correctly ranked #3, but its score reads 25.00 between 79.00 and 60.20, which looks like an error to anyone reading the list. The 25.00 is right as a percentile (it beats 1 of 4 peers) and still feeds "Top 75%". The stored scheme_rankings history would carry the wrong number too.

Fix chosen

A. composite_score = the composite; percentile = the category percentile.

It keeps both numbers the spec uses, each in its own field, and changes one assignment. Ranks were never affected.

What happens now
  • _finish_fund_ranking stores and returns scheme_scores["composite"] (2 decimals) as composite_score.
  • Every leaderboard row shows a composite; the header's "#3 of 4 · Top 75%" uses rank and percentile.
  • Test: with the 4-fund example above, your row's composite_score is 76.67 and its percentile is 25.00.
Not chosen
  • B. Show the percentile everywhere, neighbors included.
  • C. Show only ranks.

4 · Same-day repeat writes: add the test

was: Check
The problem

Each ranking computation inserts one scheme_rankings row keyed by (scheme_id, computed_at), where computed_at is midnight UTC of today. A second insert for the same fund on the same day violates the primary key. The plan catches the IntegrityError, rolls back, and still returns its freshly computed row, exactly like scorer.py:298–311 does for fund_scores.

It isn't rare, it's routine. recompute_household_analytics runs every section for the combined scope and then once per member (recompute.py:226–229). A one-member household ranks each of its funds twice in every recompute; a 3-member household up to 4 times; and every other household holding the same fund that day collides too. So the catch-and-rollback path runs constantly, and Review Focus #4 is the normal path.

sequenceDiagram
  participant R as recompute_household_analytics
  participant F as _finish_fund_ranking
  participant DB as Postgres
  R->>F: combined scope · Fund X
  F->>DB: INSERT scheme_rankings (X, today)
  DB-->>F: OK, committed
  F-->>R: row (composite 76.67)
  R->>DB: upsert section + heartbeat, commit
  R->>F: member scope · Fund X
  F->>DB: INSERT scheme_rankings (X, today)
  DB-->>F: IntegrityError (duplicate key)
  F->>DB: ROLLBACK (only this insert is pending)
  F-->>R: same freshly computed row
  R->>DB: upsert member section, commit

What the rollback can discard: only writes added to the session since the last commit. In the pipeline, the previous section and the previous fund's row were already committed, so only this one insert is pending. The test pins that.

Fix chosen

B. Add the test.

The path runs on every recompute, so it deserves a test; the test is small and changes no code.

What happens now
  • New test in test_fund_ranking.py: call compute_fund_ranking twice for the same fund in one session. Both calls return the same composite and rank; exactly one scheme_rankings row exists for today; a query after the second call still works (the session isn't left broken).
  • A second test runs compute_portfolio_ranking for a one-member household twice (combined + member) and checks both results are complete.
Not chosen
  • A. Accept untested, as the plan does.
  • C. Replace insert-and-catch with INSERT … ON CONFLICT DO NOTHING. Cleaner, but it diverges from fund_scores for no user-visible gain.

5 · Why categories look thin, and how to remove the part that isn't real

was: Proposal
Short answer

Most thinness today isn't real, but some of it is. Two data problems make categories look smaller (or bigger) than they are, and both can be fixed. A few SEBI categories genuinely have fewer than 5 funds, and no data fix changes that. For those, the answer is how we show the number.

Cause 1 · one category, several spellings

AMFI's master file (the live copy cached 9 Oct) lists each AMC's funds under a heading the AMC supplies. The same SEBI category appears under 2–3 spellings, so there are 101 headings for about 80 real categories. We match on the exact heading, so a fund is only compared with AMCs that spelled it the same way.

CategorySpellings in AMFI's fileFunds compared todayFunds in the category
Flexi Cap"Equity Scheme -" / "Equity Schemes -"30 or 1646
Contra"Equity Scheme -" / "Equity Schemes -"3 or 25
Dividend Yieldsame9 or 312
Balanced Hybrid"Hybrid Scheme -" / "Hybrid Schemes -"1 or 45
Balanced Advantage"Dynamic Asset Allocation or Balanced Advantage" / "Balanced Advantage Fund/ Dynamic Asset Allocation"splitmerged
Liquid, Overnight, Money Market, Gilt, Corporate Bond, Banking & PSU…"Debt Scheme -" / "Income/Debt Oriented Schemes -" (+ wording such as "Banking and PSU Debt Fund")splitmerged

This already affects shipped sections. The existing Category Ranking and the Scorer use the same lookup, so a Flexi Cap fund today is ranked among 30 or 16 funds instead of 46.

Fix 1
  • Map each heading to one canonical category with a short, explicit alias list in scheme_universe.py: "Schemes"→"Scheme", "Income/Debt Oriented Schemes"→"Debt Scheme", plus the named wording pairs above. No fuzzy matching.
  • get_category_universe compares canonical keys. One change fixes Category Ranking, Scorer and Fund Ranking together.
  • Old headings whose mapping is a guess ("Long Term Fund", "Ultra Short to Short Term Fund") stay separate rather than being merged wrongly.
  • Test: parse a saved copy of the real file and pin the merged groups (Flexi Cap = 46 funds, Contra = 5).
  • Effect: categories under 5 funds drop from 22 to 17, and no mainstream equity or hybrid category stays thin. Small: one function, one alias list, one test.
Cause 2 · plan variants counted as peers

The universe is every scheme code, and one fund has up to 4 (Direct/Regular × Growth/IDCW): 14,371 codes in all. Three effects:

  • "8 in category" can mean 2 funds.
  • Your Direct plan is ranked against its own Regular plan, which always trails it by the expense-ratio gap. That's a free rank step.
  • IDCW plans' NAV drops at every payout, so their NAV returns look low, they sink to the bottom, and every Growth plan's percentile rises.
Fix 2
  • Peer set = one entry per fund: the same plan type as your holding (Direct vs Direct, Regular vs Regular), Growth option.
  • A held IDCW plan is ranked by its fund's Growth series of the same plan type.
  • Counts become fund counts, so "#4 of 46 ranked · 52 in category" means funds.
  • Medium effort: UniverseRow already carries base_name and the plan, but 5,709 older codes have no plan in their name and need a grouping rule.
  • It changes numbers in the existing Category Ranking too, usually lower and more honest percentiles.
Cause 3 · the 3-year floor

Funds younger than 3 years can't be ranked; the spec says so, and they show "Insufficient History". Keep it. Ranking a 1-year-old fund on 1-year returns against 5-year track records would mislead more than a thin badge.

Cause 4 · genuinely small categories

SEBI allows each AMC one fund per category, and a Value or a Contra fund, not both. So Contra has 5 funds in all of India. Long Duration, the Life Cycle maturities, single-commodity ETFs and Children's funds are similar. No data fix changes this, so thinness can't be removed completely; it can only be shown honestly.

How to show a thin rank
  1. D1Plain words, no percentile, when thin. "2nd of 3 ranked Contra funds · 5 in category". One line under it: "Only 3 Contra funds have a 3-year record, so this compares your fund with very few others." Hide "Top 33%" and the percentile bar, because with 3 funds a percentile only restates the rank. The leaderboard (2 above, 2 below) already lists every peer in a category this small, so the user sees exactly who the fund was compared with.
  2. D2No rank below 3 ranked funds. "#1 of 1" or "#2 of 2" says nothing. Show "Not enough peers to rank: 2 funds in this category have a 3-year record", and show the fund's own numbers (3Y return, expense ratio) instead of percentiles.
  3. D3Pool with sibling categories, e.g. Value + Contra + Dividend Yield as "value-style funds", clearly labelled. More peers, but it stops being a SEBI-category rank, which is what the spec promises. Later, if at all.
Fix chosen

Fix 1 + Fix 2 + D1 + D2, all in A09 (plan Task 2a and Task 5). Fix 2 goes in now: the staging database is wiped before release, and the existing Category Ranking section switches to the same peer set so the two sections agree.

Fix 1 is small and corrects sections users already see. D1 and D2 are copy rules on the card. Together, a thin badge then appears only where a category really is small, and the card says so in plain words.

6 · Found while revising the plan: zero NAVs and TER units

was: new
Zero NAVs crash a category

AMFI's file has 241 rows at NAV 0.0000: wound-up and segregated debt schemes (Franklin, UTI, Baroda BNP). The return calculation divides by the start NAV, so one of them raises InvalidOperation and the whole category fails. The A14 synthetic run hit this. Category Ranking and Score failed for 3 of 8 test portfolios, and the same happens for any household holding a fund in those debt categories today.

Fix (plan Task 2a): a start or end NAV ≤ 0 means no return for that window, so the scheme is skipped, never shown as 0%. Test included.

TER shown 100× too big

Fix 2's toPercentString turns a fraction into a percent. Returns are fractions, but TER is stored as a percent already (0.75 means 0.75%), so it would read "75.00%". Fix: the Low-TER row prints the stored value with a % sign. Test included.

Done means

Review Focus the gate checks

  • 3Y but no 5Y history: the score is re-weighted over 4 factors, never 0 for 5Y.
  • No TER link (common since migration 0031): re-weighted, and the breakdown shows "—".
  • Ranked #1 or last: 0 neighbors on that side, no wrap-around.
  • Two same-day computations don't raise an unhandled IntegrityError.
  • Empty ranking_weights falls back to 25/25/20/15/15.
