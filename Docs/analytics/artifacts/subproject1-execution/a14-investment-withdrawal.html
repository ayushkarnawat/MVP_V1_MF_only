1 · The compute function is sync, but the pipeline awaits it

was: Blocker
The problem

recompute.py:233 runs await section.compute(db, ids) for every section. The plan's compute_investment_withdrawal is a plain def, and it calls compute_holdings (an async def, holdings.py:159) without await, so it gets a coroutine back instead of a list of holdings.

Awaiting a plain return value raises TypeError, so the section is marked failed for every household and never lands. The Analytics screen would show the skeleton forever. The plan's own tests wouldn't catch it, because they monkeypatch the value-lookup helper and never go through the pipeline.

Fix chosen

A. Make it async def and await compute_holdings(...), like the other 7 sections.

It matches every existing section's signature, touches only the new file, and leaves the shared pipeline alone.

What happens now
  • compute_investment_withdrawal and _current_value_for_household become async.
  • Task 1 tests call it through asyncio.run(...) and patch the value lookup with an AsyncMock.
  • Task 3 adds one test that runs the real section through recompute_household_analytics, so a sync/async slip can't come back.
Not chosen
  • B. Keep it sync and call asyncio.run(...) inside. This fails, because the pipeline already runs inside an event loop.
  • C. Teach recompute.py to accept sync functions. This changes shared code for one section.
Resolved

2 · Test fixtures build models that don't exist

was: Blocker
The problem

The tests import an AMC model and build Scheme(amc_id=…, category=…) and HouseholdMember(id, name). There is no AMC table. Scheme has amc_name and sebi_category (both required), and HouseholdMember needs a user_id.

Every Task 1 test fails at import, so red-green TDD can't start, and Codex would have to guess at fixtures.

Fix chosen

A. Rewrite the fixture helper with the real models, copying the style of an existing test that already seeds users, members, folios and transactions.

Real rows exercise the real joins between folios, schemes and members, which is exactly what this module does. Mocks would hide a wrong join.

What happens now
  • _seed_member_and_scheme creates a User, a HouseholdMember(user_id=…), a Scheme(amc_name=…, sebi_category=…) and a Folio.
  • The test bodies stay the same; only the setup changes.
Not chosen
  • B. Mock the database queries instead of seeding rows.

3 · Field names: camelCase types vs snake_case API

was: Decision
The problem

The plan's TypeScript types are camelCase (totalInvested), but the API sends Pydantic field names as they are (total_invested). Nothing in lib/apiClient.ts converts them.

Every value on the section would read undefined, so the tiles would show ₹NaN.

Fix chosen

A. snake_case in the new types, as the existing types.ts already does.

It's the only option that changes nothing existing.

What happens now
  • The new interfaces use total_invested, sip_summary.active_count and so on.
  • The component and its tests read those names.
Not chosen
  • B. Add a camelCase alias generator to the backend. That changes every existing response and breaks the screens that use them.
  • C. Convert to camelCase inside this section only. This creates a second convention in one feature folder.

4 · Quiet months disappear from the chart

was: Fix
The problem

The backend creates a monthly bucket only for months that have transactions. A month with no activity, sitting between active months, isn't in the list at all.

The chart would draw Jan, Feb, May next to each other as if March and April never happened, which misrepresents the cadence of investing. It's Review Focus #2. The plan's chart test passes only because it feeds a zero bucket by hand, which the real backend never sends.

Fix chosen

A. The backend fills every month (and year) from the first activity to the current month with zero buckets.

It keeps all computation on the server, like every other section. The PDF export and any future consumer get the same continuous series, and it's one place to test. Running to the current month also shows recent inactivity, which is what a missed SIP looks like.

What happens now
  • Monthly periods are continuous from the first transaction month to this month; yearly periods likewise.
  • A new backend test: activity in Jan and Apr gives Feb and Mar buckets at 0.00.
  • The chart test stays as it is and now matches real data.
Not chosen
  • B. The frontend fills the gaps before drawing.
  • C. Leave it and accept gaps.

5 · Stamp duty and bounced SIPs

was: Fix
The problem

The plan sums raw txn.amount, so Total invested leaves out the stamp duty added in migration 0032. cash_flow.py already uses paid_amount(txn), which is amount plus stamp duty. The plan also counts a bounced SIP's REVERSAL as Withdrawn. On 8 Oct you ruled that a reversal nets against Invested.

Without stamp duty, Total invested is a little lower than what actually left the bank, and it disagrees with the XIRR cash flows. Counting a reversal as Withdrawn makes a bounced ₹5,000 SIP show as ₹5,000 invested and ₹5,000 withdrawn, which inflates both tiles. Net invested and Absolute gain come out the same either way; only the Invested and Withdrawn tiles differ.

Fix chosen

A. Use paid_amount(txn), and net REVERSAL against Invested (your 8 Oct ruling).

It shows the money that actually left the household's account, matches the XIRR numbers elsewhere, and a bounce reads as "this instalment didn't happen" instead of an investment plus a withdrawal.

What happens now
  • Task 1 keeps its own query (it needs transaction_id, which compute_cash_flow doesn't return) but reads amounts through lot_rules.paid_amount.
  • A REVERSAL lowers that month's Invested; the drill-in list still shows the reversal row.
  • Two new tests: stamp duty included, and a bounced SIP nets to zero invested.
Not chosen
  • B. Use paid_amount(txn), and keep REVERSAL as Withdrawn (the plan).
  • C. Keep raw amounts and REVERSAL as Withdrawn (the plan as written).

6 · CSS tokens and a chart dependency that don't exist

was: Fix
The problem

The section uses --surface-muted, --text-muted, --warning-bg, --warning-text and --border. tokens.css only has --color-* tokens (--color-text-secondary, --color-border, --color-bg, --color-warning…). bar-chart.tsx imports d3-scale, which is in node_modules only as a dependency of another package, not in package.json.

Unknown CSS variables silently resolve to nothing, so the section would render unstyled. A transitive import works today but breaks the day the parent package drops it.

Fix chosen

A. Map to existing tokens, and compute the band and linear scales by hand (about 10 lines of arithmetic).

No new tokens and no new dependency, both locked in the frontend spec. The scale math for one grouped bar chart is trivial.

What happens now
  • --text-muted → --color-text-secondary, --border → --color-border, --surface-muted → --color-bg, warning → --color-warning.
  • bar-chart.tsx imports only @visx/group, /responsive and /shape.
  • Visual polish is deferred: this ships with existing tokens, and the UI pass comes later.
Not chosen
  • B. Map to existing tokens, and add d3-scale to package.json.
  • C. Add new tokens for this section.

7 · Money formatted with Number()

was: Fix
The problem

formatInr converts the amount string to a JavaScript number before formatting.

It breaks the decimal-discipline rule. Large or long-fraction values can round, and the formatting won't match the rest of the app.

Fix chosen

A. Use formatIndianCurrency from @/lib/decimal for every tile and SIP amount.

It's the app's existing formatter, works on strings, and matches other sections.

What happens now
  • Tiles and the SIP line show the same format as the rest of Analytics.
  • The bar chart still converts to numbers for bar heights only, which is geometry, not a displayed value.
Not chosen
  • B. Keep Number().
