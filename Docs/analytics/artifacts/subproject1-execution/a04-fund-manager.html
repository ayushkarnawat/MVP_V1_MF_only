1 · Match funds, not plan rows — and how to make matching tighter

was: Blocker
The problem

A factsheet names a fund; schemes has one row per plan and option, sharing base_name (name = base_name - plan - option, scheme_universe.py:106). The plan's matcher refuses when several rows share a base name, which is almost always, and never copies managers to sibling rows. Decided: match at fund level, then write the managers to every scheme in that (amc_name, base_name) family.

Making it tighter. Name similarity alone is the weakest signal. Factsheets carry other facts we can check against data we already hold. Layered, cheapest and strongest first:

LayerFactsheet fieldOur dataRole
1 · AMC scopewhose factsheet it isschemes.amc_nameAlready in the plan; never match across AMCs
2 · ISINISINs listed under "Plans/Options", where printedschemes.isin, isin_reinvestExact match, the strongest possible; skips names entirely
3 · Exact namescheme headingcanonical base_namePlan's first step, now at fund level
4 · Category gate"Category: Small Cap Fund"schemes.sebi_categoryFuzzy candidates must share the category, so a small-cap name can't land on a mid-cap fund
5 · Fuzzyscheme headingbase_name≥ 0.80, refuse if runner-up within 0.05 (unchanged)
6 · AUM tie-breakmonthly average AUM (₹ cr)scheme_aaum.aaum_value (quarterly)Only to settle a remaining tie, and only if exactly one family is within ±25%

Not used: inception date (we only know the first NAV we hold, which A11's backfill fills later), benchmark name (we don't store it), and a saved alias table (matching is deterministic month to month, so it would add a table without changing results). Every name that still doesn't match is logged with its AMC, for monthly review.

Fix chosen

A. Fund-level matching + family write, plus layers 2 and 4 (ISIN when printed, category gate on fuzzy).

ISIN and category are near-free once the text is extracted, and they remove the two real risks: a fuzzy match to the wrong fund, and a wrong fund in a different category. The AUM tie-break (C) is only worth adding if the all-AMC download (card 3) shows ties that A leaves unresolved. Whether each AMC prints ISIN and category is one of the things that download records.

What happens now
  • match_extracted_fund_name takes the page's extracted ISINs and category with the name, and returns a (amc_name, base_name) family.
  • upsert_scheme_fund_managers runs once per scheme in the family; the manual CLI does the same.
  • Tests: Direct, Regular and IDCW rows all get managers; an ISIN match wins over a different-looking name; a fuzzy name in another category is refused; two different funds within 0.05 are still refused.
Not chosen
  • B. Fund-level matching + family write only (layers 1, 3, 5).
  • C. All six layers, including the AUM tie-break.

2 · One AMC breaking shouldn't stop the rest, and we should hear about it

was: Fix
The problem

Decided: both options. Catch everything per AMC (and add the specific types to the log message), and commit after each AMC. Then the question you raised: how does the system notice that an AMC changed its factsheet, and what happens to the data until someone fixes it?

How it detects a change. After each AMC, the job compares the run with what it already knows, using only data it already has:

  • Fetch failed: network error, 403, 404, or no PDF link found.
  • Not a factsheet: the downloaded PDF fails the content check from card 4.
  • Layout changed: the PDF reads fine but no manager blocks are found on any page.
  • Matching collapsed: schemes matched this month is under half of last month's count for that AMC (counted from scheme_fund_managers by reference_period, so no new table).
Each of these logs one line: FUND_MANAGER_ALERT amc=<name> reason=<code> detail=<url or counts>.
flowchart LR
  job["monthly job · per AMC"] --> chk{"fetch, factsheet check,<br/>extract, match vs last month"}
  chk -->|"all fine"| ok["commit this AMC's rows"]
  chk -->|"any check fails"| log["log FUND_MANAGER_ALERT"]
  log --> mf["CloudWatch metric filter<br/>on the job's log group"]
  mf --> al["CloudWatch alarm"]
  al --> sns[("existing ops-alerts SNS topic")]
  sns --> mail["email to the 2 subscribers"]

How it adapts: it doesn't rewrite its own parser. It keeps serving last month's managers for that AMC, because the household view reads each scheme's latest period and nothing is deleted when a run fails. Someone then fits the pattern to the new layout using the PDF URL in the alert. To keep stale data from lingering, rows older than 3 months count as "not available yet".

Fix chosen

A. Catch-all per AMC + commit per AMC + alert line + metric filter and alarm on the existing ops-alerts topic.

The SNS topic and the job's log group already exist (infra/modules/scheduler/main.tf); this adds two Terraform resources and no app permissions. The detection checks reuse data the job already has.

What happens now
  • Task 3: per-AMC except Exception, rollback, commit, and the four checks with the alert line.
  • Task 4: aws_cloudwatch_log_metric_filter + aws_cloudwatch_metric_alarm → ops_alerts.
  • Task 5: rows older than 3 months are treated as unavailable.
  • Tests: an AMC raising RuntimeError doesn't stop the next one; an AMC whose matches drop from 40 to 5 logs the alert line.
Not chosen
  • B. The same, but the job publishes to SNS itself (needs a task role with sns:Publish; all jobs have task_role_arn = null today).
  • C. No alerting; read the logs monthly.

4 · Make sure the downloaded PDF is this month's factsheet

was: Fix
The problem

The API resolvers took the first document in the list; the static resolvers take the first .pdf link on the landing page. Decided: option A, the shared "newest document named factsheet" rule. You asked how much tighter it can go.

Picking the right link is only half of it. The real guard is checking the file after download, which works the same for every resolver:

CheckWhat it catches
1 · Pick: title or URL contains "factsheet", newest firstForms, notices, SAI, KYC PDFs
2 · Content: at least 3 pages with a manager blockA one-pager, a single-scheme sheet, an unrelated PDF
3 · Month: the "as on" date printed in the PDF is last monthA stale factsheet still linked after month-end
4 · Coverage: matched families ≥ half of last month'sA partial or truncated factsheet

A file that fails 2 or 3 isn't parsed; the AMC is counted as failed and raises the card 2 alert, and last month's data keeps serving. Check 4 is card 2's "matching collapsed" alert.

Fix chosen

B. Pick rule + content check + month check, for every resolver.

Checks 2 and 3 are a few lines each, use text we extract anyway, and stop the two worst failures: parsing the wrong document, and silently re-importing last month. C only if the catalogue (card 3) shows an AMC that needs it.

What happens now
  • One looks_like_current_factsheet(pages, expected_month) helper, used by both resolvers and the manual CLI.
  • Tests against the catalogue excerpts: a real factsheet passes, an SAI excerpt fails, last month's factsheet fails.
Not chosen
  • A. Pick rule only.
  • C. B + a per-AMC page-range or file-name pattern.

6 · What fetching all 57 AMCs changed in the plan

was: new
What was done

On 9 Oct a script read AMFI's factsheet directory, fetched every AMC's landing page with plain HTTP, picked the newest factsheet link, downloaded it and extracted the text. Write-up: Docs/analytics/2026-10-09-attribute-04-factsheet-layouts.md. The text dumps sit outside the repo, in Desktop/Unifolio/Factsheets/2026-10-catalogue/.

Findings
  • The directory lookup would have found no AMC. AMFI keys its directory by company ("Aditya Birla Sun Life AMC Limited"), not fund house; the plan also read a field that doesn't exist (amcName; the field is amc_name). Several registry names didn't match AMFI's either.
  • There is no generic layout. The plan's single pattern matched 5 of 22 AMCs' files. There are six layout families, and some AMCs need their own handling.
  • "First PDF on the page" is often wrong. About half the picks were stale (HSBC 2020, Zerodha 2025) or not a factsheet (a how-to guide, a methodology note). Card 4's checks are essential.
  • 22 of 57 reachable by a plain fetch, 29 render their links in JavaScript, 6 list no page. Edelweiss is reachable again.
What the plan does now
  • Registry: keyed by our fund-house name, storing AMFI's company name. 55 entries; Carnelian and Nuvama have no schemes.
  • Readers: one per AMC (Task 3b), each built on the AMC's real text with a fixture test.
  • Run 1 goes live with 4 AMCs, measured on the real files:
    • Nippon: 100 of 108 live funds.
    • Edelweiss: 75 of 76.
    • HDFC: all 53 active funds.
    • Kotak: 112 of 120.
  • Every other AMC: one onboarding procedure (Task 8), run in 5 batches before staging. Each AMC needs a source verified against its live site, a reader with a fixture, and at least 90% of its live funds covered or a reason for each miss.
Done means

Review Focus the gate checks

  • A co-managed scheme gives 2+ rows and 2+ cards, never merged.
  • Two candidates within 0.05 of each other: no auto-pick, logged as unmatched.
  • A held HDFC, Kotak or Edelweiss scheme shows in "not available yet", never fabricated or dropped.
  • Running the job twice on the same data creates no duplicates.
  • ABSL's dateless layout still produces rows with managing_since left null.
