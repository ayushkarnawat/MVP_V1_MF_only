1 · Settled scenarios are never computed

was: Blocker
The problem

Every number a user sees on a historical scenario is read from two precomputed tables: scenario_scheme_results (one % per scheme) and scenario_category_averages. The only code that fills them is compute_scenario_results(db, scenario). For one scenario it:

  1. takes every active scheme;
  2. reads its NAV on the window's start and end dates;
  3. stores the real % move for each scheme that has both NAVs;
  4. averages those by SEBI category, then by asset class;
  5. gives each scheme without its own NAVs the category average, or failing that the asset-class average, marked "proxied".

In the plan, the only caller is Task 8's step in the daily NAV job, and it runs only for is_ongoing rows: the Gold rally, the US-Iran group and its Relapse phase. Nothing ever computes the settled ones.

Scenario kindRowsWho computes it in the planWhat the user would see
Ongoing (Gold rally, US-Iran group, Relapse)3daily NAV jobnumbers
Settled (COVID, 2008, Taper Tantrum, …, Franklin, US-Iran phases 1–2)26nobodyan empty fund list and "no data"
Hypothetical5not needed: worked out when served from the assumptionsnumbers
Fix chosen

A. A one-off script, scripts/compute_all_scenarios.py, calls compute_scenario_results for every non-hypothetical row, phases and the US-Iran group row included (fix 6 needs the group's own whole-window results).

How it works
  • Order on staging: migrations (tables + seed) → A11's NAV backfill (history back to each window) → A12's daily benchmark job (TRI from 1990, used by card 10) → compute_all_scenarios.py.
  • Order matters: computing before the backfill would store "no data" for every pre-2016 window.
  • Safe to rerun: each scenario's rows are deleted and rewritten in one transaction. After a seed correction or a later backfill, run it again.
  • Per-scenario commit: one scenario failing (for example a missing NAV range) is logged and skipped; the rest still compute.
  • Output: one line per scenario, e.g. COVID crash: real=3,912 proxied=1,204 no_data=88, so a bad run is visible.
  • After that: settled windows never change, so they're never recomputed. Ongoing rows stay with the daily job, which now also refreshes the US-Iran group row.
Tests
  • Computes every non-hypothetical row, phases and group included.
  • Writes nothing for hypotheticals.
  • A second run leaves the same row counts (no duplicates).
  • One scenario raising doesn't stop the next.
Not chosen
  • B. Compute inside the seed migration: no NAV history exists yet at that point.
  • C. Compute on first open: minutes of work inside a user's request.

2 · The list column breaks SQLite tests; keep Postgres exactly as designed

was: Blocker
The problem

scenarios.had_redemption_freeze_schemes holds the Franklin scheme names as a list. The plan types it postgresql.ARRAY(String), a Postgres-only type, in three places:

  • The model. Every backend test builds a throwaway SQLite database with Base.metadata.create_all(), which creates all tables. SQLite can't create an ARRAY column, so every test file fails at setup, not just A11's.
  • The migration's table definition. tests/test_migrations.py runs every migration up and down on SQLite, so it fails too.
  • The migration's seed. It inserts with gen_random_uuid(), a Postgres function, and binds the list as a Postgres array. Both fail on SQLite.
Fix chosen

A. JSON().with_variant(postgresql.ARRAY(String), "postgresql") in the model and the migration. The same pattern is already used by folios.coverage_gap_details.

Why Postgres doesn't change
  • with_variant means "on Postgres, use exactly this type". Staging and production get the same TEXT[] column, the same stored values and the same reads; SQLite stores JSON text.
  • Python sees a list[str] on both.
  • One limit: SQL array operators (= ANY, @>) aren't available on a variant column in a query. The plan only reads the list in Python (set(scenario.had_redemption_freeze_schemes)), and the review checks that nothing queries inside it.
  • Seed: ids come from Python's uuid4() instead of gen_random_uuid(), and rows go through a typed sa.table() insert, so the list is written correctly for each database.
Verification
  • All existing backend tests still pass.
  • test_migrations.py passes on SQLite.
  • Local Postgres: upgrade, then check the column type is text[] and Franklin's row holds 6 names; downgrade, then upgrade again.
Not chosen
  • B. JSON everywhere: changes the Postgres design.
  • C. A separate table: more schema for a 6-name list.

3 · Classify every ETF, index fund and fund-of-funds by what it holds

was: Blocker
The problem

Hypothetical scenarios ("Strait of Hormuz closure" and the others) have no real data. Each held fund gets the assumed % for its asset class, so the asset class decides the answer. The plan's hypothetical_asset_class_bucket(sebi_category) decides it from the category text, checking "index" or "etf" first and sending anything that matches to Index/ETF, which carries the equity assumption.

But an ETF or index fund is a wrapper; what moves its value is what it holds. AMFI's current file has 1,197 such funds under 18 category headings, and many hold no equity at all:

What the fund holdsWhere AMFI lists itFunds (approx.)Plan sends it toHormuz closure: plan → right
Gold"Gold ETF" (2 headings), gold FoFs≈ 50Index/ETF−25% → +8%
Silver"Silver ETF", silver ETFs inside "Other ETFs", silver FoFs≈ 40Index/ETF−25% → silver assumption
Bonds / gilts / SDLs / target-maturity"Debt ETF", "Index Funds - Debt Funds", and inside "Other Scheme - Index Funds" / "Other ETFs"≈ 160Index/ETF−25% → −4%
Liquid / overnight / 1-day rateinside "Other ETFs"≈ 10Index/ETF−25% → −1%
Foreign equity (Nasdaq 100, S&P 500, Hang Seng…)"ETFs investing overseas", inside "Other ETFs" / "Index Funds"≈ 30Index/ETF−25% → −10% (Overseas)
Multi-asset / hybrid"Hybrid ETF", "Index Funds - Hybrid", domestic FoFs≈ 30Index/ETF or Other→ Hybrid
Indian equity (Nifty 50, Bank Nifty, CPSE…)"Equity ETF", "Index Funds - Equity", most of "Other ETFs" / "Index Funds"≈ 800Index/ETF−25% (correct)

Two more places get it wrong for the same reason:

  • Historical fallback. When a fund has no NAV for a window, it gets its category's average. "Other Scheme - Index Funds" mixes about 200 equity and 95 bond index funds, so a new bond index fund would get an equity-heavy average.
  • The plan's final fallback uses the dashboard's asset_class_bucket, which puts all gold, silver and generic index funds in "Other".
Fix chosen

One classifier, all ETFs, used everywhere. A single underlying_asset_class(sebi_category, scheme_name) in scenario_asset_class.py, applied in all three places together.

How it decides
  1. Not a wrapper (category has no ETF / Index / FoF): the category decides, as today (Equity, Debt-short/long, Hybrid, Other).
  2. A wrapper with a telling category: "Gold ETF" → Gold, "Silver ETF" → Silver, "Debt ETF" / "Index Funds - Debt" → Debt, "ETFs investing overseas" / "FoF Overseas" → Overseas, "Hybrid ETF" / "Index Funds - Hybrid" → Hybrid, "Equity ETF" / "Index Funds - Equity" → Index/ETF (equity).
  3. A generic wrapper ("Other ETFs", "Other Scheme - Index Funds", "FoF Domestic"): the scheme name decides, using whole-word keywords checked in this order:
    • silver
    • gold
    • overseas: Nasdaq, S&P 500, Hang Seng, MSCI, global…
    • short debt: liquid, overnight, 1D rate, money market
    • debt: gilt, G-Sec, SDL, bond, CRISIL IBX, target maturity, T-bill
    • hybrid: multi asset, balanced
    Bare "PSU" is not a debt keyword, so "Nifty PSU Bank ETF" stays equity.
  4. A generic wrapper with no keyword: ETFs and index funds → Index/ETF (equity, since most are); domestic FoFs → Other.
Where it's used
  • Hypotheticals: picks the assumption row.
  • Historical category average: wrapper categories are averaged per (category, underlying asset), so a bond index fund is proxied by other bond index funds, not by the whole heading.
  • Historical asset-class fallback: replaces the dashboard bucket inside A11 only. The dashboard's allocation chart is unchanged and listed as a follow-up.
New asset classes

Silver is added to the allowed list, and "Overseas FoF" is renamed Overseas (it now covers ETFs and index funds too). Both tables are new in this plan, so there's no migration cost. Silver's assumption values for the 5 hypotheticals are in card 11.

Tests
  • One test per row of the table above, using real AMFI names.
  • Plus a test that runs the classifier over a saved excerpt of the real file and checks no gold, silver or bond fund lands in Index/ETF.
  • The plan's 9 existing bucketing tests still pass.

6 · The headline % is each household's own number

was: Fix
The problem

The plan's portfolio_impact_pct averages every row in scenario_scheme_results, which covers all ~14,000 schemes. So the big "your portfolio would have fallen X%" is the same for every user and has nothing to do with their funds. Phase % is computed the same way. For US-Iran, the hero labelled "Cumulative" actually reads the current phase only.

Fix chosen

A, per user. Every figure on the result screen comes from that household's imported holdings, worked out when the screen is opened. Nothing household-specific is precomputed or shared.

How it's calculated
  • Inputs: the household's holdings from compute_holdings (the same numbers as the dashboard) and each held scheme's % for the scenario.
  • Rupee impact per holding = current value × %.
  • Portfolio % = Σ rupee impact ÷ Σ current value of the holdings that have a %. A holding with no data (or frozen) is left out of both sums, never counted as 0%. The screen says "Based on ₹X of your ₹Y; N funds have no data for this period".
  • Family view: the same formula per member, plus the combined household.
  • Phases: each phase's % uses the same formula over that phase's results.
  • US-Iran hero: uses the group row's own whole-window results (computed by card 1's script and the daily job). "By fund" stays on the current phase, as the spec says.

Example. ₹8 lakh in an equity fund at −38% and ₹2 lakh in a liquid fund at +1% give −₹3,04,000 + ₹2,000 = −₹3,02,000. That's −30.2% of ₹10 lakh. A different household with ₹1 lakh equity and ₹9 lakh liquid sees −2.9%.

Tests
  • The two-household example above gives −30.2% and −2.9%.
  • A no-data holding changes neither sum.
  • The US-Iran hero equals the group result, not Phase 3's.
Not chosen
  • B. Count no-data as 0%.
  • C. Unweighted average of held funds (a ₹500 SIP would count as much as a ₹10 lakh holding).

7 · Recognise a Franklin frozen holding however it's named

was: Fix
What happened at Franklin

On 23 April 2020, Franklin Templeton India wound up 6 debt schemes (about ₹25,000 crore) after credit losses and a redemption rush during COVID, and froze redemptions. Investors couldn't sell; money came back in tranches through a Supreme Court-supervised process from 2021 to 2023. For these 6 schemes, the right answer in the scenario isn't a % move. It's that the money was locked.

The problem

The seed lists the 6 by plain fund name, e.g. "Franklin India Short Term Income Plan". The plan compares that with the holding's full name ("… - Direct Plan - Growth"), so nothing ever matches. Option A (compare the base name) is the right idea, but AMFI's real base names differ again:

Seeded nameAMFI base name today
Franklin India Short Term Income PlanFranklin India Short-Term Income Plan (no. of segregated portfolios- 3)
Franklin India Low Duration FundFranklin India Low Duration Fund (No. of Segregated Portfolios-2)
Franklin India Ultra Short Bond FundFranklin India Ultra Short Bond Fund (no. of segregated portfolio-1)

The other three are the same: a suffix with varying case and spacing, and a hyphen. Live funds with close names also exist ("Franklin India Short Term Fund", "Franklin India Ultra Short Term Fund"), so a loose "contains" match would freeze the wrong funds.

Fix chosen

A, normalised. Compare base names after one fixed clean-up on both sides:

  1. lowercase;
  2. hyphens to spaces;
  3. drop a trailing "(no. of segregated portfolio(s)-N)";
  4. collapse spaces.

Also require the scheme's AMC to be Franklin Templeton. It's still an exact match, just on cleaned text.

How it runs
  • The result screen loads the held schemes' base_name. When it's empty (an older CAS-imported row), it uses the scheme name with " - plan - option" removed.
  • A frozen holding shows "Frozen: redemptions suspended" instead of a %, and is left out of the portfolio % (fix 6), since there was no price to sell at.
  • Other debt funds in the same household still show their real %.
  • Franklin's own segregated side-pocket schemes aren't in the list. They were separate schemes, and they have their own NAVs.
Tests
  • All 6 real AMFI names (as in the table) match.
  • "Franklin India Short Term Fund" and "Franklin India Ultra Short Term Fund" don't.
  • A Direct-Growth holding shows Frozen while a non-Franklin debt fund shows its %.

10 · The picker's quick stat: market and funds, side by side

was: Check
The problem

Each scenario card in the picker shows one quick %. The plan takes a plain average of every scheme's result, equity and debt together, while its comment says "AUM-weighted". Mixing debt in turns COVID's crash into about −15%, which matches nothing anyone remembers, and a plain average lets a ₹5-crore fund count as much as a ₹50,000-crore one.

Fix chosen

A + B together. Two figures, each answering one clear question, computed once with the scenario's results:

  • The market (A): Nifty 50 TRI move over the window. It's the figure people recognise for the event (COVID ≈ −38%).
  • Mutual funds (B): the AUM-weighted move of equity funds and of debt funds, kept separate because mixing them is what produced the −15%.

The card reads, for example: "Nifty 50 −38% · Equity funds −35% · Debt funds +1%".

How it's calculated
  • Market: Nifty 50 TRI on the window's end ÷ start − 1, via the TRI lookups from card 8.
  • Equity / debt funds: for each real (not proxied) scheme result in that asset class, weight = the scheme's average AUM from scheme_aaum. Use the latest quarter on or before the window's start; if none is that old, use the earliest quarter we hold, and say so in the tooltip ("weighted by fund size in <quarter>"). Funds with no AUM row aren't weighted in.
  • Where it's stored: three nullable columns on scenarios (quick_market_pct, quick_equity_pct, quick_debt_pct), filled by compute_scenario_results. The picker reads them directly. This is a new table, so no extra migration.
  • Fallbacks: no TRI for the window → the market figure is hidden. Fewer than 5 weighted funds in a class → that figure is hidden. All three missing → no quick stat. Never a substitute number.
  • Not shown for: hypotheticals (no real data), US-Iran (the card shows its phases instead), and Franklin (a freeze, not a move).
Tests
  • Two equity funds with AUM 100 and 300 and moves −40% and −20% give −25%, not −30%.
  • A debt fund doesn't change the equity figure.
  • No TRI rows → market figure is null.
  • Fewer than 5 funds → figure is null.
