01

The differentiation problem

Two existing surfaces — Scorer v1 (standalone quality score, tier badge) and Category Ranking (single-axis return percentile) — already occupy "a card with a number and a bar." A naive percentile-bar layout for attribute 09 would have been a third copy of the same shape.

Rejected 1 — Card + percentile bar: visually redundant with Scorer/Category Ranking, even though the underlying composite formula is genuinely different.

Rejected 2 — Table (fund/rank/percentile/composite/status): same problem in a different widget shape — still only shows a fund's own number.

Resolved — Leaderboard / neighbors view: show the 2 named competitor funds immediately above and 2 below a held fund's rank, by name and composite score. This is the one view that shows other funds by name — what actually earns the word "ranking."

03

Structure

Composite score = weighted sum of 5 percentile-ranked components (3Y 0.25, 5Y 0.25, category-relative 0.20, low-volatility 0.15, low-TER 0.15) — never a raw number summed directly.

Schema & computation — backend grounding

Added for implementation handoff: the real tables this screen reads and the computation pipeline that fills them. Not part of the originally approved design-problem/layout above — purely explanatory, grounded verbatim in 2026-10-07-sub-project-1-planning.md's "Attribute 09" section.

erDiagram
    SCHEMES ||--o{ SCHEME_RANKINGS : "ranked once per day"
    RANKING_WEIGHTS ||--o{ SCHEME_RANKINGS : "singleton config read at compute time"
    SCHEME_RANKINGS {
        uuid scheme_id FK
        timestamptz computed_at "pinned to day-start"
        numeric composite_score "0-100, weighted sum of 5 percentiles"
        integer category_rank
        integer category_size
        numeric percentile
        numeric return_3y "display-only, never a weighted input"
        numeric return_5y "nullable, triggers renormalization"
        numeric category_relative "fund blended return minus category AUM-weighted avg"
        numeric downside_deviation "raw, same metric Scorer already computes"
        numeric ter_value
        numeric return_3y_percentile
        numeric return_5y_percentile
        numeric category_relative_percentile
        numeric volatility_percentile "already inverted, low vol = high percentile"
        numeric ter_percentile "already inverted, low TER = high percentile"
    }
    RANKING_WEIGHTS {
        boolean id PK "CHECK(id) enforces a single row"
        numeric weight_return_3y "default 0.25"
        numeric weight_return_5y "default 0.25"
        numeric weight_category_relative "default 0.20"
        numeric weight_low_volatility "default 0.15"
        numeric weight_low_ter "default 0.15"
    }
    
sequenceDiagram
    participant FE as FundRankingSection.tsx
    participant API as GET /analytics/funds/{id}/ranking
    participant FR as fund_ranking.py (new)
    participant CR as category_ranking.py (reused)
    participant RM as risk_metrics.py (reused)
    participant TER as ter.py (reused)
    participant DB as scheme_rankings / ranking_weights

    FE->>API: request ranking for a held scheme
    API->>FR: compute_fund_ranking(scheme_id)
    FR->>CR: category universe + blended (r1, r3, r5) returns
    FR->>CR: AUM-weighted category average -> category_relative
    FR->>RM: 5yr monthly series -> downside_deviation
    FR->>TER: latest TER for scheme
    FR->>FR: percentile-rank each of 5 components within category
    FR->>DB: read ranking_weights (fallback: hardcoded PDF defaults)
    FR->>FR: renormalize weights across non-null components
    FR->>FR: composite_score = sum(renormalized_weight x percentile)
    FR->>DB: upsert scheme_rankings row (computed_at = day-start)
    FR-->>API: FundRankingRow + 2 neighbors above/below
    API-->>FE: leaderboard/neighbors view
Zero new external data source, zero new scheduled job — every input is already warmed by an existing on-demand cache (NAV) or existing scheduled job (TER daily, AAUM quarterly) with no relation to this feature, same posture as Scorer v1 and Category Ranking.
